# PY-036 · Apply SCD2 customer changes in order without overlapping intervals

**Topic:** Streaming & reliability · **Level:** hard · **Interview time:** ~40 min · **Module:** `python/practice/04_streaming_reliability/PY-036.py`

## Scenario

`dim_customer` is a Type-2 slowly changing dimension: every change to a tracked attribute (tier,
city, segment) closes the customer's current row and opens a new one, so facts can be joined to the
attributes that were **valid at the time**. A CDC feed delivers batches of changes. Within a
batch, changes for the same customer arrive in any order, can repeat, and sometimes carry no
real change. A bug here silently corrupts every historical report, so the **invariants** matter
more than the happy path:

- per customer, validity intervals never overlap and never leave a gap;
- exactly one row is current.

## Function contract

```text
apply_scd2(dimension, changes, *, tracked) -> Scd2Result(rows, rejected)
```

`Rejected(change, reason)` and `Scd2Result(rows, rejected)` are defined in the stub.

**Dimension rows** (dicts): `customer_id`, `version` (int, 1 for the first row of a customer),
`effective_from` (aware `datetime`, inclusive), `effective_to` (aware `datetime`, **exclusive**, or `None`
for the open current row), `is_current` (bool), plus one key per attribute in `tracked`. Other keys
may be present on existing rows and must be preserved on rows you do not touch.

**Changes** (dicts): `customer_id`, `change_ts` (aware `datetime`) and `attributes`, a **partial**
dict of tracked attributes (only the ones that changed or were sent).

### Rules

1. **Order.** Process the batch sorted by `change_ts`, ties by arrival order (position in
   `changes`). Different customers are independent.
2. **Unknown customer.** The first change creates `version 1`: `effective_from = change_ts`,
   `effective_to = None`, `is_current = True`; tracked attributes not supplied are `None`.
3. **Known customer.** The new attribute set is the current row's attributes overlaid with the
   change's `attributes`.
   - If it equals the current attributes (`==`) → **no-op**: no new version, no rejection. This
     includes a replay with `change_ts` equal to the current `effective_from`.
   - Otherwise close the current row (`effective_to = change_ts`, `is_current = False`) and append a
     new current row with `version + 1`, `effective_from = change_ts`, the merged attributes.
4. **Rejections** (the change has no effect and is reported in `rejected`, in *arrival* order):
   - `"out_of_order"`: `change_ts` is **before** the current row's `effective_from`, i.e. it would
     rewrite history that is already published. (Checked before the no-op rule.)
   - `"same_timestamp_conflict"`: it changes attributes but `change_ts` **equals** the current row's
     `effective_from` (an empty interval would be created). The first change at a given instant wins.
   - `"unknown_attribute"`: `attributes` names something not in `tracked`. Checked first; nothing is applied.
5. **Output.** `rows` is the complete dimension, sorted by `(customer_id, effective_from)`. Inputs are
   never mutated.
6. **Errors** (`ValueError`, before changing anything): a change without `customer_id`, a
   naive/missing `change_ts`; a customer with more than one current row, no current row, or an
   open-ended / current row that is not the latest.

## Example

Tracked `["tier", "city"]`. Current row: customer 7, v1, from 2025-01-01, tier `silver`, city `Oslo`.

| arrival | customer | change_ts | attributes | result |
|---|---|---|---|---|
| 1 | 7 | 2025-03-01 | tier = gold | applied second (sorted order): v2 closed at 03-01; v3 from 03-01: gold, Bergen |
| 2 | 7 | 2025-02-01 | city = Bergen | applied first: v1 closed at 02-01; v2 from 02-01: silver, Bergen |
| 3 | 7 | 2025-03-01 | tier = gold | no-op (nothing changes) |
| 4 | 9 | 2025-03-05 | tier = basic | new customer, v1: basic, city None |

## Corner cases to think about

- Boundary instants: the old row's `effective_to` equals the new row's `effective_from`.
- A change that arrives for a time before already-published history (late batch).
- Partial attributes, and `None` as an explicit new value (that *is* a change).
- Several changes for one customer at the same timestamp.
- Re-running the same batch against its own output.

## Clarify before you code

- How are late changes handled in production: reject, rebuild the affected slice, or merge into history?
- Closed-open intervals vs `9999-12-31` end dates; time zone of effective dates.
- Is `version` a surrogate key? What do facts reference?

## Expected complexity

O((n + m) log m) for n dimension rows and m changes. Tests run a few thousand customers.
