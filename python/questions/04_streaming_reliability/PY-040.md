# PY-040 · Incremental purchase streaks with late-arriving days

**Topic:** Streaming & reliability · **Level:** hard · **Interview time:** ~40 min · **Module:** `python/practice/04_streaming_reliability/PY-040.py`

## In plain words

> "Track purchase streaks per customer: runs of consecutive days with a purchase. Days arrive in any order, with repeats. Tell me what each new day did to the streaks, and answer current and longest streak."

**You return:** `StreakTracker().add_purchase(customer_id, day)` returns `StreakChange(kind, before, after)` with kind "new", "extend", "bridge" or "duplicate"; `current_streak`, `longest_streak` and `streaks` answer the queries.

**The fine print, in short:**
- The result must equal recomputing the runs from the full set of days, whatever the arrival order. Do not rescan the whole history on each call.
- `current_streak(c, as_of)` looks only at days on or before `as_of`; it is alive if `as_of` or the day before is a purchase day, otherwise 0.
- `day` and `as_of` must be `date` (a `datetime` raises `TypeError`). `date.min` and `date.max` must work; queries on unknown customers create nothing.

## Scenario

Marketing runs a loyalty campaign on **purchase streaks**: runs of consecutive calendar days on which
a customer bought something. Dashboards show each customer's current streak and personal best, and
the CRM fires a message when a streak is *extended* or when two streaks are *merged*.

Purchase events are processed continuously, but they do not arrive in day order: store systems
upload late, and refunds reprocessed from a backfill re-introduce old days. A late day can
**extend** a streak, **bridge** two streaks into one, or be a **duplicate**. The job sees millions
of events per hour, so recomputing a customer's streaks from their whole history for each event is not an option.

## Contract

```text
StreakChange(kind, before, after)     # defined in the stub; Run = (first_day, last_day), both inclusive

StreakTracker()
  .add_purchase(customer_id, day: date) -> StreakChange
  .current_streak(customer_id, as_of: date) -> int
  .longest_streak(customer_id) -> int
  .streaks(customer_id) -> list[Run]          # sorted by first day
```

### Definitions

- Purchases are recorded per **calendar day** (`datetime.date`); many purchases on one day are one day.
- A **run** is a maximal set of consecutive days all having a purchase. Runs are never adjacent or overlapping:
  they are separated by at least one empty day. A single day is a run of length 1.
- `streaks(c)` lists all runs of customer `c` in date order, `[]` for an unknown customer.
- `longest_streak(c)`: the length in days of the longest run, `0` for an unknown customer.
- `current_streak(c, as_of)`: consider only purchase days **on or before** `as_of`. If `as_of` itself is
  a purchase day, the answer is the length of the run up to and including `as_of`. Otherwise, if
  `as_of - 1 day` is a purchase day, the streak is **still alive** and the answer is the length of the run
  that ended yesterday. In all other cases the streak is `0`. (Days after `as_of` never count.)

### What `add_purchase` returns

`StreakChange.before` holds the existing run(s) the new day touched (in date order); `after` is the run
that now contains the day.

| situation | `kind` | `before` | `after` |
|---|---|---|---|
| the day is already inside a run | `"duplicate"` | `(that run,)` | the same run |
| not inside a run, adjacent to no run | `"new"` | `()` | `(day, day)` |
| adjacent to exactly one run (day before its start, or day after its end) | `"extend"` | `(that run,)` | the longer run |
| adjacent to both a run ending the day before **and** a run starting the day after | `"bridge"` | `(left, right)` | the merged run |

The result must be exactly what recomputing the runs from scratch on the full set of days would give,
after **any** order of arrivals and any number of duplicates.

### Constraints

- `day` and `as_of` must be `datetime.date` objects. A `datetime` is rejected with `TypeError` (it is
  a `date` subclass, so check explicitly), as is anything else.
- Customers are independent; ids are any hashable values.
- The first call for an unknown customer creates it; queries for unknown customers never create state.
- `date.min` and `date.max` are valid purchase days: neighbours outside the calendar must not crash.
- **Do not recompute from the whole history on each call.** The tests add 130,000 days for one customer
  in shuffled order, with queries interleaved, within a time limit that a re-scan cannot meet.

## Example

Days added in this order for customer `c` (all in January 2025):

| add | kind | before | after |
|---|---|---|---|
| 5 | new | `()` | 5..5 |
| 7 | new | `()` | 7..7 |
| 6 | bridge | `(5..5, 7..7)` | 5..7 |
| 6 | duplicate | `(5..7,)` | 5..7 |
| 8 | extend | `(5..7,)` | 5..8 |
| 3 | new | `()` | 3..3 |
| 4 | bridge | `(3..3, 5..8)` | 3..8 |

`longest_streak = 6`. With `as_of` = Jan 8: `current_streak` is 6; Jan 9: 6 (alive); Jan 10: 0; Jan 5: 3.

## Corner cases to think about

- Month, year and leap-day boundaries (Feb 28 and Mar 1 in 2024 are bridged by Feb 29).
- A late day far in the past, a duplicate of the first day, the same day twice in a row.
- Adding a day immediately before the earliest run, or after the last one.
- A bridge that makes the longest streak jump.
- `as_of` before every purchase, inside a run, exactly on its last day, one day after, two days after.

## Clarify before you code

- Is a streak per calendar day in UTC or in the customer's local time zone (and who decides)?
- Should a refund remove a day? (Removal can *split* a run: much harder; here only additions.)
- What if the same event can arrive months late: how much history do you keep per customer?

## Expected complexity

Each call roughly O(log r) (r = runs of that customer), never O(number of days). Memory O(runs) or O(days).
