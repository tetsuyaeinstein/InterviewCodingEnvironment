# PY-031 · Order-aware current state from out-of-order events

**Topic:** Streaming & reliability · **Level:** medium · **Interview time:** ~30 min · **Module:** `python/practice/04_streaming_reliability/PY-031.py`

## In plain words

> "Change events about customer records reach us late, twice, or out of order. Keep the current state per key so the end result is the same whatever order the events came in. The higher source sequence always wins."

**You return:** `CurrentState().apply(event)` returns "applied", "stale", "duplicate" or "conflict"; `snapshot()` returns the live payload per key and `conflicts()` lists the keys that cannot be resolved.

**The fine print, in short:**
- Our own `ingest_ts` never decides who wins. A delete keeps blocking older inserts/updates; a newer insert/update brings the key back.
- Same sequence with a different op or payload is a conflict: the key is missing from `snapshot()` until a higher sequence arrives.
- Identical repeats are duplicates (keep the copy with the earliest `ingest_ts`). Bad `op`, non-int sequence or naive `ingest_ts` raises `ValueError`.

## Scenario

A customer-profile service consumes change events from several Kafka partitions and from a
nightly replay job. Events for the same key arrive **out of order, twice, or both**. Each event
carries a **source sequence** assigned by the system of record when the change was committed.
Our own `ingest_ts` (when the consumer saw it) says nothing about business order: a replay
re-ingests old changes *after* newer ones.

Build the object that maintains the **current state per key** so that the final state depends
only on *which events exist*, never on the order they arrived in.

## Contract

```text
Event(key, sequence, ingest_ts, payload, op)         # frozen dataclass, defined in the stub
Conflict(key, sequence, variants)                    # frozen dataclass, defined in the stub

CurrentState()
  .apply(event) -> "applied" | "stale" | "duplicate" | "conflict"
  .apply_all(events) -> list[str]                    # outcomes, in iteration order
  .snapshot() -> dict[key, payload]                  # live keys only, payloads are copies
  .record(key) -> Event | None
  .conflicts() -> list[Conflict]                     # sorted by key
```

### Rules per key

- The event with the **highest `sequence`** wins. `ingest_ts` never decides anything.
- `op` is `"I"`, `"U"` or `"D"`. Payloads are **full row images**: the winning event's payload
  *is* the state (no field-level merge). Anything else for `op` → `ValueError`.
- A **delete** is a tombstone: the key disappears from `snapshot()`, but its sequence is kept
  so that an *older* insert/update arriving later cannot resurrect it. A **newer** insert/update
  (higher sequence) legitimately re-creates the key. For deletes the payload is ignored.
- `sequence` must be an `int` (not `bool`); `ingest_ts` must be timezone-aware. Violations →
  `ValueError`.

### What `apply` returns

| incoming event vs. the key's current top sequence | outcome |
|---|---|
| key unseen, or higher sequence | `"applied"` |
| lower sequence | `"stale"` (ignored) |
| equal, same `op` and equal payload (`==`; `ingest_ts` is ignored) | `"duplicate"` |
| equal, different `op` or payload | `"conflict"` |

### Conflicts

Two *different* events with the **same** top sequence cannot be ordered, so nobody knows the
truth. For such a key:

- `snapshot()` omits the key and `record(key)` returns `None`;
- `conflicts()` lists it once as `Conflict(key, sequence, variants)`, where `variants` holds
  **one event per distinct (op, payload)**, ordered by `op` then by the payload's JSON text
  with sorted keys (`json.dumps(payload, sort_keys=True, default=str)`); deletes sort first
  among equal ops. Arrival order must not matter.
- A conflict **disappears** as soon as an event with a higher sequence arrives for that key.
  A conflict at a *superseded* sequence is never reported.

### Duplicates and `ingest_ts`

When identical events arrive more than once, the retained copy is the one with the
**earliest `ingest_ts`**, so that `record(key)` is the same whatever the arrival order.

## Example

| arrival | key | seq | op | payload | outcome |
|---|---|---|---|---|---|
| 1 | c1 | 5 | U | `{"tier": "gold"}` | applied |
| 2 | c1 | 3 | U | `{"tier": "basic"}` | stale |
| 3 | c1 | 5 | U | `{"tier": "gold"}` (re-delivered) | duplicate |
| 4 | c1 | 6 | D | | applied (tombstone) |
| 5 | c1 | 4 | U | `{"tier": "silver"}` | stale |

`snapshot()` is `{}`; `record("c1")` is the `D` event at sequence 6.

## Corner cases to think about

- Replayed old events with a *newer* `ingest_ts` than the live ones.
- A delete followed by a late, older update, and by a newer insert.
- Two events with the same sequence and identical payloads but different ingest times.
- Same sequence, different payloads, then a higher sequence heals it.
- Nested (unhashable) payloads; callers mutating what `snapshot()` returned.

## Clarify before you code

- Is the sequence per key or global, and can it ever restart? (Here: per key, never.)
- Should the consumer keep the previous state while a conflict is open, or drop the key?
- How long must tombstones be retained? What happens when you purge one too early?

## Expected complexity

`apply` in O(1) amortised per event (plus the cost of comparing payloads). Memory O(keys).
Tests apply 20,000 events and shuffle small sets exhaustively.
