# PY-035 · Event-time tumbling windows with a watermark and late events

**Topic:** Streaming & reliability · **Level:** hard · **Interview time:** ~40 min · **Module:** `python/practice/04_streaming_reliability/PY-035.py`

## Scenario

Mobile apps send payment events. Network delays and offline buffering mean events arrive out of
order: a payment made at 12:04 can reach you at 12:09. Finance wants **per-merchant counts and
totals in fixed five-minute windows of event time**, emitted as soon as it is safe, and without
silently losing the stragglers: events that arrive too late must be captured on a **side output**
for reconciliation.

Implement the windowing operator that a stream engine would run per partition.

## Contract

```text
TumblingWindows(allowed_lateness: timedelta, window: timedelta = 5 minutes)
  .process(event) -> list[WindowResult]       # windows closed by this event's arrival
  .flush() -> list[WindowResult]              # end of stream: close everything still open
  .watermark -> datetime | None               # UTC
  .late_events -> list[Event]                 # side output, arrival order (a copy)

Event(event_time, key, value: Decimal)
WindowResult(window_start, window_end, key, count, total)
```

`Event` and `WindowResult` are defined in the stub.

### Windows

- Windows are aligned to the **UTC epoch**: `[start, start + window)` with `start` a multiple of
  `window` since 1970-01-01T00:00Z. Start is inclusive, end exclusive: an event exactly at
  12:05:00 belongs to `[12:05, 12:10)`.
- `event_time` is timezone-aware in any offset; convert to UTC before assigning. All datetimes in
  results (`window_start`, `window_end`, `watermark`) are **UTC-aware**. Naive datetimes → `ValueError`.
- Aggregate **per (window, key)**: `count` of events and `total` of `value` (exact `Decimal`;
  non-`Decimal` or non-finite values → `ValueError`).
- Times before the epoch must work too.

### Watermark and closing

- `watermark = max(event_time seen so far, in UTC) − allowed_lateness`, `None` before any event.
  It only ever moves **forward**: an out-of-order event never lowers it.
- A window **closes** as soon as `watermark >= window_end`. `process` returns the results of every
  window that this event's arrival closed, ordered by `(window_start, key)`. Windows that
  never received an event are never emitted.
- An event is **late** when its window is already closed (the watermark, *including this event's
  own contribution*, is `>= window_end` of its window). A late event
  is **not** aggregated, is appended to `late_events`, and `process` returns `[]` for it.
  An event whose window is still open is never late, however far behind the newest event it is.
- `flush()` closes and returns all remaining open windows, ordered by `(window_start, key)`. After
  a flush those windows are closed: a later event for one of them is late.
- Validation: `allowed_lateness < 0` or `window <= 0` → `ValueError`.

## Example

`allowed_lateness = 2 min`, window = 5 min, one merchant `m`, values 1 each:

| arrival | event time | watermark after | closed by this event |
|---|---|---|---|
| 1 | 12:00:30 | 11:58:30 | |
| 2 | 12:04:59 | 12:02:59 | |
| 3 | 12:03:00 (out of order) | 12:02:59 | |
| 4 | 12:06:00 | 12:04:00 | |
| 5 | 12:07:00 | 12:05:00 | `[12:00, 12:05)`: count 3 |
| 6 | 12:04:10 | 12:05:00 | *late*: side output |
| 7 | 12:05:00 | 12:05:00 | |
| 8 | `flush()` | | `[12:05, 12:10)`: count 3 |

## Corner cases to think about

- The watermark exactly equal to a window end (closes), one microsecond before (does not).
- An event at the boundary between two windows; the same instant given in a different UTC offset.
- Several merchants in the same window: output order; one merchant's data arriving after the window of another has closed.
- Out-of-order events inside the lateness allowance (kept) vs beyond it (late).
- A late event must not move the watermark or reopen anything.
- `allowed_lateness = 0`.

## Clarify before you code

- Where does the watermark come from in production: per partition, per source, punctuated, heuristic?
- What if one partition goes idle and holds the watermark back?
- Should late events update an already emitted result (retraction/upsert) or go to a side output?

## Expected complexity

Amortised O(log W) per event (W = number of open windows). The tests push 100,000 events
through a stream with bounded disorder in a couple of seconds.
