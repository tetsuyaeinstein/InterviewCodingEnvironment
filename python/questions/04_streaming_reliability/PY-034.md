# PY-034 · Checkpointed batch processing that survives a crash at any point

**Topic:** Streaming & reliability · **Level:** hard · **Interview time:** ~40 min · **Module:** `python/practice/04_streaming_reliability/PY-034.py`

## In plain words

> "A job reads records from a log, transforms them and writes them to a sink in batches. It can be killed at any moment and is simply restarted. When it finally catches up, the sink must hold every output exactly once, in order."

**You return:** `run_batches(source, transform, sink, dead_letters, checkpoint, *, batch_size, max_batches=None)` returns `RunReport(batches, next_offset)`.

**The fine print, in short:**
- Per batch: exactly one `sink.write`, one `dead_letters.write` (even if empty) and one `checkpoint.save` with the offset after the batch. You choose the `batch_id` and the order so that a crash anywhere is safe.
- `BadRecord` from `transform` means no rows for that record and a `DeadLetter` with the absolute offset. Any other error propagates and the batch being built leaves no trace.
- A restart may use a different `batch_size`. `ValueError` for `batch_size < 1`, negative `max_batches` or a checkpoint outside `0..len(source)`, before touching anything.

## Scenario

A micro-batch job reads a durable, append-only log of raw records (addressable by position),
transforms each record into zero or more output rows, and writes them to a sink. The job runs on
spot instances: it can be killed **at any instruction**, including halfway through a write to the
sink or to the checkpoint. After each kill the scheduler simply starts the job again.

The requirement: once the job has finally caught up, the sink contains **every output exactly
once, in source order**: nothing lost, nothing duplicated. No manual clean-up is allowed between runs.

You are given the durable pieces as interfaces. You design the **protocol** around them.

## Contract

```text
run_batches(source, transform, sink, dead_letters, checkpoint, *, batch_size, max_batches=None) -> RunReport
```

Defined in the stub: `BadRecord`, `DeadLetter(offset, record, reason)`, `RunReport(batches, next_offset)`
and the protocols:

| piece | methods | guarantees (what the infrastructure gives you) |
|---|---|---|
| `source` | a `Sequence`: `len()`, indexing, slicing | immutable, stable positions (offsets) |
| `sink`, `dead_letters` (`BatchSink`) | `write(batch_id: int, rows: list)` | durable once it returns; writing an existing `batch_id` **replaces** that batch's rows; a crash inside `write` leaves either the old or the new rows of that batch (never a mix) |
| `checkpoint` (`CheckpointStore`) | `load() -> int`, `save(offset)` | durable once `save` returns; a crash inside `save` leaves the old or the new value |

The checkpoint value is the offset of the first input record that has **not** been fully
processed. A fresh store loads `0`.

### Behaviour

- Start at `checkpoint.load()`. Process the source in consecutive batches of `batch_size` **input**
  records (the last one may be shorter). Stop when the end is reached, or after `max_batches`
  batches were completed in this call (`None` = no limit).
- For every record call `transform(record)`, which returns an iterable of output rows (possibly
  empty, possibly a generator). Rows keep source order, and within one record the transform's order.
- `transform` may raise `BadRecord("reason")`: that record produces **no** rows (discard
  anything it already yielded) and becomes `DeadLetter(offset, record, str(exc))`, with `offset`
  the **absolute** source position. Any other exception is a bug: let it propagate. The
  batch that was being built must then leave no trace, and earlier batches stay committed.
- Per batch, make **exactly one** call to `sink.write(batch_id, rows)`, one to
  `dead_letters.write(batch_id, dead)` (even when a list is empty), and one to `checkpoint.save`
  with the offset **after** the batch. Choose `batch_id` and the order of the three calls so
  the crash requirement holds. The checkpoint is loaded **once** per call.
- A restarted run may use a **different** `batch_size` than the crashed one.
- Return `RunReport(batches_completed_in_this_call, checkpoint_value_after_this_call)`.
- `ValueError` for `batch_size < 1`, negative `max_batches`, or a loaded checkpoint outside
  `0..len(source)` (a checkpoint ahead of the data means the wrong source or a corrupt store).
  Validate before touching sink or checkpoint.

## Example

`source = ["a", "bb", "", "ccc"]`, `transform = lambda s: list(s)` (one row per character),
`batch_size=2`, fresh checkpoint. Batches cover offsets `[0,2)` and `[2,4)`. Total rows
`a b b c c c`. If the process dies after the first batch's rows were written but before the
checkpoint was saved, a rerun must end with the same six rows, not seven or eight.

## Corner cases to think about

- Crash between the sink write and the checkpoint save, and between the sink and the dead-letter write.
- Saving the checkpoint *first* (what happens when the write then fails?).
- The checkpoint counts **input** records; the sink counts **output** rows, which may be more or fewer.
- Resuming with a different `batch_size`.
- A transform that fails on the 3rd record of a batch.
- Empty source; source exactly divisible by the batch size.

## Clarify before you code

- Can the sink be made idempotent (key, batch id), or transactional with the checkpoint?
- What is the unit of atomicity: record, batch, partition?
- What if `transform` has side effects or is non-deterministic: does a rerun produce the same rows?

## Expected complexity

O(n) time over the unprocessed input, O(batch_size) memory.
