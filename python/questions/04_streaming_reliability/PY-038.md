# PY-038 · Bounded pipeline with backpressure and clean failure

**Topic:** Streaming & reliability · **Level:** hard · **Interview time:** ~45 min · **Module:** `python/practice/04_streaming_reliability/PY-038.py`

## In plain words

> "Read a huge stream, enrich each item with a slow call, and write to a sink that takes one writer at a time. Never read faster than downstream can cope, and if anything fails, stop everything cleanly and report the right error."

**You return:** `run_pipeline(items, transform, consumer, *, max_in_flight, workers=1)` returns the number of items consumed.

**The fine print, in short:**
- Pull `items` lazily (it may be infinite). An item is in flight from the moment it is pulled until `consumer` is done with it; never more than `max_in_flight`. `transform` runs on `workers` threads; `consumer` runs one at a time, in input order. `None` is a valid result.
- On failure behave as if sequential: the error of the lowest input index is re-raised as the same exception object (transform, consumer or source). Everything before it was consumed, nothing at or after it.
- All threads you created have stopped before you raise. `max_in_flight < 1` or `workers < 1` raises `ValueError` before pulling anything.

## Scenario

A backfill job reads 400 million rows from a source cursor, enriches each row through a slow
HTTP lookup, and writes the result to a sink that accepts one writer at a time. The source is fast,
the lookup is slow, the sink is slower. Last time the job read everything into an unbounded queue
and the container was OOM-killed at 3 a.m. You need a small runner with real **backpressure**: when
the downstream is slow, the reader stops reading.

The runner also has to fail well: if anything breaks, it stops everything, leaves no thread
behind, and tells the caller about the right error.

## Function contract

```text
run_pipeline(items, transform, consumer, *, max_in_flight, workers=1) -> int
```

- `items`: any iterable (possibly **infinite** or one-shot). Pull from it lazily.
- `transform(item) -> result`: may be slow, called on `workers` threads concurrently. May return
  any value, including `None`.
- `consumer(result)`: called **serially** (never two calls at once) and strictly in **input order**
  (the result for item *i* is delivered before the result for item *i+1*), even when transforms
  finish out of order.
- Returns the number of items consumed.

### Bounded in-flight work

An item is *in flight* from the moment it is pulled from `items` until `consumer` has finished with
it (returned or raised). At no moment may more than `max_in_flight` items be in flight. In
particular, when the consumer is stalled the source must stop being pulled: **the producer
blocks**, memory stays bounded, and nothing is dropped. The tests measure this from the outside
with an instrumented source and consumer, so *how* you bound it is up to you.

### Exactly once

On success every item is transformed exactly once and consumed exactly once, and the consumer sees
`transform(item)` results in input order.

### Failure semantics

Behave as if the pipeline were sequential up to the first failure in **input order**:

- a **transform** error for item *k*, a **consumer** error for item *k*, or an error raised by the
  **source iterator** while producing item *k*, is re-raised to the caller **as the same exception
  object**, not wrapped;
- every item before *k* was consumed; no item at or after *k* was consumed;
- if several items fail, the one with the **lowest input index** wins, even if another one failed
  earlier in wall-clock time;
- before `run_pipeline` raises, all threads it created have stopped (no leaked threads, no deadlock
  when the producer, the workers or the consumer were blocked). It must not wait for more work.
  Pulling from the source after a failure should stop promptly.

### Validation

`max_in_flight < 1` or `workers < 1` → `ValueError`, before pulling anything from `items`.

## Example

`max_in_flight=2`, `workers=2`, items `a..z`, a consumer that blocks for a long time on `a`: at most
two items (`a`, `b`) are ever pulled while it is blocked; the producer waits. When the consumer
resumes, the pipeline continues and eventually delivers `a, b, c, ...` in order.

## Corner cases to think about

- `None` is a legal result: do not use it as an end-of-stream marker.
- `max_in_flight=1` with several workers; `max_in_flight` smaller than `workers`.
- An infinite source and a consumer that raises: the producer is blocked on a full queue at that moment.
- A transform that fails while a later item's transform has already started.
- Order preservation without an unbounded reorder buffer.
- Plain `queue.Queue(maxsize=...)` blocks forever on `put`: how does a blocked producer notice that the pipeline died?
- Threads vs `asyncio`: how would the same contract look with `asyncio.Queue(maxsize)` and `TaskGroup`?

## Clarify before you code

- What should happen to items already transformed when a later item fails: drop or flush?
- Do we need ordered delivery, or is completion order acceptable? (Here: input order.)
- Which resource is the real bottleneck: network, CPU, sink? Threads or processes?

## Expected complexity

O(1) coordination per item, O(`max_in_flight`) memory.
Tests are timing-independent: they use events, barriers and timeouts to detect deadlocks.
