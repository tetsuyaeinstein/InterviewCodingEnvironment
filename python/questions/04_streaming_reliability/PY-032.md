# PY-032 · Idempotent consumer with an atomic state store

**Topic:** Streaming & reliability · **Level:** medium · **Interview time:** ~35 min · **Module:** `python/practice/04_streaming_reliability/PY-032.py`

## In plain words

> "Our ledger reads money events from a broker that may deliver the same event twice. Apply each event_id at most once, even if the consumer crashes, and never let a balance go negative."

**You return:** `IdempotentConsumer(store).process(event)` returns "applied", "rejected" or "duplicate"; `balance(account_id)` returns a `Decimal` (0 for an unknown account).

**The fine print, in short:**
- A rejection (balance would go negative) is final for that `event_id`. A redelivery of an applied or rejected event is a "duplicate" with no store write; same id with a different account or amount raises `ConflictingEvent`.
- The store is the only state (no caches in the consumer). Its `commit` is all-or-nothing, you make one commit per new event, and store errors propagate.
- Invalid events (bad id, non-`Decimal`, non-finite or zero amount) raise `ValueError`.

## Scenario

A ledger service consumes `AccountMoney` events from a broker with **at-least-once** delivery:
a message can be redelivered after a consumer crash, a rebalance, or a lost acknowledgement.
Every event has a stable `event_id`. Applying a deposit twice is real money, so the effect of an
`event_id` must happen **at most once**, no matter how the consumer crashes or how often the
broker redelivers.

You are given a storage interface and must build the consumer on top of it.

## Contract

```text
Event(event_id, account_id, amount: Decimal)     # signed amount; defined in the stub

StateStore (Protocol, defined in the stub)
  .get(key, default=None) -> value
  .commit(writes: Mapping[str, Any]) -> None     # atomic: ALL writes or NONE (raises StoreError)

IdempotentConsumer(store)
  .process(event) -> "applied" | "rejected" | "duplicate"
  .balance(account_id) -> Decimal                # Decimal("0") for an unknown account
```

`ConflictingEvent` and `StoreError` are defined in the stub.

### Rules

- **First delivery** of an `event_id`:
  - `balance += amount`, outcome `"applied"`;
  - unless the new balance would be **negative**: then the balance is unchanged and the outcome is
    `"rejected"`. A rejection is a *decision*: it is final for that `event_id`.
- **Redelivery** of an `event_id` already decided (applied *or* rejected) with the same account
  and amount → `"duplicate"`, with **no** effect and **no** store write. This holds even if the
  balance has changed since, so a rejected withdrawal is never silently retried after a deposit.
- The same `event_id` with a **different** account or amount (by value: `Decimal("1.0") ==
  Decimal("1.00")`) → `ConflictingEvent`; nothing changes.
- Invalid events → `ValueError`: empty/non-string ids, non-`Decimal` or non-finite or zero amount.
- The store is the **only** state. Do not keep a cache of balances or processed ids in the
  consumer: a restarted consumer, or a second instance on the same store, must behave identically.
- Errors from the store (`StoreError`, anything else) **propagate**; do not catch them.

### Crash safety

The store gives you a single atomic primitive, `commit`. A crash can happen:

1. before `commit` takes effect (nothing was written);
2. after `commit` took effect but before the broker was told (the event will be redelivered).

Both must lead to **exactly one** effect after the redelivery. The tests inspect how many
`commit` calls you make per event.

## Example

| delivery | event_id | account | amount | balance before | outcome |
|---|---|---|---|---|---|
| 1 | e1 | acc-A | +100.00 | 0 | applied |
| 2 | e2 | acc-A | −130.00 | 100.00 | rejected |
| 3 | e1 | acc-A | +100.00 | 100.00 | duplicate |
| 4 | e2 | acc-A | −130.00 | 100.00 | duplicate (still rejected) |
| 5 | e3 | acc-B | −5.00 | 0 | rejected |

## Corner cases to think about

- Marker written, then the effect (or the reverse), as two separate writes: what survives a crash?
- The redelivered event arrives after the balance changed.
- Ids or accounts that contain separators, `:` for instance.
- Events for several accounts interleaved; one failing commit must not affect others.

## Clarify before you code

- Is deduplication scoped per consumer group, per topic, or global? For how long are ids kept?
- Should a conflicting redelivery stop the stream or go to a dead-letter queue?
- What if the effect is *outside* the store (an HTTP call, an email)? Is "exactly once" possible?

## Expected complexity

O(1) store reads and exactly one store `commit` per newly seen event.
