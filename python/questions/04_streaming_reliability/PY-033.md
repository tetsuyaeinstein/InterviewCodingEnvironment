# PY-033 · Retry transient failures with capped exponential backoff

**Topic:** Streaming & reliability · **Level:** medium · **Interview time:** ~30 min · **Module:** `python/practice/04_streaming_reliability/PY-033.py`

## Scenario

Your loader calls a warehouse REST endpoint and a message broker. Both fail transiently:
timeouts, 503s, deadlock victims. Retrying immediately makes an overloaded service worse, and
retrying forever keeps a batch hanging past its SLA. You need one well-behaved retry helper.

Everything time-related is **injected** (sleeper, clock, random source) so the schedule can be
tested exactly, with no real sleeping.

## Function contract

```text
retry(fn, *, retries=3, base_delay=0.1, max_delay=10.0, multiplier=2.0, jitter="none",
      retry_on=(TransientError,), sleep=time.sleep, rng=random, clock=time.monotonic,
      budget=None, on_retry=None) -> result of fn()
```

`TransientError` and `RetryError` are defined in the stub. `RetryError` is built with a message
only (`RetryError("...")`); set its `attempts` (calls made) and `last_error` attributes on the instance before raising it.

### Attempts and delays

- `fn` is called with no arguments. `retries` is the number of **re-tries**, so there are at
  most `retries + 1` attempts. `retries=0` means a single attempt.
- A successful call returns its result at once. Nothing is slept before the **first** attempt or
  after the last one.
- After the *n*-th failed attempt (n = 1, 2, ...) that will be followed by another attempt, call
  `sleep(delay)` with the **base schedule**

  `schedule(n) = min(max_delay, base_delay * multiplier ** (n - 1))`

  then apply jitter:

  | `jitter` | delay passed to `sleep` |
  |---|---|
  | `"none"` | `schedule(n)` |
  | `"full"` | `rng.uniform(0, schedule(n))` |
  | `"equal"` | `schedule(n) / 2 + rng.uniform(0, schedule(n) / 2)` |

  The cap applies **before** jitter. Call `rng.uniform` exactly once per sleep and only when
  jitter is enabled (the tests use a scripted fake with that method).
- `on_retry(n, exc, delay)`, when given, is called just before each sleep.

### Which errors

- Only exceptions that are instances of `retry_on` are retried. Any other exception
  **propagates immediately, unchanged**, with no sleep.
- When the attempts are used up, raise `RetryError` with `attempts` and `last_error` set and the
  last exception as `__cause__`. (The last error is *not* re-raised bare, so callers can tell
  "gave up" from "failed once".)

### Time budget

- `budget` (seconds, default `None` = unlimited) limits the total wall time from the start of
  `retry` according to the injected `clock`.
- Before sleeping, if `clock() + delay` would end **after** `start + budget`, do not sleep. Raise
  `RetryError` immediately (same attributes). Ending exactly **at** the budget is allowed.
- `fn` itself may take time (the clock advances while it runs).

### Validation (`ValueError`)

`retries < 0`, `base_delay < 0`, `max_delay < 0`, `multiplier < 1`, `budget < 0`, or an unknown
`jitter` mode. Validate before the first call to `fn`.

## Example

`retries=4, base_delay=0.5, multiplier=2, max_delay=3` against a function that always raises
`TransientError`: sleeps are `[0.5, 1.0, 2.0, 3.0]`, then `RetryError(attempts=5)`.

## Corner cases to think about

- Off-by-one between "retries" and "attempts".
- A very large `retries` with `multiplier=2` must not overflow (`2.0 ** 2000`).
- `max_delay` smaller than `base_delay`.
- A non-retryable error on the third attempt.
- A budget that is exhausted *because `fn` was slow*, not because of sleeping.

## Clarify before you code

- Which errors are safe to retry? Is the operation idempotent (see PY-032)?
- Full jitter vs equal jitter vs none: what happens when 10,000 clients fail at once?
- Should the deadline be per call or per pipeline? Who owns the retry budget when layers nest?

## Expected complexity

O(retries) time, O(1) memory.
