# PY-030 · Incremental load with watermark, overlap window and dedup

**Topic:** ETL & file processing · **Level:** hard · **Interview time:** ~40 min · **Module:** `python/practice/03_etl_file_processing/PY-030.py`

## In plain words

> "Every 15 minutes we pull changed rows, and some arrive late or twice. Decide which to process now, which are too late, and what state to carry to the next run."

**You return:** `select_incremental(records, state, *, overlap, upper_bound, key_field="id", ts_field="updated_at")` returns a `BatchResult` with `to_process`, `late` and the new `state`.

**The fine print, in short:**
- Process rows with `watermark - overlap <= updated_at < upper_bound`. Rows at or after `upper_bound` wait for a later run; rows before the window go to `late`. A first run (`None` watermark) has no lower limit.
- Skip any `(key, updated_at)` already processed or already seen in this batch, first delivery wins. `to_process` is ordered by `(updated_at, key)`.
- The watermark never goes down; the processed set drops pairs older than `new_watermark - overlap`. Naive times, missing keys, negative overlap, or an `upper_bound` before the watermark raise `ValueError`.

## Scenario

Every 15 minutes, a job pulls changed rows from an operational database, filtering on
`updated_at`. The naive `updated_at > last_watermark` loses rows:

- transactions commit **late**, with an `updated_at` earlier than rows already seen;
- source clocks drift.

So the job re-reads an **overlap window** behind the watermark. That makes rows arrive more than
once, and they must not be processed twice: the downstream is not idempotent.

Write the pure decision function. Given a batch of delivered records and the previous state, it
returns what to process now, what is too late, and the next state.

## Function contract

```text
select_incremental(records: Iterable[Mapping], state: WatermarkState, *,
                   overlap: timedelta, upper_bound: datetime,
                   key_field: str = "id", ts_field: str = "updated_at") -> BatchResult
```

`WatermarkState(watermark, processed)` and `BatchResult(to_process, late, state)` are defined in
the stub. `processed` is a `frozenset` of `(key, updated_at)` pairs.

**Validation**

- Every record needs a non-`None` `key_field` and an **aware** `datetime` in `ts_field`. Otherwise
  → `ValueError`.
- `upper_bound` must be aware.
- Raise `ValueError` if `overlap < 0`, or if `upper_bound < state.watermark` (the clock went
  backwards).

**The window**

- `lower = watermark - overlap`. There is no lower bound when `watermark is None` (first run).
- Selected records satisfy `lower <= updated_at < upper_bound`: inclusive lower, **exclusive**
  upper.
- Records with `updated_at >= upper_bound` are ignored this time. A later run picks them up.
- Records with `updated_at < lower` go to `late`, in any order. They can no longer be
  deduplicated safely, so they must be reported, not dropped silently and not processed.

**Dedup**

- A version is identified by `(key, updated_at)`, with timestamps compared as instants, so
  `12:00Z == 14:00+02:00`.
- A version in `state.processed`, or already selected earlier in this batch, is skipped. The
  first delivery wins.

**Output**

- `to_process` is ordered by `(updated_at, key)`.
- The new watermark is the max `updated_at` of `to_process`, but **never lower than the old
  watermark**. With nothing to process, it stays the same: `None` stays `None`.
- The new `processed` set contains exactly the pairs from `state.processed ∪ newly selected`
  with `updated_at >= new_watermark - overlap`. Older pairs can never re-enter a window, so
  keeping them would grow the state forever. With a `None` watermark it is empty.
- The input `state` is not modified.

## Example

`overlap = 10 min`, state = `(watermark 12:30, processed {("A", 12:25), ("B", 12:30)})`,
`upper_bound = 13:00`.

| record | outcome |
|---|---|
| A @ 12:25 | skipped: already processed |
| C @ 12:20 | processed: exactly at lower, which is inclusive |
| D @ 12:19:59 | late |
| B @ 12:41 | processed: a new version of B |
| E @ 13:00 | ignored: upper bound is exclusive |

The new watermark is 12:41. The new processed set is `{("B", 12:41)}`: everything else is older
than 12:31.

## Corner cases to think about

- A batch where everything is in the overlap and older than the watermark.
- An empty batch.
- The same version delivered twice in one batch.
- The same instant written with two different offsets.
- What happens to the state size after a year of runs?

## Clarify before you code

- Is `updated_at` assigned at commit time or at statement time? This decides how big the overlap
  must be.
- How should `late` records be handled downstream: a DLQ, a backfill, or an alert?
- Can two different payloads share `(key, updated_at)`? This contract says they are the same
  version.

## Expected complexity

O(n) per batch (O(n log n) if you sort). State size O(versions within one overlap window).
