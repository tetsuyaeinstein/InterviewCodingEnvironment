# PY-024 · Resolve revisions and conflicts for duplicate business keys

**Topic:** ETL & file processing · **Level:** hard · **Interview time:** ~35 min · **Module:** `python/practice/03_etl_file_processing/PY-024.py`

## In plain words

> "A CRM sends account changes, possibly twice and out of order. Give me the current record for each account, and flag cases where two different versions share the same sequence number."

**You return:** `resolve_revisions(records, key_fields, *, sequence_field="source_seq", ignore_fields=())` returns a tuple: the current records sorted by key, and a list of `Conflict`s sorted by key.

**The fine print, in short:**
- The highest sequence wins, whatever the arrival order. Records equal after removing `ignore_fields` are the same; keep the first arrival.
- Two different payloads at the winning sequence are a `Conflict` (one record per payload, first arrival each), and that key is left out of the current records. Disagreement at lower sequences doesn't matter.
- A missing or `None` key, or a bad sequence (not an int or digit string), raises `ValueError`. Digit strings compare as numbers. Shuffling the input must not change the result.

## Scenario

A CRM publishes account changes. Every message carries the account's business key and a
**source sequence number** assigned by the CRM when the change was committed. Delivery is
at-least-once and unordered:

- the same message can arrive twice (possibly from two different landing files);
- an older revision can arrive **after** a newer one.

Occasionally the CRM has a bug and emits two *different* payloads with the **same** sequence.
Nobody can tell which one is right, so it must be **reported**, not silently resolved.

Produce the current state per key, plus a conflict report.

## Function contract

```text
resolve_revisions(records: Iterable[Mapping[str, object]], key_fields: Sequence[str], *,
                  sequence_field: str = "source_seq",
                  ignore_fields: Collection[str] = ()) -> tuple[list[dict], list[Conflict]]
```

`Conflict(key: tuple, sequence: int, records: tuple[dict, ...])` is defined in the stub.

**Input**

- `records` may be a one-shot iterator.
- The **business key** is `tuple(record[f] for f in key_fields)`. A missing key field or a `None`
  key value → `ValueError`.
- The **sequence** is `record[sequence_field]`. It must be an `int` (not `bool`) or a string of
  ASCII digits. Strings compare **numerically**: `"10"` > `"9"`. Anything else (missing, `None`,
  `"1.5"`, `"abc"`, `1.0`, `True`) → `ValueError`.

**Rules per key**

- The winning sequence is the **highest** sequence seen for that key. Arrival order never matters
  for which revision wins.
- Two records are **identical** when they are equal (`==`) after removing `ignore_fields` (e.g.
  `ingested_at`, `source_file`). Values may be nested lists/dicts.
- Among the records at the winning sequence:
  - all identical → **one** current record: the **first-arriving** one, returned with all its
    fields, including ignored ones;
  - two or more distinct payloads → a `Conflict`:
    - `Conflict.records` holds one record per distinct payload (the first arrival of each), in
      first-arrival order;
    - the key does **not** appear in the current records.
- A disagreement at a **lower**, superseded sequence is not a conflict. The newer revision
  settles it.

**Output**

- `current_records` is a list of dicts **sorted by business key**.
- `conflicts` is a list of `Conflict` **sorted by key**.
- Both are deterministic: shuffling the input must not change which record wins, which keys
  conflict, or the order of either list.

## Example

| arrival | account_id | source_seq | status | ingested_at |
|---|---|---|---|---|
| 1 | K7 | 12 | ACTIVE | 09:00 |
| 2 | K7 | 11 | NEW | 09:01 |
| 3 | K7 | 12 | ACTIVE | 09:05 |
| 4 | K3 | 4 | BLOCKED | 09:02 |
| 5 | K3 | 4 | ACTIVE | 09:03 |

With `ignore_fields={"ingested_at"}`:

- current: `[K7 seq 12 ACTIVE ingested 09:00]`. Arrival 3 is an identical duplicate.
- conflicts: `[Conflict(("K3",), 4, (BLOCKED record, ACTIVE record))]`.

## Corner cases to think about

- The late-arriving older revision (arrival 2).
- `"9"` vs `"10"`.
- Identical duplicates that differ only in an ignored field.
- A tie at seq 3 that is superseded by seq 4.
- Payloads containing lists, so they are not hashable.
- `Decimal("1.0") == Decimal("1.00")`.

## Clarify before you code

- What exactly defines "the same change": every field, or every field except load metadata?
- What should downstream do with a conflicting key? Keep the previous state? Page someone?
- Is the sequence global or per key? (It doesn't matter for this contract, but ask.)

## Expected complexity

O(n) or O(n log n) time. Be ready to say how much memory your approach needs and how it would
work on 2 billion records that don't fit in RAM. The tests include 200,000 records (< 3 s).
