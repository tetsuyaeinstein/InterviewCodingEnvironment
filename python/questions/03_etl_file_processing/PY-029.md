# PY-029 · Bounded-memory external merge sort of a CSV file

**Topic:** ETL & file processing · **Level:** hard · **Interview time:** ~45 min · **Module:** `python/practice/03_etl_file_processing/PY-029.py`

## Scenario

A legacy loader needs its input file **sorted by `account_id`**, so that it can do a sequential
merge against the master file. Today's extract is 60 GB, and the worker has 4 GB of RAM, so
`sorted(rows)` is not an option. Implement the sort with a hard cap on the number of records
held in memory. It must clean up after itself even when it fails: the shared scratch disk fills
up within days otherwise.

## Function contract

```text
external_sort_csv(src: str | PathLike, dest: str | PathLike, key_column: str, *,
                  max_records_in_memory: int, work_dir: str | PathLike,
                  numeric: bool = False,
                  on_run_written: Callable[[Path], None] | None = None) -> int
```

**Input**

- `src` is a UTF-8 CSV file (an optional BOM must be ignored) whose first record is the header.
- Fields may contain quoted commas, quotes and newlines.
- Blank lines are skipped.
- A data row with a different number of fields from the header → `ValueError`.

**Sort key**

- The key is the field in column `key_column`.
- With `numeric=False`, keys compare as Python strings (code-point order: `"10" < "9"`,
  `"B" < "a"`).
- With `numeric=True`, they compare as `Decimal(field.strip())`. A non-numeric or non-finite
  value → `ValueError`.
- The sort is **stable**: rows with equal keys keep their input order. `"1.5"` and `"1.50"` are
  equal keys.

**Memory limit**

- Never hold more than `max_records_in_memory` (M) data rows in memory.
- Read M rows, sort them, and write them as a **run file** in `work_dir`.
- Every run except the last holds exactly M rows.
- After each run file is completely written and closed, call `on_run_written(Path(run_file))` if
  it is given. Then merge all runs.
- During the merge, hold at most one pending row per run.

**Output**

- `dest` receives the header followed by all data rows in sorted order. Use the standard `csv`
  module dialect; the tests read it back with `csv.reader`.
- Write `dest` **atomically**: if the function fails, an existing `dest` keeps its old content,
  and a new `dest` is not created.
- Return the number of data rows written.

**Cleanup**

- When the function returns or raises, `work_dir` contains no files of yours. This includes
  exceptions from `on_run_written`.

**Errors.** Raise `ValueError` for:

- an empty file (no header);
- `key_column` missing from the header or appearing more than once;
- `max_records_in_memory < 1`.

**Edge case:** a header-only file produces a header-only `dest`, no runs, and returns 0.

## Example

`src` is `id,name` with ids 5, 3, 9, 1, 3. With `M=2` and `numeric=True`:

| run | contents (sorted) |
|---|---|
| 1 | 3, 5 |
| 2 | 1, 9 |
| 3 | 3 |

The merged output is `1, 3 (from run 1), 3 (from run 3), 5, 9`, and the result is 5. There were
three `on_run_written` calls, and `work_dir` is empty afterwards.

## Corner cases to think about

- Equal keys in different runs (stability across the merge).
- Multi-line quoted fields: a line-based `split` corrupts them.
- An error in the 15th run, after 14 run files already exist.
- Windows will not delete a file that is still open.

## Expected complexity

- Time O(n log M) for the run sorts plus O(n log k) for merging k = ⌈n/M⌉ runs.
- I/O: each row is read twice and written twice.
- Memory O(M + k).
- The tests sort 4,000 rows of ~5 KB each with M = 200 under a tight memory budget, and check the
  number of runs.
