# PY-026 · Atomic file-to-file transform (no partial outputs)

**Topic:** ETL & file processing · **Level:** medium · **Interview time:** ~25 min · **Module:** `python/practice/03_etl_file_processing/PY-026.py`

## In plain words

> "Rewrite this file line by line, but make sure the loader that polls it never sees a half-written file, and a failure never damages the old one."

**You return:** `transform_file_atomically(src, dest, transform, *, encoding="utf-8")` returns the number of lines written to `dest`.

**The fine print, in short:**
- `transform` gets each line without its line ending. Returning `None` drops the line; a string is written followed by one `\n`. All of `\n`, `\r\n` and `\r` count as line breaks.
- On any failure, including `KeyboardInterrupt`, `dest` stays exactly as it was (or still missing), no temp file is left behind, and the original error propagates.
- Read one line at a time (files can be many GB). `src` and `dest` can be the same path. Don't touch other files in the folder.

## Scenario

A nightly job rewrites `exports/customers.csv`, which a downstream loader polls every minute. Last
month the job crashed halfway through: the loader picked up a **half-written file** and loaded
40 % of the customers, and yesterday's good file was already overwritten. Make the rewrite
**atomic**:

- readers must always see either the complete old file or the complete new file;
- a failure must leave the old file exactly as it was;
- a failure must leave no debris behind.

## Function contract

```text
transform_file_atomically(src: str | PathLike, dest: str | PathLike,
                          transform: Callable[[str], str | None], *,
                          encoding: str = "utf-8") -> int
```

**Reading**

- Read `src` as text in `encoding`, **one line at a time**. Files can be many GB.
- Line endings are universal: `\n`, `\r\n` and `\r` are all line breaks.
- Call `transform(line)` with each line **without** its line terminator. A final line without a
  terminator is still a line.
- `None` means "drop this line". A string is written to the output followed by exactly one `\n`.
- The output uses `\n` line endings on **every** OS, in the same `encoding`.

**Writing**

- Never write into `dest` directly. Write a temporary file **in the same directory as `dest`**.
- Flush it and `os.fsync` it.
- Close it, then move it over `dest` with an atomic rename (`os.replace`, or `Path.replace`).

**Failure handling.** On **any** exception during the operation:

- the error comes from `transform`, from reading/decoding `src`, or is `KeyboardInterrupt`-like
  (`BaseException`);
- `dest` is left byte-for-byte as it was, and if it did not exist, it still does not exist;
- the temporary file is removed;
- the original exception propagates unchanged.

**Other rules**

- `src` and `dest` may be **the same path** (an in-place rewrite).
- Return the number of lines written.
- Other files in the destination directory are never touched.

## Example

`src` contains `id,name\r\n1,ann\r\n2,bob\r\n` and `transform=str.upper`. Then `dest` contains
exactly `ID,NAME\n1,ANN\n2,BOB\n`, and the function returns 3.

If `transform` raises on the second line, `dest` still holds whatever it held before, and the
directory contains no leftover temporary file.

## Corner cases to think about

- Where should the temp file live, and why does it matter for `os.replace`?
- What does Windows do when you replace or delete a file that is still open, including the
  source when `src == dest`?
- What does text mode write for `"\n"` on Windows by default?
- A transform that raises after 100 MB has been written.

## Clarify before you code

- Must the new file survive a power cut immediately after the function returns? That is why we
  fsync.
- Do readers hold the file open while it is replaced? On POSIX they keep reading the old inode.
  On Windows, ask.

## Expected complexity

O(file size) time. Memory O(longest line): the tests rewrite a ~12 MB file under a small memory
budget.
