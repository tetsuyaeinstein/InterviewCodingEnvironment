# PY-023 · Normalise messy dates, numbers and nulls to a canonical schema

**Topic:** ETL & file processing · **Level:** medium · **Interview time:** ~35 min · **Module:** `python/practice/03_etl_file_processing/PY-023.py`

## Scenario

Three regional teams upload order spreadsheets as CSV. Every value arrives as a string, and every
team has its own habits:

- dates as `2025-03-01` or `03/01/2025` (the US office) or `01/03/2025` (the UK office);
- timestamps with assorted UTC offsets;
- money with thousands separators and accounting-style negatives such as `(12.00)`;
- NULL spelled `""`, `NULL` or `n/a`.

Before loading, every value must be converted to an **explicit canonical schema**. A value that
doesn't fit is reported as a **field error**. It is never guessed: a silently swapped day and
month is a data-corruption incident.

## Function contract

```text
normalise_rows(rows: Iterable[Mapping[str, str | None]], schema: Sequence[Column], *,
               slash_date_order: str) -> tuple[list[dict], list[FieldError]]
```

`Column(name, kind, nullable=True)` and `FieldError(row_index, column, value, reason)` are defined
in the stub, together with the kind and reason constants and `NULL_TOKENS`.

**Schema checks.** Raise `ValueError` if any of these is wrong:

- `slash_date_order` is not `"MDY"` or `"DMY"`;
- the schema has an unknown `kind`;
- the schema has duplicate column names.

**Input values.** Each input value is a `str` or `None`, and a key may be absent from a row.

1. Strip surrounding whitespace.
2. If the key is absent, the value is `None`, or the stripped value lower-cased is in
   `NULL_TOKENS = {"", "null", "n/a"}`, it is **NULL**:
   - the output is `None`;
   - if the column is not nullable, also record `null_not_allowed`.
3. Otherwise parse by `kind`. Any other spelling is an error with the given reason, and the output
   value is `None`.

| kind | accepted (after stripping) | canonical value | error reason |
|---|---|---|---|
| `date` | `YYYY-MM-DD`, zero-padded, exactly 4-2-2 digits | `datetime.date` | `invalid_date` |
| `date` | `A/B/YYYY` (A, B 1–2 digits, 4-digit year): month/day order given **only** by `slash_date_order` | `datetime.date` | `invalid_date` |
| `timestamp` | anything `datetime.fromisoformat` accepts **that carries a UTC offset** (`Z`, `+05:30`, …) | aware `datetime` converted to UTC (`tzinfo=timezone.utc`) | `invalid_timestamp`; no offset → `naive_timestamp` |
| `decimal` | `[-]N[.F]` or `(N[.F])` (accounting negative) | `Decimal`, exact value **and scale** (`"1,234.50"` → `Decimal("1234.50")`) | `invalid_decimal` |
| `int` | `[-]N` or `(N)` | `int` | `invalid_int` |
| `str` | anything | the stripped string | (none) |

**Notation for numbers**

- `N` is ASCII digits, **either** with no separators (`1234`) **or** with correctly placed
  thousands commas (`1,234,567`).
- `F` is one or more ASCII digits.
- Nothing else is allowed: no `+`, no exponent, no currency symbols, no inner spaces, no `.5`,
  no `1.`, no `NaN`.

**Dates that are not real.** An impossible calendar date, such as `02/30/2025` or month 13, is
`invalid_date`. With `"MDY"`, `13/01/2025` is an error. It is **not** re-read as DMY.

**Output**

- The output is one dict per input row, in input order. Each holds **exactly** the schema columns,
  in schema order. Extra input keys are dropped.
- Each error is reported as `FieldError(row_index (0-based), column, original_value, reason)`.
  `original_value` is unstripped, or `None` if the key was absent.
- Errors are ordered by row, then by schema column order.

## Example

Schema:

- `id` int, not nullable
- `day` date
- `at` timestamp
- `amt` decimal

Called with `slash_date_order="DMY"`:

| input row | output | errors |
|---|---|---|
| `{"id": "2,001", "day": "05/04/2026", "at": "2026-04-05T01:00:00+02:00", "amt": "(7.5)"}` | `{"id": 2001, "day": date(2026,4,5), "at": 2026-04-04 23:00 UTC, "amt": Decimal("-7.5")}` | none |
| `{"id": "N/A", "day": "2026-4-5", "amt": "1e3"}` | all four `None` | `(1,"id",…,null_not_allowed)`, `(1,"day",…,invalid_date)`, `(1,"amt",…,invalid_decimal)` |

## Corner cases to think about

- `date.fromisoformat` and `strptime` both accept more than the table allows. Check which.
- `int("١٢")` works, because Python accepts non-ASCII digits.
- `"NA"` in a country column is Namibia, not NULL.
- A timestamp near midnight with a negative offset belongs to the **next** UTC day.

## Clarify before you code

- Who decides MDY vs DMY? Per file or per source, never per value.
- Should a row with errors still be loaded with NULLs, or go to a reject table? (Here: both are
  returned, and the caller decides.)

## Expected complexity

O(rows × columns). Build each column's parser once, not once per row.
