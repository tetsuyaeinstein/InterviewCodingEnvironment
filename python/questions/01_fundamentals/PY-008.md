# PY-008 · In-memory inner and left join with SQL semantics

**Topic:** Python fundamentals · **Level:** medium · **Interview time:** ~25 min · **Module:** `python/practice/01_fundamentals/PY-008.py`

## Scenario

A small enrichment step joins a batch of transactions (tens of thousands of rows) to a customer
extract before writing a report. The data is already in memory as lists of dicts, so spinning up
a database for it is overkill. Analysts will compare the output with the same join in SQL, so it
must follow **SQL semantics exactly**:

- duplicates fan out;
- NULL keys never match;
- unmatched left rows survive a LEFT JOIN;
- column-name clashes are resolved predictably.

## Function contract

```text
join_records(left: Iterable[Mapping[str, Any]], right: Iterable[Mapping[str, Any]], on: str, *,
             how: str = "inner", right_suffix: str = "_right") -> list[dict[str, Any]]
```

**Matching**

- Rows match when `left_row[on] == right_row[on]`, compared as Python values with no type
  coercion (`1` does not match `"1"`).
- A key that is **missing or `None` never matches anything**, not even another `None`. This
  is SQL `NULL` semantics.
- **Many-to-many:** each left row is paired with **every** matching right row, like SQL.

**Join types**

- `how="inner"`: only matched pairs.
- `how="left"`: also every left row with no match (including missing/None keys), output as a
  **copy of the left row alone**. No right-hand fields are added; there is no right schema to
  fill with `None`.
- Any other `how` raises `ValueError`. `right_suffix` must be a non-empty `str`, otherwise
  `ValueError`.

**Merged rows**

- A merged row starts as a copy of the left row (including `on`). Then each right field
  except `on` is added in the right row's key order:
  - if the field name already exists **in the left row**, it is added as
    `name + right_suffix`; the left value keeps the plain name;
  - otherwise it is added under its own name.
- If the name to be added already exists in the merged row, raise `ValueError`. Example: left
  has `status` and `status_right`, and right has `status`.

**Order and side effects**

- Output order follows the **left input order**. For one left row, its matches appear in
  **right input order**.
- Every output row is a new dict (values are not copied). Inputs are not mutated, and both
  inputs may be one-pass iterators.

## Example (`on="customer_id"`, `how="left"`)

Left (transactions):

| transaction_id | customer_id | status |
|---|---|---|
| 1 | 10 | COMPLETED |
| 2 | 11 | COMPLETED |
| 3 | None | COMPLETED |
| 4 | 10 | PENDING |

Right (customer extract; 10 appears twice because of an SCD history row):

| customer_id | status | region |
|---|---|---|
| 10 | ACTIVE | EU |
| 12 | ACTIVE | US |
| 10 | CLOSED | EU |
| None | ACTIVE | ?? |

Result, in order:

| transaction_id | customer_id | status | status_right | region |
|---|---|---|---|---|
| 1 | 10 | COMPLETED | ACTIVE | EU |
| 1 | 10 | COMPLETED | CLOSED | EU |
| 2 | 11 | COMPLETED | (absent) | (absent) |
| 3 | None | COMPLETED | (absent) | (absent) |
| 4 | 10 | PENDING | ACTIVE | EU |
| 4 | 10 | PENDING | CLOSED | EU |

With `how="inner"`, rows 2 and 3 disappear, leaving 4 rows.

## Corner cases to think about

- `None` on both sides.
- A right side with duplicate keys, and a left side with duplicate keys at the same time.
- Overlapping column names, and a suffix that collides with an existing column.
- Right rows that don't have the key field at all.
- Inputs that can be iterated only once.

## Expected complexity

O(|left| + |right| + |output|) expected time. The tests join 20,000 × 20,000 rows; a nested loop
(400 million comparisons) will not finish in time.

## Clarify before you code

- Is a fan-out (duplicate keys on the right) expected, or is it a data bug to flag?
- Which side's value wins on a name clash?
- Should an unmatched LEFT JOIN row carry explicit `None` columns?
