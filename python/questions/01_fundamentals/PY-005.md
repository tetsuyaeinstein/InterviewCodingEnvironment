# PY-005 · Normalise ISO 8601 timestamps to UTC

**Topic:** Python fundamentals · **Level:** medium · **Interview time:** ~25 min · **Module:** `python/practice/01_fundamentals/PY-005.py`

## Scenario

Transactions reach the lake from three sources:

- the cloud API sends `2025-06-01T14:03:22.123Z`;
- the payment processor sends `2025-06-01T19:33:22+05:30`;
- older kiosk firmware sends **local wall-clock time with no offset at all**
  (`2025-06-01 10:03:22`), and the kiosk's IANA time zone is known from the device registry.

Everything must be stored as a UTC instant. Getting this wrong is silent: naive timestamps
interpreted in the server's zone shift revenue across days, and DST transitions create
duplicate or impossible local times twice a year.

## Function contract

```text
to_utc(value: str, default_tz: str | None = None, *, ambiguous: str = "raise") -> datetime
```

**Returns** an aware `datetime` whose `tzinfo` **is** `datetime.timezone.utc`, representing
the same instant as the input.

**Accepted input shape** (surrounding whitespace is stripped first):

| part | form |
|---|---|
| date | `YYYY-MM-DD` |
| separator | `T`, `t` or a single space |
| time | `HH:MM`, `HH:MM:SS` or `HH:MM:SS.fff…` (1 or more fractional digits) |
| designator (optional) | `Z` or `z` (UTC), `±HH:MM` or `±HHMM` |

- Fractional seconds beyond 6 digits (nanosecond timestamps from JVM systems) are
  **truncated**, not rounded, to microseconds.
- **Aware input** (with a designator) is converted to UTC. `default_tz` is irrelevant for it
  (but still validated, see below).
- **Naive input** (no designator):
  - if `default_tz` is `None`, raise `ValueError`. Never guess a zone;
  - otherwise interpret the wall-clock time in the IANA zone `default_tz`
    (e.g. `America/New_York`).
- **DST, for naive input with a zone:**
  - A wall time that **does not exist** (skipped by a spring-forward gap) always raises
    `ValueError`.
  - A wall time that occurs **twice** (fall-back overlap) is resolved by `ambiguous`:
    - `"raise"` (default) raises `ValueError`;
    - `"earlier"` picks the first occurrence (the earlier UTC instant);
    - `"later"` picks the second.
- **Errors**:

  | input | raises |
  |---|---|
  | `value` is not a `str` (including `None` and `datetime` objects) | `TypeError` |
  | empty/blank string, garbage, trailing junk | `ValueError` |
  | a **date-only** string such as `2025-03-09` (a date is not an instant), with or without `default_tz` | `ValueError` |
  | out-of-range fields (`2025-02-30`, hour 24, second 60) or an offset of 24 h or more | `ValueError` |
  | `default_tz` that is not a known IANA zone name (also when `value` is aware) | `ValueError` |
  | `ambiguous` that is not one of the three values | `ValueError` |

- Other ISO 8601 forms (basic format without dashes, week dates, ordinal dates) are out of
  scope. They are not tested.

## Examples

| value | default_tz | ambiguous | result (UTC) |
|---|---|---|---|
| `2025-06-01T14:03:22Z` | | | `2025-06-01 14:03:22+00:00` |
| `2025-06-01T19:33:22.5+05:30` | | | `2025-06-01 14:03:22.500000+00:00` |
| `2025-06-01 10:03:22` | `America/New_York` | | `2025-06-01 14:03:22+00:00` (EDT, −4) |
| `2025-01-15T10:03:22` | `America/New_York` | | `2025-01-15 15:03:22+00:00` (EST, −5) |
| `2025-06-01T10:03:22` | `None` | | `ValueError` (naive) |
| `2025-03-09T02:30:00` | `America/New_York` | | `ValueError` (does not exist) |
| `2025-11-02T01:30:00` | `America/New_York` | `"earlier"` | `2025-11-02 05:30:00+00:00` |
| `2025-11-02T01:30:00` | `America/New_York` | `"later"` | `2025-11-02 06:30:00+00:00` |

## Corner cases to think about

- `Z` in lower case, which RFC 3339 allows.
- `+05:30`, `+0545` (Nepal) and negative offsets that cross midnight into the previous or next
  UTC day.
- What your parser does with `2025-03-09` alone.
- Southern-hemisphere DST (e.g. `Australia/Sydney` falls back in April).

## Expected complexity

O(1) per value. Construct each `ZoneInfo` once per call at most (they are cached by the library
anyway).

## Clarify before you code

- Where does the zone for naive values come from, and is it per device or global?
- What should happen to ambiguous/non-existent local times: reject, or apply a documented
  policy?
- Is sub-microsecond precision needed downstream?
