# PY-001 · De-duplicate transaction records

**Topic:** Python fundamentals · **Level:** easy · **Interview time:** ~10 min · **Module:** `python/practice/01_fundamentals/PY-001.py`

## Scenario

Kiosks upload transaction batches over a flaky network. A retry can resend a batch that already
arrived partially, so the ingestion layer sees the **same `transaction_id` more than once**. Before
loading into the warehouse you must drop the re-sent copies. The **first** copy received is the
one of record (later copies may carry re-serialised or late-mutated fields and must be ignored).
Downstream consumers rely on the original arrival order.

## Function contract

```text
dedupe_transactions(records: Iterable[Mapping[str, Any]]) -> list[Mapping[str, Any]]
```

- `records` is any iterable of dict-like records: a list, or a **single-pass generator**.
- Two records are duplicates when their `transaction_id` values are **equal as Python values**.
  There is no coercion: `1001` (int) and `"1001"` (str) are different ids.
- The first occurrence of each id is kept. Every later record with the same id is dropped,
  even if its other fields differ.
- The output keeps the **input order** of the records that survive.
- A record whose `transaction_id` key is **missing**, or whose value is **`None`**, cannot be
  de-duplicated. Keep every such record, in its original position (a separate data-quality
  check will flag them; ingestion never silently drops data it cannot classify).
- Return the original record objects (no copies). Do not mutate the input records.

## Example

| position | record | kept? |
|---|---|---|
| 0 | `{"transaction_id": "T-9", "amount": "4.00"}` | yes |
| 1 | `{"transaction_id": "T-7", "amount": "1.50"}` | yes |
| 2 | `{"transaction_id": "T-9", "amount": "4.10"}` | no: re-sent copy of T-9 |
| 3 | `{"amount": "2.00"}` | yes: no id |
| 4 | `{"transaction_id": None, "amount": "2.00"}` | yes: no id |
| 5 | `{"transaction_id": "T-7", "amount": "1.50"}` | no |

Result: the records at positions 0, 1, 3, 4, in that order.

## Corner cases to think about

- Empty input.
- The same id three or more times, with different payloads.
- Several records without an id, including two that look identical.
- Ids of different types that print the same.
- Input that can only be iterated once.

## Expected complexity

- Time **O(n)** for n records. The tests use 30,000 records with mostly distinct ids; a
  quadratic approach will not finish in time.
- Extra space O(d) for d distinct ids, plus the output list.

## Clarify before you code

- Which copy wins: first or last? (First, here.)
- What happens to records without a usable id?
- Is order significant downstream?
