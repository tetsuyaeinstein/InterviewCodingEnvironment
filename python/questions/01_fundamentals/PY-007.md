# PY-007 · Schema validation with structured row errors

**Topic:** Python fundamentals · **Level:** hard · **Interview time:** ~40 min · **Module:** `python/practice/01_fundamentals/PY-007.py`

## Scenario

Partners upload refund and adjustment files (CSV converted to dicts, or JSON) into the
ingestion service. The old loader crashed on the first bad value, so one typo in row 48,213
blocked the whole file and the partner got a stack trace. The new validator must:

- check every row against a declared schema;
- **collect every problem** (not just the first);
- return clean, type-coerced rows for loading, plus a machine-readable error list that is
  turned into a rejection report for the partner.

It must **never raise because of bad data**. It raises only when the *schema* (the engineer's
configuration) is wrong.

## Types defined in the stub

```text
FIELD_TYPES = ("str", "int", "decimal", "bool", "date")
UNKNOWN_FIELD_POLICIES = ("error", "ignore", "keep")

class SchemaError(ValueError)

@dataclass(frozen=True)
class FieldSpec:  name: str, type: str, required: bool = True, nullable: bool = False,
                  allowed: Collection | None = None

@dataclass(frozen=True)
class RowError:   row_index: int, field: str | None, error_code: str, message: str
```

## Function contract

```text
validate_rows(rows: Iterable[Any], schema: Sequence[FieldSpec], *,
              unknown_fields: str = "error") -> tuple[list[dict], list[RowError]]
```

### Schema checks (before any row is read)

Raise `SchemaError` if:

- any schema entry is not a `FieldSpec`;
- a `name` is not a non-empty `str`, or two fields share a name;
- `type` is not in `FIELD_TYPES`;
- `required` or `nullable` is not a `bool`;
- `allowed` is not `None` and is either empty, a `str`, or contains a value whose Python type
  doesn't match the field type. The expected Python types are:

  | field type | `str` | `int` | `decimal` | `bool` | `date` |
  |---|---|---|---|---|---|
  | allowed values must be | `str` | `int` (not `bool`) | `Decimal` | `bool` | `date` (not `datetime`) |

An `unknown_fields` value outside `UNKNOWN_FIELD_POLICIES` raises `ValueError`. An empty schema
is allowed.

### Per-row validation

`row_index` is the 0-based position in `rows`. A row that is not a `Mapping` gets one error
(`not_a_mapping`, `field=None`) and nothing else.

Each schema field is checked **in schema order**. At most one error is reported per field: the
first check that fails.

1. **Presence.** The key is absent:
   - if `required`, report `missing_required`;
   - otherwise the field is simply omitted from the output row.
2. **Null.** The value is null if it is `None`, or, for every type except `"str"`, a string that
   is empty after stripping. A null value is:
   - an error `null_not_allowed` unless `nullable`;
   - otherwise output as `None`, skipping steps 3–4.
3. **Type / format.** Coerce the value to its canonical Python type. Report `invalid_type` when
   the Python type is unacceptable, or `invalid_format` when a string cannot be parsed:

   | type | accepted as is | accepted strings (surrounding whitespace stripped) | `invalid_type` examples |
   |---|---|---|---|
   | `str` | `str`, unchanged (not stripped) | n/a | `5`, `b"x"`, `["a"]` |
   | `int` | `int` (not `bool`) | optional sign + digits: `" -42 "` | `True`, `3.0`, `Decimal("3")` |
   | `decimal` | finite `Decimal`, `int` (not `bool`) | any finite decimal: `"12.50"`, `"1e3"` | `1.5` (float), `True` |
   | `bool` | `bool` | `"true"` / `"false"`, any case | `1`, `0` |
   | `date` | `date` (not `datetime`) | `YYYY-MM-DD` | `datetime(...)`, `20250101` |

   - A decimal string that doesn't parse, or parses to `NaN`/`Infinity` (also a non-finite
     `Decimal` object), is `invalid_format`.
   - So is an int string like `"3.0"` or `"1,000"`, a bool string like `"yes"`, and a date
     string like `"2025-02-30"` or `"01/02/2025"`.
4. **Allowed values.** If `allowed` is set, a coerced non-null value not in it is
   `not_allowed`.

**Unknown keys** (keys not named in the schema) depend on `unknown_fields`:

| policy | effect |
|---|---|
| `"error"` | one `unknown_field` error per key, `field=str(key)`, reported after the schema fields, in ascending `str(key)` order |
| `"ignore"` | dropped from the output |
| `"keep"` | copied unchanged into the output, after the schema fields, in the row's key order |

### Output

- `valid_rows`: one new dict per row with **zero** errors, in input order. It contains the
  coerced schema fields in schema order (absent optional fields omitted), plus kept unknown
  keys.
- `errors`: every `RowError`, ordered by `row_index`, then schema-field order, then unknown
  keys. `message` is a human-readable, non-empty string (wording is free). Error codes are
  exactly:
  - `not_a_mapping`
  - `missing_required`
  - `null_not_allowed`
  - `invalid_type`
  - `invalid_format`
  - `not_allowed`
  - `unknown_field`
- Input rows are not mutated. `rows` may be a one-pass iterator.

## Example

Schema:

- `refund_id`: `int`
- `amount`: `decimal`
- `reason`: `str`, allowed `{"DAMAGED", "DUPLICATE", "OTHER"}`
- `approved`: `bool`, optional
- `refund_date`: `date`, nullable

| row | data | outcome |
|---|---|---|
| 0 | `{"refund_id": "7", "amount": "12.50", "reason": "OTHER", "refund_date": "2025-06-01"}` | valid → `{refund_id: 7, amount: Decimal("12.50"), reason: "OTHER", refund_date: date(2025, 6, 1)}` |
| 1 | `{"refund_id": "x", "amount": 1.5, "reason": "LOST", "refund_date": "", "note": "hi"}` | 4 errors: `refund_id` invalid_format, `amount` invalid_type, `reason` not_allowed, `note` unknown_field. `refund_date` is null and nullable, so it is fine |
| 2 | `["7", "12.50"]` | `not_a_mapping` |

## Corner cases to think about

- `bool` is a subclass of `int`, and `datetime` is a subclass of `date`.
- `Decimal("NaN")` parses without error.
- Empty strings in CSV: null for typed fields, but a legitimate value for `str` fields.
- A row with several bad fields and several unknown keys.
- A schema mistake must surface even if there are no rows at all.

## Expected complexity

O(rows × fields) time. Memory proportional to the output (valid rows + errors).

## Clarify before you code

- Is a missing optional field "absent" or "null"? (Absent here.)
- Should valid rows of a file with errors still be loaded (partial acceptance), or should the
  whole file be rejected? (The caller decides; you return both.)
- Is there an error budget, e.g. stop after 1,000 errors? (Not here.)
