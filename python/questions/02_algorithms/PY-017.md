# PY-017 · Merge sorted event streams lazily

**Topic:** algorithms & interview patterns · **Level:** hard · **Interview time:** ~30 min · **Module:** `python/practice/02_algorithms/PY-017.py`

## In plain words

> "Each region writes its events to its own log, already sorted by time. Give me one combined stream in time order, without loading the logs into memory."

**You return:** `merge_sorted_streams(streams, key=None)` returns an iterator over every item of every stream, in non-decreasing key order.

**The fine print, in short:**
- Items with equal keys come out in stream order (stream 0 first). Items within a stream keep their order. `key` is called exactly once per item read.
- Do nothing until the first `next()`, and never read more than one item ahead on any stream. Infinite streams must work.
- Never compare two raw items, and never load a whole stream. No streams, or only empty ones, give an empty iterator.

## Scenario

Each kiosk region writes its events to its own log, **already sorted by timestamp**. The analytics
job needs one globally ordered stream of events across K regions. The logs are far too large to
load: they are generators over files or network cursors, and some live feeds never end. The merged
stream must therefore be produced **lazily**, one event at a time, with memory proportional to K,
not to the number of events.

## Function contract

```text
merge_sorted_streams(
    streams: Iterable[Iterable[T]],
    key: Callable[[T], Any] | None = None,
) -> Iterator[T]
```

- `streams` is an iterable of iterables. Each inner iterable is sorted in **non-decreasing** order
  of `key(item)` (or of the item itself when `key` is `None`). You may assume this and don't have
  to validate it.
- Return an **iterator** that yields every item of every stream exactly once, in non-decreasing
  key order.
- **Stability:** items with equal keys come out in order of **stream position** (stream 0 before
  stream 1, ...). Items from the same stream keep their own order.
- `key` is optional. When given, call it **exactly once per item** that is read.
- **Laziness (tested):**
  - Calling `merge_sorted_streams(...)` reads **nothing** from the streams. Work starts at the
    first `next()`.
  - At any time, a stream may have been read at most **one item ahead** of what has been yielded
    from it: if `y` items of stream `s` were yielded, at most `y + 1` items were read from `s`.
  - A stream that has finished (`StopIteration`) is never asked for another item.
  - Infinite streams are valid. Taking the first `n` items must terminate.
- Never materialise a stream (`list(...)`, `sorted(...)` over everything, `itertools.chain` plus
  sort). Items may not be comparable with each other when keys differ: **never compare two raw
  items** when a key is given, or when equal keys are possible.
- No streams, or only empty streams, give an empty iterator.

## Example

```text
a = [1, 4, 9]        b = [2, 4, 10]        c = []
merge_sorted_streams([a, b, c])        ->  1, 2, 4, 4, 9, 10
```

With records `(ts, source)` and `key=lambda r: r[0]`:

```text
a = [(1, "A"), (5, "A")]     b = [(1, "B"), (5, "B")]
->  (1, "A"), (1, "B"), (5, "A"), (5, "B")        # ties: stream 0 first
```

## Corner cases to think about

- The same key in many streams, and many equal keys inside one stream.
- Empty streams in the middle, at the front, or all of them.
- A single stream.
- Items that can't be compared with each other (for example dicts) when a key is supplied.
- A stream that is infinite or that raises if read too far.

## Expected complexity

**O(N log K)** time for N items over K streams, and **O(K)** extra memory. The tests merge 1,000
streams of 200 items each, which a "scan all K heads for every output" approach (O(N · K)) will not
finish in time.

## Clarify before you code

- What does "stable" mean when keys tie? (Lower stream index first, then stream order.)
- May I read the next item of a stream before the consumer asks for it? (At most one ahead.)
- Are the inputs guaranteed sorted? (Yes. Validation is out of scope.)
