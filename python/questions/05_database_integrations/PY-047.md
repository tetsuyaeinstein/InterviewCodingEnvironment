# PY-047 · Respect an API rate limit (429 / Retry-After)

**Topic:** PostgreSQL, APIs & backend patterns · **Level:** hard · **Interview time:** ~30 min · **Needs:** nothing external (injected clock and sleeper)

## In plain words

> "Our partner API answers 429 and says how long to wait. Write a wrapper that waits exactly that long, gives up sensibly, and can be tested without real waiting. Also write a client-side limiter."

**You return:** `call_with_rate_limit(call, *, sleep, clock, ...)` returns the first successful result or re-raises `RateLimited`; `RateLimiter(...).acquire()` returns the seconds it waited.

**The fine print, in short:**
- Wait exactly `retry_after` (negative counts as 0); if it is `None`, use `default_backoff`, doubling each time. Sleep only for waits above 0. On the last allowed attempt, or when the wait would push total elapsed time strictly past `max_total_wait`, re-raise at once without sleeping. Other exceptions propagate immediately.
- Limiter: at most `max_calls` admissions in any window of `period` seconds; a call at time t is admitted if fewer than `max_calls` earlier ones fall in `(t - period, t]`. Re-check after waking up.
- Time is injected (`sleep`, `clock`), never use `time` directly. `max_attempts < 1`, `max_calls < 1` or `period <= 0` raises `ValueError`.

## Scenario

Your sync job calls a partner API that answers **HTTP 429** when you exceed its quota and says,
in a `Retry-After` header, how long to wait. The previous implementation slept a fixed 1 second
and retried forever, and was banned for hammering the API. You need a wrapper that does what the
server asks, gives up sensibly, and is fully testable **without real waiting**: time is injected.

## Part 1: `call_with_rate_limit`

```text
class RateLimited(Exception):        # raised by your HTTP layer on a 429
    retry_after: float | None        # seconds from the Retry-After header; None if absent

call_with_rate_limit(call, *, sleep, clock, max_attempts=5, max_total_wait=60.0, default_backoff=1.0)
```

- `call()` takes no arguments and returns the result. `sleep(seconds)` and `clock() -> float`
  (monotonic seconds) are injected. Never use `time` directly.
- If `call()` raises `RateLimited`, wait and call again; return the first successful result.
- **Wait time:** when `retry_after` is given, wait **exactly** that many seconds (a float is fine; a
  negative value counts as 0). When it is `None`, use exponential backoff: `default_backoff`, then `2x`,
  `4x`, ... for the 1st, 2nd, 3rd ... rate-limited failure. Call `sleep` only for waits greater than 0.
- `max_attempts` is the maximum number of calls to `call()`. When the last allowed attempt is
  rate limited, re-raise that `RateLimited` **without sleeping**.
- `max_total_wait` caps the **elapsed time** since the first attempt, measured with `clock()`
  (so time spent inside `call()` counts too). If `clock() - start + wait` would exceed
  `max_total_wait` (strictly greater), do not sleep: re-raise the current `RateLimited` immediately.
  A server asking for an hour must not park your worker for an hour.
- **Any other exception propagates immediately**: no sleep, no retry.
- `max_attempts < 1` raises `ValueError`.

## Part 2: `RateLimiter` (proactive, client side)

```text
RateLimiter(max_calls: int, period: float, *, clock, sleep)
limiter.acquire() -> float        # seconds waited
```

At most `max_calls` calls may be admitted in any window of `period` seconds. A call at time *t* is
admitted if fewer than `max_calls` earlier admissions happened in the interval `(t - period, t]`.
`acquire()` returns immediately (0.0) when allowed; otherwise it sleeps exactly until the oldest
admission in the window leaves it, then admits (re-checking after waking up, since a real `sleep` may
return early), and returns the sum of the durations it passed to `sleep`. `max_calls < 1` or `period <= 0` raises `ValueError`.

## Example (made-up)

Responses: 429 (Retry-After 2), 429 (no header), 429 (Retry-After 0.5), then 200 with `"ok"`.
With the defaults, `sleep` is called with `2`, `2.0` (the second failure, no header: `default_backoff * 2`) and `0.5`, in that order, and `"ok"` is returned.

Limiter with `max_calls=2, period=10`: acquisitions at t = 0, 1 are immediate; a third at t = 1 sleeps 9
seconds (until t = 10).

## Corner cases

- Retry-After of 0, negative, or a float like 0.25.
- The call itself takes time and the budget runs out mid-way.
- `Retry-After` larger than the whole budget.
- A non-429 error (e.g. `ValueError`, a 500) on the 2nd attempt.
- Limiter: acquisitions exactly `period` apart (the old one has left the window).

## Expected complexity

O(attempts) per call; O(max_calls) memory for the limiter.
