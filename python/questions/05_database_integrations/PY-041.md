# PY-041 · Parameterized customer transaction lookup with psycopg

**Topic:** PostgreSQL, APIs & backend patterns · **Level:** easy · **Interview time:** ~15 min · **Needs:** running lab PostgreSQL (`requires_postgres`)

## In plain words

> "Support agents look up a customer's transactions for a date range, optionally filtered by status. The values come straight from a web form, so handle them safely."

**You return:** `fetch_customer_transactions(conn, customer_id, start, end, statuses=None)` returns a list of dicts with `transaction_id`, `transaction_ts`, `gross_amount` and `transaction_status`.

**The fine print, in short:**
- The range is on the UTC date, `start` inclusive and `end` exclusive. Order by `transaction_ts`, then `transaction_id`.
- `statuses=None` means all statuses; an empty list returns no rows.
- Every user value must be a bind parameter, and a non-integer `customer_id` must fail. Do not commit or close the connection.

## Scenario

A support tool lets an agent look up a customer's transactions for a date range, optionally
filtered by status. The values come straight from a web form, so the query **must** be
parameterized. Building SQL text from user input (f-strings, `%` formatting, `+`) is an automatic
fail in code review, and in this exercise.

## Function contract

```text
fetch_customer_transactions(conn, customer_id: int, start: date, end: date,
                            statuses: Sequence[str] | None = None) -> list[dict]
```

- `conn` is an open **psycopg 3** connection (the tests pass a read-only lab connection). Do not
  commit and do not close it.
- Return the rows of `transactions` for `customer_id` whose **UTC business date** satisfies
  `start <= date < end`. The range is **half-open**: `end` is exclusive.
- `statuses=None` means all statuses. A list restricts to those `transaction_status` values. An
  **empty list** therefore returns no rows.
- Each row is a dict with exactly these keys:
  - `transaction_id` (int)
  - `transaction_ts` (aware `datetime`)
  - `gross_amount` (`Decimal`)
  - `transaction_status` (str)
- Order by `transaction_ts`, then `transaction_id`.
- Every user-supplied value must reach PostgreSQL as a **bind parameter**.

## Example (fixture data in the lab database)

`fetch_customer_transactions(conn, 26, date(2025, 10, 1), date(2025, 11, 1))` returns transactions
2602, 2603 (both at `2025-10-05 18:00:00+00`, ordered by id) and 2604 (PENDING).

With `statuses=["COMPLETED"]`, only 2602 and 2603 are returned.

## Corner cases

- Two transactions at exactly the same timestamp: the order must still be deterministic.
- A transaction at exactly `end` midnight UTC must be excluded. One at exactly `start` midnight
  must be included.
- A hostile status value such as `"COMPLETED' OR '1'='1"` must simply match nothing.
- `customer_id` that is not an integer (e.g. `"26 OR 1=1"`): the call must fail. It must not
  return other customers' data.

## Expected complexity

One round trip to the database. Server side, it is a range scan for one customer: be ready to
say which index helps.
