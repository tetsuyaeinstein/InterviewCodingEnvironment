# PY-046 · Consume a paginated REST source safely

**Topic:** PostgreSQL, APIs & backend patterns · **Level:** medium · **Interview time:** ~25 min · **Needs:** nothing external (fake client)

## In plain words

> "A partner API returns pages of records plus a token for the next page, but it is messy: empty pages in the middle, the same record showing up twice, and once an endless token loop. Write the page-walking iterator."

**You return:** `iterate_pages(client, *, page_size=None, max_pages=1000, id_key="id")` yields the records lazily, in server order.

**The fine print, in short:**
- Do not request the next page until the consumer has taken every record of the current one. `page_size`, if given, goes to every `get_page` call. An empty page with a next token is normal. A record whose id was already yielded is dropped (first one wins).
- A next token that was already requested raises `PaginationLoopError`, after yielding that page's records and with no further request. Still having a next token after `max_pages` pages raises `PaginationLimitError` instead of a further request.
- `ValueError` for a bad `page_size`, `max_pages < 1`, or a record without `id_key`. Client exceptions propagate unchanged.

## Scenario

You ingest orders from a partner's HTTP API. It returns pages of records and a token for the next
page. In practice the API is not as tidy as its documentation: some pages are empty although more
data follows, records shift between pages while you read (so the same record can show up twice),
and a buggy deployment once returned the same "next" token forever, which took a nightly job down
for six hours. Write the page-walking iterator that the rest of the ingestion code builds on.

## The client protocol

```text
client.get_page(token: str | None, page_size: int | None = None) -> {"items": [dict, ...], "next": str | None}
```

`token=None` means the first page. `next` is `None` on the last page. Tokens are opaque strings:
compare them for equality only. Every item is a dict with a unique identifier under `id_key`.
Network errors surface as exceptions from `get_page`; they are not your concern here (no retries).

## Function contract

```text
iterate_pages(client, *, page_size: int | None = None, max_pages: int = 1000, id_key: str = "id") -> Iterator[dict]
```

- Yield records **lazily, in server order**. The next page is not requested until the consumer has
  taken every record of the current one (a consumer that stops early causes no extra requests).
- `page_size` (if not `None`) must be a positive int (`ValueError` otherwise) and is passed to **every**
  `get_page` call as `page_size=...`.
- Stop after the page whose `next` is `None`.
- **Empty pages** (`items == []`) with a non-`None` `next` are normal: keep going.
- **Duplicates across pages:** a record whose id was already yielded is dropped. The **first**
  occurrence wins, even if the later copy differs.
- **Loops:** if a page's `next` token is one that has **already been requested** in this walk
  (including the token that produced the current page), raise
  `PaginationLoopError`. The records of the page that carried the bad token are yielded **before** the
  error is raised, and no further request is made.
- **Safety cap:** at most `max_pages` pages are requested. If the server still has a `next` after
  `max_pages` pages, raise `PaginationLimitError` instead of requesting page `max_pages + 1`.
  `max_pages < 1` raises `ValueError`.
- A record without `id_key` raises `ValueError`.
- Exceptions raised by the client propagate unchanged.

## Example (made-up)

Server pages: `None -> {A, B} next "t2"`, `"t2" -> {} next "t3"`, `"t3" -> {B, C} next None`.
`iterate_pages` yields `A, B, C` (the second `B` is dropped) and made three requests.

If `"t3"` had said `next "t2"`, the walk would yield `A, B, C`, then raise `PaginationLoopError`.

## Corner cases

- An empty first page with `next=None` (no data): yields nothing.
- Only empty pages, ending properly.
- Token loop of length 1 (a page pointing at itself) and of length 2.
- Cap reached exactly on the last page (fine) versus one page short (error).
- Consumer breaks out of the loop early.

## Expected complexity

O(total records) time, O(distinct ids + tokens) memory. State what that memory costs at 100M records
and what you would do instead.
