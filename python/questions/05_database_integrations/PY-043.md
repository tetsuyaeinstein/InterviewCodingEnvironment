# PY-043 · Batched idempotent upserts with a stale-version guard

**Topic:** PostgreSQL, APIs & backend patterns · **Level:** medium · **Interview time:** ~30 min · **Needs:** running lab PostgreSQL (`requires_postgres`)

## Scenario

An upstream system re-sends order snapshots. The same snapshot may arrive twice, an *older*
version may arrive after a newer one, and one file may even contain several versions of the same
order. You load them into a target table in batches. A retry of the whole job must be harmless,
and a bad row must never leave the table half-loaded.

## Target table (created by the caller, in the connection's current schema)

| column | type | notes |
|---|---|---|
| `business_key` | text | **primary key** |
| `amount` | numeric(12,2) | NOT NULL |
| `status` | text | NOT NULL |
| `seq` | integer | NOT NULL; version number from the source, higher = newer |

The table name is a parameter (it is an identifier, so it needs special care).

## Function contract

```text
load_batch(conn, rows: Iterable[dict], *, table: str = "txn_load", batch_size: int = 500) -> LoadResult
LoadResult(inserted: int, updated: int, skipped: int)
```

Each input row is a dict with `business_key` (str), `amount` (`Decimal`), `status` (str), `seq` (int).

Semantics:

1. **Upsert by `business_key`.** An unknown key is inserted. A known key is updated **only if
   the incoming `seq` is strictly greater** than the stored `seq` (then amount, status and seq all
   take the incoming values). A lower or equal `seq` leaves the stored row untouched.
2. **Duplicates inside the input:** for one key the row with the highest `seq` wins. If several
   have the same highest `seq`, the one that appears **last** wins. The losing rows are not sent
   to the database.
3. **Counts**, over distinct keys plus the dropped duplicates:
   - `inserted`: keys that did not exist before this call;
   - `updated`: existing keys whose stored row was changed;
   - `skipped`: every input row that did not cause a write (stale or equal `seq` against the
     table, **plus** the rows dropped as in-input duplicates).
   - So `inserted + updated + skipped == number of input rows`.
4. **Idempotent:** running the same call twice leaves the same table state; the second call
   reports `inserted == 0` and `updated == 0`.
5. **Atomic:** the whole call is one transaction. If any row fails (for example `amount` is
   `None`, violating NOT NULL), the exception propagates and **none** of the rows of this call,
   including those in earlier batches, remain.
6. **Batching:** send at most `batch_size` distinct rows per statement (one round trip per
   batch, not one per row). `batch_size < 1` raises `ValueError`. Empty input returns
   `LoadResult(0, 0, 0)`.
7. Every value is a bind parameter. The table name must be composed safely: a hostile name must
   not execute anything else.
8. A row missing a required key raises `KeyError` or `ValueError` **before** anything is written.
   `rows` may be any iterable (including a generator).

You may not commit explicitly. Wrap the work so that, if the caller has no transaction open, it
is committed on success, and rolled back on failure.

## Example (made-up data)

Table holds `A` (seq 1). Input: `A` seq 1, `B` seq 5, `C` seq 2, `C` seq 4, `A` seq 0.
Result: `B` inserted, `C` inserted (seq 4 wins), `A` untouched. `LoadResult(inserted=2, updated=0, skipped=3)`.

## Corner cases

- Input spanning several batches with the same key in different batches.
- The same job run twice, or an older snapshot replayed after a newer one.
- `amount` values such as `Decimal("0.10")` must survive exactly.
- Keys containing quotes, `;` or `%`.

## Expected complexity

O(n) time and O(n) extra memory for the in-input de-duplication; O(n / batch_size) round trips.
