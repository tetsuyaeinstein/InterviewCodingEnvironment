# PY-042 · Stream a large result set with bounded memory

**Topic:** PostgreSQL, APIs & backend patterns · **Level:** medium · **Interview time:** ~20 min · **Needs:** running lab PostgreSQL (`requires_postgres`)

## In plain words

> "A nightly export has to read every transaction in a date range, possibly hundreds of millions of rows, without holding them all in memory. Give the caller a plain iterator."

**You return:** `stream_transactions(conn, start, end, batch_size=1000)` yields one dict per transaction (`transaction_id`, `store_id`, `transaction_ts`, `gross_amount`, `transaction_status`), ordered by `transaction_ts`, then `transaction_id`.

**The fine print, in short:**
- UTC date range, `start` inclusive, `end` exclusive; `start == end` yields nothing. `batch_size < 1` or `start > end` raises `ValueError` (it may surface on the first `next()`).
- At most about `batch_size` fetched-but-not-yet-yielded rows (use a server-side cursor, as required). The first row must be available before the full result is fetched.
- When the iterator is exhausted or abandoned early, the cursor is closed and the transaction is finished (never left idle in transaction). Nothing is committed and the connection stays usable.

## Scenario

A nightly export job reads every transaction in a date range and writes it to a file. On
production the range can hold hundreds of millions of rows, so the job must never hold the whole
result in memory, neither in Python nor in the driver. The caller wants a simple iterator and
should not have to know anything about cursors.

## Function contract

```text
stream_transactions(conn, start: date, end: date, batch_size: int = 1000) -> Iterator[dict]
```

- `conn` is an open **psycopg 3** connection (non-autocommit, as in the tests). Do not close it.
- Yield one dict per row of `transactions` whose **UTC business date** satisfies
  `start <= date < end` (half-open; `end` exclusive).
- Keys, exactly: `transaction_id`, `store_id`, `transaction_ts` (aware `datetime`),
  `gross_amount` (`Decimal`), `transaction_status`.
- Order by `transaction_ts`, then `transaction_id`.
- **Memory:** use a **server-side (named) cursor**. At any moment the process may hold at most
  about `batch_size` rows that were fetched but not yet yielded. The first row must be available
  **before** the full result has been fetched.
- `batch_size < 1` or `start > end` raises `ValueError` (the error may surface on the first
  `next()` if your function is a generator).
- `start == end` yields nothing.
- Values must be bind parameters.

## Transaction and cleanup rules

- A named cursor lives inside a transaction. Make sure the work happens in a transaction that is
  **finished** when the iterator is exhausted: the connection must not be left "idle in
  transaction" (that holds a snapshot and blocks vacuum on a production database).
- If the consumer stops early (`close()` on the generator, or `break` from a `for` loop followed by
  garbage collection), the server-side cursor must be closed and the transaction ended too.
- Nothing is committed that was not there before; the connection stays usable afterwards.

## Example

`list(stream_transactions(conn, date(2025, 10, 1), date(2025, 10, 8), batch_size=50))` returns the
same rows as one big query, in the same order, while only ever asking the server for 50 rows at a
time.

## Corner cases

- Range with no rows.
- `batch_size` larger than the result; `batch_size = 1`.
- Two rows with identical timestamps keep a stable order.
- Consumer abandons the iterator after one row.

## Expected complexity

O(n) time, O(batch_size) memory. One round trip per batch.
