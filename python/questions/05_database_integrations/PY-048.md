# PY-048 · Bounded asyncio concurrency with predictable errors

**Topic:** PostgreSQL, APIs & backend patterns · **Level:** hard · **Interview time:** ~30 min · **Needs:** nothing external (asyncio only)

## Scenario

An enrichment job must call a partner API for 20,000 customer ids. `asyncio.gather` over all of them
opens 20,000 sockets at once and the partner (and your own connection pool) falls over. You need a
helper that runs the work with a fixed concurrency limit, hands the results back in the order the
work was submitted, and has **clearly defined behaviour when something fails or the caller gives up**.

## Function contract

```text
async gather_limited(factories, *, limit: int, return_exceptions: bool = False) -> list
```

- `factories` is an iterable of **zero-argument callables**; each call returns an awaitable (usually
  a coroutine object: pass `lambda: fetch(i)` or `functools.partial(fetch, i)`). The work for an
  item must **not start before a slot is free**: that is why callables are passed instead of
  coroutines.
- At most `limit` of the awaitables are in flight at any moment, and when there is enough work,
  exactly `limit` are in flight at some moment (the limit must actually be used).
- Returns a list of results **in input order**, whatever the completion order.
- Empty input returns `[]`.
- `limit` must be an int >= 1, otherwise `ValueError` (raised when the coroutine is awaited).

### Error policy

- `return_exceptions=False` (default, **fail fast**): when the first awaitable raises an
  `Exception`, no further item may be started, every awaitable that is still running is
  **cancelled and awaited to completion** (their `finally` blocks have run), and then **that first
  exception** (the same object) is raised. "First" means first in time. When the call returns or
  raises, no task created by the helper may still be pending.
- `return_exceptions=True` (**collect**): nothing is cancelled; every item runs. An item that raised
  appears in the result list **as the exception object** at its own position.
- A factory that raises when *called* (before returning an awaitable) is treated exactly like an
  awaitable that raised.

### Cancellation

If the task running `gather_limited` is cancelled, every in-flight awaitable is cancelled and
awaited, nothing new is started, and `CancelledError` propagates. No orphan tasks remain.

## Example (made-up)

`limit=2`, work durations (in event-loop ticks) A=3, B=1, C=1, D=1. A and B start; B finishes first so C
starts in its slot; and so on. The result is `[res_A, res_B, res_C, res_D]` regardless of who finished first.

## Corner cases

- `limit` greater than the number of items, and `limit == 1` (strictly sequential, in order).
- Results that finish in reverse order.
- Two failures: the **earlier** one is reported.
- A never-ending awaitable running when another one fails (it must be cancelled, not leaked).
- Items that have not started when the first failure happens must never start.
- Outer cancellation during execution.

## Expected complexity

O(n) time overall; the number of concurrently running awaitables is bounded by `limit`. Say what
bounds your memory if `factories` is a generator with 10 million items.
