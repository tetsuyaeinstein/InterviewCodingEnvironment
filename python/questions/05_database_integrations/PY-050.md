# PY-050 · Mini project: ingest, validate, dedupe, stage, summarise, reconcile

**Topic:** PostgreSQL, APIs & backend patterns · **Level:** hard · **Interview time:** ~45 min · **Needs:** running lab PostgreSQL (`requires_postgres`)

## In plain words

> "A partner drops a file of JSON lines of transactions every hour, untrusted and often re-delivered. Land the valid rows in a staging table, produce a daily revenue summary, and prove the two agree. One bad line must not sink the file."

**You return:** `run_pipeline(conn, lines, *, batch_size=500, strict=False)` returns a `RunReport` with the rejected lines, the counts, `daily_summary` and `reconciliation_ok`.

**The fine print, in short:**
- Check each non-blank line in the given order; the first failure gives its reason code. Blank lines are ignored but still count in line numbers. Per `transaction_id`, the highest `sequence` wins (ties: the later line); the losers count in `duplicates_dropped`.
- A staged row is replaced only if the incoming `sequence` is strictly greater. The whole run is one transaction. Amounts never pass through `float`. The summary is the sum of `COMPLETED` winners per UTC day.
- With `strict=True`, a failed reconciliation raises `ReconciliationError` and leaves nothing from the run. `batch_size < 1` raises `ValueError` before reading.

## Scenario

A partner drops a newline-delimited JSON (NDJSON) file of transactions every hour. The file is untrusted:
malformed lines, naive timestamps, amounts as strings or numbers, the same transaction repeated with
different version numbers, and whole files that get re-delivered. You own the ingestion step that lands the
data in a **staging table** and produces a **daily revenue summary** that finance will compare with the
warehouse. Re-running a file must be harmless, one bad line must not sink the file, and you must be able to
**prove** the staged data agrees with the summary you computed.

## Function contract

```text
run_pipeline(conn, lines: Iterable[str], *, batch_size: int = 500, strict: bool = False) -> RunReport
```

`conn` is an open psycopg 3 connection (the tests give you a sandbox schema first on the `search_path`). `lines`
may be any iterable of text lines (a file object, a list, a generator). Do not close the connection.

### 1. Parse and validate each non-blank line

Blank / whitespace-only lines are ignored (not counted as read, not rejected), but they **do count** in line
numbering. Each other line is one JSON object with these fields. The first failing check (in the order given)
rejects the line with the **reason code** shown:

| check | reason code |
|---|---|
| not valid JSON | `invalid_json` |
| JSON value is not an object | `not_an_object` |
| a required field is absent (first missing in the order below) | `missing_field:<name>` |
| `transaction_id`: JSON integer (not bool), 1 .. 2^63-1 | `invalid_transaction_id` |
| `store_id`: JSON integer (not bool), 1 .. 2^31-1 | `invalid_store_id` |
| `transaction_ts`: string, ISO-8601 with an explicit offset or `Z`; a string that parses but has **no** offset (including a date only) | `naive_timestamp` |
| `transaction_ts`: not a string, or not parseable | `invalid_timestamp` |
| `amount`: a JSON string or number representing a finite decimal, **>= 0**, at most **2 fractional digits**, at most 9999999999.99 | `invalid_amount` |
| `status`: one of `COMPLETED`, `PENDING`, `CANCELLED`, `DECLINED` (exact, upper case) | `invalid_status` |
| `sequence`: JSON integer (not bool), 0 .. 2^31-1 (the version number, higher = newer) | `invalid_sequence` |

Required fields, in checking order: `transaction_id`, `store_id`, `transaction_ts`, `amount`, `status`, `sequence`.
Extra fields are ignored. Amounts must never pass through `float`: a JSON number such as `0.1` must become
exactly `Decimal("0.10")`. Timestamps are converted to UTC.

### 2. De-duplicate within the run (by `transaction_id`)

Among valid rows with the same `transaction_id`, the one with the **highest `sequence`** wins; on equal
`sequence` the **later line** wins. Every valid row that loses (including exact repeats) counts in
`duplicates_dropped`.

### 3. Upsert into `stg_txn`

Create it if needed, **in the connection's current schema** (never schema-qualified), with columns:

| column | type |
|---|---|
| `transaction_id` | bigint, **primary key** |
| `store_id` | integer, not null |
| `transaction_ts` | timestamptz, not null |
| `amount` | numeric(12,2), not null |
| `status` | text, not null |
| `sequence` | integer, not null |

Upsert the winners in batches of at most `batch_size` rows per statement. An existing row is replaced
**only if the incoming `sequence` is strictly greater**; otherwise it is left alone. `upserted` counts rows
inserted or changed; `unchanged` counts winning rows that did not change the table. A table created by the caller
beforehand (e.g. with extra constraints) must be used as it is. The whole run is **one transaction**: if anything
fails, nothing from the run remains and the exception propagates.

### 4. Summary and reconciliation

- `daily_summary`: `{UTC date: Decimal}` with the **sum of `amount` of the winning rows with status `COMPLETED`**,
  computed in Python, only for days that have at least one such row.
- Reconciliation: query the staging table for the same ids and aggregate the same way in SQL (UTC day,
  `COMPLETED`, sum). `reconciliation_ok` is `True` iff the SQL result equals `daily_summary` exactly (same days,
  same totals). This will be `False` when a stale (lower-`sequence`) row from this run was ignored because the table
  already holds a newer version: the table then differs from what this run supplied.
- `strict=True`: if reconciliation fails raise `ReconciliationError` and leave **nothing** from the run in the table.

### Report invariants

`rows_read == len(rejected) + duplicates_dropped + upserted + unchanged`. `rejected` is in line order.
`batch_size < 1` raises `ValueError` before anything is read.

## Example (made-up)

```text
{"transaction_id": 1, "store_id": 2, "transaction_ts": "2025-03-02T23:30:00-07:00", "amount": "10.5", "status": "COMPLETED", "sequence": 1}
{"transaction_id": 1, "store_id": 2, "transaction_ts": "2025-03-02T23:30:00-07:00", "amount": 12.25, "status": "COMPLETED", "sequence": 2}
{"transaction_id": 2, "store_id": 2, "transaction_ts": "2025-03-03T08:00:00", "amount": "5", "status": "PENDING", "sequence": 1}
```
Row 2 supersedes row 1 (`duplicates_dropped = 1`); row 3 is rejected `naive_timestamp` (line 3);
one row is staged (`12.25`) and `daily_summary == {2025-03-03: 12.25}` (06:30 UTC on March 3).

## Corner cases

- A file delivered twice, and an older version of a file delivered after a newer one.
- Amounts as numbers (`0.1`, `20`), strings (`"0.20"`), more than two decimals, negative.
- Offsets (`-07:00`) that move the UTC day.
- Blank lines between records; an entirely empty input.
- A database error halfway through a multi-batch run.

## Expected complexity

O(n) time, O(distinct ids) memory for the de-duplication; O(n / batch_size) statements. Discuss what you would
change for a 50-million-line file.
