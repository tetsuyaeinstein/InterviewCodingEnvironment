# PY-049 · Reconcile Python daily totals against PostgreSQL

**Topic:** PostgreSQL, APIs & backend patterns · **Level:** hard · **Interview time:** ~35 min · **Needs:** running lab PostgreSQL (`requires_postgres`)

## Scenario

A nightly job pulls transactions from the source system into Python, aggregates daily revenue per
store, and publishes it. Finance noticed last month that the published numbers were a few cents
off from the warehouse, and that one day was missing entirely. You are asked to build the
reconciliation check that runs after every load: **compute the totals in Python, ask PostgreSQL
the same question, and report exactly where the two sides disagree**.

## Function contract

```text
reconcile_daily_totals(conn, transactions, store_ids, start, end) -> ReconciliationReport
```

- `conn`: open psycopg 3 connection (read-only is fine; do not commit/close; do not change session settings
  permanently).
- `transactions`: iterable of dicts with `transaction_id` (int), `store_id` (int), `transaction_ts`
  (**aware** `datetime`, in **any** time zone: normalise to UTC yourself), `gross_amount` (`Decimal`),
  `transaction_status` (str). It may be a generator; consume it once.
- `store_ids`: non-empty sequence of store ids (empty raises `ValueError`).
- `start`, `end`: dates; the window is **half-open on the UTC business date**: `start <= day < end`.
  `start > end` raises `ValueError`; `start == end` is an empty window.
- **What is compared:** for each `(store_id, UTC day)` the sum of `gross_amount` of rows with
  `transaction_status = 'COMPLETED'`, restricted to `store_ids` and the window.
  - Python side: from `transactions`, ignoring rows outside the stores/window/status.
  - SQL side: one aggregate query against `transactions` (bind parameters only). The day bucketing in SQL must be
    explicitly UTC and **must not depend on the session's `TimeZone` setting**.
- A key `(store_id, day)` present on only one side is reported on its own, even if the total is `0.00`.
- **Exactness:** all amounts are `Decimal`; no floats anywhere. A `float` amount raises `TypeError`; a naive
  timestamp raises `ValueError` (its UTC day would be a guess).
  Totals are compared by exact decimal value (`Decimal("1.10") == Decimal("1.1")`).

### Report

```text
ReconciliationReport(matching, mismatches, only_in_python, only_in_sql)   + property ok
Mismatch(store_id, day, python_total, sql_total)
```

- `matching`: sorted list of `(store_id, day)` whose totals are equal.
- `mismatches`: sorted by `(store_id, day)`, both totals included.
- `only_in_python`: `(store_id, day, python_total)` present in Python only (sorted).
- `only_in_sql`: `(store_id, day, sql_total)` present in the database only (sorted).
- `ok` is `True` only when there are no mismatches and nothing is one-sided.

## Example (made-up)

Python says store 9 had 100.00 on Jan 3 and 40.00 on Jan 4; the database says 100.00 and 40.10 on those days,
and 15.00 on Jan 5. The report has `(9, Jan 3)` matching, a mismatch `(9, Jan 4, 40.00, 40.10)`, and
`only_in_sql = [(9, Jan 5, 15.00)]`; `ok` is `False`.

## Corner cases

- A transaction at `2025-03-02 23:30 -07:00` belongs to **UTC** day March 3.
- The database session runs in a non-UTC time zone.
- Amounts such as `0.10 + 0.20` that float arithmetic gets wrong.
- Non-COMPLETED rows, stores that were not requested, and rows outside the window in the Python list.
- The same transaction present twice in the Python list (it is **not** de-duplicated here: a double count is a real
  discrepancy that the reconciliation must surface).

## Expected complexity

O(n) over the Python rows and one grouped query on the database side. State which index helps the SQL aggregate.
