# PY-025 · Single-pass column profile: explanation

## Approach: one incremental accumulator per column (`PY-025.py`)

Each column gets an `_Acc` with:

| state | used for |
|---|---|
| `non_null` | `null_count = rows - non_null`. Columns that appear late are handled automatically. |
| `types: set[str]` | `types_seen`, `inferred_type` |
| `values: {(family, v): [first_v, count]}` | `distinct_count`, `top_values` (first-seen representative, ties in first-seen order) |
| `lo/hi: {family: value}` | `min`/`max`, kept **per family**, so `10 < "10"` is never evaluated |
| `total: Decimal` | exact `mean` |

**Identity key.** `(family, value)`, where all numerics share the family `"num"`.

- Python already makes `1 == 1.0 == Decimal("1.00")` with equal hashes, so they collapse.
- The family tag keeps `True` apart from `1`. Without it, `Counter([True, 1])` reports one value
  with count 2.
- The family tag keeps `date(2025,1,1)` apart from a datetime too. The type name, not
  `isinstance` order, decides.

**Mean.** `Decimal` addition is exact up to 28 significant digits. Floats are converted via
`repr`, so `0.1` becomes `Decimal("0.1")` and not `0.1000000000000000055…`. A float mean is
wrong twice over: drift (`0.1 × 3`), and loss of precision on large ints (`10**20 + 1`).

**Top-k.** `sorted(..., key=-count)` is stable, and dicts keep insertion order, so ties come out
in first-occurrence order. `Counter.most_common` happens to be stable too, but relying on it
silently couples you to an implementation detail. Sorting by value for ties fails on mixed
columns.

**Cost:**

- Time: O(rows × cols).
- Memory: O(Σ distinct) for exact distinct and top-k, plus O(cols) for everything else.

## Alternatives and trade-offs

- **Materialise, then compute** (`list(rows)`, then one comprehension per statistic). This is
  simple, but it needs O(rows) memory, needs multiple passes, and is impossible on a
  non-rewindable cursor.
- **pandas `describe()` / `value_counts()`.** Fast and vectorised, but `object` columns hide mixed
  types, `True`/`1` collapse, and the mean is float. Fine for exploration, weak as a DQ gate.
- **Approximate sketches for big data:**
  - **HyperLogLog** for distinct counts: about 1.5 KB per column, ~1 % error;
  - **Count-Min Sketch / Misra-Gries / Space-Saving** for heavy hitters (top-k);
  - **KLL / t-digest** for quantiles.

  These are what Deequ, Great Expectations on Spark, and BigQuery `APPROX_COUNT_DISTINCT` use.
  The exact dict here costs ~100 bytes per distinct value. That is fine for 1M distinct values,
  but not for 1B.

## Mergeability (the scale-up story)

Every statistic here is a **monoid**: `count`, `non_null`, `total` and the per-family
`min`/`max` merge trivially. The distinct map merges by adding counts. "First seen" needs a
global row index to merge correctly, so carry `(first_index, value)` instead of relying on
insertion order. So you can:

- profile file shards or Spark partitions in parallel and merge;
- profile a daily increment and merge it into yesterday's profile, without rescanning history.

## Production notes

- Persist profiles per load (table, column, date) and **alert on drift**: null rate jumps,
  distinct-count collapse, a new type appearing (`types_seen` grows), the mean shifting by more
  than N σ.
- `inferred_type == "mixed"` on a source column is the early warning for "someone started
  sending `'N/A'` in a numeric field" (see PY-023).
