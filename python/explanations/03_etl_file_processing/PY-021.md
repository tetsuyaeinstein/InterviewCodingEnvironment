# PY-021 · Streaming customer spend: explanation

## Approach 1: single streaming pass (`PY-021.py`)

1. **Open correctly.** For a path, use `open(path, encoding="utf-8-sig", newline="")`.
   - `utf-8-sig` silently drops a BOM.
   - `newline=""` hands raw line endings to the `csv` module. Without it, a `\r\n` inside a quoted
     field is translated, and on Windows you can get phantom empty rows.

   For a caller-supplied iterable, use it as-is and **don't close it**. Strip a leftover `﻿`
   from the first header name, because a file opened with plain `utf-8` still carries it.
2. **Validate the header once.** Build `name -> position`, and fail on missing **or duplicated**
   required columns. `csv.DictReader` silently keeps the *last* duplicate, which is how a
   mis-generated export ends up double-counting or using the wrong column.
3. **Stream rows** from `csv.reader`:
   - skip `[]` and whitespace-only rows;
   - reject width mismatches. `reader.line_num` gives the physical line for the error message;
   - filter on status **before** parsing the amount;
   - parse `Decimal(text.strip())` and reject non-finite values;
   - add to `totals[customer]`.

| fixture row | status | customer_id | amount | effect |
|---|---|---|---|---|
| T1 | COMPLETED | C001 | 4.50 | C001 = 4.50 |
| T3 | PENDING | C001 | 99.99 | ignored, not parsed |
| T5 | COMPLETED | `""` | 7.00 | guest: excluded, or `guest_key` |
| T6 | `completed ` | C002 | -2.10 | normalised status counts |

Time O(rows). Memory O(customers), plus one row at a time.

## Approach 2: chunked map/merge (`PY-021_alt.py`)

Cut the row stream into chunks with `itertools.islice` and reduce each chunk to a partial dict
(**map**). Then add each partial into the running total (**merge**). The merge is associative and
commutative, so:

- chunks can be processed by different workers (a process pool, Spark tasks, one Lambda per file);
- partials can be combined in any order;
- partials can even be re-aggregated hierarchically (combiner → reducer).

**Trade-off:** in a single process it is the same big-O with a little more code and one extra dict
per chunk. Its value is that it is the shape that parallelises. The chunk size bounds memory as
`chunk_rows + customers`.

Two related design choices:

- **Positional `csv.reader` vs `DictReader`.** Positional access is faster, because no dict is
  built per row, and it lets you detect duplicate headers. `DictReader` is more readable and
  tolerant of column order, but it hides duplicates and makes width errors invisible: short rows
  are padded with `None`, and long rows go into a `None` key.
- **Fail fast vs quarantine.** Money pipelines usually fail the batch on an unparseable amount,
  because a silent skip under-reports revenue. Contrast PY-022, where bad lines go to a
  quarantine instead.

## Why the edge cases matter

- **Quoted newline (T2 in the fixture).** A line-based `split(",")` produces two broken records.
  `csv` reads one.
- **`COMPLETED_REVERSED`.** A substring/`startswith` check would count it.
- **`PENDING` with `not-a-number`.** Parsing before filtering makes a valid file fail.
- **`NaN` / `Infinity`.** `Decimal` accepts them, and one `NaN` poisons every total it touches.
- **`"007"` vs `"7"`.** Casting ids to `int` merges two customers.
- **The 200k-row generator.** `list(reader)` or `readlines()` costs about 60 MB here. At 10 GB the
  job is OOM-killed.

## Scale-up

- **Multi-GB file, one machine.** This is already O(customers) memory. The bottleneck is CPU in the
  `csv` module, roughly 0.5–1 M rows/s. You can parallelise by byte-range splitting **only** if
  you can find record boundaries. Quoted newlines make naive splitting at `\n` wrong, which is one
  reason many lakes prefer splittable, length-delimited formats (Parquet/Avro) or "no embedded
  newlines" export contracts.
- **Millions of customers.** The dict itself becomes the memory problem (~200 bytes per entry).
  Partition by `hash(customer_id) % N` into N spill files, then aggregate each one. Or push the
  aggregation into the warehouse (`COPY` + `GROUP BY`).
- **Cloud object store.** Stream the object body (`boto3` `StreamingBody.iter_lines` /
  `smart_open`) wrapped in `io.TextIOWrapper(..., newline="")`. Never download the whole file
  first unless you need retries with seeks.
- **Re-runs.** The result is a pure function of the file, so the load step should be an
  idempotent overwrite of the `(export_date)` partition, not an append.

## Follow-up questions

1. Amounts arrive in mixed currencies with an FX table: where do you convert, and how do you round
   (per row or per total), to match the ledger?
2. The export is 40 GB and must finish in 5 minutes. How do you parallelise without breaking
   quoted multi-line records?
3. How would you report the *number* of skipped guest rows and malformed lines to monitoring
   without changing the return type?
4. Finance says yesterday's total is off by 0.01. Which of your choices (Decimal, status
   normalisation, guest exclusion) do you check first, and how do you prove it?
