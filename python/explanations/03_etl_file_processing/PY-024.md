# PY-024 · Revisions and conflicts: explanation

## Approach 1: single pass, per-key state (`PY-024.py`)

`state[key] = (best_seq, [(payload, record), ...distinct at best_seq])`

| incoming vs best_seq | action |
|---|---|
| no state / higher | replace with `(seq, [(payload, record)])`. Any earlier tie is now irrelevant. |
| equal | append if the payload differs from every stored one. Identical duplicates are dropped, so the first arrival is kept. |
| lower | ignore. It is a superseded revision arriving late. |

At the end, iterate `sorted(state)`. One distinct payload is the current record; more than one is
a `Conflict`.

- **Time:** O(n), plus O(k log k) to sort k keys.
- **Memory:** O(k). Only the current best (plus rare tie candidates) per key, never every record.
- **Works on a one-shot stream.**

Worked example (from the question, `ignore_fields={"ingested_at"}`):

| arrival | event | state for K7 / K3 |
|---|---|---|
| 1 | K7 seq 12 | K7: (12, [ACTIVE@09:00]) |
| 2 | K7 seq 11 | lower → unchanged |
| 3 | K7 seq 12 | equal + identical → unchanged |
| 4 | K3 seq 4 | K3: (4, [BLOCKED]) |
| 5 | K3 seq 4 | equal + different → K3: (4, [BLOCKED, ACTIVE]) → Conflict |

## Approach 2: sort + groupby (`PY-024_alt.py`)

Decorate each record with `(key, seq, arrival)`, sort, and `groupby(key)`. Each group's tail
holds the highest-sequence records, in arrival order.

- **Here:** O(n log n) time and O(n) memory, because `sorted` materialises everything. That is
  worse on one machine.
- **At scale:** the shape wins. Swap the in-memory sort for:
  - an **external merge sort** (PY-029);
  - a shuffle/sort in Spark: `Window.partitionBy(key).orderBy(desc(seq))`;
  - SQL: `ROW_NUMBER() / RANK() OVER (PARTITION BY key ORDER BY seq DESC)`.

  The grouping step then needs memory for **one key's group** only. In SQL, use `RANK() = 1` +
  `COUNT(DISTINCT payload_hash) > 1` to find conflicts. `ROW_NUMBER() = 1` alone silently picks
  one of the conflicting rows, which is the bug this exercise is about.

## Why the edge cases matter

- **Late older revision.** "Last arrival wins" (`dict[key] = rec`, or `>=` on the sequence)
  regresses the account to an old state. This is the most common CDC bug.
- **`"9"` vs `"10"`.** Comparing strings lexically makes 9 newer than 10. LSNs and offsets often
  arrive as strings.
- **Superseded ties.** Reporting them creates alert noise for problems that have already healed.
- **Unhashable payloads.** `frozenset(rec.items())` crashes on nested JSON. Comparing with `==`
  against a short list avoids hashing entirely. At scale, compare **canonical payload hashes**
  instead (PY-028).
- **Ignore fields.** Without them, the same message landed in two files looks like a conflict.

## Production notes

- **Idempotency.** Re-running on the same input gives the same output, and merging a new batch
  into the stored state follows the same rules. So the operation is associative: you can resolve
  per file, then resolve the results.
- **Conflicts** go to a review queue with both payloads. Downstream keeps the **previous** good
  state for that key, rather than either candidate, until resolved.
- **Deletes / tombstones** are just revisions with `op = 'D'`. The winner may be a tombstone that
  later physically removes the row.
- **Memory at scale.** k = 100M keys × ~200 B ≈ 20 GB for the dict. Hash-partition by key into N
  spill files (or Spark partitions) and resolve each partition independently.

## Follow-up questions

1. Sequences are per *partition* of the source (Kafka offsets). How do you build a total order per
   key? What if a key moves between partitions?
2. Support tombstones: a delete at seq 9 followed by an insert at seq 8 that arrives late.
3. You resolve daily batches. How do you merge today's winners with yesterday's stored state
   without reprocessing history?
4. 2 billion records, 300M keys, one 64 GB machine: design it end to end.
