# PY-026 · Atomic file transform: explanation

## Approach: write-aside, fsync, rename (`PY-026.py`)

```text
open src (fails early, nothing to clean)
tmp = mkstemp(dir=dirname(dest), prefix=".dest.", suffix=".tmp")
try:
    stream lines: transform -> write(result + "\n")    # newline="\n"
    flush; fsync(tmp)
    close tmp
except BaseException:
    unlink(tmp); raise
close src                                               # needed on Windows for src == dest
os.replace(tmp, dest)                                    # the atomic commit point
fsync(dirname(dest))                                     # POSIX: make the rename durable
```

| step | what goes wrong without it |
|---|---|
| temp in **dest's directory** | `/tmp` may be another filesystem. `os.replace` then raises `OSError: cross-device link`, and `shutil.move` silently degrades to copy + delete, which is not atomic. |
| `flush` + `fsync` before the rename | After a power cut, the journal can contain the rename but not the data: you get an empty or truncated "new" file. (ext4 `data=ordered` mostly saves you; XFS and others don't.) |
| `newline="\n"` | Windows text mode turns every `\n` into `\r\n`, so the output differs by OS. |
| close before replace/unlink | Windows refuses to rename over, or delete, an open file (`PermissionError [WinError 32]`). Closing the source matters when `src == dest`. |
| `except BaseException` | Ctrl+C / `SystemExit` would leave `.dest.xxxx.tmp` files that accumulate. |
| directory fsync | Without it, the rename itself may be lost after a crash on POSIX. Directories can't be opened on Windows, so it's skipped there. NTFS journals metadata. |

**Commit point.** Before `os.replace` returns, readers see only the old file. Afterwards they
see only the new one. A reader that already had the old file open keeps reading the old data
(POSIX inode semantics).

**Cost:**

- Time: O(bytes).
- Memory: O(longest line), because both files are streamed.
- Disk: up to 2× the file size during the rewrite.

## Alternatives and trade-offs

- **Write directly + "done" marker file** (`_SUCCESS`, `.ready`). Common in Hadoop/Spark
  directories, but only safe if *every* reader honours the marker. It doesn't protect the old
  content either.
- **Versioned outputs + pointer swap.** Write `customers_2025-03-01T0200.csv` and atomically update
  a symlink or a manifest/`latest` pointer. This keeps history for rollback and lets readers pin a
  version. It is the basis of table formats (Delta/Iceberg commit = atomic manifest swap).
- **Object stores (S3, GCS, ADLS).** There is no rename. A `PUT` of a whole object is already
  atomic: readers never see a partial object. Multipart uploads become visible only on
  `CompleteMultipartUpload`. A "rename" (copy + delete) is **not** atomic, so write the final key
  once, or use a manifest/table format.
- **Libraries.** `atomicwrites` (deprecated) and `safer` wrap this pattern. Know the underlying
  steps anyway, because the interview question is about the semantics.

## Production notes

- **Permissions.** `mkstemp` creates the file with mode `0600`, so copy `dest`'s mode/owner
  (`shutil.copymode`) if downstream users need to read it.
- **Concurrent writers.** Two jobs replacing the same file is "last rename wins". Use a lock or
  unique output names plus a pointer if that matters.
- **Stale temp files** after a hard kill (`kill -9` / power loss): use a recognisable prefix so a
  janitor can delete `.dest.*.tmp` older than N hours.
- **Idempotency.** Re-running the job produces the same file and replaces it atomically, so a
  retry is safe.
