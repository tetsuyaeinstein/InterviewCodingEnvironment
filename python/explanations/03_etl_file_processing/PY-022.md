# PY-022 · NDJSON reader with quarantine: explanation

## Approach: a strict, lazy generator (`PY-022.py`)

```text
for line_number, line in enumerate(lines, 1):
    raw  = line minus "\r\n"/"\n"
    text = raw minus a leading BOM  (line 1 only)
    blank?                  -> skip
    strict decode fails?    -> Rejected(invalid_json | duplicate_key)
    not a dict?             -> Rejected(not_an_object)
    missing required keys?  -> Rejected(missing_keys, "k1, k2")
    else                    -> yield obj
```

The strict decoder is `json.JSONDecoder(object_pairs_hook=..., parse_float=Decimal, parse_constant=...)`:

| knob | default behaviour | why it matters |
|---|---|---|
| `object_pairs_hook` | `{"id": 1, "id": 2}` → `{"id": 2}` silently | Duplicate keys mean the producer is broken. Raise in the hook so you can tell which value was meant. |
| `parse_float=Decimal` | `0.1` → binary float, `1e400` → `inf` | Money and IDs survive. Integers are unaffected. |
| `parse_constant` | accepts `NaN`, `Infinity` | They are not JSON (RFC 8259), and downstream systems (Postgres `jsonb`, Spark) reject them anyway. |

`RecursionError` from the C scanner on absurd nesting is caught too. One hostile line must not
kill the job.

The quarantine is a **caller-owned sink** (a list here). The same code can stream rejects to a
file, a dead-letter topic or a `quarantine` table, because the generator appends at the moment it
sees the line.

## Why the edge cases matter

- **Line numbers include blank lines.** Operators open the file in an editor and go to line N.
  Enumerating after filtering blanks gives wrong numbers.
- **`raw` keeps inner whitespace.** You may need the exact original to replay or byte-compare.
  Only the terminator is removed.
- **BOM only on line 1.** `utf-8` (not `-sig`) leaves `﻿` on the first line. A BOM on line 3
  means two files were concatenated, which is worth flagging rather than normalising silently.
- **Laziness.** `list(lines)` or `f.read().splitlines()` works on the sample and OOMs on a 20 GB
  file. The test pulls one record and checks that only about 2 lines were consumed.

## Alternatives and trade-offs

- **`json.loads` per line + post-validation.** This is simpler, but it misses duplicate keys and
  NaN, and it turns decimals into floats. It's fine for logs, wrong for financial events.
- **Return `(records, rejects)` lists.** This is easy to test, but it caps the input at RAM.
- **Schema validation (`jsonschema`, `pydantic`).** It gives richer per-field errors, but it's
  10–50× slower per record. Use it after the structural checks, or on samples.
- **`orjson` / `simdjson`.** These are 3–10× faster parsers. Check their duplicate-key and
  big-number semantics before adopting one, because most keep the last duplicate and parse to
  float.

## Complexity

O(bytes) time. Memory O(longest line + one parsed record + quarantine size). If the quarantine
can be huge (a whole bad file), write it to disk instead of a list.

## Production notes

- Add a **reject-rate circuit breaker** in the caller: e.g. fail the batch when more than 1 % of
  lines are quarantined. That usually indicates a format change, not bad rows.
- Store `(file, line_number, raw, reason, detail, ingested_at)` so rejects can be **replayed**
  idempotently after a fix.
- **Gzip/object store input:** wrap with `io.TextIOWrapper(gzip.open(...), encoding="utf-8")`.
  Line iteration still streams.
- **Bytes that aren't UTF-8** fail in the *decoder of the file object*, before your code sees the
  line. Decode with `errors="strict"` per line yourself (iterate bytes) if you want those
  quarantined too.
