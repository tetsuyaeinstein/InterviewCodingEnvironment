# PY-028 · Canonical hashing and reconciliation: explanation

## Canonicalisation: decide the policy, then encode it unambiguously

| value | canonical token | why |
|---|---|---|
| `None` / absent | *(no entry)* | sparse writers omit NULLs; both spellings must match |
| `True` / `False` | `("b", "true"/"false")` | the tag keeps `True` apart from `1` and `"true"` |
| `int` / `Decimal` | `("n", format(d.normalize(), "f"))`, with zero → `"0"` | `1`, `1.0`, `1.00` → `"1"`; `1E+2` → `"100"`; `-0.00` → `"0"` |
| `str` | `("s", value)` | exact |
| float, list, … | `TypeError` | float repr is a policy decision, so make the caller choose |

`normalize()` alone isn't enough (and it rounds to the 28-digit context precision, so `10**30` and `10**30 + 1` would collide; strip trailing zeros via `as_tuple()` instead):

- `Decimal("100").normalize()` is `1E+2`, so format it with `"f"`;
- `Decimal("-0").normalize()` keeps the sign, hence the explicit zero case.

**Encoding.**

- **Reference:** `json.dumps(sorted([name, tag, text]))`. JSON escapes quotes, backslashes and
  control characters, so the byte string can be parsed back uniquely, which makes it injective.
- **Alt:** length-prefixes every token (`5:hello`). It is equally injective, and cheaper.

What fails:

| encoding | collision |
|---|---|
| `"\|".join(values)` | `{"a": "x\|y", "b": "z"}` vs `{"a": "x", "b": "y\|z"}` |
| `"\|".join(f"{k}={v}")` | `{"a": "1\|b=2"}` vs `{"a": "1", "b": "2"}` |
| `str(v)` | `True` vs `"True"`; `None` vs `"None"`; `Decimal("1.0")` vs `Decimal("1.00")` *differ* |
| `"".join(values)` without names | field-order and boundary ambiguity everywhere |

SHA-256 rather than MD5 or Python `hash()`:

- Python `hash()` is salted per process for strings, so it is useless across runs and machines.
- MD5 is fine against accidental collisions, but SHA-256 costs little more and ends the
  discussion.
- In a warehouse, use the engine's `SHA2(..., 256)` over the **same** canonical string, so Python
  and SQL agree.

## Approach 1: hash map of one side (`PY-028.py`)

1. Build `target_map[key] = (hash, canonical_items)`.
2. Stream the source: `pop(key)`.
   - absent → missing;
   - equal hash → unchanged;
   - else → changed, plus the field diff.
3. Leftover keys → extra.

- **Time:** O(n + m) hashing, plus sorting the report.
- **Memory:** O(m) for the target map, plus the set of source keys for duplicate detection.
  Use the **smaller** side as the map.
- Field-level diffs need the canonical values, not just the hash. Dropping them saves memory but
  costs a second pass to explain *why* a row changed.

## Approach 2: sort-merge (`PY-028_alt.py`)

Sort both sides by key, then walk them together:

- smaller key → missing/extra;
- equal keys → compare.

The **merge needs O(1) memory**: one row per side. Duplicate keys show up as adjacent equal keys.

Here the inputs are unsorted, so `sorted()` costs O(n) memory. At scale, the sort is an
external merge sort (PY-029), or both databases emit `ORDER BY key` extracts. **Collation
caveat:** both sides must sort keys identically (byte order vs locale collation), or the merge
reports phantom missing/extra pairs.

| | hash map | sort-merge |
|---|---|---|
| memory | O(smaller side) | O(1) merge (+ external sort) |
| input order | any | must be sorted identically |
| time | O(n + m) | O((n + m) log) for sorting, or O(n + m) if presorted |
| parallelism | hash-partition both sides by key into N buckets, diff each bucket | range-partition, merge each range |

## Scale-up: 2 billion rows per side

- **Partition by `hash(key) % N`** on both sides. Each bucket pair fits in memory, and the
  buckets diff in parallel. This is how Spark's `full_outer_join` on key works.
- **Tiered comparison:** compare per-bucket aggregate hashes first (XOR/sum of row hashes, or a
  Merkle tree over key ranges). Only drill into buckets whose aggregates differ. Most nightly
  diffs touch < 1 % of buckets.
- **Push down to the databases:** compute `key, sha256(canonical_string)` server side, and ship
  only 40 bytes per row instead of full rows.

## Production notes

- **Version the canonicalisation.** Changing the policy (e.g. trimming strings) changes every
  hash. Store `hash_version` next to stored hashes.
- **Timestamps** (not in scope here): canonicalise to UTC ISO-8601 with fixed precision.
  Microseconds vs milliseconds is a classic phantom diff.
- Report **counts and samples** (first N keys per category) to monitoring. Fail the migration
  gate on thresholds, not on any difference.
