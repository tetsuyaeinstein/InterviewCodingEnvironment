# PY-029 · External merge sort: explanation

## Approach: run generation + k-way merge (`PY-029.py`)

**Phase 1 (runs).** Stream the CSV, appending rows to a buffer.

- When the buffer reaches M rows:
  1. `buffer.sort(key=key)` (Timsort is stable);
  2. write it with `csv.writer` to `mkstemp(dir=work_dir)`;
  3. close it, then call `on_run_written`.
- Flush the final partial buffer the same way.
- Numeric keys are validated as rows are read, so a bad value fails fast.

**Phase 2 (merge).**

1. Open one lazy `csv.reader` per run inside an `ExitStack`.
2. `heapq.merge(*readers, key=key)` streams the global order with a heap of k heads.
3. Write the header and the merged rows to a temp file next to `dest`, then `fsync` and
   `os.replace` (the same pattern as PY-026).

**Cleanup.** Run paths are appended to `runs` *before* they are written. A `finally:` unlinks
them after all handles are closed, so cleanup happens on success, on `ValueError` mid-file, and
on exceptions raised by the callback.

**Stability.** `heapq.merge` breaks ties by iterable index. Runs are created in input order, and
each run is sorted stably, so equal keys come out in input order:

| input (key, seq) | M=2 runs | merged |
|---|---|---|
| (b,0) (a,1) (b,2) (a,3) (a,4) | [(a,1),(b,0)] [(a,3),(b,2)] [(a,4)] | (a,1) (a,3) (a,4) (b,0) (b,2) |

**Cost:**

| | phase 1 | phase 2 |
|---|---|---|
| CPU | O(n log M) | O(n log k) |
| I/O | read n, write n | read n, write n |
| memory | M rows | k rows + k file buffers |

Note the second memory term: with k = 80 open runs, the file buffers (~8–30 KB each with text
decoding) dominate. That is why the test uses a moderate k, and why real systems cap the fan-in
(below).

## Why the edge cases matter

- **Quoted newlines.** Writing runs as raw `line` strings, or `"\n".join(fields)`, breaks
  multi-line records. Use `csv` for both runs and output.
- **Stability.** Merging with a heap of `(key, row)` tuples compares *rows* on ties: it is
  deterministic, but the order depends on the other column values, not on input order. Merging
  runs in the wrong order breaks stability too.
- **"Merge" by reading all runs back into one list** is the most common fake. It produces the
  right output with O(n) memory. The memory test catches it.
- **Cleanup on error.** A crash at run 15 must not leave 14 × 1 GB files on a shared disk.

## Alternatives and scale-up

- **Fan-in limit / multi-pass merge.** With 60 GB and M ≈ 1 GB there are ~60 runs, which is
  fine. With 10,000 runs you hit the OS limits on open files (`ulimit -n`; the Windows CRT
  default is 512) and tiny read buffers thrash the disk. Merge in passes of F runs (e.g. F = 64),
  which takes log_F(k) passes. Larger read buffers (1–8 MB per run) turn random seeks into
  sequential reads.
- **Replacement selection.** A heap-based run generator produces runs of about 2M on average,
  and a single run if the input is already almost sorted. That halves the run count.
- **Compression of runs** (gzip, lz4) trades CPU for scratch-disk I/O. It's often a win on
  network disks.
- **Parallelism.** Sort runs on multiple cores. A final single merge is I/O-bound. For true
  scale, range-partition by key (sample to find splitters) and sort partitions independently.
  That is what Spark's `sortByKey` / Hadoop's shuffle does.
- **Just use a tool.** GNU `sort -t, -k1,1 -S 2G --parallel=8` is an external merge sort (but
  not CSV-quote-aware), and DuckDB `COPY (SELECT * FROM read_csv(...) ORDER BY k) TO ...`
  spills to disk automatically. In an interview, say so, and then show you know what they do
  inside.

## Production notes

- Put `work_dir` on a local SSD, not the same network volume as input and output.
- Check free space up front: you need about 2× the input (runs + output).
- Emit metrics: rows, runs, bytes spilled, merge duration.
- Make the job **idempotent**: atomic output plus cleanup makes a retry safe.
