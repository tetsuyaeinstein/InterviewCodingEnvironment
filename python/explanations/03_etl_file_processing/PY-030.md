# PY-030 · Watermark with overlap and dedup: explanation

## Why `updated_at > watermark` loses data

Transaction T1 sets `updated_at = 12:00:00` but commits at 12:00:05. Meanwhile T2 commits at
12:00:02 with `updated_at = 12:00:02`. A run at 12:00:03 sees only T2 and advances the watermark
to 12:00:02. T1 becomes visible later, but `12:00:00 > 12:00:02` is false, so T1 is **never
loaded**.

The overlap re-reads `[watermark - overlap, …)`. As long as `overlap >= max(commit delay + clock
skew)`, every version is seen at least once. Dedup by `(key, updated_at)` turns at-least-once
into **exactly-once** processing.

## Approach 1: stateless window filter + set dedup (`PY-030.py`)

For each record:

| check | outcome |
|---|---|
| `ts >= upper_bound` | ignore: next run's window covers it |
| `ts < lower` | `late`: it can't be deduplicated, because its pair may have been pruned |
| `(key, ts) in processed ∪ taken` | skip (re-delivery) |
| otherwise | select |

Then:

- `new_wm = max(old_wm, max selected ts)`. It is never lower: an overlap-only batch must not
  rewind the watermark, or the next window would re-open history.
- `processed' = {p ∈ processed ∪ taken : p.ts >= new_wm - overlap}`.

**Why pruning is safe:** next run's `lower' = new_wm' - overlap >= new_wm - overlap`. A pair older
than that can only arrive as `late`, never as "selected", so remembering it is useless.

**Cost:**

- Time: O(n) per batch, plus O(s log s) to sort the s selected records.
- State: O(versions inside one overlap window), independent of history. Without pruning, the set
  grows by every version ever loaded. That is a slow memory leak that shows up months later as
  OOM or a multi-GB state blob.

## Approach 2: sort + bisect, time-bucketed state (`PY-030_alt.py`)

1. Sort the batch by `(ts, key)`.
2. `bisect_left(stamps, lower)` and `bisect_left(stamps, upper)` split it into
   `late | window | future` slices.
3. The dedup state is held as `{ts: {keys}}`. Pruning drops whole buckets below the floor.

| | set filter (ref) | sort + bisect (alt) |
|---|---|---|
| time per batch | O(n) | O(n log n) |
| window logic | per-record comparisons | two bisects: mirrors an index range scan |
| pruning | filter every pair | drop whole buckets (TTL-friendly: Redis keys per minute, RocksDB range delete) |
| `late` order | input order | time order |

At small n, both are trivial. The bucketed state matters when it lives outside the process:
expire buckets instead of scanning keys.

## Boundaries, precisely

| boundary | operator | reason |
|---|---|---|
| upper | `ts < upper_bound` (exclusive) | Records at exactly `upper_bound` are taken by the next run, whose window starts below it. An inclusive bound plus a next lower of `> wm` double-counts or drops ties. |
| lower | `ts >= wm - overlap` (inclusive) | A version exactly at the edge is still deduplicable, because pairs with `ts >= floor` are kept. |
| pruning floor | `ts >= new_wm - overlap` | Must equal the next run's lower bound, or a re-delivery at the edge is processed twice. |

`upper_bound` should be `now() - safety_margin` from a **trusted clock** (the database's), not
the worker's clock.

## Production notes

- **Persist the state atomically with the output** (same transaction, or a commit protocol).
  Otherwise a crash between "loaded" and "state saved" reprocesses the batch.
  - **Idempotent sinks** (MERGE on `(key, updated_at)`) make that crash harmless, and that is
    the strongest guarantee.
  - Here the dedup state exists because the sink is not idempotent.
- **Choosing `overlap`:** measure the actual lag (`commit_ts - updated_at`, using
  `pg_xact_commit_timestamp` or CDC metadata) and set the overlap to p99.99 plus margin.
  Monitor the `late` count. A non-zero rate means the overlap is too small.
- **Better source of truth:** a monotonically increasing commit sequence (LSN, rowversion, CDC
  offset) instead of `updated_at` removes the overlap problem entirely. Prefer CDC when you can.
- **Deletes** are invisible to an `updated_at` filter. You need soft-delete flags or CDC.
