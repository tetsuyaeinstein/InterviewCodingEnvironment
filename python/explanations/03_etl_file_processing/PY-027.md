# PY-027 · Date partition paths: explanation

## Approach (`PY-027.py`)

1. Resolve `tz` once: `ZoneInfo(name)` or the given `tzinfo`.
2. For each record:
   1. Parse ISO strings with `fromisoformat`.
   2. **Reject naive** values and non-datetimes.
   3. `astimezone(zone)`.
   4. Format `year={y:04d}/month={m:02d}/day={d:02d}`.
3. Group with `setdefault`, then rebuild the dict in sorted key order.

Zero-padding makes the lexicographic order equal the chronological order. That is why
`sorted(keys)` is meaningful, and why lake listings and prefix scans line up with time.

| event | in UTC | in America/New_York |
|---|---|---|
| `2025-03-09T04:59Z` | 2025-03-09 | 2025-03-08 23:59 EST |
| `2025-03-10T03:59Z` | 2025-03-10 | 2025-03-09 23:59 EDT |

Time O(n + p log p) for p partitions. Memory O(n) for the grouped output. A writer would stream
instead (see below).

## Why the edge cases matter

- **Wall-clock date of the source.** `ts.date()` without conversion files an event at
  `21:00-05:00` under day 1 when it is already day 2 in UTC. This is the single most common
  partitioning bug.
- **Naive timestamps.** Treating them as UTC "works" until a device sends local time. Rejecting
  them forces the contract upstream.
- **`os.path.join`.** On Windows it produces `year=2025\month=03`, which becomes a different (and
  nonsensical) S3 key.
- **`strftime("%Y")`** is platform-dependent for years < 1000 (glibc prints `999`). Explicit
  formatting is portable.
- **DST.** A named zone's offset changes during the year. A fixed `-05:00` offset is wrong half
  the year, which is why we accept zone names, not just offsets.

## Alternatives

- **A single `dt=YYYY-MM-DD` partition** (one level) versus `year/month/day`. One level is easier
  to prune with range predicates in most engines and produces fewer directories. Nested levels
  help tools that prune only on equality. Pick one convention per lake.
- **Partitioning by ingestion time instead of event time.** Ingestion time never needs late-data
  handling, but queries by event time must scan several partitions. Many lakes store both.

## Production notes

- **Late data.** Events from yesterday arriving today are written into yesterday's partition. The
  writer must append (new part files), not overwrite, or must rewrite the partition atomically
  (PY-026 / table formats).
- **Small files.** Thousands of partitions with a few events each kill query performance. Buffer
  per partition and flush at a size threshold, or compact later.
- **Streaming writers** keep one open file per active partition with a bounded LRU of handles,
  instead of materialising `dict -> list` as here.
- Keep the **UTC timestamp** in the data even when partitioning by local day. The local day is a
  derived attribute.

## Follow-up questions

1. The US mart wants New York days, but the lake is partitioned by UTC day. Which UTC partitions
   must a query read for "2025-03-09 New York"?
2. Add an `hour=HH` level. What happens on the DST fall-back day, when one local hour occurs twice?
3. 5% of events arrive up to 3 days late. How do you write and compact without rewriting whole
   days?
