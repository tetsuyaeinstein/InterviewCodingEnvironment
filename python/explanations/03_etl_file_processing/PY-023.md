# PY-023 · Canonical schema normalisation: explanation

## Approach: strict per-kind parsers, chosen once per column (`PY-023.py`)

1. **Validate the schema up front.** Check the kinds, duplicate names and `slash_date_order`.
   Configuration errors are programming errors, so raise them instead of reporting them per row.
2. **Build a plan** `[(column, parser)]`. The date parser closes over the declared order, so the
   MDY/DMY decision is made **once per source**, never per value.
3. **For each field:**
   1. `raw → strip →` NULL check.
   2. If it is NULL, emit `None`, plus an error if the column is not nullable.
   3. Otherwise run the parser. It returns a canonical value or raises `_Bad(reason)`.

**Grammars come before conversion.** Anchored regexes over `[0-9]` define exactly what is accepted.
The standard converters are more permissive than the contract:

| converter | also accepts | consequence |
|---|---|---|
| `Decimal(s.replace(",", ""))` | `12,34`, `1e3`, `NaN`, `Infinity`, `١٢` | misplaced separators, exponents and non-finite values sneak in |
| `datetime.strptime(s, "%Y-%m-%d")` | `2025-3-1` | unpadded dates pass |
| `date.fromisoformat` (3.11+) | `20250301`, `2025-W09-6` | compact and ISO-week forms pass |
| `int(s)` | `'١٢'`, `' 1_000 '` | non-ASCII digits and underscores pass |

**Accounting negatives.** Rewrite `(1,234.50)` to `-1234.50` *as text*, then call `Decimal(...)`.
This keeps the scale (`Decimal("-1234.50")`, exponent −2), which matters for downstream
`NUMERIC(12,2)` checks and for row hashes (PY-028).

**Timestamps.** Use `fromisoformat` (it handles `Z`, `+05:30` and fractions in 3.11+). A result
with no `tzinfo` is `naive_timestamp`. We never attach UTC "because it's probably UTC". Then
convert with `astimezone(timezone.utc)`. `2025-03-01T23:30-05:00` lands on **2 March** in UTC,
which is exactly the case that shifts daily aggregates if you strip the offset instead.

## Why the edge cases matter

- **`13/01/2025` with MDY.** The "try the other order" fallback is the classic corruption. It
  makes the outcome depend on the day number: 12/01 and 13/01 from the same file get opposite
  interpretations.
- **`NA` as a string.** Over-broad null tokens erase legitimate data (Namibia's ISO code, sodium,
  "not applicable" vs "unknown").
- **The original value in `FieldError`.** The quarantine must show what was actually received,
  untrimmed, so the producer can fix it.

## Alternative designs

- **Column-at-a-time (vectorised) parsing** (pandas `to_datetime(format=..., errors="coerce")`,
  Polars `str.strptime(strict=True)`) is 10–100× faster. Be careful, though: `errors="coerce"`
  produces NaT/NaN with **no reason**, so you must diff the null masks to rebuild the error list.
  And `dayfirst=` in pandas is only a *hint*, not a guarantee.
- **Pydantic / attrs models** give declarative validation and good error messages. Per-row object
  construction is slow for millions of rows, and the defaults are lenient (pydantic coerces
  `"1e3"` to a float), so configure strict mode.
- **A collect-errors vs fail-fast policy.** Here we collect, so one pass yields a complete
  report. A load step then decides "reject the row", "reject the file above X % errors" or
  "load with NULLs and flag".

## Complexity

O(rows × columns) with constant work per field. The regexes are compiled once. Memory is
O(output). For files larger than memory, make the function a generator yielding
`(row, errors_for_row)` pairs.

## Production notes

- Record **which source/format rule** produced each value (lineage). When a sender changes
  format, you can then find affected rows.
- Keep the **raw value** next to the normalised one in the bronze/raw layer, so a re-parse after a
  rule fix is possible.
- Time zones: offsets come from the data. If a source sends local wall-clock times without an
  offset, the fix is a *declared* source zone (`ZoneInfo("Europe/London")`) plus a rule for
  DST-gap and DST-fold times. It is never a guess.

## Follow-up questions

1. The UK office starts sending `2025-03-01` in some rows and `01/03/2025` in others. How do you
   detect a sender whose slash order looks wrong (e.g. `month > 12` rates)?
2. A source sends local times without offsets in `America/New_York`. Specify what happens to
   `2025-03-09 02:30` (it doesn't exist) and `2025-11-02 01:30` (it exists twice).
3. Support European numbers (`1.234,50`) without making `1.234` ambiguous.
4. 200 million rows a day: what would you change, and how do you keep the error report?
