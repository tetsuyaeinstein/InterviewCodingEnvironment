# PY-013 · Merge kiosk outage windows: explanation

## Pin the semantics first

Interval questions are mostly about the boundary rules. With **half-open** windows `[start, end)`:

| windows | instants covered | merged? |
|---|---|---|
| `[1, 5)` and `[5, 9)` | 1..4.999 and 5..8.999: no gap | **yes** → `[1, 9)` |
| `[1, 5)` and `[6, 9)` | gap `[5, 6)` | no |
| `[6, 6)` | nothing | dropped |
| `[1, 5)`, `[6, 6)`, `[7, 9)` | the zero-length window covers no instant, so it can't fill the gap | `[1, 5)`, `[7, 9)` |

Half-open windows are the standard for time in data engineering (partition boundaries,
`ts >= start AND ts < end`). Consecutive windows tile the timeline with no overlap and no hole, and
"touching" means "continuous".

## Approach 1: sort + sweep (`PY-013.py`)

1. Validate (`start > end` raises), drop zero-length windows.
2. Sort by `start`.
3. Keep the last output window. If the next `start <= current_end`, extend the end to
   `max(current_end, end)`. Otherwise start a new output window.

Why sorting makes one pass enough: after sorting, every window that could still overlap the
current one starts at or after its start. So once a window starts strictly after `current_end`,
nothing later can reach back into the finished window.

Time **O(n log n)** for the sort plus O(n) for the sweep. Memory O(n) for the sorted copy (the
input may be a generator, so a copy is needed anyway).

Common wrong answers the tests catch:

- `start < current_end` (strict): touching windows stay separate.
- `current_end = end` instead of `max(...)`: `[(0, 100), (10, 20)]` shrinks to `[(0, 20)]`.
- Skipping the sort: unsorted input produces overlapping output.
- Keeping zero-length windows: `[(4, 4)]` returns `[(4, 4)]`, and `[(1, 5), (5, 5), (5, 5)]` is
  harmless only by luck.
- `windows.sort()` on raw tuples also works, but sorting by start only is enough and never
  compares ends.

## Approach 2: boundary events (`PY-013_alt.py`)

Turn each window into two events, `(start, START)` and `(end, END)`, sort them, and keep a running
depth (number of windows covering "now"). Open an output window at 0 → 1 and close it at 1 → 0.

The tie rule at equal timestamps **is** the touching rule:

- starts before ends: `[1, 5)` + `[5, 9)` stays at depth ≥ 1 at t = 5 → merged (our contract);
- ends before starts: depth hits 0 at t = 5 → two windows ("touching stays separate").

| | sort + sweep | boundary events |
|---|---|---|
| time | O(n log n) | O(n log n), 2n items to sort |
| memory | n windows | 2n events |
| clarity of the touching rule | `<=` vs `<` | tie order of events |
| generalises to | merge with gap tolerance (`start <= end + grace`) | "covered by ≥ K windows", peak concurrency, coverage per depth |

A **heap** variant (push windows by start, pop and merge) has the same complexity. It is useful
when windows arrive from several already-sorted sources: merge the sources lazily (see PY-017)
instead of sorting everything.

## Library / runtime notes

- Aware `datetime` objects compare correctly across offsets. Mixing naive and aware datetimes
  raises `TypeError` on comparison: validate at the boundary of your pipeline, not here.
- `list.sort(key=...)` is stable Timsort, which is very fast on partly sorted input (monitoring
  feeds usually are).

## Scale-up discussion

- **Millions of windows per kiosk** rarely happens; millions of kiosks does. Partition by kiosk
  and merge per partition. In SQL this is a gaps-and-islands problem:
  `SUM(new_group_flag) OVER (ORDER BY start)`, where the flag is `start > MAX(end) OVER (preceding rows)`.
- **Streaming:** windows arrive roughly in start order with bounded lateness. Buffer until the
  watermark passes `current_end`, then emit the merged window. A late window that overlaps an
  already emitted one forces a retraction (or an upsert keyed by kiosk + start).
- **Memory:** the sweep needs only the current window once the input is sorted. If the source is
  already sorted (for example by an index or file order), the whole thing streams in O(1) memory.
