# PY-014 · Most frequently scanned SKUs: explanation

## Two phases: count, then rank

1. **Count** in one pass: `Counter(sku for sku in skus if sku is not None)`. O(n) time, O(d)
   memory for d distinct SKUs. This is the only phase that touches all n events, and it reads the
   stream exactly once.
2. **Rank** the d `(sku, count)` pairs with the key `(-count, sku)`. Ascending order on that key
   means "count descending, sku ascending", and because SKUs are unique after counting, the order is
   **total**. Every server computes the same list, whatever order the events arrived in.

Validate `k` **before** phase 1. An invalid `k` should fail fast, not after reading a million
events (and on a one-shot stream, those events would be lost).

## The trap: `Counter.most_common(k)`

`most_common` sorts by count only, and ties come out in **first-seen order** (dict insertion order
plus a stable sort). In the example `"C-3"` is scanned before `"A-1"`, so `most_common(2)` returns
`[("B-7", 3), ("C-3", 2)]`, while the contract asks for `("A-1", 2)`. Two servers that consumed
the same events in a different order would disagree. It is a perfectly good function for a quick
look, and a reproducibility bug in a pipeline.

Other wrong answers the tests catch:

- `sorted(counts.items(), key=lambda kv: (kv[1], kv[0]), reverse=True)`: `reverse` flips the
  tie-break too, so the **larger** SKU wins.
- Counting `None` as a SKU.
- Reading the stream twice (`len(list(skus))` then `Counter(skus)`): the second pass over a
  generator is empty.
- Validating `k` after counting: the tests pass a stream that fails if it is touched.

## Approach 1: bounded heap (`PY-014.py`)

`heapq.nsmallest(k, counts.items(), key=...)` keeps the best k candidates in a heap while it
scans the d pairs. **O(d log k)** time and O(k) extra memory. It also accepts an iterator, so
the ranking phase works even if the counts come from a spilled file or a database cursor.

## Approach 2: bucket by count (`PY-014_alt.py`)

Counts are integers in `1..n`. Group SKUs by count and walk the groups from the highest count down,
sorting only the groups you actually take. With small k, few groups are visited. That is close to
**O(d)** after counting, plus sorting the distinct count values.

| | bounded heap | bucket by count | full sort |
|---|---|---|---|
| ranking time | O(d log k) | O(d) + sort of visited ties | O(d log d) |
| extra memory | O(k) | O(d) buckets | O(d) |
| streaming the counts | yes | no, needs all counts | no |
| worst case | none | one huge tie bucket → O(d log d) | none |
| in CPython | Python-level key calls | dict + small sorts | Timsort in C: often fastest for d ≈ 100k |

Be honest in the interview: for d = 100,000, all three run in milliseconds, and counting the
1,000,000 events dominates. The choice matters when d is huge, k is tiny and memory is tight (heap),
or when you need **all** ranks (full sort).

## Library / runtime notes

- `Counter` counts in C when fed an iterable (`Counter(iterable)` uses a fast path), which is much
  faster than a Python loop with `dict.get`.
- `heapq.nsmallest` with `k >= d` falls back to `sorted`, and with `k == 1` to `min`.

## Scale-up discussion

- **Billions of events, millions of SKUs:** count in a distributed engine (`GROUP BY sku`), then rank
  with `ORDER BY count DESC, sku LIMIT k`. Top-k per partition plus a merge is only correct **after**
  the counts are complete: a SKU can be rank 1,000 in every partition and rank 1 globally.
- **Memory-bounded streaming:** exact counts need O(d) memory. When that is too much, use a
  **Count-Min Sketch** plus a heap, or the **Space-Saving / Misra-Gries** algorithms. They report
  approximate heavy hitters with error bounds in O(k) or O(1/ε) memory.
- **Sliding "trending now" windows:** keep counts per minute bucket and add/subtract buckets as the
  window slides, instead of recounting the whole hour.
