# PY-020 · Customer purchase streaks (pure Python): explanation

This is the Python twin of SQL-021. The edge cases are the same. Only the tools change.

## Step 1: reduce the stream to distinct purchase days

One pass builds `{customer_id: set of UTC dates}`:

| rule | where it is applied |
|---|---|
| status must be exactly `"COMPLETED"` | skip the record |
| guest (`customer_id is None`) | skip the record |
| business date = **UTC date** | `purchased_at.astimezone(timezone.utc).date()` |
| several purchases on one day = one day | a `set` stores each date once |
| naive datetime | reject with `ValueError` (silently assuming UTC hides bugs) |

After this step the question is purely about sets of dates.

The UTC conversion matters. `datetime.date()` on an aware datetime returns the **local** date of
that value's own offset: `2025-03-01 23:30-05:00` has `.date() == Mar 1`, but its UTC date is Mar 2.
Two records for the same instant in different offsets must land on the same day.

## Approach 1: sort the distinct dates, scan once (`PY-020.py`)

For each customer, sort the dates and walk them:

```text
dates: Mar 1, 2, 3, 4, 5, 8, 9      (min_days = 5)
       |-------- run 1 --------|  gap  |- run 2 -|
run 1: Mar 1..5 length 5  -> reported
run 2: Mar 8..9 length 2  -> dropped
```

A run continues while `day - previous == timedelta(days=1)`. A gap closes the run, which is
kept if its length is at least `min_days`. Do not forget to close the **last** run after the loop.

Real date arithmetic makes month ends, year ends and leap days automatic. There is no special
case for `2024-02-29`: Feb 28 + 1 day is Feb 29 in 2024, and Mar 1 in 2025.

Time: O(n) to build the sets plus O(d log d) to sort d distinct (customer, day) pairs. Memory O(d).

Common wrong answers the tests catch:

- Counting **records** instead of distinct days (a customer with 6 purchases on one day).
- `day.day - previous.day == 1`: wrong at every month end. `day.toordinal()` or `timedelta`
  are the correct tools.
- Using the local date, or the date of `datetime.now()`, instead of the UTC date.
- Ignoring status, or matching `"completed"` case-insensitively.
- `>` instead of `>=` against `min_days` (4 vs 5 days boundary), or forgetting to close the
  final run, which loses a streak that ends on the customer's last purchase day.
- Reporting overlapping windows (two 5-day windows for a 6-day run) instead of the maximal run.
- Leaving customers with no streak in the result as `[]`.

## Approach 2: set membership, count only from run starts (`PY-020_alt.py`)

A date starts a run exactly when `date - 1 day` is **not** in the set. From each start, walk forward while
`date + 1 day` is in the set. Every date is passed over by exactly one walk, so the total work is O(d), with
no sorting of the days. Only the reported streaks are sorted so that the output is chronological.

| | sort + scan | start-of-run walk over a set |
|---|---|---|
| time | O(n + d log d) | O(n + d) |
| extra memory | the set + a sorted list per customer | the set |
| needs a total order on the keys | yes | no, only "next key" arithmetic (`+ 1 day`) |
| streaming-friendly | needs all dates of a customer | same |
| clarity | easy to explain, run-closing bug at the end | needs the "only count from starts" insight |

Why "only from starts" matters: starting a walk from **every** date is O(d · run length) in the
worst case (a 365-day run walks 365 + 364 + ... steps). Skipping non-start dates makes it
linear. This is the same trick as "longest consecutive sequence" in the usual interview list.

The sorted approach needs an ordering of the keys. The set approach needs only `+1`. That
matters for data that can't be sorted cheaply, but it is no real advantage for dates.

## Library / runtime notes

- `datetime.astimezone(timezone.utc)` raises on naive datetimes in some versions and **assumes
  local time** in others, so check `tzinfo` explicitly. `utcoffset() is None` also catches
  aware-looking types with a broken offset.
- `date.toordinal()` gives an integer day number: consecutive days differ by exactly 1. It is a
  handy alternative to `timedelta` and a better key for numeric structures (arrays, bitsets).
- Store dates, not datetimes, in the sets. A `date` is small and hashable.

## Scale-up discussion

- **500 million rows:** the SQL answer (SQL-021) is a gaps-and-islands query: dedupe to
  `(customer, date)`, then `date - row_number()` is constant inside a run. The Python code is the
  same logic as a streaming job: build the `(customer, date)` set in a **pre-aggregation**, since
  distinct days per customer are tiny compared with the raw rows.
- **Memory:** 5 million customers × 365 days is 1.8 billion pairs, too many for one process. Partition
  by `customer_id` (hash), run per partition, or keep per customer a **bitmap of days since an epoch** (365 bits
  ≈ 46 bytes). A run is then a bit pattern, found with shifts and masks.
- **Incremental / daily runs:** do not recompute. Keep per customer `(current_run_start,
  last_purchase_date)`. A new day extends the run if it is `last + 1`, restarts it if later, and ignores
  it if the same. Emit when `length` reaches `min_days`. Late data older than `last_purchase_date` forces
  a recompute for that customer.
- **Time zones:** "UTC date" is an agreed business rule here. A store-local rule needs the store's
  time zone per record (and DST-aware conversion).
- **Idempotency:** the function is pure and deterministic (sorted dict, sorted streaks), so a re-run
  produces byte-identical output.
