# PY-016 · First transaction at or after a cutoff: explanation

## Approach 1: hand-written lower bound (`PY-016.py`)

Binary search is easy to describe and famously easy to get wrong by one. The cure is to fix the
**invariant** first:

> every index `< lo` holds a value `< target`; every index `>= hi` holds a value `>= target`.

Use a half-open range `[lo, hi)` with `hi = len(seq)` at the start. The answer is always a valid
position in `0..len(seq)`, including "nothing qualifies" (`len(seq)`).

```text
while lo < hi:
    mid = (lo + hi) // 2
    if seq[mid] < target:  lo = mid + 1      # mid is too small: discard it and everything left
    else:                  hi = mid          # mid might be the answer: keep it
return lo
```

Why the details matter:

| choice | effect |
|---|---|
| `hi = len(seq)` | "not found" needs no special case |
| `lo < hi` (not `<=`) | the range is empty exactly when `lo == hi`, which is the answer |
| `hi = mid` on `>=` | keeps the first of several equal elements; `hi = mid - 1` skips it |
| `lo = mid + 1` on `<` | guarantees progress; `lo = mid` loops forever on 2 elements |

Time **O(log n)** reads, O(1) space. On 1,000,000 elements that is about 20 reads, and the tests
fail anything that needs far more.

Common wrong answers the tests catch:

- Returning on `seq[mid] == target`: finds *some* duplicate, not the first.
- A "first match" scan after the binary search lands on a duplicate: correct but O(n) when the
  whole sequence is one value.
- Using `<=` in the comparison: that is the *strictly after* variant (`bisect_right`).
- `-1` or an exception when nothing qualifies.
- `list(seq)`, slicing or iteration: the sequence wrapper rejects them, since in production each
  access is a remote read.

## Approach 2: `bisect.bisect_left` (`PY-016_alt.py`)

The standard library already has it. `bisect_left(seq, target)` returns the leftmost insertion
point, which is "first index with `seq[i] >= target`". `bisect_right` is the "first index
`> target`" twin.

| | hand-written | `bisect_left` |
|---|---|---|
| reads / time | O(log n) | O(log n), in C |
| risk | off-by-one bugs | none |
| flexibility | any predicate (e.g. "first batch whose total exceeds X") | comparison on the element or `key=` (3.10+) |
| interview value | shows you hold the invariant | shows you know the library |

Say both in an interview: write the loop, mention that production code uses `bisect`.

Related idiom: a range query `[start, end)` over sorted timestamps is
`lo = bisect_left(ts, start)`, `hi = bisect_left(ts, end)`, and the slice `ts[lo:hi]`.

## Library / runtime notes

- `(lo + hi) // 2` can't overflow in Python. In Java/C use `lo + (hi - lo) / 2`.
- Datetimes must be all aware or all naive. Mixing them raises `TypeError` on comparison.
- The input must truly be sorted. Binary search on unsorted data returns garbage silently, so
  validate at ingestion, or assert in tests.

## Scale-up discussion

- **A table with billions of rows:** this is what a B-tree index does: `WHERE ts >= :cutoff
  ORDER BY ts LIMIT 1` costs a handful of page reads. Each probe is a disk or network read, so
  the read count is the cost model (hence the counting wrapper).
- **Sorted files in object storage (Parquet/ORC):** use the footer min/max statistics to pick the
  file and row group, then search inside it.
- **Streaming/appended data:** keep an index of `(first_ts, offset)` per segment; binary search the
  index, then within the segment.

## Follow-up questions

1. Return the first index strictly **after** the cutoff, and then the count of elements in
   `[start, end)`. Which of the two searches do you reuse?
2. The sequence is sorted but **rotated** (`[7, 8, 9, 1, 2, 3]`). How do you search it?
3. You don't know `len(seq)` (an unbounded append-only log). How do you find an upper bound first?
4. Timestamps live in 10,000 sorted Parquet files. How do you avoid opening most of them?
