# PY-011 · Match a refund to a pair of charges: explanation

## The policy decides the algorithm

"Find two numbers that sum to a target" is the most famous interview question there is. The
senior part is the **deterministic answer policy**: smallest `j`, then smallest `i`. Ask about it
before coding. "Any pair" answers are not reproducible, and auditors comparing two runs will
flag the difference.

Ordering candidates by `(j, i)` matches a left-to-right scan exactly:

| j | amount | complement needed (1000 - amount) | first position of complement before j | result |
|---|---|---|---|---|
| 0 | 250 | 750 | none | record 250 → 0 |
| 1 | 250 | 750 | none | 250 already recorded: keep 0 |
| 2 | 10 | 990 | none | record 10 → 2 |
| 3 | 250 | 750 | none | keep 0 |
| 4 | 750 | 250 | **0** | return `(0, 4)` |

## Approach 1: one-pass hash map (`PY-011.py`)

For each `j`, look up `target - amounts[j]` in a dict of **first** positions, then record
`amounts[j]` only if it isn't there yet (`setdefault`).

- The first `j` with any earlier partner is the smallest possible `j`. Return immediately.
- Keeping the first position (never overwriting) makes `i` minimal for that `j`.
- Looking up **before** inserting means a charge never pairs with itself, so `[500]` with target
  1000 is `None`. `[500, 500]` is `(0, 1)`.

Time **O(n)** expected (dict operations are O(1) on average). Space O(d) for d distinct amounts.
It also exits early: on the large test the match is near the end, but in typical data it stops
as soon as the refund is covered.

Common wrong answers the tests catch:

- `seen[amount] = j` (overwrite): returns the **latest** partner, e.g. `(3, 4)` instead of
  `(0, 4)`.
- Building the whole dict first, then scanning: `[500]` finds itself unless you compare indices.
  It also loses "first `j`" unless you re-scan in order.
- Nested loops `for i ... for j > i`: returns the smallest **`i`** first, e.g. `(0, 4)` instead
  of `(2, 3)`. It is also O(n²) and times out on 200,000 charges.
- Accepting `True` or `10.0` as the target: `bool` is a subclass of `int`, so check it explicitly.

## Approach 2: sort + two pointers (`PY-011_alt.py`)

The textbook alternative sorts the values and moves two pointers inward. Two traps:

1. Sorting loses the original positions, so carry them along. The alt keeps the first two
   positions of each distinct amount.
2. The two pointers find value pairs in **value order**, not in `(j, i)` order. To honour the
   policy you must enumerate **every** matching value pair and keep the best positions. You can't
   stop at the first hit.

For a value pair `a != b` the best positions are the first occurrences of each value. For `a == b`
they are the first two occurrences of `a`.

| | hash map | sort + two pointers |
|---|---|---|
| time | O(n) expected, early exit | O(n log n) (O(n + d log d)), no early exit |
| extra memory | O(d) dict | O(d) positions + sorted copy |
| streaming input (one pass, unknown length) | yes | no, needs everything first |
| worst case | hash collisions (pathological keys) | guaranteed O(n log n) |
| natural extension | "pairs in a window of N minutes" (evict old keys) | "pair closest to the target", "count pairs ≤ target" |

The two-pointer pattern wins when the data is **already sorted** (for example read from an index or
a sorted file) and memory is tight. Then it is O(n) time with O(1) extra space, as long as the
policy only needs values, not positions.

## Library / runtime notes

- Money as `int` cents (or `Decimal`) keeps equality exact. With floats, `0.1 + 0.2 == 0.3` is
  `False`, and a two-sum on floats needs a tolerance, which breaks hashing.
- `dict.setdefault` does the "insert only if absent" step in one lookup.
- Python ints are arbitrary precision, so `target - amount` never overflows. In Java/C#/SQL,
  think about the column type.

## Scale-up discussion

- **Millions of charges per card per day** is unusual; millions of cards is the real scale.
  Partition by card (or merchant + card) and run the one-pass scan per partition. State is one dict
  per partition.
- **Streaming:** charges arrive continuously and a refund must match charges from the last N days.
  Keep a dict of amount → earliest position (or a deque of positions) per card. Evict entries older
  than the window, and checkpoint the state.
- **In SQL:** a self-join `a.card = b.card AND a.amount + b.amount = r.amount AND a.seq < b.seq`
  with `ORDER BY b.seq, a.seq LIMIT 1`. An index on `(card, amount)` makes it a lookup per row:
  the same hash-map idea, run by the engine.

## Follow-up questions

1. The refund may cover **three** charges. What is the complexity of 3-sum, and how does the
   policy generalise?
2. Each charge can be matched at most once across many refunds processed in order. What state do
   you keep, and what happens to the "first position" rule?
3. Amounts arrive as decimal strings with mixed scales (`"12.5"`, `"12.50"`). How do you normalise
   them before hashing?
4. 50 million cards, refunds arriving as a stream: where does the per-card state live and how is it
   expired?
