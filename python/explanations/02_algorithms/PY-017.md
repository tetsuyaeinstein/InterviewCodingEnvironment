# PY-017 · Merge sorted event streams lazily: explanation

## The idea: one head per stream

The next output is always the smallest of the **current heads** of the K streams. Keep exactly one
head per stream in a min-heap. Pop the smallest, yield it, and replace it with the next item of
**the same stream**. Memory is O(K), and each output costs one heap operation, O(log K), so the total
is **O(N log K)** for N items.

| step | heap (key, stream) | yields |
|---|---|---|
| start (a=[1,4], b=[1,3]) | (1,a) (1,b) | |
| 1 | pop (1,a), push (4,a) | 1 from a |
| 2 | pop (1,b), push (3,b) | 1 from b |
| 3 | pop (3,b), b exhausted | 3 |
| 4 | pop (4,a), a exhausted | 4 |

## Approach 1: manual heap (`PY-017.py`)

Entries are `(key, stream_index, item, iterator)`.

- Each stream has **one** entry at a time, so `(key, stream_index)` is unique. The tuple
  comparison never reaches `item` or the iterator, so raw items are never compared (dicts or
  custom objects are fine) and equal keys are ordered by stream index: the **stability** rule.
- `heapq.heapreplace` pops and pushes in a single sift, which is cheaper than `heappop` plus
  `heappush`.
- It is a **generator**: nothing is read until the first `next()`.
- Only the stream just emitted from is advanced, and only when the consumer asks for the next
  item. A stream is therefore at most one item ahead of what the consumer has seen. This is what
  makes infinite and expensive-to-read streams safe: `islice(merge(...), 100)` reads about 100 + K items.
- An exhausted stream is dropped and never polled again (some cursors raise if you do).

Common wrong answers the tests catch:

- `sorted(chain(*streams))`: materialises everything (infinite streams never finish, and memory is O(N)).
  It is also O(N log N).
- `heap.append((key, item, index))`: ties compare the **items**, so dict items crash and the tie
  rule is wrong. The stream index must come before the item.
- Reading the first item of every stream in the function body (not in the generator): the
  "creation reads nothing" test fails.
- Refilling a stream **before** yielding, or pulling the next item of every stream each round:
  breaks the one-ahead bound.
- Scanning all K heads for every output (`min(...)`): O(N · K), too slow at K = 1,000.

## Approach 2: tournament (winner) tree (`PY-017_alt.py`)

A complete binary tree whose leaves are the streams. Each internal node stores the winner of its
two children. The root is the next output. After emitting, advance only that stream and replay
the matches up its leaf-to-root path.

| | heap | tournament tree |
|---|---|---|
| time per output | O(log K), about 2 comparisons per level on sift-down | O(log K), 1 comparison per level |
| memory | K entries, dynamic | 2K slots, fixed shape (padded to a power of two) |
| code | ~10 lines on `heapq` (C-implemented) | ~40 lines, all Python |
| CPython speed | faster (C) | about 1.5 to 3 times slower |
| where it wins | almost everywhere in Python | languages where comparisons dominate (external merge sort, losers trees in databases) |

`heapq.merge(*streams, key=...)` is the standard-library version of approach 1 and satisfies this
contract. Know it exists, say so in the interview, and still be able to write it by hand.

A third option, **pairwise merging** (merge streams 0+1, 2+3, ..., then merge the results as a
balanced tree of 2-way merges) is also O(N log K), but each intermediate generator holds its own
look-ahead, so a stream can be read several items ahead of the output. A left-fold
(`merge(merge(merge(a, b), c), d)`) is worse: O(N · K) and a deep chain of generators.

## Library / runtime notes

- Generators give laziness for free: state (heap, iterators) lives in the generator frame.
- `for x in it: ...; break` is a compact "take one item or detect exhaustion" idiom. It avoids
  catching `StopIteration`, which inside a generator would otherwise need care (PEP 479).
- `key` is evaluated once per item and stored in the heap entry, so an expensive key is not
  recomputed on every comparison.

## Scale-up discussion

- **External sort / compaction:** this is the merge phase of external merge sort and of LSM-tree
  compaction. Memory holds one buffered block per run, and K is limited by file handles and
  buffers, so very large K is merged in several passes (merge 64 files at a time).
- **Partitioned Kafka topics:** merging partitions by event time needs **watermarks**. A quiet
  partition can block the merge forever, since you can't emit past its head. Real systems add idle
  timeouts or per-partition watermarks, and accept late events.
- **Spark / SQL:** a global `ORDER BY` across partitions is a range-partitioned sort. The k-way
  merge is what each reducer does with its sorted map outputs.
- **Back-pressure:** the one-ahead guarantee means a slow consumer slows all producers, not memory.

## Follow-up questions

1. One stream stalls (no data for minutes). What can the merge safely emit, and what policy would
   you add (idle timeout, watermark)?
2. Streams are sorted **descending**. What changes, and what if the key is not negatable?
3. You need to merge 10,000 sorted files but only 256 file handles are available. Describe the plan.
4. Add a `dedupe=True` option that drops items with equal keys across streams (keep the first).
   Where do you keep the state and how large is it?
