# PY-015 · Group scrambled product labels: explanation

## Approach: a canonical key per label (`PY-015.py`)

Two labels are in the same group exactly when their normalised characters form the same
**multiset**. So compute one value per label that depends only on that multiset, and use it as a
dict key:

| label | casefold, whitespace removed | sorted characters (key) |
|---|---|---|
| `"TEA BAG"` | `teabag` | `aabegt` |
| `"tae gab"` | `taegab` | `aabegt` |
| `"Bag Eat"` | `bageat` | `aabegt` |
| `"teabags"` | `teabags` | `aabegst` |
| `"Straße"` | `strasse` | `aerssst` |

`groups.setdefault(key, []).append(label)` does the grouping in one pass. Python dicts keep
insertion order, so:

- groups come out in order of their **first** label;
- members keep **input order**;
- duplicates stay, because nothing removes them.

Time **O(n · L log L)** (sorting each label's characters), memory O(n · L). Each label costs one
dict lookup, compared with O(n²) label comparisons for the pairwise approach.

Common wrong answers the tests catch:

- `frozenset(label)` as the key: it ignores multiplicity, so `"aab"` and `"abb"` merge.
- `lower()` instead of `casefold()`: `"Straße".lower()` keeps `ß`, so it never matches
  `"STRASSE"`.
- `replace(" ", "")`: tabs and newlines are whitespace too.
- Returning `sorted(groups.values())` or sorting members: the contract is feed order.
- Using `set` for members: duplicates disappear (dedup is a separate, later decision).

## Alternative: character-count signature (`PY-015_alt.py`)

Use `frozenset(Counter(normalised).items())` as the key. It is O(L) per label instead of
O(L log L), and the key size is the number of **distinct** characters. For a fixed small alphabet
(say `A-Z0-9-`), a tuple of 37 counts is another classic O(L) key.

| | sorted-string key | count signature |
|---|---|---|
| time per label | O(L log L), but the sort runs in C | O(L), with Python-level `Counter` overhead |
| key size | L characters | distinct characters (or alphabet size) |
| readability / debuggability | key is a readable string | key is opaque |
| best for | short labels (typical product codes) | very long labels with few distinct characters |

For short labels the sorted string is faster in CPython in practice. Big-O isn't everything when
the constant factor is "C vs Python".

## Library / runtime notes

- `str.casefold()` is the Unicode-correct way to compare case-insensitively (`ß` → `ss`,
  Greek final sigma, etc.). `lower()` is for display.
- Unicode **normalisation** is a separate concern: `"é"` can be one code point (NFC) or `e` plus a
  combining accent (NFD). In a real feed, apply `unicodedata.normalize("NFC", s)` first, or the
  same visible label produces two keys.
- `str.isspace()` covers all Unicode whitespace, including non-breaking spaces.

## Scale-up discussion

- **100 million labels:** this is a GROUP BY on a computed key. Compute the key in a map step
  (Spark UDF or SQL: `string_agg(ch, '' ORDER BY ch)` over the characters), then group. Keep the
  "first appearance" order with the minimum source offset per group.
- **Memory:** holding every label in memory is O(total characters). For a streaming feed, emit
  `(key, label, offset)` records and let a sort/shuffle do the grouping.
- **Data quality:** scrambled characters are a symptom. Log the group sizes and alert when a feed
  suddenly produces many multi-member groups.

## Follow-up questions

1. The supplier also drops or duplicates **one** character sometimes. How would you find labels
   within one edit of each other without comparing every pair?
2. How do you handle `"é"` written as one code point in one label and as `e` + accent in another?
3. Return only the groups with at least two **distinct** spellings, sorted by group size
   descending, deterministically.
