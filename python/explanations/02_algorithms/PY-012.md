# PY-012 · Longest window of distinct status codes: explanation

## Approach 1: last-seen index map (`PY-012.py`)

Keep the invariant that `s[left:right+1]` has no repeats. For each new character:

- If it was last seen **at or after `left`**, the window now holds a duplicate. Jump `left` to
  `last_seen + 1`.
- If it was last seen **before `left`**, it is already outside the window. Ignore it.

  This is the classic bug: `"abba"` moves `left` back to index 1 when the second `a` arrives if you
  don't check `prev >= left`.
- Record `last_seen[ch] = right`, then update the best window with a **strict** `>` so the
  earliest window wins ties.

Time O(n) with one dict lookup per character. Space O(k) for k distinct characters.

## Approach 2: membership set (`PY-012_alt.py`)

Keep the set of characters in the window. On a repeat, pop `s[left]` and advance `left` until the
incoming character is unique. Each index is added once and removed at most once, so the cost is
O(n) amortised.

- **Pros:** it does not depend on index bookkeeping, so it's easy to reason about and extends
  naturally to "at most K repeats" or "at most K distinct" variants. Use a `Counter` instead of a
  set for those.
- **Cons:** up to 2n set operations, and the left pointer crawls instead of jumping.

## Why brute force fails

The O(n²) restart-from-every-index approach does about 20,000 × 20,000 steps on the large-alphabet
test, so it won't finish in time. The O(n³) "check every substring" approach is hopeless.

## Scale-up discussion

- **Streaming input** (an unbounded status feed): approach 1 works online, one character at a
  time. Memory is bounded by the alphabet, not the stream.

  To evict old indices, keep only entries `>= left`. With an `OrderedDict` you can pop from the
  front as `left` advances.
- **Millions of devices:** state is per device (`left`, best window, last-seen map). In Spark or
  Flink this is keyed state; checkpoint it so restarts don't recompute the whole history.
- **Late or out-of-order events:** contiguous-window problems assume ordered input. Buffer by event
  time up to a watermark and process in order, or accept approximate answers.

## Follow-up questions
