# PY-018 · Design a small LRU cache: explanation

## What has to be O(1)

An LRU cache needs two operations to be constant time:

1. **find** an entry by key;
2. **find the oldest** entry, and **move an entry to the newest position** when it is used.

A dict alone does (1). A list ordered by recency does (2) only if you can reach and unlink an
arbitrary node in O(1), which a Python `list` can't (`remove` is O(n)). So the classic answer
combines a **hash map** with a **doubly linked list**.

## Approach 1: `OrderedDict` (`PY-018.py`)

`collections.OrderedDict` is exactly that combination, implemented in C:

- `move_to_end(key)`: mark as newest, O(1);
- `popitem(last=False)`: remove the oldest, O(1);
- membership and lookup: O(1).

Contract details that tests probe:

| rule | why it matters |
|---|---|
| `get` hit: `move_to_end` | a read is a use |
| `get` miss: return `default`, don't insert | a cache lookup must not create entries |
| stored `None` is a hit | don't write `if value is None: return default` |
| `put` on existing key: update + refresh, **no eviction** | the size did not grow |
| `put` on a new key: evict **after** inserting, only when `len > capacity` | at most one eviction per put |
| `in`: plain membership, **no refresh** | otherwise a "does it exist?" check protects an entry |
| callback: once per evicted entry, after removal | observers see a consistent cache |

Why `__contains__` must not refresh: monitoring code that asks `key in cache` would otherwise make
those keys immortal and distort what the cache holds. If refresh-on-check is wanted, it is a
different method (`touch`).

Common wrong answers the tests catch:

- A list plus `list.remove` or `list.index`: O(n) per operation, which fails at 50,000 entries.
- Refreshing in `__contains__`.
- Evicting when `put` updates an existing key at full capacity (evicts a neighbour unnecessarily).
- Calling `on_evict` for replaced values.
- `get` returning `default` for a stored `None`, or inserting `default` on a miss.
- Using the value `None` as the "missing" sentinel inside the cache.
- Accepting `capacity=True` (a `bool` is an `int`) or `capacity=0` (which would evict every insert).

## Approach 2: dict + hand-built doubly linked list (`PY-018_alt.py`)

```text
head <-> oldest <-> ... <-> newest <-> tail        dict: key -> node
```

- **Doubly linked**: unlinking a node needs its predecessor. A singly linked list would need an
  O(n) walk.
- **Sentinels** (`head`, `tail`) mean the list is never empty and no node is first or last, so
  `_unlink` and `_append_newest` have no `if` branches.
- The node stores its **key**, because eviction starts from the node and must delete the dict entry.

| | `OrderedDict` | dict + linked list |
|---|---|---|
| time | O(1) average, C speed | O(1) average, Python speed (about 2 to 4 times slower) |
| code | about 10 lines | about 40 lines |
| memory per entry | smaller | `__slots__` node + dict entry |
| flexibility | limited to what the class offers | can add frequency counters (LFU), TTL buckets, segmented LRU |

In an interview, mention `OrderedDict` first, then show the linked list if asked to build it
from scratch.

## Library / runtime notes

- `functools.lru_cache` is the standard-library cache for **pure functions**. It has no
  per-entry eviction callback, no `put`, and no `in` that leaves recency alone, hence this class.
- Python dicts also preserve insertion order, so `d.pop(key); d[key] = value` can emulate
  "move to end", and `next(iter(d))` is the oldest. It works, but deleting from the front of a
  dict leaves tombstones, so `OrderedDict` is the better tool.
- Not thread-safe. A cache shared by threads needs a lock around `get` and `put` (reads mutate
  the order, so even `get` is a write).

## Scale-up discussion

- **Memory bound by bytes, not entries:** track an estimated size per entry and evict until the
  total fits. Capacity then becomes a weight, and one put may evict several entries.
- **Multi-process / multi-host:** each process holds its own cache, so hit rates fall and
  entries go stale. Use Redis or Memcached (`maxmemory-policy allkeys-lru` is an approximated
  LRU, sampled instead of exact), or a consistent-hash router in front of the services.
- **Staleness:** LRU says nothing about freshness. Add a TTL, or invalidate on change events (CDC).
- **Cache stampede:** many concurrent misses on the same key all hit the database. Use a
  per-key lock or "single flight", and negative caching for missing products.
- **Scan resistance:** one large scan flushes a pure LRU. 2Q, LRU-K or TinyLFU keep the hot set.

## Follow-up questions

1. Make it thread-safe. What exactly needs the lock, and how would you reduce contention?
2. Add a time-to-live per entry using an injected clock. Where are expired entries removed,
   and what does `len()` report?
3. Turn it into an LFU cache (evict the least frequently used, ties by recency) with O(1)
   operations. What structure do you add?
4. The cache is in front of a 50 ms database call and the hit rate is 60%. How do you measure and
   improve it?
