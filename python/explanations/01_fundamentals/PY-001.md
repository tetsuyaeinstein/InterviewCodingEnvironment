# PY-001 · De-duplicate transaction records: explanation

## Approach 1: seen-set in a single pass (`PY-001.py`)

Walk the records once, keeping a `set` of ids already emitted:

| record | id | in `seen`? | action | `seen` after |
|---|---|---|---|---|
| 0 | T-9 | no | emit | {T-9} |
| 1 | T-7 | no | emit | {T-9, T-7} |
| 2 | T-9 | yes | drop | unchanged |
| 3 | (missing) | n/a | emit, bypass the set | unchanged |
| 4 | None | n/a | emit, bypass the set | unchanged |
| 5 | T-7 | yes | drop | unchanged |

- **First wins** falls out naturally: an id is added the first time it is emitted, and every
  later copy finds it in the set.
- **Order** is preserved because records are emitted in arrival order and never reordered.
- **Missing / None ids** are decided *before* the membership test. If you put `None` into the set
  you silently drop the second id-less record: data loss.
- **No coercion:** `1001` and `"1001"` hash differently and are different ids. Normalising with
  `str()` "works" on clean data, then merges genuinely different keys from two source systems.
  If the business wants normalisation, it belongs in an explicit, tested step before de-dup.

Time O(n) average (one hash + lookup per record). Space O(d) for d distinct ids. The set stores
ids only, never records.

The core is a generator, so the same logic de-duplicates an unbounded feed lazily. The public
function wraps it in `list()` because the contract returns a list.

## Approach 2: insertion-ordered dict (`PY-001_alt.py`)

`index.setdefault(key, record)` inserts only the first record per key, and a `dict` remembers
insertion order, so `list(index.values())` is the answer. Id-less records get a unique
`object()` sentinel key, so they never collide with each other or with real ids.

| | seen-set + generator | ordered dict |
|---|---|---|
| memory | ids only (+ output) | every surviving record, held until the end |
| streaming | yes: emits as it goes | no: the result exists only after the last input |
| "last wins" variant | needs a buffer or a second pass | `index[key] = record` (keeps the *first* position) |
| clarity | explicit | compact, but the sentinel trick needs a comment |

## Why the tests look the way they do

- **Different payloads for the same id** catch "last wins" implementations
  (`{r["transaction_id"]: r for r in records}` is the classic one-liner bug).
- **Two identical id-less records** catch implementations that put `None` in the set.
- **`1001` vs `"1001"`** catch `str()` normalisation.
- **A generator input** catches code that iterates twice (`len(records)`, a counting pre-pass).
- **30,000 distinct ids** catch `if tid not in seen_list`, which is O(n²): about half a billion
  comparisons.

## Library / runtime notes

- `dict` insertion order is guaranteed since Python 3.7, so `dict.fromkeys(ids)` is the idiomatic
  "ordered unique" for plain values. It doesn't help directly here because we keep records, not ids.
- `True == 1` and `hash(True) == hash(1)`: a bool id would collide with integer 1. Real ids are
  never bools, but it is a nice illustration that "equal as Python values" is a precise contract.

## Scale-up discussion

- **Millions of records per batch:** a set of 10M short string ids costs roughly 1 GB in
  CPython. Options: store a compact fingerprint (e.g. a 64-bit hash of the id, with a tiny,
  documented collision risk), de-duplicate per partition when the id embeds the kiosk/shard, or
  push de-dup into the warehouse (`ROW_NUMBER() OVER (PARTITION BY transaction_id ORDER BY
  received_at)`, a `MERGE`, or a unique constraint).
- **Streaming / across batches:** the seen-set becomes keyed state with a **TTL** equal to the
  maximum resend window (e.g. 7 days). Without a TTL the state grows forever. A Bloom filter
  cuts memory but its false positives drop real transactions. That is unacceptable for money, so
  use one only as a pre-filter in front of an exact store.
- **Idempotent loads:** the strongest guarantee is a unique key at the sink
  (`INSERT ... ON CONFLICT DO NOTHING`), so replaying a whole batch is harmless. In-memory
  de-dup is an optimisation on top of that, not a replacement.
- **Monitoring:** emit the duplicate count and the id-less count per batch. A sudden jump
  signals a retry storm or an upstream schema change.

## Follow-up questions

1. The business now wants the **latest** copy (by a `received_at` field) but in the original
   position. What changes?
2. Duplicates can arrive up to 7 days apart in separate batch files. Where does the seen-state
   live, and how is it expired?
3. 500 million ids per day: what is your memory budget for exact de-dup, and what would you
   trade (fingerprints, partitioning, pushing it into the database)?
4. Two source systems use `1001` and `"1001"` for the same transaction. How do you handle that
   without loosening the type-strict contract for everyone else?
