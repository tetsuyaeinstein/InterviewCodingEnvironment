# PY-003 · Top-K customers: explanation

## The ranking key

Both rules fit into one ascending sort key: `(-spend, customer_id)`.

| customer | spend | key |
|---|---|---|
| 502 | 120.00 | (-120.00, 502) |
| 505 | 120.00 | (-120.00, 505) |
| 501 | 80.00 | (-80.00, 501) |
| 503 | 80.00 | (-80.00, 503) |
| 504 | 15.00 | (-15.00, 504) |

Negating the spend turns "descending" into "ascending". `Decimal` negation is exact, so no
precision is lost. The id stays positive, so ties go to the lower id. Every key is unique
(customer ids are unique), so the order is **total**, and the result is independent of the
mapping's insertion order.

Common wrong answers and why the tests catch them:

- `sorted(spend.items(), key=lambda kv: kv[1], reverse=True)[:k]`: ties come out in
  **insertion order** (sort stability), which differs between runs that build the mapping
  differently.
- `sorted(..., key=lambda kv: (kv[1], kv[0]), reverse=True)`: ties go to the **higher** id,
  because `reverse` flips both components.
- `heapq.nlargest(k, items, key=lambda kv: kv[1])`: same insertion-order problem.
- Forgetting `bool` (`k=True` behaves like 1) or silently clamping a negative `k` to 0.

## Approach 1: bounded heap via `heapq.nsmallest` (`PY-003.py`)

`heapq.nsmallest(k, items, key=...)` keeps a heap of the best k seen so far. Each new item is
compared with the worst of those k, and replaces it in O(log k) when it is better.

- Time **O(n log k)**, extra space **O(k)**.
- It consumes an iterator, so it works on a stream of `(customer, spend)` pairs that never fits
  in memory.
- CPython special-cases `k == 1` (uses `min`) and `k >= n` (uses `sorted`).

## Approach 2: full sort and slice (`PY-003_alt.py`)

`sorted(items, key=...)[:k]` is O(n log n) time and O(n) extra memory.

| | bounded heap | full sort |
|---|---|---|
| time | O(n log k) | O(n log n) |
| extra memory | O(k) | O(n) |
| streaming input | yes | no (needs all items) |
| constant factors in CPython | Python-level loop for comparisons | Timsort in C, very fast |
| k ≈ n | no gain | same or better |

In practice, at n = 300,000 both take well under a second in CPython. The full sort can even be
faster for moderate n, because Timsort is pure C. The heap's real advantage is **memory and
streaming**, and the argument gets stronger as n grows and k stays small. Say this in the
interview: complexity is not the only cost model.

`heapq.nlargest(k, items, key=lambda kv: (kv[1], -kv[0]))` also works, but only because ids are
integers that can be negated. The `nsmallest` form with negated *spend* is more general, since
the tie-break column can be any orderable type.

## Library / runtime notes

- `Decimal` supports unary minus and total ordering, so it works directly in sort keys. Mixing
  `Decimal` with `float` in comparisons works but hides precision bugs.
- If the tie-break column could be a string, you can't negate it. Use `nsmallest` with a
  negated *numeric* component, or two stable sorts (`sort by id asc`, then `sort by spend desc`).

## Scale-up discussion

- **Millions of customers in a database:** push it down: `ORDER BY spend DESC, customer_id
  LIMIT k`. PostgreSQL does a top-N heapsort (visible in `EXPLAIN ANALYZE`), the same algorithm.
- **Distributed (Spark):** compute a local top-k per partition, then merge the partial results
  (k × partitions items) and take the global top-k. That is correct because the global top-k
  must be inside the union of the local top-k sets. With a total order (the id tie-break), the
  merge is deterministic too.
- **Streaming leaderboard:** totals change over time, so a static heap goes stale. Keep the
  totals in keyed state, and recompute top-k per window, or maintain a sorted structure (a
  balanced tree / Redis sorted set) keyed by `(-spend, id)`.
