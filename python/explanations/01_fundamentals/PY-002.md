# PY-002 · Completed spend per customer: explanation

## Approach 1: dict of exact running sums (`PY-002.py`)

One pass over the transactions:

1. **Filter first.** Check the status (`strip().upper() == "COMPLETED"`), then the guest rule.
   Only then parse the amount. Rows we don't count may carry garbage amounts (a PENDING row
   that failed upstream validation) and must not abort the run.
2. **Convert to `Decimal` without floats.**
   - Reject `bool` before `int`, because `isinstance(True, int)` is true.
   - Reject `float` outright: `Decimal(0.015)` is
     `0.01499999999999999944488848768742172978818416595458984375`, so the damage is already done
     by the time you see it.
   - `Decimal(str.strip())` for strings. `Decimal("NaN")` and `Decimal("Infinity")` parse
     successfully, so an explicit `is_finite()` check is needed.
3. **Accumulate unrounded** sums in a plain `dict`.
4. **Round once** per customer with `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. This
   also normalises the exponent, so `Decimal("10")` becomes `Decimal("10.00")`.

| rounding strategy | `"0.005" + "0.005"` | why |
|---|---|---|
| round each row, half-up | 0.02 | 0.01 + 0.01 |
| sum exactly, round once | 0.01 | 0.010 → 0.01 |
| Python `round()` / default context | banker's rounding | `2.125` → 2.12, not 2.13 |

Time O(n), space O(c) for c customers.

`defaultdict(Decimal)` is a fine accumulator, but **return a plain dict**: a `defaultdict`
silently creates a `0` entry when a caller looks up a customer who isn't there, which hides bugs
in reconciliation code. The comprehension at the end does that conversion for free.

## Approach 2: sort + `itertools.groupby` (`PY-002_alt.py`)

Filter and convert as a generator, sort by customer, `groupby`, then `sum` each group.

| | dict accumulator | sort + groupby |
|---|---|---|
| time (unsorted input) | O(n) | O(n log n) |
| memory | O(customers) | O(n): the sorted list is materialised |
| input already ordered by customer | no benefit | sort can be dropped: O(1) memory per group |
| emits results early | no: totals final only at the end | yes: each group is final when it closes |
| key requirements | hashable | orderable (mixed `int`/`str` ids break `sorted`) |

The groupby shape is how you aggregate output that is **already clustered**: an
`ORDER BY customer_id` server-side cursor, files partitioned by customer, or a k-way merge of
sorted runs. It is a classic way to aggregate data larger than memory. The common bug is calling
`groupby` on unsorted data: it then returns several groups per key, and a dict comprehension
silently keeps only the last one.

## Why the tests look the way they do

- `"0.005" + "0.005"` separates round-once from round-per-row.
- `"2.125"` separates half-up from banker's rounding (Python's default).
- `"0.015"` catches a `float()` round trip.
- `"NaN"` / `"Infinity"` parse as `Decimal`, so only an explicit finiteness check rejects them.
- `True` as an amount would otherwise count as 1.00.
- Bad amounts on PENDING rows prove the filter runs before parsing.
- `type(result) is dict` rules out returning a `defaultdict`.

## Library / runtime notes

- The `decimal` default context has 28 significant digits. That is plenty for currency sums,
  but a pipeline summing billions of rows of large amounts should set the precision explicitly
  with `localcontext()`.
- `Decimal` arithmetic is roughly 3–10x slower than float in CPython (the C `_decimal` module
  helps). For tens of millions of rows, consider summing **integer cents** (`int` is exact and
  fast) and converting once at the end, provided the inputs have at most 2 decimal places.
- PostgreSQL `numeric` arrives as `Decimal` through psycopg. Keep it that way end to end.

## Scale-up discussion

- **Millions of transactions:** one pass with a dict is fine up to millions of customers (each
  entry ≈ 100–200 bytes). Beyond that, aggregate in the database (`SUM(amount) ... GROUP BY
  customer_id`) or in Spark/DuckDB. The same Decimal rules apply (`DecimalType(18,2)`, never
  `DoubleType`).
- **Streaming:** the dict accumulator is already incremental. In a stream processor, the state
  is per customer, keyed and checkpointed. Late refunds simply adjust the total, which is why
  "net" must be defined as including negative completed rows.
- **Reconciliation:** publish the row count and the sum of all counted amounts, so finance can
  check that the per-customer totals add up to the processor's figure. Rounding per customer
  means the sum of rounded totals can differ from the rounded grand total by up to half a cent
  per customer. Document which one is the reference.
