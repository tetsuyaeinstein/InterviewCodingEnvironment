# PY-007 · Schema validation with structured row errors: explanation

## Architecture (`PY-007.py`)

Three layers with different failure contracts:

| layer | input | on failure |
|---|---|---|
| `_check_schema` | engineer's config | raises `SchemaError`, **before** any row is read |
| `_validate_field` + `_to_<type>` coercers | one value | raises a private `_Invalid(code, message)` |
| `validate_rows` loop | rows | catches `_Invalid`, appends a `RowError`, never raises |

The private exception is the key design choice:

- each coercer is a short, linear function that bails out at the first problem;
- "at most one error per field" is guaranteed by construction;
- the row loop is the only place that knows about `row_index`.

A version that returns `(value, error)` tuples everywhere works too, but it is noisier and easy
to get wrong (forgetting to check the error half).

Per field, the pipeline is: **presence → null → type/format coercion → allowed values.** The
order matters:

- `allowed` must see the *coerced* value (`" 2 "` → `2` ∈ `{1, 2, 3}`, `"1.0"` →
  `Decimal("1.0")` equals `Decimal("1.00")`);
- null must be decided before coercion, so a blank CSV cell in a nullable decimal column is
  `None`, not `invalid_format`.

## The subclass traps

| trap | consequence if ignored |
|---|---|
| `isinstance(True, int)` is true | `True` is accepted as refund_id 1 |
| `isinstance(datetime(...), date)` is true | a timestamp slips into a date column, and the time is silently truncated later |
| `Decimal("NaN")` parses without error | `NaN` poisons every sum downstream (`NaN` ≠ `NaN`, so comparisons fail mysteriously) |
| `float` → `Decimal` | `Decimal(1.1)` = `1.100000000000000088817841970012523...` |
| `int("٣")` accepts non-ASCII digits | the ASCII-only regex makes the accepted alphabet explicit |
| `date.fromisoformat` in 3.11+ accepts `20250101` and `2025-W01-1` | the regex pins the contract to `YYYY-MM-DD` |

## Determinism

Errors come out ordered by row, then by schema order, then by unknown keys sorted by `str(key)`.
Sorting the unknown keys matters because the same file read by `csv.DictReader` and by a JSON
loader can present keys in different orders, and the rejection report (and its tests, and its
diffs between runs) must be stable.

## Alternatives

- **pydantic / attrs / marshmallow / pandera:** in production, a declarative model library is
  usually the right choice. Know its defaults, though: pydantic in lax mode converts `"1"` to
  `True` and `1.0` to `1` unless you configure strict mode. The value of this exercise is
  knowing *what* to configure.
- **Columnar validation:** for large files, validate per column with vectorised operations
  (pyarrow compute, Polars, pandera on DataFrames). Errors become a boolean mask per rule,
  turned into the same `(row_index, field, code)` triples at the end. It is orders of magnitude
  faster than a Python loop over dicts.
- **JSON Schema** (`jsonschema` library): a portable, language-neutral contract with partners.
  But `Decimal` and date coercion still need custom formats.

## Complexity

O(R × F) for R rows and F schema fields, plus O(K log K) per row for K unknown keys under the
error policy. Memory is O(valid rows + errors). For huge files, make the function a generator of
`(index, row | errors)` so both streams can be written out incrementally.

## Production considerations

- **Error budgets:** a file with 2 million rows that are all invalid produces 10 million error
  objects. Cap errors per file (e.g. stop collecting after 1,000, but keep counting), or
  aggregate them by `(field, error_code)` with sample row indexes.
- **Partial acceptance:** decide per feed. Money files are usually all-or-nothing (reject the
  file if any row fails). Telemetry tolerates partial loads. Either way, write the rejected rows
  with their errors to a quarantine table keyed by file id + row index, so you can replay them.
- **Schema versioning:** keep the schema in config, version it, and log the version with every
  load. A partner adding a column should produce `unknown_field` errors, or be accepted under
  `keep`, by explicit decision, not by accident.
- **PII in messages:** messages here include the offending value. For card or customer data,
  redact values before the report leaves the platform.

   cap the error output?
2. Add cross-field rules (e.g. `refund_date` ≥ the original sale date, `amount` < 0 only when

3. How would you express this schema in pydantic v2 with *exactly* these semantics (strict
