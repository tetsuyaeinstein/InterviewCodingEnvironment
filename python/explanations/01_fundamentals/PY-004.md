# PY-004 · Flatten nested payloads: explanation

## Approach: iterative depth-first walk (`PY-004.py`)

The natural first draft is recursive:

```text
walk(container, prefix):
    for segment, value in children(container):
        key = join(prefix, segment)
        if expandable(value): walk(value, key) else emit(key, value)
```

It is correct, and in an interview it is a fine *first* answer, but it fails the 5,000-level
test with `RecursionError`. CPython's default limit is ~1,000 frames, and raising it with
`sys.setrecursionlimit` risks crashing the interpreter on the C stack. A message API should
treat "very deep JSON" as an attack vector (the same reason `json` parsers have depth limits).

The reference keeps an explicit stack of frames `(prefix, depth, iterator)`:

| step | stack top | next child | action |
|---|---|---|---|
| 1 | ("", 0, record) | `id` → "T-1" | emit `id` |
| 2 | ("", 0, record) | `payment` → {…} | push ("payment", 1, …) |
| 3 | ("payment", 1, …) | `method` → "card" | emit `payment.method` |
| 4 | ("payment", 1, …) | `card` → {…} | push ("payment.card", 2, …) |
| 5 | ("payment.card", 2, …) | `last4`, `network` | emit both, then the iterator is exhausted: pop |
| … | | | |

Storing an **iterator** per frame, rather than pushing every child onto the stack, is the detail
that preserves input order (a naive "push all children" stack emits them in reverse). It also
keeps the stack size equal to the depth, not the width.

Design decisions the contract forces:

- **Expand or emit:** expand only non-empty containers below `max_depth`. Empty containers
  become leaves (`{}` / `[]`), so `{"meta": {}}` doesn't vanish from the wide table. "Missing
  column" and "present but empty" mean different things downstream.
- **One emit function** checks for collisions and deep-copies container values. Centralising it
  means no branch can forget either rule.
- **Collisions fail loudly.** `{"a.b": 1, "a": {"b": 2}}` maps two different paths to `a.b`.
  Overwriting would silently lose data depending on key order. The alternatives are escaping
  (`a\.b`) or a reversible encoding, but they change the column names for every consumer.
- **Non-string keys raise:** coercing `1` to `"1"` would collide with list index `1` and make
  the scheme ambiguous.
- **Deep copies:** without them, `flat["payment.card"]["last4"] = ...` edits the caller's
  payload. That is a classic aliasing bug when a record is flattened, enriched, then also
  archived raw.

Complexity: O(N) for N total nodes. The key strings cost O(depth) each to build, so a
pathological deep chain is O(depth²) characters in total. Extra space is O(depth) for the stack
plus the output.

## Alternatives

- **Recursive generator** (`yield from walk(...)`): elegant, same order, same recursion limit
  problem. Fine when payload depth is bounded by a schema, and worth saying so.
- **Pass a tuple of segments instead of a string prefix:** keys are joined only at emit time.
  This avoids O(depth²) string building for deep chains, and it makes it easy to also return the
  segment tuple for a *reversible* scheme.
- **`pandas.json_normalize`:** handles nested dicts with a separator and `max_level`, but it
  does not expand lists into indexed columns, and it silently overwrites colliding keys. Know its
  semantics before relying on it in a pipeline.

## Production considerations

- **Schema drift:** flattening turns every new nested field into a new column. Track the set of
  flattened keys per day and alert on new ones, or route unknown paths into a JSON overflow
  column.
- **Arrays:** indexed columns (`items.0.sku`) are fine for small fixed arrays. For line items,
  the better model is usually a **child table** (explode the list into rows keyed by
  `transaction_id` + index).
- **Limits:** enforce maximum depth and key count at the API edge. The flattener's job is to be
  correct, not to be the only defence.

## Follow-up questions

1. Write the inverse, `unflatten`. Which inputs make it ambiguous, and how would you change the
   key scheme to make it lossless?
2. The payloads are 2 GB NDJSON files. What changes if you have to stream records and you want
   a stable column set for Parquet output?
3. Line items should go to a child table instead of indexed columns. How would you split one
   record into a parent row and N child rows?
4. How would you process 10 million payloads per hour? Where is the CPU going, and what would
   you change first?
