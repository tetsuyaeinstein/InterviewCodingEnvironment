# PY-008 · In-memory joins with SQL semantics: explanation

## Approach 1: hash join (`PY-008.py`)

**Build** a hash table on the right side, then **probe** it with the left side:

```text
index = {}                                   # key -> [right rows, in right order]
for r in right:  if r[on] is not None: index[r[on]].append(r)
for l in left:   for m in index.get(l[on], []): emit merge(l, m)    # + unmatched rows for LEFT
```

| rule | where it lives |
|---|---|
| many-to-many | the index stores a **list** per key, and the probe emits one row per element |
| NULL never matches | `None`/missing keys are never indexed, and a None probe short-circuits |
| left order | the probe streams the left input once, in order |
| right order within a key | `append` preserves right input order |
| LEFT JOIN | no matches → copy of the left row |

Time O(L + R + output), memory O(R) for the index. The classic bug is `{r[on]: r for r in
right}`: a dict of single rows silently keeps only the **last** duplicate, so the fan-out
disappears and totals no longer match SQL. Another subtle bug is probing a `defaultdict` with
`index[key]`, which inserts an empty list for every unmatched key and makes memory grow with the
left side.

Why is `None` special? In SQL, `NULL = NULL` is unknown, not true. In Python, `None == None` is
`True`, so a naive dict join pairs every NULL-keyed transaction with every NULL-keyed customer: a
silent cartesian product on dirty data.

The merge policy: left wins the plain name, and right gets a suffix only when the name clashes.
That mirrors `pandas.merge(suffixes=("", "_right"))`. Raising on a second-order clash
(`status_right` already present) is better than overwriting: overwriting would make the output
depend on column order.

## Approach 2: sort-merge join (`PY-008_alt.py`)

Sort both sides by key (stable sort keeps the input order inside a key), walk them with two
pointers, and emit the cross product of each equal-key run. The contract asks for left input
order, so results are tagged with the left position and re-ordered at the end.

| | hash join | sort-merge join |
|---|---|---|
| time | O(L + R + out) | O(L log L + R log R + out); O(L + R + out) if pre-sorted |
| memory | the whole build side in a hash table | O(one key group) when inputs stream pre-sorted |
| key requirement | hashable | orderable (mixed types need a `(type, value)` sort key) |
| output order | naturally left order | naturally key order (left order costs a re-sort) |
| larger than RAM | needs partitioning (grace hash join) | external sort + merge, the textbook spill path |

**Rule of thumb:** build the hash table on the **smaller** side. Use sort-merge when both inputs
are already sorted (Parquet files sorted by key, `ORDER BY` server-side cursors), when the build
side doesn't fit in memory, or when you need key-ordered output anyway.

## Why the tests look the way they do

- A right side with **duplicate keys** catches the dict-of-one-row bug.
- **None on both sides** catches `None == None` matching.
- **`1` vs `"1"`** catches `str()` key normalisation.
- **Both sides as generators** catch double iteration of the left input (e.g. `len(left)`).
- **20,000 × 20,000** catches nested loops (400M comparisons).
- The random oracle is a literal nested loop. Slow, but obviously correct.

## Production considerations

- **Fan-out monitoring:** an unexpected duplicate key in a dimension (the example's SCD history
  row) silently multiplies revenue. Assert key uniqueness on the side that should be unique, or
  log `len(output) / len(left)` and alert when it is > 1.
- **SCD2 dimensions:** the right join is usually "the version valid at the transaction time".
  That is a range join (`valid_from <= ts < valid_to`), not an equality join. In memory, use
  per-key sorted version lists + `bisect`.
- **Scale:** in Spark, a small dimension becomes a *broadcast hash join* (exactly approach 1 on
  every executor). Two large sides become a *sort-merge join* after a shuffle (approach 2). Know
  which one your plan picked, and watch out for skewed keys (one hot customer) that overload a
  single task.
