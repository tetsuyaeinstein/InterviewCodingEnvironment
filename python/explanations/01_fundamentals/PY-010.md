# PY-010 · Lazy chunking: explanation

## Approach 1: eager validation + inner generator (`PY-010.py`)

```text
def chunked(iterable, size):
    validate size            # runs at call time
    it = iter(iterable)      # runs at call time: TypeError for non-iterables
    def _chunks():           # generator: runs only when consumed
        while chunk := list(islice(it, size)):
            yield chunk
    return _chunks()
```

Three details carry the whole exercise:

1. **Where validation runs.** If `chunked` itself contains `yield`, it is a generator function,
   and *nothing* in its body runs until the first `next()`. So `chunked(rows, 0)` "succeeds", and
   the `ValueError` surfaces later, far from the bug, maybe inside a library's retry loop.
   Returning an inner generator from a plain function gives eager validation *and* lazy
   iteration.
2. **One shared iterator.** `islice(iterable, size)` called repeatedly on a **list** restarts
   from index 0 every time (infinite loop of the first chunk). On a generator it happens to
   work. Calling `iter()` once makes both behave the same way.
3. **No read-ahead.** `islice` pulls at most `size` items. A hand-rolled loop of the form "append,
   and when `len == size` yield" is also fine. A version that **peeks** one item ahead to avoid an
   empty final chunk pulls item N+1 before the consumer has asked for it. If the consumer commits
   offsets per batch and then crashes, that peeked record is lost.

Memory O(size). Time O(1) amortised per item.

Wrong answers the tests target:

| bug | test that fails |
|---|---|
| `list(iterable)` first, then slice | infinite source hangs (guarded by `next()` calls); pull counter > chunk size |
| generator-function-only (lazy `ValueError`) | `test_non_positive_size_raises_at_call_time` |
| reusing one buffer list (`buf.clear()`) | `test_each_chunk_is_a_new_list` |
| `while True: yield list(islice(...))` with no empty check | trailing `[]` chunk |
| `isinstance(size, int)` without the bool check | `size=True` accepted as 1 |
| peeking one item ahead | `test_no_read_ahead`, `test_source_failure_...` |

## Approach 2: `itertools.batched` (`PY-010_alt.py`, Python 3.12+)

`map(list, batched(iterable, size))`:

- the C implementation is the fastest option;
- `batched` validates `n >= 1` eagerly, calls `iter()` eagerly, and is equally lazy;
- the trade-offs: it yields **tuples** (the contract wants lists, so each chunk is copied
  once); it is unavailable before 3.12 (`more_itertools.chunked` is the long-standing
  equivalent); and it doesn't reject `bool`.

In an interview, mentioning `batched` is a plus, and implementing the generator yourself shows
you understand why it behaves as it does.

## Production considerations

- **Batch size choice:** the trade-off is round trips vs memory vs blast radius of a failed
  batch. For database inserts, 500–5,000 rows per `executemany`/`COPY` chunk is typical. For
  APIs, the provider's payload limit decides. A byte-size-aware variant (close the chunk when
  the encoded size reaches X MB) is a common follow-up.
- **At-least-once delivery:** with a consumer that commits offsets per chunk, laziness is what
  makes "commit after successful write" correct. Pair it with idempotent writes (PY-001) so
  replays after a crash are harmless.
- **Back-pressure:** generators give natural back-pressure. Nothing is read faster than the sink
  consumes it. Wrapping the source in a thread or async prefetch breaks that unless the
  buffer is bounded.
- **Time-based flush:** for streams, a chunk should also close after T seconds even if it is
  not full. That needs an injectable clock, and it can't be done with a blocking `next()`
  alone.
