# PY-005 · Normalise timestamps to UTC: explanation

## Approach (`PY-005.py`)

1. **Validate configuration first:** the `ambiguous` policy, and `default_tz` when given.
   A typo in a zone name is a deployment bug. It should fail on the first record, not only when
   the first naive timestamp happens to show up at 3 a.m.
2. **Match the accepted shape with a strict regex**, then build the `datetime` from the captured
   fields. The constructor rejects out-of-range values (Feb 30, hour 24, second 60).
3. **Aware input:** attach `timezone.utc` (`Z`/`z`) or `timezone(offset)`, then call
   `.astimezone(timezone.utc)`.
4. **Naive input:** without a zone, raise. With a zone, resolve the wall time explicitly (below).

### Why not just `datetime.fromisoformat`?

It is a good parser, but since Python 3.11 it is deliberately **lenient**:

| input | `fromisoformat` result | our contract |
|---|---|---|
| `2025-03-09` | `datetime(2025, 3, 9, 0, 0)`, naive midnight | `ValueError`: a date is not an instant |
| `2025-03-09T10:00:00z` | `ValueError` | accepted (RFC 3339 allows lower case) |
| `.123456789` | truncated to `.123456` (3.11+) | same, explicitly |
| `2025-W10-1T10:00` | accepted (week date) | out of scope |

The date-only row is the dangerous one. With `default_tz` set, the lenient path silently turns
`2025-03-09` into local midnight, which is a fabricated time. Using `fromisoformat` after a
shape check is a perfectly good alternative design. Say which inputs you accept and test it.

### DST resolution with `fold`

`zoneinfo` implements PEP 495: a wall time carries `fold=0` (first occurrence) or `fold=1`
(second occurrence).

| local time (America/New_York) | offset with fold=0 | offset with fold=1 | round trip of fold=0 | verdict |
|---|---|---|---|---|
| 2025-06-01 10:03 | −4 | −4 | same | normal |
| 2025-11-02 01:30 | −4 (EDT) | −5 (EST) | 01:30, same | **ambiguous** |
| 2025-03-09 02:30 | −5 (EST) | −4 (EDT) | 03:30, changed | **does not exist** |

- Equal offsets mean one instant.
- Different offsets mean a gap or an overlap. The round trip (local → UTC → local) tells which:
  a gap time comes back as a different wall-clock time.
- Never "fix" a gap time silently. A kiosk clock reading 02:30 on spring-forward night is either
  misconfigured or reporting in the wrong zone, and data quality wants to know.
- `pytz` users will recognise this as `localize(..., is_dst=None)`. `zoneinfo` is the modern
  standard-library equivalent. Note that `datetime.replace(tzinfo=pytz_zone)` is a classic bug,
  because it picks the LMT offset (e.g. −4:56).

Complexity is O(1) per value. `ZoneInfo(name)` is cached by the library, so repeated calls are
cheap.

## Testing notes

- `result.tzinfo is timezone.utc` is asserted on purpose. Returning the input's
  `timezone(+05:30)` compares equal, but it serialises differently (`+05:30` in `isoformat()`),
  and downstream code that partitions by `str(ts)[:10]` would put it on the wrong day.
- Both hemispheres are tested. Southern zones fall back in April, so "DST = summer = June"
  assumptions break.
- Times one second away from a transition must **not** be flagged as ambiguous.

## Production considerations

- **Where the zone comes from:** per device, from a registry, versioned over time. A kiosk moved
  from Denver to Phoenix changes its zone on a specific date. Store the original string, the
  zone used, and the resulting UTC instant for auditability.
- **Policy as configuration:** finance may prefer `"earlier"` for the fall-back hour, or route
  ambiguous rows to quarantine. Make it explicit, and count how often each branch fires.
- **tzdata updates:** zone rules change (governments move DST). The `tzdata` package and the OS
  database must be kept current. Re-processing historical data with a new tzdata release can
  change results for future-dated rows.
- **Vectorised paths:** in pandas, `tz_localize(..., ambiguous=..., nonexistent=...)` exposes the
  same decisions. In Spark, `to_utc_timestamp` silently shifts gap times, so know the defaults.
