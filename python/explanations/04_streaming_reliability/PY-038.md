# PY-038 · Backpressure with bounded stages: explanation

## Approach (`PY-038.py`)

```
producer thread:  slot = acquire(); item = next(source); tasks.put((i, item))
worker threads :  (i, item) = tasks.get(); results[i] = ok(transform(item)) | err(exc)
caller thread  :  for i = 0,1,2...: wait results[i]; if err: raise; consumer(value); release(slot)
```

- A **counting semaphore of `max_in_flight` slots** is taken *before* pulling and released *after*
  consuming, so `pulled - finished <= max_in_flight` regardless of how many items are in a queue,
  a worker, the reorder buffer or the consumer. The task queue and the results dict need no
  `maxsize` of their own: they can never hold more than `max_in_flight` entries.
- **Ordered delivery** comes from consuming index by index out of the results dict. A slow item at the
  head holds up later ones, but the semaphore bounds how many can pile up behind it (head-of-line blocking
  is the price of ordering; see "alternatives").
- **Failures are results.** An exception from `transform` (or from the source, recorded at the index
  where it occurred) is stored like a value. The consumer thread stops at the first failing index, so
  the pipeline behaves like the sequential program up to that point. Consumer errors propagate directly.
- **Clean shutdown.** Every blocking call in the producer and workers uses a short timeout and checks a
  `stop` event; `finally: stop.set(); join()` guarantees no leaked threads and no deadlock even when
  the producer is blocked on a full pipeline.
- **Time:** O(1) coordination per item. **Memory:** O(max_in_flight).

## Why the edge cases matter

- **`queue.Queue(maxsize)` alone is not enough.** Two bounded queues bound the *queues*, not the work in
  workers and the reorder buffer, and a blocked `put` never wakes up when the consumer died (classic
  shutdown deadlock). Counting items end to end, plus timeouts/poison pills, avoids both.
- **Release after consuming, not before.** Releasing early lets one extra item in flight, so the bound
  silently becomes `max_in_flight + 1` and memory sizing is wrong by a factor under load.
- **`None` as sentinel** is the textbook bug: a transform that legitimately returns `None` terminates the run early.
- **First failure by input order**, not by time, makes the outcome reproducible: the same bad row gives the same
  error and the same committed prefix on every run; this is what makes a retry from a checkpoint (PY-034) meaningful.
- **Lazy pulling** matters for infinite or huge sources (cursors, Kafka consumers): a failure must not
  trigger an eager read of the rest.

## Alternatives

- **Two bounded `queue.Queue`s** (input and output) + sentinel/poison pills: the textbook shape, simple for
  unordered delivery. Bound is `2*maxsize + workers + 2`; ordered delivery needs a reorder buffer that must itself
  be bounded.
- **`concurrent.futures.ThreadPoolExecutor.map`** keeps order but submits *everything* eagerly (unbounded); a
  windowed submit (`deque` of futures, refill as the head completes) gives the same bound with less code.
- **`asyncio`:** `asyncio.Queue(maxsize)` + `TaskGroup` (3.11+): cancellation propagates to all tasks, `await`
  makes backpressure cheap, but CPU-bound transforms still need `run_in_executor` / processes.
- **Unordered, completion-order** delivery has no head-of-line blocking and higher throughput; use it when the
  sink does not care about order or events carry their own sequence (PY-031).

## Production notes

- Pick `max_in_flight` from memory (`item_size * bound`) and latency (`workers * 2` keeps workers busy); monitor
  queue depth, time blocked on the semaphore (producer stalled = downstream-bound) and time workers wait for work.
- Backpressure must be propagated to the *source*: Kafka consumers `pause()` partitions and keep polling
  (otherwise `max.poll.interval.ms` triggers a rebalance); Flink propagates credits upstream through network
  buffers; Spark Structured Streaming uses `maxOffsetsPerTrigger`; reactive streams use `request(n)`.
- Commit offsets/checkpoints only for the **consumed prefix** (that is what ordered delivery buys you).
- Python threads help I/O-bound transforms only (GIL); CPU-bound work needs processes (`ProcessPoolExecutor`).

## Follow-up questions

1. Make delivery unordered: what changes in the bound, in the failure semantics and in checkpointing?
2. The consumer is also slow and must batch (flush every 500 items or 2 s): where does the timer live?
3. Rewrite with `asyncio`: how do cancellation and exception groups change the failure contract?
4. A transform call hangs forever: add per-item timeouts without leaking threads.
