# PY-035 · Tumbling windows, watermarks and late data: explanation

## Approach (`PY-035.py`)

```
t        = event_time in UTC
max_time = max(max_time, t)
wm       = max_time - allowed_lateness              (monotonic)
start    = epoch + ((t - epoch) // window) * window
if start + window <= closed_until(wm): late -> side output
else: aggregate into open[start][key]
emit every open window with end <= wm, ordered by (start, key)
```

- `open` is a dict of window start to per-key `[count, total]`; a **min-heap** of starts pops
  windows in order as the watermark advances, so every event costs O(log W) amortised and each window
  is emitted once.
- `flush()` pops everything left and advances `closed_until` so later events for those windows are late.

**Worked example** (see the question): events 12:00:30, 12:04:59, 12:03:00 go to `[12:00,12:05)`;
12:06:00 opens `[12:05,12:10)`; the watermark reaches 12:05:00 at 12:07:00, which closes
`[12:00,12:05)` (count 3). The 12:04:10 event that arrives afterwards is late.

## Why the edge cases matter

- **`>=` vs `>`.** The window end is exclusive, so a watermark *equal* to the end means "no more
  events with time < end are expected": it closes. Using `>` delays emission by one tick forever.
- **Max, not last.** An out-of-order event must not move the watermark backwards, or windows would
  "un-close" and results be emitted twice.
- **Late vs just out of order.** Out-of-order is normal and absorbed by `allowed_lateness`; *late*
  means "its window has already been emitted". The test is against the *window*, not
  against the event's age, so an old event for a still-open window is aggregated.
- **Time zones.** Alignment must be in UTC/epoch so that +09:00 or -05:30 offsets do not shift
  window boundaries (5-minute windows happen to align across whole-minute zone offsets, but 1-hour
  windows do not, so convert first).
- **Pre-epoch times** need floor division (`//`), not truncation toward zero.
- **Side output.** Dropping late events silently makes totals disagree with the source with no
  trace. Keeping them lets you reconcile, replay, or emit a correction.
- **Deterministic order.** Several windows closing at once must come out in `(start, key)` order, or
  reruns yield differently ordered files and diffs are noisy.

## Alternative (`PY-035_alt.py`)

A flat dict keyed by `(window_start, key)` and a scan of all open aggregates on every event. Simpler,
O(open aggregates) per event; fine with small lateness, bad when keys × open windows is large.

## Production notes (Flink / Spark / Kafka Streams)

- **Flink:** `WatermarkStrategy.forBoundedOutOfOrderness(Duration)` is exactly
  `max - lateness`; `allowedLateness` on the window keeps state and *re-fires* updated results;
  `sideOutputLateData(tag)` is our `late_events`. Watermark of an operator = **min** over input
  channels, so one idle partition stalls everything: use `withIdleness`.
- **Spark Structured Streaming:** `withWatermark("event_time", "2 minutes")`; in append mode a window
  is emitted when the watermark passes its end; events older than the watermark are **dropped**,
  not side-output. State is bounded by the watermark.
- **Kafka Streams:** `TimeWindows.ofSizeAndGrace` + `suppress(untilWindowCloses)`.
- State size = open windows × keys; bound it with lateness. Persist (event, watermark) in a checkpoint
  (PY-034) so a restart does not re-emit windows.
- Processing-time vs event-time: processing-time windows are deterministic to implement but wrong
  for delayed data.
