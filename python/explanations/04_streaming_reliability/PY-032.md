# PY-032 · Idempotent consumer: explanation

## Approach (`PY-032.py`)

```
process(event):
    marker = store.get("event:<id>")
    if marker: same fingerprint -> "duplicate" ; else -> ConflictingEvent
    new_balance = balance + amount
    writes = {"event:<id>": (account, amount, outcome)}
    if new_balance >= 0: writes["balance:<account>"] = new_balance
    store.commit(writes)            # ONE atomic call
```

| crash point | store state | after redelivery |
|---|---|---|
| before `commit` | untouched | first delivery again: applied once |
| after `commit`, before ack | marker + balance | duplicate: no second effect |
| between two separate writes (the bug) | marker only, or balance only | effect lost, or applied twice |

The essence: **"effect applied" and "event recorded as processed" must be one atomic fact.**
This is the *transactional outbox / inbox* pattern: the inbox table (`processed_events`) and the
business table are updated in the same database transaction, e.g. `INSERT ... ON CONFLICT DO
NOTHING` into the inbox and `UPDATE balance` inside one `BEGIN ... COMMIT`.

## Why the edge cases matter

- **Rejection markers.** Without one, a withdrawal rejected today is "new" tomorrow and succeeds
  when the account is richer: the outcome of an event would depend on redelivery timing.
- **Fingerprint on the marker.** A reused id with different content is a producer bug (or a
  hash collision in a derived id). Silently ignoring it hides lost money; raising stops the line
  so a human can decide. Many teams dead-letter it instead.
- **No cache.** A balance cache in the consumer survives a failed commit and then disagrees with
  the store. State used for decisions must come from the store being committed to.
- **Decimal.** Money is never float, and `Decimal` equality makes `1.0` and `1.00` the same
  payload.
- **Prefixes.** `event:` and `balance:` keep ids and accounts from colliding in one key space.

## Exactly-once: what is actually true

- Brokers give at-least-once (or at-most-once). "Exactly-once" is **at-least-once delivery +
  idempotent / transactional processing**, effective only for effects inside the transaction.
- Kafka transactions / Flink two-phase-commit sinks make "consume offset + produce output" atomic
  *within Kafka*. A side effect on an external system (HTTP, email) needs an idempotency key sent
  to that system, or an outbox processed by a relay that retries safely.
- Dedup state is bounded in practice: keep markers for the maximum redelivery horizon (retention
  of the topic + replay window), then expire. Document that horizon.

## Alternatives

- **Offset-based dedup:** store the last processed offset per partition with the state in one
  transaction; redeliveries have lower offsets. Cheaper than per-id markers but only works for a
  single ordered partition and not across replays from different sources.
- **Naturally idempotent effects:** set `balance = X` (version-guarded upsert) instead of
  `balance += X`. Deposits are not naturally idempotent, so a marker is required.

## Follow-up questions

1. Two consumers race on the same event_id: what does the store need to guarantee (unique
   constraint / compare-and-set / serialisable transaction)?
2. How would you bound marker storage for 1 billion events per day?
3. The effect also has to publish `BalanceChanged` to Kafka. How do you keep that atomic with the
   database update (outbox + CDC relay)?
4. How does this change if events for one account must be applied in order?
