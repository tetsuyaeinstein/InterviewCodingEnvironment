# PY-031 · Order-aware current state: explanation

## Approach (`PY-031.py`)

State per key: `[top_sequence, [distinct variants at top_sequence]]`.

| incoming vs. top | action | outcome |
|---|---|---|
| no state / higher | replace the entry with `[seq, [event]]` | applied |
| lower | nothing | stale |
| equal, matches a variant | keep the copy with the smaller `ingest_ts` | duplicate |
| equal, matches none | append a variant | conflict |

`snapshot()` = keys with exactly one variant whose op is not `D`. `conflicts()` = keys with more
than one variant. The resulting state is a **pure function of the set of events**: max sequence,
distinct variants at it, earliest `ingest_ts` per variant. That is why any permutation produces
the same snapshot (the test shuffles inputs and compares with an oracle that sorts first).

- **Time:** O(1) per event (payload `==` is proportional to payload size; the variant list is
  almost always length 1).
- **Memory:** O(keys), including tombstones.

## Why the edge cases matter

- **Sequence vs ingest time.** Replays and backfills re-ingest old changes late. Last-write-wins on
  ingest time silently reverts customers to old tiers: the classic CDC bug.
- **Tombstones.** If a delete removes the key outright, a late older update recreates a deleted
  customer (a "zombie row"). The delete must remember its sequence. That costs state, which is
  why Kafka log compaction has `delete.retention.ms` and Debezium emits explicit tombstones.
- **Resurrection.** A *newer* insert after a delete is legitimate, which is why the tombstone is
  compared by sequence rather than blocking all later events.
- **Same sequence, same payload.** Redelivery is normal (at-least-once). `ingest_ts` differs, so
  it must be excluded from the equality, and the retained copy must not depend on arrival order.
- **Same sequence, different payload.** Two sources claim the same version. Picking one silently
  (last arrival, `max(payload)`) makes the result order-dependent and hides a source bug.
- **Mutable payloads.** Returning internal dicts lets callers corrupt state.

## Alternatives

- **Append-only log + periodic compaction:** store every event, derive state with
  `ROW_NUMBER() OVER (PARTITION BY key ORDER BY sequence DESC)` / `QUALIFY`. More storage but fully
  replayable and auditable; this is the lakehouse "bronze to silver" shape.
- **Field-level merge** (partial updates) needs per-field versions, or events must be applied in
  order; a full-image payload keeps the operation commutative, associative and idempotent (a CRDT
  "last-writer-wins register" keyed on the sequence).

## Production notes

- Emit `conflict` and counts of `stale`/`duplicate` as metrics; a sudden rise in `stale` means a
  replay is running or a partition rebalanced.
- Merge into a table with `MERGE ... WHEN MATCHED AND src.seq > tgt.seq`: the predicate is the
  same rule, and makes a retried batch idempotent.
- Flink: keyed `ValueState<(seq, event)>` with state TTL for tombstones; Spark: `dropDuplicates`
  is not enough, use `mapGroupsWithState` or a Delta `MERGE` in `foreachBatch`.

1. How long do you keep tombstones, and what breaks if a replay is older than that horizon?
2. Sequences are per Kafka partition, and a key can move partitions. How do you get a total order?
3. Partial-update events (only changed columns): what do you need to keep the result
   permutation-independent?
4. 500 million keys: where does this state live (RocksDB / Delta table), and how do you rebuild it
