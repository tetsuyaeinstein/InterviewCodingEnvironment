# PY-036 · SCD2 application: explanation

## Approach (`PY-036.py`)

1. Validate and index dimension rows by customer (sorted by `effective_from`; the current row is
   the last and open-ended).
2. Sort the batch by `(change_ts, arrival)`.
3. For each change:

| situation | action |
|---|---|
| unknown attribute | reject `unknown_attribute` |
| no current row | create version 1 |
| `change_ts < current.effective_from` | reject `out_of_order` |
| merged attributes == current | no-op |
| `change_ts == current.effective_from` (and different) | reject `same_timestamp_conflict` |
| otherwise | close current at `change_ts`, append `version + 1` |

4. Emit rows sorted by `(customer_id, effective_from)`; rejected changes in arrival order.

Because the same timestamp closes the old row and opens the new one, the intervals are
half-open `[from, to)` and **adjacent**: no gaps, no overlaps, one current row. The test suite
checks these as *properties* on random batches (an invariant checker, not just examples).

- **Time:** O((n + m) log m); **memory:** O(n + m).

## Why the edge cases matter

- **Batch order.** Applying changes in arrival order closes a row at a *later* timestamp than the
  next change opens, so intervals overlap; sorting first makes the fold valid.
- **No-op detection.** CDC emits "touch" updates (row rewritten, nothing changed) all the time.
  Creating a version per touch explodes the dimension and breaks "number of changes" reports.
  Compare *merged* attributes, not just the supplied ones, since partial updates are common.
- **Out-of-order vs the published history.** Retroactive changes are the hard part of SCD2: either
  reject and alert (here), or rebuild the affected slice (split an existing interval in the
  middle, then re-close). A wrong silent insert here makes facts join to the wrong version.
- **Same instant, two values.** An empty interval `[t, t)` is invalid and ambiguous; the first
  wins and the rest is reported rather than silently dropped.
- **Half-open intervals** make point-in-time joins `from <= ts AND ts < to` correct without `-1
  second` hacks; open row = `NULL` (or `9999-12-31`, which breaks `BETWEEN` semantics when time zones differ).
- **Replay safety.** Re-applying the same batch to its own output changes nothing (changes
  older than the current row are rejected, equal ones are no-ops): the *dimension* is idempotent even
  though the rejection list is not empty.

## SQL / warehouse equivalent

```
MERGE INTO dim USING (staged changes, latest per customer per ts) s ON dim.customer_id = s.customer_id AND dim.is_current
WHEN MATCHED AND s.hash <> dim.hash THEN UPDATE SET effective_to = s.change_ts, is_current = false
-- followed by INSERT of the new version (the classic two-statement pattern, or the "union of NULL key" trick)
```

Delta/Snowflake/BigQuery have no single-statement SCD2: use the "stage rows twice" trick (once with
the real key to close, once with a NULL key to insert) or two statements in one transaction. A row
hash over tracked columns (PY-037) makes "did anything change" cheap.

## Production notes

- Run per customer ordered partition; late batches go to a repair job that re-derives the affected
  customers' full history from the change log (the log is the source of truth, the dimension is a
  projection).
- Add `dq` checks after each load: one current row per customer, no overlaps, no gaps, monotonic versions.
- Surrogate keys for facts are assigned at insert; closing a row never changes its key.
