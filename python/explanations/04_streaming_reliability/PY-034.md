# PY-034 · Checkpointed batches with crash recovery: explanation

## Approach (`PY-034.py`): idempotent sink + checkpoint last

Per batch `[start, end)`:

1. Compute rows and dead letters **in memory** (no side effects).
2. `sink.write(start, rows)`: batch id = first input offset; replace semantics.
3. `dead_letters.write(start, dead)`.
4. `checkpoint.save(end)`: the commit point.

| crash during | durable state | rerun does |
|---|---|---|
| steps 1 | old checkpoint, nothing new | recompute the batch |
| step 2 or 3 | old checkpoint, maybe rows for batch `start` | recompute, overwrite batch `start` (same id) |
| step 4 | old or new checkpoint (atomic cell) | either redo the batch (idempotent) or move on |
| after 4 | new checkpoint | continues with the next batch |

The invariant: **checkpoint ≤ what is durably in the sink**, so work is repeated but never skipped,
and repeated work is idempotent, so it is never doubled. "At-least-once processing + idempotent
sink = effectively-once output".

The test harness crashes before *and* after every single store call (and twice in a row) and
compares the final sink with an uninterrupted run.

## Why the edge cases matter

- **Checkpoint first** (the "optimistic" order) loses a whole batch if the write fails: the rerun
  starts past it. That is at-most-once, and it is silent.
- **`batch_id` as a counter** restarts at 0 in the new process, overwriting batch 0 and leaving a hole
  or duplicates. The id must be a function of *position in the source*.
- **Different `batch_size` on restart.** Because the id is the first offset and the batch always
  starts at the checkpoint, the stale partial batch at that id is replaced, whatever its old extent.
  Ids that "come from the future" cannot exist: nothing beyond the checkpoint's batch was ever written.
- **Input vs output counts.** A `flatMap` transform makes row counts unrelated to offsets; the
  checkpoint is always in *input* coordinates.
- **Poison records.** Dead-lettering needs absolute offsets for replay; a partially consumed
  generator must not leak rows. A non-`BadRecord` exception is a code bug: aborting the batch
  atomically and keeping earlier work lets a fixed deployment resume.
- **Checkpoint beyond the data** means the wrong source or a restored backup: failing loudly beats
  silently producing nothing.

## Alternatives

- **Transactional sink:** commit rows **and** the offset in one transaction (Postgres: `INSERT` +
  `UPDATE checkpoint` in one `BEGIN/COMMIT`; Delta/Iceberg: the commit carries the offset in table
  properties / `txnAppId, txnVersion`). No idempotency needed, but the sink must support it.
- **Idempotent by record key:** `INSERT ... ON CONFLICT DO NOTHING/UPDATE`, or `MERGE`. Works across
  batch-size changes and replays, but costs an index and needs stable, unique output keys.
- **Two-phase commit** (Flink `TwoPhaseCommitSinkFunction`, Kafka transactions): pre-commit at
  checkpoint barrier, commit when the checkpoint completes.

## Production notes

- Checkpoint = (offset per partition, state snapshot). Flink aligns barriers so state and offsets
  are consistent; Spark Structured Streaming keeps `offsets/` and `commits/` logs plus a
  `batchId`-addressed sink contract; Kafka Connect commits offsets after the sink's `flush`.
- Files: write to a temp name then rename (atomic, PY-026); name batch files by id for replace-semantics.
- Monitor checkpoint lag (source length - checkpoint) and the count of replaced batches (a rise = crash loops).
- Non-deterministic transforms (timestamps, random ids, external lookups) break "same batch, same rows".
  Make the rows a pure function of the input, or persist the planned batch before writing.
