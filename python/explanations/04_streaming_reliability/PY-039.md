# PY-039 · Duplicates versus conflicts: explanation

## Approach (`PY-039.py`)

1. Turn each payload into a **canonical string**: a tagged structure (`["num", "10"]`, `["str", "EUR"]`,
   `["map", [[key, value], ...sorted by key]]`, `["list", [...]]`) serialised with `json.dumps`.
2. Keep `seen[message_id] = {canonical: [first_payload, count]}`, in one pass.
3. Walk `sorted(seen)`:

| variants for the id | count | class |
|---|---|---|
| 1 | 1 | unique |
| 1 | >= 2 | exact duplicate |
| >= 2 | any | conflict (payloads in first-arrival order) |

- **Time:** O(total payload size). Each payload is canonicalised once; no pairwise comparisons.
- **Memory:** O(distinct (id, payload) pairs); store a hash (e.g. SHA-256 of the canonical string) instead of
  the string for huge payloads.

## Why the edge cases matter

- **Representation noise is not a conflict.** `Decimal("10.0")` from one producer and `10` from another
  describe the same amount; flagging it floods the quarantine. Conversely `True` vs `1` and `"1"` vs `1`
  are different facts and must not be merged. Python's `True == 1` and `hash(True) == hash(1)` make the naive
  `==`/`set` approach wrong for this.
- **Key order** is never meaningful in JSON; list order is.
- **Unhashable payloads** (lists, dicts) rule out `set(map(tuple, ...))` shortcuts: canonicalise instead.
- **`None` vs missing key** is a deliberate difference here: a producer that stops sending a field *has*
  changed the message. (PY-037 takes the opposite policy for fingerprints under schema evolution; know which one
  you are using and say so.)
- **Counting deliveries** gives you the redelivery rate per id, a useful health metric.
- **`decimal.normalize()` rounds** to the context precision (28 digits): strip zeros through `as_tuple()`.

## Alternatives

- **Hash instead of canonical text:** `sha256(canonical)` keeps memory flat; collisions are negligible but
  report the pair for conflicts using stored first payloads.
- **Sort + groupby:** `sorted(messages, key=(id, canon))`, then group. O(n log n) but streams from disk (external
  sort) when the batch does not fit in memory.
- **SQL:** `GROUP BY message_id HAVING COUNT(*) > 1` and `COUNT(DISTINCT md5(payload::jsonb::text))`; `jsonb`
  normalises key order but keeps `1.0` and `1` distinct inside numerics unless you cast.

## Production notes

- Dedup state has a horizon: ids repeat within minutes (redelivery) or within days (replays). Keep a keyed state
  with TTL (Flink `ValueState` + TTL, Kafka Streams window store) and document the horizon.
- Conflicts go to a dead-letter / quarantine table with *both* payloads and metadata (topic, partition, offset).
- Distinguish producer-side idempotence (Kafka `enable.idempotence`) from consumer-side dedup (PY-032).
- Batch-local classification only sees duplicates inside the batch; cross-batch duplicates need the stored state.
