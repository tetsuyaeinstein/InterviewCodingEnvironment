# PY-040 · Incremental streaks with late days: explanation

## Approach 1: sorted disjoint runs + binary search (`PY-040.py`)

Per customer: two parallel sorted lists `starts`, `ends` of day ordinals (disjoint, never adjacent).
For a new day `o`:

1. `i = bisect_right(starts, o) - 1` is the last run starting at or before `o`.
2. `ends[i] >= o` → **duplicate**.
3. `left = ends[i] == o - 1`, `right = starts[i+1] == o + 1`:

| left | right | action | kind |
|---|---|---|---|
| yes | yes | `ends[i] = ends[i+1]`, delete run `i+1` | bridge |
| yes | no | `ends[i] = o` | extend |
| no | yes | `starts[i+1] = o` | extend |
| no | no | insert `(o, o)` at `i+1` | new |

The invariants (disjoint and not adjacent) are exactly what makes the result equal to recomputing from
scratch. `longest` only grows (runs only merge or extend), so it is a running max.

- `add_purchase`: O(log r) search + a list insert/delete (a memmove in C; fine up to millions of runs per customer).
- `current_streak`: O(log r). `longest_streak`: O(1). `streaks`: O(r).
- **Never** re-scans the history. A "recompute on every event" version is O(n) per event, so O(n²) for a backfill.

## Approach 2: union-find over days (`PY-040_alt.py`)

Each distinct day is a node; adding day `d` unions it with `d-1` and `d+1` when present; each root stores the
run's `[start, end]`. All operations are dict lookups, O(α(n)) amortised. Trade-offs: memory is O(days) rather than
O(runs), and ordered listing needs a sort of the roots. Prefer it when you only need counts/lengths and the
"is this day known" check dominates; prefer the sorted-runs structure when you need range queries, ordered iteration or a
compact state.

## Incremental vs recompute: why the oracle test is the real specification

The correctness criterion is "equal to recomputing from scratch" (a gaps-and-islands query in SQL:
`date - ROW_NUMBER() OVER (PARTITION BY customer ORDER BY date)` grouped). The test uses that oracle on thousands of
random insertion orders, including duplicates, and also checks each returned change against the oracle's before/after
runs. This is the standard way to test any incremental / streaming algorithm: keep the naive batch version as the
reference.

## Why the edge cases matter

- **Bridge.** A late day that joins two runs must *remove* one run and fix the longest streak. Implementations that
  only handle "extend" leave two runs that should be one.
- **Duplicates** are the common case in at-least-once delivery and must be a no-op returning the run, so downstream
  campaigns are not triggered twice.
- **"Alive" semantics.** A streak ending yesterday has not broken yet (the customer may still buy today). Off-by-one here
  sends the "you lost your streak!" message a day early.
- **Truncation at `as_of`.** Late data about *future* days (relative to the report date) must not inflate an as-of report.
- **Calendar edges.** Leap days, month and year ends are why ordinals beat string/`timedelta` juggling; `date.max + 1`
  raises `OverflowError`.
- **`datetime` is a `date`.** Passing timestamps silently would create one "day" per instant.

## Production notes

- State per customer is small (runs, not events): store it in a keyed state store (Flink `MapState`/RocksDB, Redis
  hash, Kafka Streams KTable) and emit the `StreakChange` as an event for the campaign service. Because `before/after`
  is deterministic, the emitted event can be used as an idempotency key.
- Duplicates and reordering are absorbed by the structure itself (the operation is commutative and idempotent: a CRDT-like
  "set of days"), so no exactly-once machinery is needed for correctness (compare PY-031 / PY-032).
- Compact old state: runs older than the maximum allowed lateness never change again; keep only their length for the
  "longest" statistic.
- Removals (refunds) break monotonicity: a removal can split a run and reduce the longest streak, so you need either the
  per-day set (approach 2) plus a recomputation of the affected run, or a segment tree / balanced tree storing run lengths.
