# PY-048 · Bounded asyncio concurrency: explanation

## Approach 1: worker pool over a shared iterator (`PY-048.py`)

`limit` worker tasks each loop `for index, factory in source:`. Because `next()` on the shared
`enumerate` iterator never awaits, two workers can never receive the same item (asyncio is cooperative:
there is no preemption between `next()` and the assignment).

- **Structural limit:** exactly `limit` tasks exist, so concurrency cannot exceed `limit`. Memory is O(limit + results),
  and the input may be a lazy generator of millions of items.
- **Results by index**, then rebuilt in input order. Completion order is irrelevant.
- **Fail fast:** the first exception is recorded (first in *time*), the worker re-raises, `asyncio.wait(...,
  FIRST_EXCEPTION)` returns, and the `finally` cancels the other workers. Items nobody has pulled yet never start.
- **Collect mode:** workers swallow `Exception` into `results[index]` and carry on.
- **Cleanup in `finally`:** `cancel()` only *requests* cancellation. Awaiting the tasks afterwards runs their
  `finally`/`async with` blocks (closing connections, releasing locks) *before* we raise or return. Skipping the second step
  leaves "Task was destroyed but it is pending" warnings and leaked resources. The same `finally` handles **outer**
  cancellation of `gather_limited` itself, so the behaviour is identical.
- Note `CancelledError` is a `BaseException` since Python 3.8: `except Exception` does not swallow it, which is what we want.

## Approach 2: Semaphore (`PY-048_alt.py`)

One task per item, each wrapped in `async with semaphore`. Easy to read and the common answer, but:

- it creates all n tasks immediately (10 million items means 10 million tasks);
- cancellation must also reach tasks that are parked on the semaphore (handled by the same `finally`).

## Alternatives

- **`asyncio.TaskGroup` (3.11+):** structured concurrency does the cancel-and-await for you; first failure cancels
  siblings and raises an `ExceptionGroup` (use `except*`). Fine in new code, but the contract here is "raise the first exception itself".
- **`asyncio.Queue` + workers:** same shape as Approach 1, useful when items are produced concurrently (backpressure through `maxsize`).
- **`asyncio.timeout`/`wait_for`** per item to bound a stuck call: add it inside the factory, not here.

## Complexity

O(n) time; scheduling overhead per item is small (microseconds). Concurrency is bounded by `limit`; the choice of `limit` is
set by the downstream capacity (partner rate limit, DB pool size, file descriptors), not by CPU.

## Production considerations

- Match `limit` to the connection pool: 50 concurrent tasks with a 10-connection pool just queue inside the pool.
- Add a rate limiter (PY-047) in addition to a concurrency limit: concurrency caps in-flight requests, not requests per second.
- Per-item timeouts and retries belong in the factory; this helper only schedules.
- CPU-bound or blocking work does not benefit: `await` yields only at I/O. Use `asyncio.to_thread`/process pools for blocking calls.
- Log which items failed in collect mode and decide whether partial success is acceptable (dead-letter queue).
