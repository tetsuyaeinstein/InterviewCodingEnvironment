# PY-046 · Paginated REST consumption: explanation

## Approach: lazy generator + three safety nets

```text
token = None
loop:
    guard: pages requested < max_pages        # else PaginationLimitError
    page = client.get_page(token)
    yield each item whose id is new           # dedupe, first occurrence wins
    token = page.next
    stop if None; raise PaginationLoopError if token already requested
```

- **Lazy:** a generator pulls the next page only when the consumer has drained the current one, so a
  consumer that stops early costs no additional requests, and memory is one page plus the id set.
- **Termination is defined by the token, not by the content:** an empty page does not mean "end"; some APIs
  filter server-side after paginating, so pages can be sparse. Only `next is None` ends the walk.
- **Loop detection** (a set of requested tokens) catches repeating tokens of any cycle length. A
  `max_pages` cap is the backstop for *non-repeating* runaway pagination (a server that mints a new
  token forever). Both are needed: the set catches cycles quickly; the cap bounds everything else.
  Raising is better than silently stopping: a truncated import that looks successful is the worst outcome.
- **Dedupe by id** is required because offset-based APIs shift while data is inserted (a row moves from page 3 to
  page 2's boundary...) and so can repeat records. The opposite failure, *missing* records, cannot be repaired
  by the client at all: ask for a stable cursor (keyset, PY-044) or re-read with an overlap window.
  First-wins keeps behaviour deterministic; if records carry a version/updated_at, keep the max instead.
- **Order of operations** matters for observable behaviour: items of the page that carries a bad token are still
  delivered, because they are valid data.

## Complexity

O(n) time. Memory O(distinct ids + pages). At 100M records a Python set of ids is gigabytes: dedupe downstream in the
database (`ON CONFLICT DO NOTHING` on the business key) or use a Bloom filter / sorted-run merge if exact is not required.

## Production considerations

- Wrap `get_page` with timeouts, retries and backoff on 429/5xx (PY-047) *outside* this function so it stays pure.
- Persist the last successfully processed token so a restart resumes rather than starts over (tokens may expire: handle by restarting from a watermark).
- Prefer `updated_since` filters or change feeds over full re-pagination.
- Log pages, empty pages and duplicate counts: a rising duplicate ratio is an early sign that offset pagination is
  drifting under write load.
- Respect `Link`/`Retry-After` headers and rate limits; do not parallelise pages that depend on a previous token, but do parallelise across independent partitions.
