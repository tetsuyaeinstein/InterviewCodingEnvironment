# PY-044 · Keyset pagination: explanation

## Why not OFFSET

`OFFSET n` makes PostgreSQL produce and discard `n` rows, so page *k* costs O(k * page_size). It is
also **unstable**: if a row is inserted before your position between two requests, every later page
shifts by one and you either repeat or skip a row. Keyset ("seek") pagination remembers *where you
were*, not *how many you passed*.

## Approach 1: row-value comparison (`PY-044.py`)

```text
WHERE ... AND (transaction_ts, transaction_id) > (:ts, :id)
ORDER BY transaction_ts, transaction_id LIMIT page_size + 1
```

- The sort key must be **unique** or the cursor cannot identify a position. `transaction_ts` is not
  unique (customer 26's 2602/2603 share an instant; customer 64 has six rows at 05:00; guests 9801/9802),
  so `transaction_id` is the tiebreaker. A cursor of `ts` only with `>` skips the rest of a tie group; with `>=`
  it repeats the group forever (a page_size smaller than the tie group never advances).
- The row-value comparison is lexicographic, exactly like `ORDER BY a, b`, and can be satisfied by one
  index range scan on `(store_id, transaction_ts, transaction_id)`. The lab has `(store_id, transaction_ts)`;
  `transaction_id` as a trailing column makes the order fully index-supplied (no sort).
- `LIMIT page_size + 1` answers "is there another page?" without a `count(*)` or a trailing empty page.
- The cursor is a position, not a row id: it keeps working if that row is deleted.
- Cursors are best handed to HTTP clients as opaque, signed/base64 tokens so you can change the internals later;
  here they are plain tuples to keep the contract testable.

## Approach 2: OR-expanded predicate (`PY-044_alt.py`)

`(ts > :ts OR (ts = :ts AND id > :id))`: identical results, portable to SQL Server/Synapse and MySQL < 8.
Older planners could not use an index for the OR form as one range; PostgreSQL handles both
well in practice, but verify with `EXPLAIN`. Mixed-direction sorts (`ts DESC, id ASC`) cannot use a row
comparison at all and need the OR form (or negated keys).

## Complexity

O(log n + page_size) per page, independent of depth. Walking everything is O(n) total.

## Production considerations

- **Consistency:** keyset pages are consistent with respect to rows *after* the cursor, but rows inserted with an
  earlier key than the cursor are never seen by that walk. With late-arriving data (`ingested_at` > `transaction_ts`) paginate on a
  monotonic ingestion key (`ingested_at, id` or a sequence) for sync/export use cases.
- **Totals and "jump to page 37"** are not possible with keysets; offer search/filters instead, or a separate cached count.
- **Sorting by user-chosen columns:** append the primary key to any sort key and index accordingly.
- **Nullable sort keys:** NULLs break `>` comparisons; use `COALESCE` in both order and predicate, or avoid nullable keys.
- **Limits:** cap `page_size` (here 1000) so a client cannot ask for the world.

## Follow-up questions

1. The client wants descending order (newest first). What changes in the predicate and the index?
2. The API must remain correct while rows are inserted late with older timestamps. What key do you page on?
3. At 500 million rows, which index and which `EXPLAIN` features confirm a bounded scan per page?
4. How would you make the cursor opaque and tamper-evident?
