# PY-045 · ETL runner with injected dependencies: explanation

## Approach: one streaming loop, three injected callables

```text
for position, record in enumerate(extract()):
    row = transform(record)        # None -> filtered; exception -> quarantine / raise
    pending.append((position, row))
    if len(pending) == batch_size: flush()
flush()                            # final partial batch
```

- **Dependency injection instead of classes/inheritance.** Three plain callables (`Extract`,
  `Transform`, `Load`) are the interfaces. Unit tests pass lists and a list-appending sink; production passes
  a generator over `COPY`/pagination, a validator, and a database loader. You could equally define
  `typing.Protocol` classes when the components carry state (connections, clocks).
- **Streaming and bounded memory:** the loop holds only `pending`. A batch is flushed *as soon as it is
  full*, so peak memory is O(batch_size) and loaded data is committed incrementally (progress survives a crash).
- **Poison-row isolation:** when a batch fails, the runner assumes the sink is atomic per call and retries rows
  singly. This costs up to `batch_size` extra calls only for failing batches. Large production systems bisect
  (split the batch in halves) to find a single bad row in O(log n) calls; the one-by-one version is simpler and
  fine when failures are rare. Note it relies on `load` being atomic and idempotent per call.
- **`Exception`, not `BaseException`:** `KeyboardInterrupt`/`SystemExit` must stop the job.
- **`on_error="raise"`** is the fail-fast mode for development and for sources where any bad row means a
  broken upstream contract. Quarantine is for tolerant pipelines; add a *threshold* (abort if >1% bad) in real jobs.
- **Summary object** is the contract with monitoring: `read == filtered + loaded + quarantined` is the invariant
  you alert on. Return data, don't print or log inside the core.

## Idempotent reruns

The runner itself holds no state, so reruns are safe when the *sink* is idempotent: upsert by business key
(PY-043), `INSERT ... ON CONFLICT DO NOTHING`, or write-to-staging then swap partition. Do not try to make the runner
"remember" what it loaded; that state belongs next to the data, in the same transaction as the load.

## Complexity

O(n) time, O(batch_size) memory; load calls: n / batch_size (+ retries per failing batch).

## Production considerations

- Quarantined rows should land in a **dead-letter table or file** with run id, source offset, error and original payload, so they can be fixed and replayed.
- Load per-batch commits mean a half-loaded run is visible; use a run id / staging table and publish atomically if consumers cannot tolerate that.
- Backpressure and retries with backoff (PY-047) belong in the loader, around transient errors, not in the runner.
- Record the **source position** (file offset, cursor) per batch to resume instead of restarting.
- Parallelism: partition the source (by key range/file) and run several runners; keep the sink idempotent.

## Follow-up questions

1. How would you replace the one-by-one retry with bisection, and when is that worth it?
2. Add a failure threshold: abort the run when more than 2% of records are quarantined. Where does the check live?
3. The source is an at-least-once queue. What must change in `load` to be safe, and when do you acknowledge messages?
4. How would you add per-stage metrics (rows/sec, latency histograms) without coupling the runner to a metrics library?
