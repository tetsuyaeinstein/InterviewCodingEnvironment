# PY-041 · Parameterized lookup: explanation

## Approach 1: static SQL with named parameters (`PY-041.py`)

- **One SQL text, values bound separately.** psycopg 3 uses server-side binding, so values never
  become part of the statement text. Injection is impossible by construction, and the statement
  can be prepared and cached (psycopg auto-prepares after `prepare_threshold` executions).
- **Optional filter in SQL:** `(%(statuses)s::text[] IS NULL OR transaction_status = ANY(%(statuses)s::text[]))`.
  - The explicit `::text[]` cast is needed because a `None` parameter has no type.
  - An empty list becomes `'{}'`, so `ANY` is false and no rows come back. That is the correct
    semantics for "filter by no statuses".
- **Half-open UTC range on the raw column:** `transaction_ts >= start_utc AND transaction_ts < end_utc`.
  This is sargable: it can use `ix_transactions_customer` / a `(customer_id, transaction_ts)` index.
  Writing `transaction_ts::date BETWEEN ...` instead would apply a cast to every row, depend on the
  session timezone, and make `end` inclusive by accident.
- `dict_row` produces the required dict shape. `numeric` arrives as `Decimal` and `timestamptz` as
  an aware `datetime`.

## Approach 2: dynamic composition with `psycopg.sql` (`PY-041_alt.py`)

Build the `WHERE` list in code, adding only the conditions that are present.

- **Better for** search screens with many optional filters: the planner sees a simpler predicate
  and no `IS NULL OR` branches.
- **Cost:** the statement text varies, so there are more distinct prepared statements and plans.
- Identifiers that come from data (column/table names) must go through `sql.Identifier`, never
  string formatting.

## Why the tests use a spy connection

A query built with f-strings returns the right rows for honest input, so the behaviour tests alone
can't catch it. The spy records every `(query, params)` pair and asserts that no user value appears
in the SQL text. The hostile-input tests show what goes wrong otherwise: the status value would
widen the predicate, and `"26 OR 1=1"` would leak every customer.

## Scale-up / production questions

- **Connection handling:** in a web service use a pool (`psycopg_pool.ConnectionPool`). Set
  `statement_timeout` per role or per transaction, and use a read-only role for lookups (as this
  lab does).
- **Large results:** for millions of rows, stream with a server-side cursor
  (`conn.cursor(name=...)`) and `itersize` (PY-042), or paginate with keysets (PY-044). Avoid
  `OFFSET`.
- **Index:** `CREATE INDEX ON transactions (customer_id, transaction_ts)` turns the lookup into one
  index range scan, already in the order the query wants, with no sort.
