# PY-050 · Mini project (ingest, validate, dedupe, stage, summarise, reconcile): explanation

## Shape of the solution

```text
lines -> parse_line (pure) -> valid rows | Rejection(line, reason)
      -> dedupe by transaction_id (max sequence, later line on ties)   [pure, O(distinct ids)]
      -> daily_summary in Python (Decimal, UTC day)                    [pure]
      -> ONE transaction: CREATE TABLE IF NOT EXISTS; batched guarded upserts; SQL aggregate for the same ids
      -> compare dict == dict -> reconciliation_ok (strict: raise and roll everything back)
```

Everything except the last block is pure and unit-testable without a database. Separating the steps is the point:
interviewers look for functions with one job, a report object instead of print statements, and a clear boundary
where the transaction starts.

## Decisions worth explaining

- **Reason codes, not messages.** Rejections are data (`Rejection(line, reason)`): countable, alertable, and
  testable. Messages are for humans and change; codes are a contract. Real systems keep the raw line next to the code in a quarantine table.
- **Validation order is specified** so results are deterministic when a line has several defects.
- **Decimal end to end.** `json.loads(parse_float=Decimal)` turns `0.1` into `Decimal("0.1")` (not `0.1000000000000000055...`).
  Amounts are quantised to cents after checking that nothing was *rounded away* (more than 2 decimals is rejected, never rounded).
  `bool` is an `int` subclass in Python, so integer fields explicitly exclude it.
- **Aware timestamps only.** A naive timestamp has no instant; guessing a zone silently shifts revenue between days.
  Convert to UTC once, at the edge, and bucket with UTC dates (matching the database's `AT TIME ZONE 'UTC'`).
- **Two layers of idempotency.** *Within* the run: highest `sequence` wins. *Across* runs: the upsert is guarded by
  `WHERE t.sequence < EXCLUDED.sequence`, so replays and out-of-order files cannot move a row backwards, and re-running a file
  reports `upserted == 0, unchanged == n`. Without the guard "last write wins" lets a delayed old file clobber newer data.
- **Reconciliation is a real check, not a tautology.** The Python summary is computed from the input; the SQL
  aggregate reads what is *actually in the table*. They differ when rows were ignored by the guard, when a constraint/trigger
  altered data, or when the DDL types truncate values (try `numeric(12,0)`), which is exactly what such a check exists to catch.
  Restricting to this run's ids means other files' rows do not pollute the comparison.
- **One transaction** covers DDL, upserts, and the reconciliation read. PostgreSQL DDL is transactional, so even the
  table creation rolls back. In `strict` mode the exception raised inside `conn.transaction()` rolls everything back, so "failed
  reconciliation" never leaves partial data visible.
- **Stable lock order:** sorting winners by id avoids deadlocks between two concurrent loaders upserting overlapping ids.
- **Counts add up:** `rows_read == rejected + duplicates_dropped + upserted + unchanged` makes the report self-auditing.

## Complexity

O(n) parsing; dict-based dedupe O(n) time and O(distinct ids) memory; O(n / batch_size) statements.

## Scale-up (50 million lines)

- Stream the file in chunks; dedupe within a chunk, and let the database dedupe across chunks with the guarded upsert.
- Replace per-batch `INSERT ... unnest` with `COPY` into a **temp/unlogged staging table**, then one set-based `INSERT ... SELECT DISTINCT ON
  (transaction_id) ... ORDER BY transaction_id, sequence DESC, line DESC ... ON CONFLICT ... WHERE` (or `MERGE`). 5-20x faster.
- Reconcile in SQL for the whole run (per-day sums and counts on staged vs. source file loaded into another temp table) instead of
  an in-memory dict, and compare counts and hashes as well as sums.
- Quarantine rejected lines to a dead-letter table with run id and line number; set an acceptance threshold (e.g. abort if > 1% rejected).
- Record a **run ledger** (file name, checksum, line count, report) in the same transaction so a re-delivered file is recognised cheaply.
- Backfills: rerun by file/date range; the guard makes repetition safe. Partition `stg_txn` by day if you purge by retention.

## Library notes

psycopg 3 adapts Python lists to arrays and `Decimal` to `numeric`; `datetime` with tzinfo to `timestamptz`. On SQL Server/Synapse
use `MERGE` (with `HOLDLOCK`) or a staging table plus `UPDATE ... FROM` and `INSERT ... WHERE NOT EXISTS`.

## Follow-up questions

1. Two copies of the pipeline process overlapping files at the same time. Which guarantees remain, and what could deadlock?
2. A partner sends corrections *without* a sequence number. What can you use instead (event time, hash, source LSN), and what are the risks?
3. Finance wants store-local days. What changes in the summary, the SQL, and the reconciliation (DST)?
4. How would you expose this run report to monitoring, and which thresholds would page someone?
