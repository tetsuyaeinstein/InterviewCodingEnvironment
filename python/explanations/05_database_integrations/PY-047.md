# PY-047 · Rate limits and Retry-After: explanation

## Approach 1: server-directed retry (`call_with_rate_limit`)

- The server knows its own quota; **do what it says** (`Retry-After`) rather than guessing. Waiting
  *less* than asked gets you another 429 (and possibly a ban); waiting *more* wastes throughput.
  Hence "exactly".
- When the header is absent, fall back to **exponential backoff** (1, 2, 4, ...). In production add
  **jitter** (random 0-100% of the delay) so a fleet of workers that were all limited at the same moment does not
  retry in lockstep. We leave jitter out here only to keep the sleep sequence assertable; inject a `random` source if you add it.
- **Three budgets**, each protecting a different resource: attempts (bounded work), elapsed time (a thread/worker is not
  parked for an hour), and the decision not to sleep at all when the next wait already exceeds the budget (fail fast
  and let the scheduler retry later; don't sleep *then* fail).
- No sleep after the final failed attempt: sleeping and then raising is pure waste.
- **Only retry what is safe to retry:** here only `RateLimited` (the request was rejected before processing). A 500 or a
  timeout may have executed a non-idempotent write; retrying needs idempotency keys. Everything else propagates untouched.
- `Retry-After` can also be an **HTTP-date**; parse it in the HTTP layer into seconds (`date - now`) and raise `RateLimited(seconds)`.
- Injecting `sleep` and `clock` makes the whole schedule a pure, deterministic function: tests assert the exact sleep list
  and run in microseconds. Use `time.monotonic` (not `time.time`) in production: wall clocks jump.

## Approach 2: proactive limiter (`RateLimiter`)

Reacting to 429s is a recovery path; staying under the quota avoids them. A **sliding-window log** stores admission
times (O(max_calls) memory) and is exact. Alternatives:

| algorithm | memory | behaviour |
|---|---|---|
| fixed window counter | O(1) | allows 2x bursts at window boundaries |
| sliding window log (here) | O(N) | exact, no boundary bursts |
| token bucket | O(1) | allows controlled bursts up to the bucket size, smooth refill; what most APIs implement |
| leaky bucket | O(1) | perfectly smooth output rate |

The `while True` re-check after `sleep` matters: real sleeps can wake early, and other threads may have taken the slot
(add a lock for multi-threaded use; for asyncio use an `asyncio.Lock` or a semaphore-per-window).

## Complexity

O(attempts) per call. Limiter: amortised O(1) per acquire.

## Production considerations

- Share the limiter across workers: a quota is per API key, so per-process limiters over-admit by the number of processes.
  Use a central limiter (Redis, a token service) or divide the quota statically.
- Respect secondary headers (`X-RateLimit-Remaining`, `X-RateLimit-Reset`) to slow down *before* the 429.
- Emit metrics: count of 429s, total seconds slept, give-ups. A rising give-up rate is an alert.
- Treat budgets as part of the job's SLA: a nightly job with a 6-hour window may allow a much higher `max_total_wait`.
- Idempotency keys make retrying writes safe (see PY-043).

## Follow-up questions

1. Add jitter without making tests flaky. Where does the randomness come from?
2. 50 workers share one API key with 100 requests/minute. How do you divide or coordinate the quota?
3. The API returns `Retry-After` as an HTTP date. Where do you parse it, and what about clock skew between you and the server?
4. When is it better to fail the job than to wait, and how does the scheduler know to retry later?
