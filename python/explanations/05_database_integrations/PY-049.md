# PY-049 · Reconciling Python and SQL aggregates: explanation

## Approach: normalise both sides to `{(store, day): Decimal}` and diff

1. **Python side:** one pass, `defaultdict(Decimal)`, key `(store_id, ts.astimezone(UTC).date())`. Rows outside the stores,
   window or status are skipped. Type checks first: a `float` amount (0.1 + 0.2 != 0.3), or a naive timestamp (its day is
   ambiguous) must fail loudly instead of producing a plausible-looking number.
2. **SQL side:** one grouped query with bind parameters. Bucketing uses `(transaction_ts AT TIME ZONE 'UTC')::date`.
   `transaction_ts::date` converts using the *session* TimeZone, so the same query yields different days for a session
   in Auckland: the classic "works on my machine (UTC)" reconciliation bug. The window is expressed on the raw column
   (`>= start_utc AND < end_utc`) so the `(store_id, transaction_ts)` index can be used for the range.
3. **Diff by keys:** common keys compare totals (exact `Decimal` equality: no tolerance, because money is exact);
   one-sided keys are reported separately. A day missing on one side is a different failure class (lost file, failed load)
   from a total that differs by a cent (a rounding or double-count bug), so the report keeps them apart.
4. The report is a *value*: deterministic ordering makes it diffable, loggable and assertable.

## Why each corruption in the tests matters

| corruption | what it reveals |
|---|---|
| a day removed from the Python rows | `only_in_sql`: lost data |
| one amount off by 0.01 | `mismatches` with both totals: rounding / transformation bug |
| an extra row on a new day | `only_in_python`: phantom data |
| a duplicated row | mismatch: double load (so the check must not dedupe silently) |
| status flipped | disagreement about which rows count |
| timestamps in another offset | the UTC-normalisation step |
| session in another time zone | SQL-side bucketing independent of session settings |

## Complexity

O(n) Python; SQL is a range scan plus hash/sort aggregate. At warehouse scale push the aggregate into the database
on *both* sides (two `GROUP BY` queries, compared in Python) and compare **totals and row counts and a checksum** per day.

## Production considerations

- Reconcile **counts and sums** together: two offsetting errors can leave the sum unchanged.
- Compare only *closed* days: late-arriving rows (`ingested_at` after the day) make today's numbers legitimately differ.
  Use a watermark and an agreed lateness window.
- Persist the report (run id, window, per-key diffs), alert on `ok == False`, and rerun automatically after a
  backfill. Keep a tolerance policy only for derived/FX values, never for money in one currency.
- For big diffs use a per-day hash of sorted `(id, amount)` pairs on both sides and drill down only into differing days.
- Snapshot consistency: read both sides at one point in time (`REPEATABLE READ`), otherwise concurrent loads create false alarms.

## Library notes

`Decimal` sums are exact for any number of cents; `sum()` of floats is not. In pandas, `groupby().sum()` on a float column
reintroduces the problem: use integer cents or `decimal`.
