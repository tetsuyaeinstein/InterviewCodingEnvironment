# PY-042 · Streaming a large result set: explanation

## Approach: named cursor + `itersize` inside a transaction

- A normal psycopg cursor is **client-side**: `execute()` pulls the entire result into the driver
  (libpq) before you see row one, even if you then call `fetchone()` in a loop. Memory is O(n).
- `conn.cursor(name=...)` creates a **server-side cursor** (`DECLARE ... CURSOR`). The server keeps
  the result position; each `FETCH n` brings back `n` rows. Memory is O(batch).
- `cur.itersize = batch_size` controls how many rows `for row in cur` pulls per round trip
  (default 100). `fetchmany(batch_size)` in a loop is equivalent.
- A non-`WITH HOLD` cursor only exists inside a transaction, so wrap everything in
  `conn.transaction()`. When the generator is exhausted it COMMITs; when it is closed early,
  `GeneratorExit` unwinds through the block and psycopg ROLLBACKs, which also drops the cursor.
  The `with conn.cursor(...)` block issues `CLOSE` explicitly.
- Validation lives in a plain function that returns the generator, so `ValueError` is raised at
  call time rather than on the first `next()`.
- A unique cursor name per call avoids collisions when two streams share one connection.

## Why the tests look the way they do

Row-by-row output looks identical for `fetchall()` and for a real stream, so the tests observe
the mechanism instead: the spy checks that a *named* cursor was created, counts how many rows the
cursor handed over after the first `next()`, and the tests query `pg_cursors` and
`transaction_status` to prove cleanup (no leftover cursor, no idle-in-transaction connection).

## Complexity

O(n) time overall; O(batch_size) memory in the client. On the server the sort for `ORDER BY` is
needed once when the cursor is first fetched (there is an index on `transaction_ts`, so an index
scan can start returning rows immediately; with `ORDER BY transaction_ts, transaction_id` the planner
may still sort, so check the plan).

## Production considerations

- A long-running cursor holds a snapshot: vacuum cannot clean rows newer than it. Prefer short
  streams, or keyset pagination (PY-044) with a fresh transaction per page for very long exports.
- Set `statement_timeout`/`idle_in_transaction_session_timeout` for the role so a stalled consumer
  cannot hold the transaction forever. A slow consumer *is* a stalled consumer from the server's view.
- On a pooled connection (PgBouncer in transaction mode) named cursors work only within one
  transaction, which is exactly what we use. `WITH HOLD` cursors do not survive pool switching.
- Writing to a file? Stream into `COPY (SELECT ...) TO STDOUT` (`cur.copy`) for a 5-10x faster
  export when you do not need Python objects.
- Read replicas for exports: replication conflicts may cancel long queries (`max_standby_streaming_delay`).

## Library notes

`psycopg2` named cursors behave alike (`conn.cursor("name")`, `itersize`), but psycopg2 requires you
to manage the transaction yourself. psycopg 3's `ServerCursor` also supports `scrollable` and `withhold`.

## Follow-up questions

1. The consumer is slow (an HTTP upload per row). What does that do to the server, and what would you change?
2. How would you resume the export after a crash at row 40 million without restarting?
3. The result is 500 million rows: would you still use one cursor? Think snapshots, replicas, parallel range splits.
4. How do you measure the memory bound in a test without trusting `tracemalloc` on a shared runner?
