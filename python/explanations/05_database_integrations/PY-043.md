# PY-043 · Batched idempotent upserts: explanation

## Approach 1: dedupe in Python, `INSERT ... SELECT unnest(...) ON CONFLICT` per batch (`PY-043.py`)

1. **Collapse duplicates first.** `ON CONFLICT DO UPDATE` raises *"cannot affect row a second time"*
   if two proposed rows hit the same key in one statement. A dict keyed by `business_key` keeps the
   highest `seq` (later wins ties). Dropped rows count as `skipped`.
2. **Upsert with a version guard.** `DO UPDATE ... WHERE t.seq < EXCLUDED.seq` makes the operation
   *monotonic*: replays and late, older messages cannot move a row backwards. That is what makes
   the load idempotent *and* order-tolerant. Without the guard, "last write wins" lets a delayed
   retry overwrite newer data.
3. **Counting.** `RETURNING (xmax = 0)`: rows skipped by the `WHERE` are not returned at all;
   returned rows are inserts (`xmax = 0`) or updates. `skipped = total - inserted - updated`.
   The `xmax` trick is an implementation detail of MVCC, not a documented contract: it is widely used
   and fine for reporting, but do not build correctness on it. A portable alternative is a
   `RETURNING (SELECT ... )` against a pre-read, or `MERGE ... RETURNING merge_action()` on PostgreSQL 17.
4. **Atomicity.** `with conn.transaction()` wraps all batches. If batch 3 fails, batches 1 and 2 roll
   back with it. The alternative, a commit per batch, trades atomicity for shorter transactions;
   it is acceptable only when the upsert is idempotent and the job can resume (be explicit about it).
5. **Safe identifiers.** The table name is composed with `sql.Identifier`, which quotes it, so a
   hostile name becomes "table not found", never an injected statement. Values are bind parameters.
6. **One round trip per batch** by sending columns as arrays and unnesting server-side.

## Approach 2: `executemany(returning=True)` (`PY-043_alt.py`)

Row-shaped parameters, no array juggling. psycopg 3 uses pipeline mode so the network cost is
modest, but each row is still a separate statement execution on the server, and you iterate result
sets with `nextset()`. Fine up to tens of thousands of rows.

## Approach 3 (scale-up): COPY into a temp table, then one set-based statement

`CREATE TEMP TABLE stage (LIKE target) ON COMMIT DROP; COPY stage FROM STDIN;` then
`INSERT ... SELECT DISTINCT ON (business_key) ... ORDER BY business_key, seq DESC, ordinal DESC
ON CONFLICT ... WHERE`. COPY is typically 5-20x faster than any INSERT form, and the dedupe moves into SQL.
On PostgreSQL 15+ `MERGE` expresses the same with explicit `WHEN MATCHED AND ... THEN UPDATE`.

## Complexity

O(n) in Python, O(n log n) or O(n) index probes in the database; round trips O(n / batch_size). Large
batches reduce overhead but lengthen lock hold times on hot keys and bloat the transaction; 500-5,000 rows is a sane range.

## Production considerations

- **Idempotency key vs. version guard:** the business key + monotonic `seq` is a natural idempotency
  scheme. If the source has no version, use a content hash or `source_lsn`, and store `ingested_at` for audit.
- **Dead tuples:** `DO UPDATE` with an unchanged value still writes a new row version if the guard passes;
  add `AND (t.amount, t.status) IS DISTINCT FROM (EXCLUDED.amount, EXCLUDED.status)` to avoid no-op updates (bloat, WAL).
- **Deadlocks:** concurrent loaders touching the same keys in different orders can deadlock; sort rows by key within a batch.
- **Poison rows:** all-or-nothing means one bad row fails the file. Validate and quarantine upstream (PY-045/PY-050) rather than relying on the database to reject.
- **Backfills:** run in key ranges, commit per range, record progress in a control table; the guard makes re-running a failed range safe.

## Library notes

psycopg2: `execute_values(cur, "INSERT ... VALUES %s ON CONFLICT ...", rows)`. SQL Server / Synapse
have no `ON CONFLICT`; use `MERGE` (with `HOLDLOCK`) or stage + `UPDATE`/`INSERT`.

3. Switch to COPY for 50 million rows: where does dedupe happen and how do you count inserted/updated?
