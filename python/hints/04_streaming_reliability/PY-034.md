## Hint 1
Think of three states a crash can leave behind: "nothing written", "output written but checkpoint old", "everything written". Which of them can the rerun recover from if it simply starts at the saved checkpoint? Which order of the three durable calls makes the *bad* state (checkpoint ahead of the output) impossible?

## Hint 2
The checkpoint is the commit point, so it goes last. A crash before it means the same batch is processed again: for that to be harmless the sink write must be repeatable. Your sink replaces a batch when it sees the same `batch_id`, so the id has to be something that is identical on the rerun, and not a counter that restarts at zero in the new process.

## Hint 3
Use the batch's first input offset as the id: after a restart the batch starts at the checkpoint, so it gets the same id and overwrites the half-written one, even when the new `batch_size` differs. Build rows and dead letters in memory first, materialising each record's rows with `list(...)` inside the `try` so a `BadRecord` raised mid-generator drops everything that record produced. Advance by input positions (`end`), never by the number of rows.
