## Hint 1
Redelivery detection needs durable memory of what you have already processed, and that memory must live in the same place as the balances. Think about what is stored per event_id besides "seen".

## Hint 2
The dangerous design is two writes: "mark processed" then "update balance" (or vice versa). Whichever order you pick, a crash between them loses or duplicates the effect. Your store has one atomic primitive; build a dict containing *both* the marker and the new balance and hand it over in a single call.

## Hint 3
Store a small record under a marker key (account, amount, outcome) so that a redelivery can be classified: same fingerprint → duplicate, different → `ConflictingEvent`. Use distinct key prefixes for markers and balances. Rejections must also write a marker (with no balance change), otherwise the same withdrawal would be re-evaluated later against a bigger balance. Do not cache anything in the object.
