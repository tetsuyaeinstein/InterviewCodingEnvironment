## Hint 1
Per customer only the *last* row matters when applying a change, because the history before it is frozen. Group the dimension rows by customer first and keep each list ordered by `effective_from`; the current row is the tail.

## Hint 2
Sort the batch by `(change_ts, arrival index)` and fold it one change at a time against the customer's tail row. After sorting, the question "is this change older than the current version?" only fires for history that existed before the batch. Compute the merged attributes first, then compare with the current ones to decide no-op vs new version; this also makes a replayed change harmless.

## Hint 3
Close the old row with `effective_to = change_ts` and open the new one with `effective_from = change_ts` using the *same* timestamp object, so that intervals touch exactly with no overlap or gap. Remember the rejection ordering: unknown attribute first, then out-of-order, then (only if something actually changes) the same-timestamp conflict. Record the arrival index of rejected changes so the report can be sorted back into arrival order. Copy rows before editing: the inputs must stay untouched.
