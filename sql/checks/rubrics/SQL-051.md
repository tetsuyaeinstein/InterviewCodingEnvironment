# SQL-051 rubric · interpreting EXPLAIN (ANALYZE, BUFFERS)

Self-assess: tick each point your own notes covered **before** you read this. A strong senior answer
covers at least 8 of the 11. The plan on the small seed typically looks like this (yours may
differ slightly):

```
Incremental Sort  (rows=16) (actual rows=24)
  Sort Key: transaction_ts, transaction_id   Presorted Key: transaction_ts
  ->  Index Scan using ix_transactions_ts on transactions  (rows=16) (actual rows=24)
        Index Cond: (transaction_ts >= ... AND transaction_ts < ...)
        Filter: (customer_id = 1001 AND transaction_status = 'COMPLETED')
        Rows Removed by Filter: ~676
        Buffers: shared hit=~21
```

## Access path

- [ ] **Reads bottom-up**: names the leaf node (Index Scan or Bitmap Heap/Index Scan) and the index
      it uses, then the node above it.
- [ ] **Index Cond vs Filter**: only the time range is in `Index Cond`; customer and status are a
      `Filter` that runs after each heap row is fetched. `Rows Removed by Filter ≈ 680` for 24
      returned rows means about 97% of the work was wasted.
- [ ] **Why this index**: the planner had two single-column choices. `ix_transactions_customer`
      gives selectivity (about 530 rows for 1001, across 2 years). `ix_transactions_ts` gives
      December (about 700 rows) **and** the row order for the ORDER BY. The table is loaded in
      time order (high physical correlation for `transaction_ts`), which makes the time index
      cheap to follow. Says that the choice can flip between the two with different statistics
      or month sizes, and that a Bitmap Heap Scan (customer index, then recheck of the range) is
      the other plausible plan.
- [ ] **At 500M rows**: the same plan reads every December row of every customer (about 20M rows)
      to return a few hundred. A single-column index on `customer_id` alone is no better for the
      heavy account: it reads all of the customer's history across all months.

## Estimates

- [ ] **Estimated vs actual**: compares `rows=` (estimate) with `actual ... rows=` per node, for
      example 16 vs 24. Close enough: the plan choice is not driven by a misestimate here.
- [ ] **Where the estimate comes from**: the most-common-values list in `pg_stats` (1001 is the top
      MCV, about 2.5% of rows), the histogram for the time range, and the status MCV, multiplied as
      if independent. Mentions that correlated predicates make that product wrong (extended
      statistics, `CREATE STATISTICS ... (dependencies, mcv)`, help for equality combinations) and
      that `ANALYZE` must be recent.
- [ ] **loops**: reads per-node numbers as per-loop values (multiply by `loops` for nested loops).

## Sort

- [ ] **Incremental Sort / Presorted Key**: the index already returns rows in `transaction_ts`
      order. Only rows that share a timestamp need sorting by `transaction_id`. Memory is tiny
      (`quicksort`, KB), so it never spills. A full `Sort` with `external merge` would mean
      `work_mem` was exceeded.

## Buffers and timing

- [ ] **Buffers**: `shared hit` = 8 kB pages found in PostgreSQL's buffer cache. `read` = pages
      requested from the OS (page cache or disk). Counts on a parent node include its children.
      Planning has its own buffers (catalog lookups). Pages, not rows, are the real I/O cost: about
      20 pages for 24 rows; the time-ordered heap keeps that low here, a scattered heap would not.
- [ ] **Timing is not evidence**: one run on a warm 21k-row table says nothing. Repeat runs, look at
      buffers and rows, and remember that `EXPLAIN ANALYZE` executes the statement (wrap DML in
      `BEGIN ... ROLLBACK`) and adds timing overhead (`TIMING OFF` for per-row-heavy plans).

## Proposal

- [ ] **Index proposal with column order**: `(customer_id, transaction_ts)`: equality column first,
      then the range/sort column, so the index narrows to exactly one customer-month **and** returns
      rows in order. Better still `(customer_id, transaction_ts, transaction_id)` to remove even the
      incremental sort. Optional refinements, each with its trade-off:
      - partial `WHERE transaction_status = 'COMPLETED'` (smaller; only for queries that repeat that predicate);
      - `INCLUDE (store_id, gross_amount)` for an index-only scan (bigger; needs a fresh visibility map);
      - replacing the now-redundant `ix_transactions_customer`.
      Mentions write amplification (every insert maintains one more B-tree), build with
      `CREATE INDEX CONCURRENTLY` in production, and verifying the new plan with the same
      EXPLAIN (SQL-053 lets you try it in a sandbox).

## Red flags (subtract a point each)

- Proposing an index on `transaction_status` (4 distinct values) or one index per column.
- Claiming "the query is fast, 0.3 ms" as the conclusion.
- Wrapping `transaction_ts` in a function to get "December" (kills the index range; see SQL-052).
