# SQL-052 rubric · sargable predicates

The result and the plan facts are graded automatically. Use this list to check that you can
**explain** the rewrite the way an interviewer expects. Strong answers cover at least 6 of 8.

- [ ] **Defines sargable**: a predicate the index can use to *search* (seek to a start key and
      scan to an end key). `column op constant` qualifies. `f(column) op constant` does not,
      because the B-tree is ordered by `column`, not by `f(column)`.
- [ ] **Explains why the cast hurts**: `transaction_ts::date` (or `date_trunc('day', ...)`)
      has to be computed for **every** row before it can be compared, hence the Seq Scan. Also
      mentions the estimate: an expression without statistics gets a default selectivity
      (often 0.5% for `=`), so even the row estimate is a guess.
- [ ] **Half-open bounds**: `>= day start AND < next day start`. Explains why
      `BETWEEN '2025-02-28' AND '2025-02-28 23:59:59'` is wrong (loses 23:59:59.5; timestamps have
      microsecond precision) and why `<= '2025-03-01'` is wrong (includes the midnight row, fixture
      txn 5302).
- [ ] **Time-zone dependence**: the original `::date` cast and an untyped `'2025-02-28'` literal both
      use the session `TimeZone`. Writing `TIMESTAMPTZ '2025-02-28 00:00:00+00'` pins the bounds.
      For a store-local day, compute the bounds from the local date
      (`(DATE '2025-02-28')::timestamp AT TIME ZONE 'America/Phoenix'`). That keeps the column bare
      and the predicate sargable.
- [ ] **Reads the new plan**: `Index Scan` (or `Bitmap Index Scan` + `Bitmap Heap Scan`) on
      `ix_transactions_ts` with the bounds in `Index Cond`. Status stays a `Filter`.
      Rows read ≈ rows in the day, not the table.
- [ ] **Knows the alternative and its cost**: an expression index
      `CREATE INDEX ON transactions (((transaction_ts AT TIME ZONE 'UTC')::date))` makes the old
      predicate indexable. Note that it must be built on an IMMUTABLE expression:
      `transaction_ts::date` on a timestamptz is only STABLE (it depends on TimeZone), so
      PostgreSQL rejects it. The cost is one more index to maintain, and it only helps queries
      written with exactly that expression.
- [ ] **Generalises**: the same rule applies to `lower(email) = ...`, `amount * 1.1 > ...`,
      implicit casts in joins (`text_col = int_col`), `COALESCE(col, x) = y`, and leading-wildcard
      `LIKE '%abc'`. Each needs a rewrite or a matching expression/trigram index.
- [ ] **At 500M rows**: a one-day read touches roughly 1/730 of the table. The Seq Scan reads all of
      it, and with partitioning the cast also blocks partition pruning (SQL-059). In Synapse/Spark
      the same rewrite is what enables partition and rowgroup/file elimination (min/max stats).

## Red flags

- "Add an index on transaction_ts". It already exists; the predicate was the problem.
- `transaction_ts >= '2025-02-28' AND transaction_ts <= '2025-02-28 23:59:59.999'`.
- Fixing it with `SET enable_seqscan = off`.
