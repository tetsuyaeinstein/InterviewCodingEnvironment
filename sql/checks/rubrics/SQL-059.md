# SQL-059 rubric · partition pruning

Automatic checks prove that only `fact_sales_p2025_12` is scanned. Use this list to check the
explanation behind it. Strong answers cover at least 6 of 8.

Reference plan (small seed):

```
HashAggregate  (Group Key: store_id)
  ->  Seq Scan on fact_sales_p2025_12 fact_sales_partitioned  (actual rows=3969)
        Filter: ((sale_date >= '2025-12-01') AND (sale_date < '2026-01-01'))
```

Note that the filter is still shown on the surviving partition: pruning removes *whole*
partitions, the `Filter` is the row-level predicate inside the one that remains (here it is
redundant because the partition bounds already imply it; PostgreSQL does not drop it).

## How pruning works

- [ ] **Compares predicate with partition bounds**: the planner proves from `sale_date >= a AND sale_date < b`
      that partitions whose range does not overlap `[a, b)` cannot contain matching rows, and
      leaves them out of the plan. Needs the predicate to be on the **partition key column** compared
      with a value the planner can evaluate (constant, immutable/stable expression, or parameter).
- [ ] **Plan-time pruning**: constants and immutable expressions (`DATE '2025-12-01'`, `make_date(...)`)
      are folded when the statement is planned: pruned partitions never appear in `EXPLAIN`.
- [ ] **Run-time (executor) pruning**: with a **stable** expression (`CURRENT_DATE - 30`), a bind
      parameter (`$1`, prepared statements with a generic plan), or a nested-loop join key, the
      planner cannot decide yet. The plan keeps every partition under the `Append`, and the executor
      prunes at start-up ("initial pruning", shows `Subplans Removed: N`) or per outer row ("run-time
      pruning", `(never executed)` on subplans). Controlled by `enable_partition_pruning`.
- [ ] **Prepared statements**: the first five executions use custom plans (pruned at plan time with
      the actual parameter); after that PostgreSQL may switch to a generic plan, which relies on
      executor pruning. `plan_cache_mode` forces one or the other. Knows that `EXPLAIN` of a
      generic plan shows all partitions plus `Subplans Removed`.

## Why the original filter cannot prune

- [ ] **`to_char(sale_date, 'YYYY-MM') = '2025-12'`** applies a function to the key. Partition bounds
      are expressed on `sale_date` itself, and the planner has no way to invert `to_char`, so the
      predicate is opaque. Result: an `Append` over all 25 partitions, each with a `Filter`
      evaluated row by row (full scan of 500M rows at scale).
      The same holds for `date_trunc('month', sale_date) = ...`, `extract(year ...)`,
      `sale_date::text LIKE '2025-12%'`, and implicit casts that wrap the column.
- [ ] **Fixes**: bare-column range (this exercise); for a month parameter compute the bounds from
      the parameter (`$1::date`, `$1::date + interval '1 month'`, which are stable and prune at
      execution time); or partition on an expression and use the same expression in queries
      (rarely worth it).

## Design costs and limits

- [ ] **Partitioning is not a free index**: more partitions mean higher planning time (hundreds are
      fine, thousands are not), more locks per query, and a primary key must include the partition key
      (`(sale_date, transaction_id, line_number)` here). Unique constraints cannot span partitions otherwise.
      Too-small partitions (daily on small data) or too-large (yearly) lose most of the benefit.
- [ ] **Maintenance wins**: `DROP`/`DETACH PARTITION` for retention instead of a huge `DELETE`,
      `VACUUM`/`ANALYZE`/index builds per partition, bulk load into a staging table then
      `ATTACH PARTITION`. Mentions the default partition risk: rows that match no partition pile up
      there (and a new partition cannot be created until its rows are moved out), and the default
      is scanned unless the query's bounds exclude it (it was pruned here).

## Red flags

- Naming the partition directly (`FROM fact_sales_p2025_12`): works once, breaks on the next month,
  and bypasses the contract of the parent table.
- "Add an index on sale_date" as the fix.
- Believing `EXPLAIN` listing all partitions always means no pruning (it can be executor pruning),
  or that a surviving `Filter` means pruning failed.
