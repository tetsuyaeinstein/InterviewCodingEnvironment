# SQL-054 rubric · skew and distribution keys

The numbers (small seed; shares hold at every size because the skew is generated by design):

| key | rows | share |
|---|---:|---:|
| store 6 (online flagship) | 3,487 | 16.40% |
| store 1 | 1,276 | 6.00% |
| customer 1001 | 529 | 2.49% |
| guest bucket `NULL` | 302 | 1.42% |
| typical top-10 customer | 70-72 | 0.34% |

A perfectly even spread over 60 distributions gives each **1.67%**. Self-assess your RATIONALE:
a strong answer covers at least 7 of the 9 points.

## Reading the numbers

- [ ] **Compares with the fair share**: 100% / 60 = 1.67% per distribution. `store_id` is far
      worse: store 6 alone is ~10x a fair share, so one distribution holds 16% of the table
      (plus whatever else hashes there) and the other 59 hold ~1.4% each.
- [ ] **Explains the consequence**: a distributed query finishes when its **slowest** distribution
      finishes. With 16% on one node, scans, aggregations and joins on `store_id` run at the speed
      of one node (roughly 10x slower than perfect), memory pressure and tempdb spills appear
      there first, and adding more DWUs does not help (it adds distributions, not speed for the
      hot one). Spark: one straggler task in the shuffle stage, long tail, spill or OOM; AQE skew
      join settings help but do not remove the root cause.
- [ ] **Customer key is better but not clean**: top key 2.49% (about 1.5x a fair share) is
      tolerable on its own; the problem items are customer 1001 and the NULL bucket (1.42%).
      Concludes sensibly (for example "customer_id is acceptable if NULLs are handled", or
      "neither is ideal for a fact table: use a high-cardinality surrogate such as
      transaction_id unless joins demand otherwise").

## NULL keys

- [ ] **Hash(NULL) is one value**: every guest row lands on the same distribution/partition.
      Joins on a NULL key never match anyway (NULL = NULL is unknown), so these rows are
      shuffled for nothing. Mentions Synapse's behaviour (NULLs hash to one distribution)
      and Spark's null-key partition.
- [ ] **Policy**: split the null path (filter NULLs out of the keyed join and handle them
      separately, then UNION), or assign a surrogate that spreads them
      (`COALESCE(customer_id, -abs(hash(transaction_id) % 1000))` as a salted pseudo-key, plus a
      flag that it is not a real customer). Documents the decision and how consumers must treat it.

## Mitigations with trade-offs (at least two)

- [ ] **Choose a different distribution key** for the fact: high cardinality, even (a surrogate
      like `transaction_id`), accepting that joins on `customer_id` or `store_id` need shuffles
      (data movement) at query time. The key should also match the most frequent join/group key;
      "even" alone is not enough.
- [ ] **Salting** hot keys: add a random suffix 0..N-1 to the hot key (store 6, customer 1001),
      aggregate partially per salted key, then merge in a second stage. Trade-off: more complex
      code, joins need the dimension replicated N times for the hot keys only.
- [ ] **Replicate / broadcast small dimensions** (`stores` has 40 rows, `products` 200): turns a
      shuffle join into a local join, so the fact's key can be chosen for evenness.
      Trade-offs: replicated tables are rebuilt after every change and cost memory per node;
      broadcast threshold limits in Spark.
- [ ] **Other valid ideas**: round-robin staging then CTAS into the final distribution; isolating
      the flagship store in its own table/partition; pre-aggregation before shuffle (map-side
      combine); skew-join hints/AQE; monitoring with `sys.dm_pdw_nodes_db_partition_stats`
      (rows per distribution) or Spark UI task-duration quantiles.

## Red flags

- Choosing `store_id` because it is a "natural" dimension key.
- "Use more partitions/DWUs" as the whole answer.
- Dropping NULL customers silently without saying so.
- Confusing **partitioning** (pruning/maintenance, e.g. by month) with **distribution**
  (spreading rows over compute nodes).
