# SQL-053 rubric · composite index column order

Automatic checks enforce the outcome (index scan, `customer_id` leading the `Index Cond`, no Sort,
no Seq Scan). The rubric checks that you can **justify** it. Strong answers hit at least 7 of 9.

Reference plan (index `(customer_id, transaction_ts)`):

```
Limit  (actual rows=20)
  ->  Index Scan using ix_txn_copy_cust_ts on txn_copy  (actual rows=20)
        Index Cond: ((customer_id = 1001) AND (transaction_ts >= ...) AND (transaction_ts < ...))
        Buffers: shared hit=~13
```

## The rule

- [ ] **Equality columns first, then the range / sort column.** Within one `customer_id` the index
      entries are sorted by `transaction_ts`, so the quarter is one contiguous slice and its order
      is the ORDER BY order.
- [ ] **Why no Sort node**: the index provides the ordering. Says that this only works because the
      leading column is pinned by `=`. With `customer_id` as a range or `IN (...)` list the order
      across customers would not be time order and a Sort (or a merge of several index scans)
      comes back.
- [ ] **LIMIT 20 stops early**: the scan reads about 20 index entries, not the whole quarter.
      `actual rows=20` on the scan node, instead of 50 rows read then sorted (top-N heapsort) is
      the visible proof. At 500M rows with a customer that has millions of rows in the quarter,
      this is the difference between microseconds and seconds.

## The other orders

- [ ] **`(transaction_ts, customer_id)`**: the plan also shows an Index Scan and no Sort (the index
      is in time order), but `Index Cond` lists `transaction_ts` first: the scan walks **every
      customer's** rows from 2025-04-01 and filters on `customer_id` inside the index, until it has
      found 20 of customer 1001's. On the small seed the heavy customer is dense enough that it
      looks fine. For an average customer with 40 rows a year it would read most of the quarter
      (millions of entries at 500M rows). Says that `LIMIT` + a selective predicate on a
      non-leading column is the classic trap, and that "the plan looks the same" is not evidence;
      the `Index Cond` line and `Buffers` are.
- [ ] **`(customer_id)` alone**: Bitmap Index Scan (529 entries) + Bitmap Heap Scan (about 180
      heap pages) + Sort. Rows are fetched and sorted before LIMIT can cut anything. Works for
      small customers, scales with the customer's whole history.
- [ ] **No index**: Seq Scan (every page of the table) + top-N heapsort.

## Refinements and costs

- [ ] **Covering / partial / tie-break variants**: `INCLUDE (store_id, gross_amount)` allows an
      Index Only Scan (`Heap Fetches` shrink only after VACUUM updates the visibility map; bigger
      index, more write cost). A third key column `transaction_id` gives a deterministic ORDER BY
      without a sort. `WHERE transaction_status = 'COMPLETED'` partial index shrinks it if every
      query has that predicate.
- [ ] **What the index costs**: one more B-tree to maintain on every insert, HOT updates lost if
      indexed columns change, extra WAL and buffer cache. Can it replace `ix_transactions_customer`?
      (Yes: it serves every `customer_id =` query. Check `pg_stat_user_indexes.idx_scan` first.)
- [ ] **Production rollout**: `CREATE INDEX CONCURRENTLY`, lock behaviour, an INVALID index left
      after failure, `maintenance_work_mem`, building per partition and attaching on a partitioned
      table.

## Red flags

- "Put the more selective column first" as a universal rule. Equality-before-range is the rule;
  selectivity only orders columns **within** the equality group.
- Creating three single-column indexes and hoping for a bitmap AND.
- Using `SET enable_sort = off` or `enable_seqscan = off` to force the plan without having an index
  that supports it.
