# SQL-036 · Daily product availability snapshot from interval history

**Topic:** dimensional modeling · **Level:** medium · **Interview time:** ~30 min · **Mode:** modeling (query + written rationale)

## Business context

Store availability is stored as **interval history**: one row per period during which a product's
status was constant. Merchandising wants a **daily snapshot fact**, one row per day per product,
so BI tools can chart availability without interval logic. Two teams disagree on the definition:
operations says "available today" means it could be sold at **any moment** of the day; the
replenishment team says it means **the status at the end of the day**. You must deliver both
(plus the minutes available) and explain, in the rationale block, which definition serves which
question and what you would store in the warehouse.

## Source tables

| table | grain | columns you need |
|---|---|---|
| `store_product_availability` | one row per status period | `store_id`, `product_id`, `valid_from`, `valid_to` (timestamptz), `available` (boolean) |
| `products` | one row per product | `product_id` |

Periods are half-open `[valid_from, valid_to)`; `valid_to IS NULL` means open-ended. Periods of
one product never overlap. **Any instant covered by no row means the product is not stocked, which
counts as unavailable.**

## Requirements

1. Scope: store **2**, products **4, 5 and 6**, UTC days **2025-05-09 … 2025-05-12** inclusive.
   Output exactly one row per day per product (12 rows), even if the product has no row at all that day.
2. `available_any_time`: true if some instant of the UTC day `[D 00:00, D+1 00:00)` is covered by
   a row with `available = true`.
3. `available_end_of_day`: status at the last instant of the day, i.e. 23:59:59.999999 (just before
   the next midnight). Covered by an `available = true` row means true; unavailable or uncovered
   means false. A period that starts exactly at the next midnight does not count.
4. `available_minutes`: total minutes of the day covered by `available = true` rows (numeric,
   rounded to 2 decimals; a full day is 1440).
5. Write your reasoning in the `-- RATIONALE:` block at the end of the file (at least 30 words):
   which measure answers which business question, what each one hides, how you treated uncovered
   time, and what you would persist in the snapshot fact.

## Output contract

| column | type | notes |
|---|---|---|
| `snapshot_date` | date | UTC day |
| `product_id` | integer | |
| `available_any_time` | boolean | |
| `available_end_of_day` | boolean | |
| `available_minutes` | numeric | 0 … 1440 |

Ordering: none required.

## Illustrative example (not the real data)

Product 901 history: available until 08-01 18:00, unavailable `[18:00, 08-02 06:00)`, available again after.

| day | any_time | end_of_day | minutes |
|---|---|---|---|
| 08-01 | true | false | 1080 |
| 08-02 | true | true | 1080 |

## Edge cases you must handle

- Intervals that start or end exactly at midnight, and one starting exactly at the next midnight.
- Outages wholly inside a day that no end-of-day check can see.
- Uncovered (not stocked) stretches, including a whole day with none at all.
- Several history rows within one day for one product.

## Constraints

- One read-only `SELECT` / `WITH` statement, PostgreSQL 17, plus the rationale comment block.

## Clarify before you code (what a strong candidate asks)

- Which time zone defines the day (store-local or UTC)?
- Is "not stocked" the same as "out of stock"?
- Which downstream question is this snapshot for: sales validation, replenishment, or KPI?
