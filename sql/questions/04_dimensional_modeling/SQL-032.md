# SQL-032 · Data-quality audit of the customer SCD2 dimension

**Topic:** dimensional modeling · **Level:** medium · **Interview time:** ~25 min · **Mode:** query

## In plain words

> "Audit our customer history table and give me one row for every defect you find: overlapping versions, and wrongly flagged current or non-current versions."

**You return:** one row per finding: `customer_id`, `issue_type`, `customer_sk`, `other_customer_sk`, `overlap_from`, `overlap_to`. Clean customers give no rows.

**The fine print, in short:**
- Versions that only touch (one ends exactly when the next starts) do **not** overlap. Report an overlapping pair once: smaller key in `customer_sk`, larger in `other_customer_sk`.
- The other three issue types are one row per version, with the last three columns NULL. "Open-ended" means the end is exactly 9999-12-31 00:00 UTC.
- One version can show up under several issue types.

## Business context

The point-in-time joins in finance reporting assume that the customer dimension is well formed:
for every customer, versions never overlap and exactly the open-ended version is flagged current.
After an incident where revenue was double-counted, the data platform team wants a **nightly
audit query** that lists every defect, one row per finding, so it can feed an alerting table.

## Source table

| table | grain | columns you need |
|---|---|---|
| `dim_customer_scd2` | one row per customer version | `customer_sk` (bigint, surrogate key), `customer_id`, `effective_from`, `effective_to` (timestamptz), `is_current` (boolean) |

Conventions: a version is valid on the half-open interval `[effective_from, effective_to)`. An
**open-ended** version has `effective_to = 9999-12-31 00:00:00+00` exactly. `customer_id` is not
unique (one row per version) and has no constraints.

## Requirements

Report four issue types. Check the **whole table**.

| issue_type | one row per | rule |
|---|---|---|
| `OVERLAPPING_VERSIONS` | unordered pair of versions of the same customer | their validity intervals share at least one instant |
| `MULTIPLE_CURRENT` | version | `is_current` is true and the customer has more than one current version |
| `CLOSED_BUT_CURRENT` | version | `is_current` is true but the version is not open-ended |
| `OPEN_BUT_NOT_CURRENT` | version | the version is open-ended but `is_current` is false |

1. Two versions that only **touch** (one ends exactly when the next starts) do **not** overlap.
2. For an overlapping pair, report it once: `customer_sk` is the smaller surrogate key,
   `other_customer_sk` the larger. `overlap_from` / `overlap_to` describe the shared interval
   (half-open; it may end at the sentinel date).
3. For the three single-version issues, `other_customer_sk`, `overlap_from` and `overlap_to` are NULL.
4. A version can appear under several issue types, and a customer can have several findings.
5. Clean customers produce no rows.

## Output contract

| column | type | notes |
|---|---|---|
| `customer_id` | integer | |
| `issue_type` | text | one of the four codes above |
| `customer_sk` | bigint | the offending version (smaller key of a pair) |
| `other_customer_sk` | bigint | larger key of an overlapping pair, else NULL |
| `overlap_from` | timestamptz | start of the shared interval, else NULL |
| `overlap_to` | timestamptz | end (exclusive) of the shared interval, else NULL |

Ordering: none required.

## Illustrative example (not the real data)

Customer 801 has versions 9001 `[2024-01-01, 2024-09-01)` current=false and 9002
`[2024-08-15, 9999-12-31)` current=true. Customer 802 has 9011 `[2024-01-01, 2024-05-01)` and
9012 `[2024-05-01, 9999-12-31)` current=true.

| customer_id | issue_type | customer_sk | other_customer_sk | overlap_from | overlap_to |
|---|---|---|---|---|---|
| 801 | OVERLAPPING_VERSIONS | 9001 | 9002 | 2024-08-15 00:00+00 | 2024-09-01 00:00+00 |

Customer 802 is clean (touching versions).

## Edge cases you must handle

- Versions that touch exactly at a boundary.
- Two open-ended versions that both claim to be current.
- A customer whose only version is open-ended but not flagged current.
- A version must never be compared with itself, and a pair must not be reported twice.

## Constraints

- One read-only `SELECT` / `WITH` statement, PostgreSQL 17.
- The production dimension has about 5 million versions; think about how the pair search scales.

## Clarify before you code (what a strong candidate asks)

- Is the end of a version inclusive or exclusive? Do touching versions count as overlaps?
- Is the open-ended marker NULL or a sentinel date? Is the sentinel exactly one value?
- Should a pair be reported once or once per version?
- Is the result an alert list (row per finding) or a per-customer status?
