# SQL-031 · Customer region and segment as of each June sale

**Topic:** dimensional modeling · **Level:** medium · **Interview time:** ~15 min · **Mode:** query

## In plain words

> "For every completed June 2025 sale, show me which region and segment the customer was in at the moment they bought, and also their region today."

**You return:** one row per in-scope transaction: `transaction_id`, `customer_id`, `transaction_ts`, `region_at_purchase`, `segment_at_purchase`, `current_region`.

**The fine print, in short:**
- Only **completed** sales from 1 June up to, but not including, 1 July 2025 (UTC). Guests are included.
- A customer's record is valid from its start time up to, but not including, its end time. At the exact instant of a change, the new record applies.
- If no record matches (guest, or a gap), keep the sale and leave both historical columns NULL. Never use another record instead.

## Business context

Finance restates June 2025 revenue by sales region. Customers move between regions and change
segment, and the June report must show the region and segment the customer had **at the moment
of each purchase**, not what the customer record says today. The dimension team keeps a type-2
slowly changing dimension for exactly this purpose. The analyst also wants today's region next to
it, to see how much the restatement moves.

## Source tables

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `transaction_id`, `customer_id` (NULL = guest), `transaction_ts` (timestamptz, UTC), `transaction_status` |
| `dim_customer_scd2` | one row per customer version | `customer_id`, `region`, `segment`, `effective_from`, `effective_to` (timestamptz) |
| `customers` | one row per customer, current attributes | `customer_id`, `home_region` |

A dimension version is valid on the half-open interval `[effective_from, effective_to)`. The
current version has `effective_to = 9999-12-31 00:00:00+00`.

## Requirements

1. Scope: `COMPLETED` transactions with `transaction_ts` in **[2025-06-01 00:00, 2025-07-01 00:00) UTC**.
   Guest checkouts are included.
2. `region_at_purchase` / `segment_at_purchase` come from the dimension version whose validity
   interval contains `transaction_ts`. At the exact instant a new version starts, the **new**
   version applies.
3. If no version matches (guest checkout, or a gap in the dimension), the transaction is still
   returned, with both historical attributes NULL. Do not fall back to another version.
4. `current_region` = `customers.home_region` (today's value; NULL for guests or unknown).
5. Exactly one output row per in-scope transaction.

## Output contract

| column | type | notes |
|---|---|---|
| `transaction_id` | bigint | |
| `customer_id` | integer | NULL for guests |
| `transaction_ts` | timestamptz | |
| `region_at_purchase` | text | historical region, NULL if no version matches |
| `segment_at_purchase` | text | historical segment, NULL if no version matches |
| `current_region` | text | today's region from `customers` |

Ordering: none required.

## Illustrative example (not the real data)

Customer 701: version A `[2024-01-01, 2025-06-03 08:00)` SOUTH/CONSUMER, version B
`[2025-06-03 08:00, 9999-12-31)` NORTH/SMALL_BUSINESS.

| transaction_ts | region_at_purchase | segment_at_purchase | current_region |
|---|---|---|---|
| 2025-06-03 07:59:59 | SOUTH | CONSUMER | NORTH |
| 2025-06-03 08:00:00 | NORTH | SMALL_BUSINESS | NORTH |
| guest, 2025-06-04 | NULL | NULL | NULL |

## Edge cases you must handle

- A purchase one second before, and exactly at, a version change.
- Customers whose current region differs from the region at purchase time.
- Guest checkouts.
- Non-completed transactions in the same period.
- Customers with several versions: the join must not multiply transactions.

## Constraints

- One read-only `SELECT` / `WITH` statement, PostgreSQL 17.
- Expect about a thousand rows. In production the fact has hundreds of millions of rows and the
  dimension a few million versions.

## Clarify before you code (what a strong candidate asks)

- Is `effective_to` inclusive or exclusive?
- Which version wins at the exact change instant?
- What should unmatched facts show: NULL, an "unknown" member, or the current row?
- Is the change time in UTC or in some local time zone?
