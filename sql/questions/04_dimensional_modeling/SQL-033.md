# SQL-033 · Sales with no matching customer version, and why

**Topic:** dimensional modeling · **Level:** hard · **Interview time:** ~25 min · **Mode:** query

## Business context

The fact loader stamps every sale with the customer dimension version that was valid at the
moment of the sale. Sales that find no version end up as "unknown customer" in finance reports.
Before the month-end close, the data-quality team wants the **exception list**: every completed
sale of a known customer that has **no matching dimension version**, plus a reason code that tells
the dimension team what to fix (load a missing early version, close a gap, or extend the last one).

## Source tables

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `transaction_id`, `customer_id` (NULL = guest), `transaction_ts` (timestamptz, UTC), `transaction_status` |
| `dim_customer_scd2` | one row per customer version | `customer_sk`, `customer_id`, `effective_from`, `effective_to` (timestamptz) |

A version is valid on the half-open interval `[effective_from, effective_to)`; the open-ended
version has `effective_to = 9999-12-31 00:00:00+00`.

## Requirements

1. Scope: **all** `COMPLETED` transactions with a non-NULL `customer_id` (no date filter).
   Guest checkouts are out of scope.
2. A sale **matches** if at least one version of its customer contains `transaction_ts`. At an
   exact boundary instant, the version that starts there matches and the one that ends there
   does not.
3. Return only sales that do **not** match, one row per sale.
4. `previous_version_end` = the latest `effective_to` among the customer's versions that ended
   at or before `transaction_ts` (NULL if none).
   `next_version_start` = the earliest `effective_from` among versions that start after
   `transaction_ts` (NULL if none).
5. `reason`:

| reason | rule |
|---|---|
| `CUSTOMER_NOT_IN_DIMENSION` | the customer has no versions at all |
| `NO_VERSION_YET` | versions exist, but all of them start after the sale |
| `AFTER_LAST_VERSION` | versions exist, but all of them ended at or before the sale |
| `GAP_BETWEEN_VERSIONS` | a version ended before the sale and another starts after it |

## Output contract

| column | type | notes |
|---|---|---|
| `transaction_id` | bigint | |
| `customer_id` | integer | |
| `transaction_ts` | timestamptz | |
| `reason` | text | one of the four codes |
| `previous_version_end` | timestamptz | NULL if none |
| `next_version_start` | timestamptz | NULL if none |

Ordering: none required.

## Illustrative example (not the real data)

Customer 901 has versions `[2024-05-01, 2024-08-01)` and `[2024-09-01, 9999-12-31)`.

| sale at | matches? | reason | previous_version_end | next_version_start |
|---|---|---|---|---|
| 2024-04-30 23:00 | no | NO_VERSION_YET | NULL | 2024-05-01 |
| 2024-07-31 23:59:59 | yes | – | – | – |
| 2024-08-01 00:00 | no | GAP_BETWEEN_VERSIONS | 2024-08-01 | 2024-09-01 |
| 2024-09-01 00:00 | yes | – | – | – |

## Edge cases you must handle

- A sale exactly at the end of a version, and exactly at the start of the next one.
- A sale one second before a customer's very first version starts.
- Customers with several versions: each unmatched sale appears once.
- Generated customers always match; non-completed sales and guests are ignored.

## Constraints

- One read-only `SELECT` / `WITH` statement, PostgreSQL 17.
- The production fact has 500M rows and only a few hundred exceptions. Think about the plan.

## Clarify before you code (what a strong candidate asks)

- Are guests "unknown customers" for this report or a separate category?
- Is an exception defined at the instant of the sale or on its business date?
- Does the loader apply an "unknown member" row today, and should those be listed too?
- Should a sale covered by a defective (overlapping) version count as matched?
