# SQL-029 · Were all selected products available at checkout time?

**Topic:** gaps, islands & time · **Level:** hard · **Interview time:** ~30 min · **Mode:** query

## In plain words

> "For store 2 on 10 and 11 May 2025, at the time of each checkout, were products 4, 5 and 6 available on the shelf?"

**You return:** one row per transaction: `transaction_id`, `transaction_ts`, `all_available`, `any_available`, `available_products` (0 to 3).

**The fine print, in short:**
- Every **completed** transaction at store 2 with UTC time from 10 May to the end of 11 May, whatever it bought.
- Available means a record covering that moment says so. No record covering it means not available.
- At the exact instant a record starts, that record applies.

## Business context

Store 2 ran a "meal deal" on 10 and 11 May 2025: products **4, 5 and 6** sold together.
Complaints came in that the deal could not be completed because items were out of stock. For
every checkout at store 2 in that period, the category manager wants to know whether the
**whole** deal was available at that instant, whether **at least one** item was, and how many.

## Source tables

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `transaction_id`, `store_id`, `transaction_ts` (timestamptz, UTC), `transaction_status` |
| `store_product_availability` | one row per availability version | `store_id`, `product_id`, `valid_from`, `valid_to` (timestamptz), `available` (boolean) |

Availability versions are half-open `[valid_from, valid_to)`; `valid_to IS NULL` = still valid.
Versions of one (store, product) never overlap, but they **may leave gaps**: an instant that is
covered by **no** version means the product was **not stocked**, which counts as **unavailable**.

## Requirements

1. Scope: `COMPLETED` transactions at `store_id = 2` with `transaction_ts` in
   **[2025-05-10 00:00, 2025-05-12 00:00) UTC**. Every such transaction is reported, whatever
   it actually bought: the question is about the shelf at that instant, not the basket.
2. For each transaction and each of the products {4, 5, 6}, the product is available at
   `transaction_ts` if and only if a version covering that instant exists with `available = true`.
   At the exact instant a version starts, that version applies.
3. `all_available` = all three products available; `any_available` = at least one available;
   `available_products` = how many of the three were available (0–3).

## Output contract

| column | type | notes |
|---|---|---|
| `transaction_id` | bigint | one row per in-scope transaction |
| `transaction_ts` | timestamptz | |
| `all_available` | boolean | never NULL |
| `any_available` | boolean | never NULL |
| `available_products` | integer | 0 … 3 |

Ordering: none required.

## Illustrative example (not the real data)

Products A, B. A: `[00:00, 10:00) true`, `[10:00, 12:00) false`, `[12:00, NULL) true`.
B: `[00:00, 18:00) true`, no row after 18:00.

| checkout at | A | B | all | any | count |
|---|---|---|---|---|---|
| 09:59:59 | yes | yes | true | true | 2 |
| 10:00:00 | no | yes | false | true | 1 |
| 12:00:00 | yes | yes | true | true | 2 |
| 19:00:00 | yes | no (not stocked) | false | true | 1 |

## Edge cases you must handle

- A checkout exactly at the start and one second before the end of an unavailability window.
- An instant covered by no row at all.
- A product that is available for the whole period.
- "All of a set" semantics must hold for any size of product set, not just three.

## Constraints

- One read-only `SELECT` / `WITH` statement, PostgreSQL 17.
- Write the product set once (for example as a small inline list), so it can be changed in one place.

## Clarify before you code (what a strong candidate asks)

- Does "no row" mean unavailable, unknown, or available?
- Which version applies at the boundary instant?
- Should the answer depend on what was in the basket?
- Is availability tracked in UTC or store-local time?
