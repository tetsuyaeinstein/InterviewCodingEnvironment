# SQL-021 · Five consecutive purchase days

**Topic:** gaps, islands & time · **Level:** medium · **Interview time:** ~20 min · **Mode:** query

## In plain words

> "Which customers bought on at least five days in a row?"

**You return:** one row per qualifying customer: `customer_id`.

**The fine print, in short:**
- Only **completed** transactions. The day is the UTC date. Guests are excluded.
- Several purchases on one day count as one day.
- Each customer appears once, even with several such runs.

## Business context

The loyalty team wants to reward "habit" customers: anyone who made a purchase on **five
consecutive calendar days** at least once. In production the transaction fact holds about
**500 million rows**. Here you work on the seeded subset, but the interviewer will ask how your
approach scales.

## Source table

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `customer_id`, `transaction_ts` (timestamptz, UTC), `transaction_status` |

## Requirements

1. Only `transaction_status = 'COMPLETED'` transactions count as purchases.
2. The purchase date is the **UTC calendar date** of `transaction_ts`. Store-local time is not used here.
3. A customer qualifies if there is at least one run of **5 or more consecutive calendar
   days**, each with at least one completed purchase.
4. Several purchases on the same day count as **one** purchase day.
5. Guest checkouts (`customer_id IS NULL`) are excluded.
6. Return each qualifying customer **once**, even if they have several qualifying runs.

## Output contract

| column | type | notes |
|---|---|---|
| `customer_id` | integer | one row per qualifying customer |

Ordering: none required (rows are compared as an unordered set).

## Illustrative example (not the real data)

| customer_id | completed purchase dates (UTC) | qualifies? |
|---|---|---|
| 501 | Mar 1, Mar 2, Mar 2, Mar 3, Mar 4, Mar 5 | yes (5 distinct consecutive days) |
| 502 | Mar 1, Mar 2, Mar 3, Mar 4, Mar 6, Mar 7 | no (longest run is 4) |
| 503 | Dec 30, Dec 31, Jan 1, Jan 2, Jan 3 | yes |

Expected output: `501`, `503`.

## Edge cases you must handle

- Exactly 4 consecutive days → **not** a match. Exactly 5 → match.
- Several purchases on one day must not inflate the run length.
- Runs that cross a month end, a year end, or leap day 2024-02-29.
- A day whose only transaction was `CANCELLED` or `PENDING` breaks the run.
- Two separate qualifying runs → the customer still appears once.

## Constraints

- One read-only `SELECT` / `WITH` statement, valid PostgreSQL 17.
- Use PostgreSQL date arithmetic (`date - integer`, `interval`). Do not use T-SQL `DATEADD`/`DATEDIFF`.
- Assume the interviewer will ask you to explain the cost on 500M rows and which indexes or
  pre-aggregations you would want.

## Clarify before you code (what a strong candidate asks)

- Which timezone defines the calendar day?
- Do refunds or cancellations undo a purchase day?
- Does a 6-day run count as "at least 5"?
- Should guest checkouts be included?
