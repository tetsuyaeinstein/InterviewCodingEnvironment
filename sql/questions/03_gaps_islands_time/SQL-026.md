# SQL-026 · Sessionize clickstream events with a 30-minute inactivity rule

**Topic:** gaps, islands & time · **Level:** medium · **Interview time:** ~20 min · **Mode:** query

## Business context

Product analytics wants session-level metrics (sessions per customer, session length, events
per session). The `session_id` sent by the app is unreliable: often NULL, sometimes reused or
changed in the middle of a visit. The team decided to derive sessions **server-side** from
event timestamps alone, with the industry-standard inactivity timeout.

## Source table

| table | grain | columns you need |
|---|---|---|
| `customer_events` | one row per clickstream event | `event_id` (bigint, unique), `customer_id` (NULL = anonymous), `event_ts` (timestamptz, UTC) |

Ignore `session_id`, `event_type` and `payload`.

## Requirements

1. Scope: events with `customer_id IS NOT NULL` and `event_ts` in
   **[2025-07-01 00:00, 2025-08-01 00:00) UTC**. Events outside the window do not exist for this
   report, even if they would extend a session.
2. Within one customer, order events by `event_ts`; events with **identical** timestamps are
   ordered by `event_id`.
3. A customer's first event starts session 1. Each later event starts a **new** session if the
   time since the customer's **previous** event is **more than 30 minutes**. A gap of exactly
   30 minutes 00 seconds stays in the same session.
4. Sessions may cross midnight. Calendar days play no role.
5. Number sessions per customer 1, 2, 3, … in chronological order.

## Output contract

| column | type | notes |
|---|---|---|
| `customer_id` | integer | |
| `session_number` | integer | 1-based, per customer, chronological |
| `session_start` | timestamptz | timestamp of the session's first event |
| `session_end` | timestamptz | timestamp of the session's last event (equals `session_start` for one-event sessions) |
| `event_count` | integer | events in the session, counting duplicates of the same timestamp |

One row per session. Ordering: none required.

## Illustrative example (not the real data)

Events of customer 1201 on one day: 08:00:00, 08:29:59, 08:59:59, 09:30:01, 09:30:01, 10:00:01,
10:45:00, and 00:10:00 on the next day.

| gap to previous event | 29:59 | 30:00 | 30:02 | 0:00 | 30:00 | 44:59 | 13:25:00 |
|---|---|---|---|---|---|---|---|
| new session? | no | no | **yes** | no | no | **yes** | **yes** |

| session_number | session_start | session_end | event_count |
|---|---|---|---|
| 1 | 08:00:00 | 08:59:59 | 3 |
| 2 | 09:30:01 | 10:00:01 | 3 |
| 3 | 10:45:00 | 10:45:00 | 1 |
| 4 | 00:10:00 (next day) | 00:10:00 (next day) | 1 |

## Edge cases you must handle

- A gap of exactly 30:00 continues the session; 30:01 starts a new one.
- Two events with the same timestamp belong to the same session and both count.
- A session spanning midnight is one session.
- The client `session_id` changes inside a server-side session and is often NULL.
- Single-event sessions.

## Constraints

- One read-only `SELECT` / `WITH` statement, PostgreSQL 17.
- Use `interval` arithmetic on timestamps; no epoch-second string tricks needed.

## Clarify before you code (what a strong candidate asks)

- Is the timeout "more than" or "at least" 30 minutes?
- How are equal timestamps ordered, and does that ordering change any result?
- Do anonymous events get stitched to a customer after login?
- What happens to sessions that cross the reporting window boundaries?
