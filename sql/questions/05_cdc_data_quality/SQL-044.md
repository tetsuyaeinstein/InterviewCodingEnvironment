# SQL-044 · Source vs target reconciliation with column-level differences

**Topic:** CDC, incremental processing & data quality · **Level:** medium · **Interview time:** ~25 min · **Mode:** query

## Business context

After the December 2025 migration, the data platform team must sign off that the warehouse table
matches the source extract. The auditors want a **row-by-row exception report**: every
transaction that is missing, unexpected, or different, and for differences, *which* columns
differ, so engineers can tell a rounding bug from a timezone bug at a glance.

## Source tables

| table | grain | columns |
|---|---|---|
| `source_transactions` | one row per `transaction_id` (unique) | `transaction_id`, `customer_id`, `store_id`, `transaction_ts`, `amount`, `status`, `payment_method`, `merchant_ref`, `note`, `extracted_at` |
| `target_transactions` | one row per `transaction_id` (unique) | same business columns, plus `loaded_at` |

## Requirements

1. Match rows on `transaction_id`.
2. Compare these **business columns**, in this fixed order: `customer_id`, `store_id`,
   `transaction_ts`, `amount`, `status`, `payment_method`, `merchant_ref`, `note`.
   `extracted_at` / `loaded_at` are load metadata and are **not** compared.
3. Two values are equal if both are NULL, or both are non-NULL and equal. NULL vs a value is a
   difference. An empty string `''` is a value, so `''` vs NULL is a difference.
4. Classify each reported key:
   - `MISSING_IN_TARGET`: only in the source;
   - `EXTRA_IN_TARGET`: only in the target;
   - `CHANGED`: in both, at least one business column differs.
5. Keys that match on every business column are **not** reported.

## Output contract

| column | type | notes |
|---|---|---|
| `transaction_id` | bigint | one row per reported key |
| `diff_type` | text | `MISSING_IN_TARGET`, `EXTRA_IN_TARGET` or `CHANGED` |
| `diff_columns` | text | for `CHANGED`: the differing column names, comma-separated with no spaces, in the order of requirement 2 (e.g. `amount,status`); NULL for the other two types |

Ordering: none required.

## Illustrative example (not the real data)

| id | source (amount, status, note) | target | output |
|---|---|---|---|
| 1 | 5.00, PAID, NULL | 5.00, PAID, NULL | not reported |
| 2 | 5.00, PAID, NULL | 5.10, VOID, NULL | `CHANGED`, `amount,status` |
| 3 | 7.00, PAID, `''` | 7.00, PAID, NULL | `CHANGED`, `note` |
| 4 | present | absent | `MISSING_IN_TARGET`, NULL |

## Edge cases you must handle

- NULL on one side only, NULL on both sides.
- Empty string vs NULL.
- A timestamp that differs by one second.
- Rows that exist on only one side.
- Different load timestamps on otherwise identical rows.

## Constraints

One read-only `SELECT`/`WITH` statement, PostgreSQL 17. About 2,000 rows per side here. Be ready
to discuss reconciling 500M-row tables.

## Clarify before you code (what a strong candidate asks)

- Which columns are business data and which are metadata?
- Is `''` the same as NULL for the business? (Here: no.)
- Is there a tolerance for amounts or timestamps? (Here: no, exact comparison.)
- Is `transaction_id` guaranteed unique on both sides?
