# SQL-050 · Safe committed watermark after failed and retried batches

**Topic:** CDC, incremental processing & data quality · **Level:** medium · **Interview time:** ~25 min · **Mode:** query

## Business context

`transactions_incremental` loads hourly windows per source system. Each run processes the
half-open window `[window_start, window_end)` and ends `SUCCEEDED`, `FAILED` or is still
`RUNNING`. Failed windows are retried later by a new run. The job also writes its own high-water
mark to `pipeline_watermarks`, but an incident review showed that it advances that mark past
failed windows. Downstream consumers then believe data is complete when it is not.

The on-call lead wants an independent check: per source, the **safe watermark** derived from the
run history, the recorded one, and whether the recorded one is unsafe.

## Source tables

| table | grain | columns you need |
|---|---|---|
| `pipeline_runs` | one row per run attempt | `run_id`, `pipeline_name`, `source_system`, `status`, `window_start`, `window_end`, `started_at` |
| `pipeline_watermarks` | one row per (`pipeline_name`, `source_system`) | `watermark_ts` (the recorded mark) |

## Requirements

Only `pipeline_name = 'transactions_incremental'`. The pipeline's history starts at
**2025-12-15 00:00:00 UTC** for every source.

1. Return one row per source that has a row in `pipeline_watermarks` for this pipeline.
2. `safe_watermark` = the latest time T such that **every instant in [2025-12-15 00:00, T) is
   covered by at least one `SUCCEEDED` run window**. Retries and re-runs of the same window count
   once. Failed or running attempts cover nothing. If the very first window has no successful
   run, `safe_watermark` is NULL.
3. `recorded_watermark` = `pipeline_watermarks.watermark_ts`.
4. `recorded_is_unsafe` = the recorded watermark is later than the safe watermark (when the safe
   watermark is NULL, compare with the history start 2025-12-15 00:00).
5. `next_window_status` = the status of the **most recent attempt** (latest `started_at`, ties by
   higher `run_id`) of the window that starts at the safe watermark (or at the history start when
   it is NULL). This is the window blocking progress. Use `'NOT_RUN'` if no attempt exists.

## Output contract

| column | type | notes |
|---|---|---|
| `source_system` | text | |
| `safe_watermark` | timestamptz | NULL if nothing is safely loaded |
| `recorded_watermark` | timestamptz | |
| `recorded_is_unsafe` | boolean | |
| `next_window_status` | text | `FAILED`, `RUNNING`, `SUCCEEDED` (not possible here) or `NOT_RUN` |

Ordering: none required.

## Illustrative example (not the real data)

Source `X`, history start 00:00, recorded mark 05:00:

| window | attempts |
|---|---|
| 00–01 | SUCCEEDED |
| 01–02 | FAILED, then SUCCEEDED (retry) |
| 02–03 | FAILED |
| 03–04 | SUCCEEDED |
| 04–05 | SUCCEEDED |

Result: `safe_watermark = 02:00`, `recorded_is_unsafe = true`, `next_window_status = FAILED`.

## Edge cases you must handle

- A failed window that was retried successfully later (by a run that started after newer windows).
- A failed window that was never retried, followed by successful later windows.
- A window whose only attempt is still running.
- A source whose first window never succeeded.
- A window that succeeded twice.

## Constraints

One read-only `SELECT`/`WITH` statement, PostgreSQL 17.

## Clarify before you code (what a strong candidate asks)

- Where does history start: a fixed date, or the first run of each source?
- Do overlapping or multi-hour windows exist?
- Is a RUNNING window "done" for watermark purposes? (No.)
- What should consumers see when nothing is safe yet?
