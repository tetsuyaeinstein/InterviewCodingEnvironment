# SQL-045 · Null-safe, unambiguous row fingerprints for change detection

**Topic:** CDC, incremental processing & data quality · **Level:** hard · **Interview time:** ~30 min · **Mode:** query (graded by contract + edge-case assertions)

## In plain words

> "Give every row in both tables a fingerprint of its business data, so two systems can compare rows by exchanging only the fingerprints."

**You return:** one row per row of both tables: `system` (`SOURCE` or `TARGET`), `transaction_id`, `row_fingerprint` (a lowercase hex digest from `md5` or `sha256`, never NULL).

**The fine print, in short:**
- Cover the eight business columns in order. Leave out the key and the load timestamps. Equal business values give the same fingerprint in either table.
- Different values must never give the same hash input: NULL versus empty versus the text 'NULL' versus 0, values moved between columns, values containing your delimiter.
- Use built-in functions only, and no schema prefix on the tables. The grader re-runs your query on extra test rows.

## Business context

Comparing 500M-row tables column by column across systems is too expensive. The platform team
wants a **fingerprint** (hash) per row of business data. Each system computes it locally, only
`(key, fingerprint)` pairs are exchanged, and a mismatch means "this row changed". The same
fingerprint will drive SCD2 change detection ("did any attribute change since the last load?").

A fingerprint is only useful if it is **deterministic** (same business values give the same
fingerprint, in both systems, on every run) and **unambiguous** (different business values must
not produce the same hash input).

## Source tables

| table | columns |
|---|---|
| `source_transactions` | `transaction_id`, `customer_id` int, `store_id` int, `transaction_ts` timestamptz, `amount` numeric(12,2), `status`, `payment_method`, `merchant_ref`, `note` (text), `extracted_at` |
| `target_transactions` | same business columns, plus `loaded_at` |

## Requirements

1. Return one row per row of **both** tables: `system = 'SOURCE'` for `source_transactions`,
   `'TARGET'` for `target_transactions`.
2. The fingerprint covers exactly the business columns `customer_id, store_id, transaction_ts,
   amount, status, payment_method, merchant_ref, note`, in that order. It does **not** include
   `transaction_id` (the key) or the load metadata (`extracted_at`, `loaded_at`).
3. Two rows with equal business values (NULL counts as equal to NULL) must get the **same**
   fingerprint, whichever table they come from.
4. Two rows whose business values differ in any way must get **different** hash inputs. That
   includes NULL vs `''`, NULL vs the string `'NULL'`, NULL vs `0`, a value moved from one column
   to the next, and values containing your delimiter.
5. The fingerprint is the **lowercase hex digest** of `md5` (32 characters) or `sha256`
   (64 characters), returned as `text`. `pgcrypto` is not installed. Use built-ins.
6. Reference the two tables **without a schema prefix**. The grader re-runs your query against
   additional synthetic test rows.

## Output contract

| column | type | notes |
|---|---|---|
| `system` | text | `SOURCE` or `TARGET` |
| `transaction_id` | bigint | |
| `row_fingerprint` | text | hex digest, never NULL |

Ordering: none required. The hash values themselves are not compared (implementations differ).
Your result is graded by the column contract and edge-case assertions.

## Illustrative example (not the real data)

| merchant_ref | note | naive `merchant_ref \|\| note` | must the fingerprints differ? |
|---|---|---|---|
| `'PQ'` | `'R'` | `PQR` | yes |
| `'P'` | `'QR'` | `PQR` | yes |
| `'P'` | NULL | NULL (the whole expression becomes NULL) | yes, vs `('P', '')` too |

## Edge cases you must handle

- Values that contain the delimiter you choose.
- NULL in different positions; NULL vs empty string vs the text `'NULL'`; NULL vs zero.
- Identical rows in the two systems loaded at different times.
- Formatting that could depend on session settings (timestamps, numeric scale).

## Constraints

One read-only `SELECT`/`WITH` statement, PostgreSQL 17. About 4,000 output rows.

## Clarify before you code (what a strong candidate asks)

- Which columns are in scope, and will new columns be added later?
- Will both systems compute the fingerprint the same way (different engines, collations,
  time zones)?
- How much collision risk is acceptable, and are inputs adversarial?
- Is the fingerprint used only to compare the same key, or also to find duplicates across keys?
