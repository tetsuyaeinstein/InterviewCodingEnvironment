# SQL-041 · Current state of every CDC key (latest by commit order)

**Topic:** CDC, incremental processing & data quality · **Level:** medium · **Interview time:** ~20 min · **Mode:** query

## In plain words

> "From the raw change log, rebuild the current state of every transaction. Events can arrive out of order, so go by the source's commit sequence, not by arrival."

**You return:** one row per key (`source_system`, `business_key`), both systems: `source_system`, `business_key`, `cdc_event_id`, `last_operation`, `source_lsn`, `amount`, `status`, `is_deleted`, `has_lsn_conflict`.

**The fine print, in short:**
- The current version is the event with the highest `source_lsn` for that key. POS and ECOM are separate keys, even with the same `business_key` text.
- If several events tie on the highest LSN, take the latest arrival (highest `cdc_event_id`). Flag a conflict only if the tied events differ in operation or payload.
- If the current version is a delete, set `is_deleted` to true and `amount` and `status` to NULL.

## Business context

The payments team replicates POS and ECOM transactions into the lake through a change-data-capture
(CDC) feed. Before building the warehouse table, they want a query that rebuilds the **current
version of every transaction** from the raw change log. The feed is at-least-once and messages
do not arrive in commit order, so "the row that arrived last" is not necessarily the newest one.

## Source table

| table | grain | columns you need |
|---|---|---|
| `cdc_transaction_events` | one row per received change event | `cdc_event_id` (arrival order), `source_system`, `business_key`, `operation` (`I`/`U`/`D`), `source_lsn` (bigint), `commit_ts`, `ingested_at`, `payload` (jsonb) |

- A transaction is identified by **(`source_system`, `business_key`)**. The same `business_key` text
  can exist in POS and ECOM as two unrelated transactions, and the two systems even reuse LSN numbers.
- `source_lsn` is the source database's commit sequence **within one source system**. It is the
  only reliable "which version is newer" signal. `ingested_at` and `cdc_event_id` only tell you when
  the event reached the lake.
- For `I` and `U` the `payload` is the full after-image: `amount` (a string such as `"60.00"`) and
  `status`, among others. For `D` the payload carries only the key.

## Requirements

1. Return **one row per key** (all keys in the table, both source systems).
2. The current version is the event with the **highest `source_lsn`** for that key.
3. **Tie policy:** several events can share a key's highest LSN (redelivered duplicates, or a
   genuine conflict). In that case pick the one with the highest `cdc_event_id` (the latest
   arrival), and set `has_lsn_conflict = true` **only if** the tied events differ in operation
   or payload. Identical redeliveries are not a conflict.
4. If the current version is a delete, the key is reported with `is_deleted = true` and NULL
   `amount` / `status` (do not carry values forward from older versions).

## Output contract

| column | type | notes |
|---|---|---|
| `source_system` | text | |
| `business_key` | text | |
| `cdc_event_id` | bigint | the chosen event |
| `last_operation` | text | `I`, `U` or `D` of the chosen event |
| `source_lsn` | bigint | LSN of the chosen event |
| `amount` | numeric(12,2) | from the payload; NULL when deleted |
| `status` | text | from the payload; NULL when deleted |
| `is_deleted` | boolean | chosen event is a `D` |
| `has_lsn_conflict` | boolean | see requirement 3 |

Ordering: none required. Amounts are compared rounded to 2 decimals.

## Illustrative example (not the real data)

| cdc_event_id | key | op | lsn | payload amount |
|---|---|---|---|---|
| 11 | (POS, K9) | I | 100 | 5.00 |
| 12 | (POS, K9) | U | 120 | 9.00 |
| 13 | (POS, K9) | U | 110 | 7.00 ← arrived last, but older |
| 14 | (ECOM, K9) | I | 100 | 70.00 |

Result: (POS, K9) → event 12, `U`, 9.00, not deleted, no conflict; (ECOM, K9) → event 14, 70.00.

## Edge cases you must handle

- An older update that arrives after a newer one.
- A stale update that arrives after the key was deleted. The key must stay deleted.
- A key that is deleted and later legitimately inserted again.
- A delete for a key that was never inserted.
- An update that arrives before its own insert.
- Two updates with the same `commit_ts` but different LSNs.
- Identical duplicate deliveries vs two *different* events sharing one LSN.
- The same `business_key` in both source systems.

## Constraints

One read-only `SELECT`/`WITH` statement, PostgreSQL 17. Expect about 1,500 keys here. Be ready to
explain how you would maintain this incrementally on a 500M-event log.

## Clarify before you code (what a strong candidate asks)

- Is the LSN comparable across source systems? (No.)
- What should a deleted key look like in the output: absent, or flagged?
- What happens when two events share the top LSN, and who needs to know?
- Is `payload.amount` always numeric text?
