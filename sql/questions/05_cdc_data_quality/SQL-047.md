# SQL-047 · Apply a CDC batch with deletes and tombstones (no resurrection)

**Topic:** CDC, incremental processing & data quality · **Level:** hard · **Interview time:** ~35 min · **Mode:** mutation (sandboxed)

## Business context

The warehouse keeps the **current version** of every POS/ECOM transaction in `txn_current`.
Change events arrive in micro-batches, out of order and occasionally duplicated, and they now
include **deletes**. Last quarter an auditor found voided transactions back in the warehouse. A
delete had been applied, and an *older* update for the same key arrived in a later batch and
re-created the row.

The team introduced `txn_tombstone`, which remembers the commit position (LSN) at which each key was
deleted. Write the DML that applies one batch to both tables.

## Tables (created for you inside a disposable sandbox schema)

| table | grain | columns |
|---|---|---|
| `txn_current` | one row per live key; PK (`source_system`, `business_key`) | `amount numeric(12,2)`, `status text`, `source_lsn bigint` (LSN of the version stored) |
| `txn_tombstone` | one row per deleted key; PK (`source_system`, `business_key`) | `deleted_lsn bigint` (LSN of the delete) |
| `cdc_batch` | one row per received event (**not unique**) | `cdc_event_id` (arrival order), `source_system`, `business_key`, `operation` (`I`/`U`/`D`), `source_lsn`, `amount`, `status` (NULL for `D`) |

Before your statements run, the tables hold the result of earlier batches: some live rows,
some tombstones (including keys that this batch touches), and the batch itself is the next slice
of `cdc_transaction_events` for the `FX-*` keys. `python -m lab run SQL-047` prints the graded
state after your statements. You can also query `cdc_transaction_events` read-only to study the
`FX-*` events.

`source_lsn` orders versions **within one source system** only. POS and ECOM are independent,
and the same `business_key` text in both systems means two different transactions.

## Requirements

For every key in the batch:

1. Take the key's **newest event in the batch**: highest `source_lsn`. If several events share
   that LSN, the one with the highest `cdc_event_id` wins (documented tie policy).
2. Apply it **only if** its LSN is strictly greater than everything already known about the key:
   the live row's `source_lsn` **and** the tombstone's `deleted_lsn`. Otherwise ignore it (stale).
3. Applying an `I` or `U`: the payload is a full after-image. Insert the live row or overwrite it
   (an update for a key with no live row is inserted), and **remove** the key's tombstone if any.
4. Applying a `D`: remove the live row if any, and record or raise the tombstone at the delete's
   LSN. Do this **even if the key has no live row**, so that older events arriving later are
   recognised as stale.
5. Keys that are not in the batch must not change.
6. Invariant afterwards: a key is never both live and tombstoned.

You may use several statements, helper tables and either `INSERT ... ON CONFLICT` / `DELETE` or
`MERGE`. Do not write `BEGIN`/`COMMIT`.

## What is graded

The final state of both tables, via:
`SELECT 'CURRENT' AS state, source_system, business_key, amount, status, source_lsn FROM txn_current
UNION ALL SELECT 'DELETED', source_system, business_key, NULL, NULL, deleted_lsn FROM txn_tombstone`
(unordered), plus edge-case assertions.

## Illustrative example (not the real data)

Before: live `(POS, K1, 10.00, PAID, lsn 50)`; tombstone `(POS, K2, deleted_lsn 70)`.

Batch: `K1 D 60`, `K1 U 55` (arrives after the delete), `K2 U 65`, `K3 I 40`, `K3 D 45`, `K3 I 48`.

After: K1 tombstoned at 60 (the U 55 is older than the delete); K2 still tombstoned at 70 (U 65 is
stale); K3 live at lsn 48 with no tombstone.

## Edge cases you must handle

- A stale update for a key deleted in an **earlier** batch.
- A delete followed by a legitimate re-insert with a higher LSN.
- An old tombstone that a newer insert must override.
- A delete for a key that was never live.
- An update that arrives before its insert; duplicate deliveries; two different events at one LSN.
- The same `business_key` in another source system (live row or tombstone).

## Constraints

PostgreSQL 17. Prefer set-based statements (no loops). Be ready to explain what happens if this
batch is applied twice, and how long tombstones must be kept.

## Clarify before you code (what a strong candidate asks)

- Is the LSN comparable across source systems?
- Should a delete for an unknown key be remembered? For how long?
- What is the policy when two different events share an LSN?
- Does an update carry the full row or only changed columns?
