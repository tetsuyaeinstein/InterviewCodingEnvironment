# SQL-048 · Idempotent restatement of a daily sales summary

**Topic:** CDC, incremental processing & data quality · **Level:** hard · **Interview time:** ~30 min · **Mode:** mutation (sandboxed, your script runs **twice**)

## Business context

`daily_store_sales` feeds the store managers' dashboard. Upstream, the extract job re-sends
**every delivery of every business date it touched** in its window. Late transactions,
redeliveries and status/amount corrections all arrive as new deliveries. Orchestrators retry
failed tasks, so **the same batch can be applied more than once**. Last month a retry doubled
two days of revenue.

Write the load so that it produces the right summary and running it again changes nothing.

## Tables (created for you inside a disposable sandbox schema)

| table | grain | columns |
|---|---|---|
| `daily_store_sales` | PK (`sales_date`, `store_id`) | `txn_count integer`, `gross_amount numeric(14,2)` |
| `stg_sales_batch` | one row per delivery; PK `delivery_id` | `transaction_id`, `store_id`, `transaction_ts timestamptz`, `transaction_status`, `gross_amount numeric(12,2)` |

- `daily_store_sales` already contains 2025-12-01 … 2025-12-09 from an earlier load. Some of
  those numbers are now outdated.
- A transaction can be delivered several times. **The delivery with the highest `delivery_id`
  is the current version** of that transaction (it may change the status or the amount).
  Some deliveries are exact repeats.
- The batch is **complete per business date**: for every date that occurs in the batch, it holds
  every transaction of that date.

## Requirements

1. `sales_date` is the **UTC calendar date** of `transaction_ts`.
2. For every business date present in the batch, the summary must end up **exactly** equal to the
   batch's content: per (`sales_date`, `store_id`), `txn_count` = number of distinct transactions
   whose current version is `COMPLETED`, and `gross_amount` = sum of their current amounts.
3. A (`sales_date`, `store_id`) row for a date in the batch that no longer has any completed sale
   must **not exist** afterwards.
4. Rows for dates **not** in the batch must be left exactly as they are, even if you think they
   are stale.
5. Your statements are executed **twice in a row** on the same data. The final state after the
   second run must be identical to the state after the first. If you create helper tables, make
   that safe to repeat (e.g. `DROP TABLE IF EXISTS` first, or avoid them).

Do not write `BEGIN`/`COMMIT`.

## What is graded

`SELECT sales_date, store_id, txn_count, gross_amount FROM daily_store_sales` after the second run,
compared as an unordered set, plus edge-case assertions.

## Illustrative example (not the real data)

Summary before: `(06-02, store 7, 2, 30.00)`, `(06-02, store 8, 1, 5.00)`, `(06-01, store 7, 1, 9.00)`.

Batch (date 06-02 only):

| delivery_id | txn | store | status | amount |
|---|---|---|---|---|
| 11 | 501 | 7 | PENDING | 10.00 |
| 12 | 501 | 7 | COMPLETED | 10.00 |
| 13 | 502 | 7 | COMPLETED | 20.00 |
| 14 | 502 | 7 | COMPLETED | 20.00 |
| 15 | 503 | 8 | CANCELLED | 5.00 |

After (any number of runs): `(06-02, 7, 2, 30.00)`, `(06-01, 7, 1, 9.00)`. The store 8 row is gone,
and 06-01 is untouched.

## Edge cases you must handle

- Exact redeliveries of a transaction.
- A later delivery that changes the status (to or from `COMPLETED`) or corrects the amount.
- A summary row that must disappear because its date was restated without sales for that store.
- Dates outside the batch.
- A second run of the same script.

## Constraints

PostgreSQL 17, set-based statements. Be ready to discuss how this maps onto partitioned tables
and warehouse engines.

## Clarify before you code (what a strong candidate asks)

- Is the batch complete per date (restatement) or a delta of new transactions?
- Which delivery wins when a transaction is sent several times?
- Must rows disappear when a store has no sales left on a restated day?
- Can two batches for the same date run concurrently?
