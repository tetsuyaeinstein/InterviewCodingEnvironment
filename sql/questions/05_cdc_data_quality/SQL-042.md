# SQL-042 · Rows for the next incremental run (watermark with overlap)

**Topic:** CDC, incremental processing & data quality · **Level:** medium · **Interview time:** ~15 min · **Mode:** query

## Business context

The hourly job `transactions_incremental` copies new POS transactions into the warehouse. It
selects rows by **arrival time** (`transactions.ingested_at`) and records how far it got in
`pipeline_watermarks`. Last month the job silently skipped rows. Rows committed in the source
just before a run finished became visible to the extract only after the watermark had already
moved past them. The fix the team agreed on: every run **re-reads a 10-minute overlap** before
the committed watermark, and the downstream load is an idempotent upsert.

Write the extract query for the next POS run.

## Source tables

| table | grain | columns you need |
|---|---|---|
| `pipeline_watermarks` | one row per (`pipeline_name`, `source_system`) | `watermark_ts` (timestamptz): last committed high-water mark |
| `transactions` | one row per transaction | `transaction_id`, `source_system` (`POS`/`ECOM`), `ingested_at` (timestamptz, UTC) |

## Requirements

1. Read the current watermark `W` for `pipeline_name = 'transactions_incremental'` and
   `source_system = 'POS'` **from `pipeline_watermarks`** (do not hard-code it).
2. The run's upper bound (its new high mark) is fixed: **`2025-12-15 07:00:00 UTC`, exclusive**.
3. Select POS transactions whose `ingested_at` falls in the half-open interval
   **[W − 10 minutes, 2025-12-15 07:00 UTC)**.
4. Flag rows that fall inside the overlap, i.e. `ingested_at < W` (they were probably processed
   by the previous run and are re-read on purpose).
5. Only `source_system = 'POS'` transactions. Every status counts (the load is not a sales report).

## Output contract

| column | type | notes |
|---|---|---|
| `transaction_id` | bigint | one row per transaction |
| `ingested_at` | timestamptz | |
| `is_overlap_reread` | boolean | `true` when `ingested_at < W` |

Ordering: none required.

## Illustrative example (not the real data)

Watermark 10:00, overlap 10 minutes, high mark 11:00:

| ingested_at | selected? | is_overlap_reread |
|---|---|---|
| 09:49:59 | no | |
| 09:50:00 | yes | true |
| 10:00:00 | yes | false |
| 10:59:59 | yes | false |
| 11:00:00 | no (next run) | |

## Edge cases you must handle

- A row ingested exactly at `W − 10 minutes`, and one a second earlier.
- A row ingested exactly at `W`: is it overlap or new?
- A row ingested exactly at the high mark.
- Transactions whose business timestamp (`transaction_ts`) is much older than their arrival.

## Constraints

One read-only `SELECT`/`WITH` statement, PostgreSQL 17. Use interval arithmetic
(`interval '10 minutes'`).

## Clarify before you code (what a strong candidate asks)

- Is the watermark compared to the event time or the arrival time?
- Are the bounds inclusive or exclusive, and is that consistent with how the previous run ended?
- How is the overlap made harmless downstream (re-reads must not create duplicates)?
- What sets the new high mark, and what if the clock of the ingesting system is skewed?
