# SQL-049 · Commit order vs arrival order: CDC sequence anomalies

**Topic:** CDC, incremental processing & data quality · **Level:** hard · **Interview time:** ~35 min · **Mode:** query

## In plain words

> "Check the change log for events that did not arrive once and in commit order. List each bad event with its problem type and an event that proves it."

**You return:** one row per flagged event: `cdc_event_id`, `source_system`, `business_key`, `operation`, `source_lsn`, `issue_type`, `related_event_id`.

**The fine print, in short:**
- Compare only events of the same key (`source_system`, `business_key`). Arrival order is `cdc_event_id`. The five issue types are defined in the table below.
- If an event fits several types, report only the highest: conflict, then duplicate, then stale, then orphan, then commit-time tie.
- The first copy of a duplicate is not flagged, only later ones. Events with no problem are not returned.

## Business context

The CDC connector team suspects that the message bus reorders and redelivers events. Before
they tune the connector, they want a **data-quality report** on the change log: every event that
violates "arrives once, in commit order", classified by type, with a pointer to the event that
proves the problem.

## Source table

| table | grain | columns you need |
|---|---|---|
| `cdc_transaction_events` | one row per received event | `cdc_event_id` (**arrival order**: a lower id arrived earlier), `source_system`, `business_key`, `operation` (`I`/`U`/`D`), `source_lsn` (commit order within one source system), `commit_ts`, `payload` (jsonb) |

A key is (`source_system`, `business_key`). All comparisons below are between events **of the
same key**.

## Issue definitions

| issue_type | an event E is flagged when ... | related_event_id |
|---|---|---|
| `LSN_CONFLICT` | another event has the same LSN but a different `operation` or `payload` | the lowest `cdc_event_id` among those other events |
| `DUPLICATE_DELIVERY` | an event with the same LSN, same operation and identical payload **arrived earlier** | the lowest `cdc_event_id` among those earlier copies |
| `STALE_ARRIVAL` | an event with a **strictly higher** LSN **arrived earlier** | the lowest `cdc_event_id` among those earlier, higher-LSN events |
| `ORPHAN_CHANGE` | E is a `U` or `D` and no `I` of the key has a lower LSN | NULL |
| `COMMIT_TS_TIE` | another event has the same `commit_ts` but a different LSN (informational: the LSN still decides) | the lowest `cdc_event_id` among those other events |

## Requirements

1. Return **one row per flagged event**. If an event matches several definitions, report only the
   one with the highest precedence:
   `LSN_CONFLICT` > `DUPLICATE_DELIVERY` > `STALE_ARRIVAL` > `ORPHAN_CHANGE` > `COMMIT_TS_TIE`.
2. Events that match no definition are not returned.
3. Arrival order is `cdc_event_id` only (`ingested_at` has ties).
4. Payloads are compared as `jsonb` values (key order and whitespace don't matter).

## Output contract

| column | type | notes |
|---|---|---|
| `cdc_event_id` | bigint | the flagged event |
| `source_system` | text | |
| `business_key` | text | |
| `operation` | text | `I`/`U`/`D` |
| `source_lsn` | bigint | |

## Illustrative example (not the real data)

| cdc_event_id | key | op | lsn | commit_ts | flagged as |
|---|---|---|---|---|---|
| 1 | K | I | 10 | 09:00 | — |
| 2 | K | U | 30 | 09:10 | — |
| 3 | K | U | 20 | 09:05 | `STALE_ARRIVAL`, related 2 |
| 4 | K | U | 30 | 09:10 | `DUPLICATE_DELIVERY`, related 2 (identical to 2) |
| 5 | J | D | 50 | 09:20 | `ORPHAN_CHANGE` (no insert of J) |

## Edge cases you must handle

- The first copy of a duplicated event is **not** a duplicate. Only later copies are.
- Two different events at the same LSN: both are conflicts.
- An event that is both stale and part of a commit_ts tie.
- An insert that arrives after its own update.
- A stale update arriving after a delete.
- A re-insert after a delete is legitimate (not an orphan, not stale).
- The same `business_key` in POS and ECOM, which even share LSN numbers.

## Constraints

One read-only `SELECT`/`WITH` statement, PostgreSQL 17. The log has ~3,800 events here. Be ready
to discuss computing this continuously on a high-volume stream.

## Clarify before you code (what a strong candidate asks)

- Is a duplicate's first copy an anomaly?
- Should an event be reported once or once per issue?
- Are LSNs comparable across source systems?
