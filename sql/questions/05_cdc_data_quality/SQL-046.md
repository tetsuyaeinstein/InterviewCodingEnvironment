# SQL-046 · Incremental upsert of a CDC batch with ON CONFLICT

**Topic:** CDC, incremental processing & data quality · **Level:** medium · **Interview time:** ~20 min · **Mode:** mutation (sandboxed)

## In plain words

> "Write the statement that applies a staging batch of change events to the current-state table, so the table ends up correct even if the batch has repeats or old versions. Running it twice must change nothing."

**You return:** no result set. What is graded is the final contents of `txn_current` (`source_system`, `business_key`, `amount`, `status`, `source_lsn`).

**The fine print, in short:**
- Use PostgreSQL's native upsert. New keys are inserted. An existing key is updated only if the batch's newest version has a strictly higher `source_lsn`.
- The batch can hold one key several times, including exact duplicates. Older or equal versions leave the row unchanged.
- POS and ECOM are separate: the same `business_key` in both systems is two different transactions.

## Business context

A micro-batch job lands change events from the POS and ECOM systems into a staging table every
few minutes. Your job is to apply each batch to the warehouse table holding the **current
version** of every transaction. The table must stay correct even when a batch repeats rows,
contains several versions of the same key, or carries versions older than what the warehouse
already holds.

## Tables (created for you inside a disposable sandbox schema)

| table | grain | columns |
|---|---|---|
| `txn_current` | one row per `(source_system, business_key)`, which is the primary key | `source_system`, `business_key`, `amount numeric(12,2)`, `status`, `source_lsn bigint` |
| `stg_txn_batch` | one row per received change event (**not unique**) | same columns, from inserts and updates in `cdc_transaction_events` |

`source_lsn` is the source system's commit sequence. A higher LSN means a newer version
**within one source system**. POS and ECOM have independent sequences, and the same
`business_key` text can exist in both systems as different transactions.

## Requirements

Write the DML that applies `stg_txn_batch` to `txn_current`:

1. Keys not yet in `txn_current` are inserted.
2. Existing keys are updated to the **newest** version in the batch, but **only if** that version
   is newer than the one already stored (`source_lsn` strictly greater).
3. A batch version that is older than (or equal to) the stored version must leave the row unchanged.
4. The batch may contain the same key several times, including exact duplicates.
5. Use PostgreSQL's native upsert, `INSERT ... ON CONFLICT ... DO UPDATE`.

Your statements run as the grader role inside a sandbox schema whose `search_path` puts the
sandbox first. Everything is rolled back afterwards, so you cannot damage the shared data. Do not
write `BEGIN`/`COMMIT`.

## What is graded

The final contents of `txn_current`, i.e.
`SELECT source_system, business_key, amount, status, source_lsn FROM txn_current`, compared as an
unordered set, plus edge-case assertions.

## Illustrative example (not the real data)

`txn_current` before: `(POS, K1, 10.00, PENDING, 100)`

`stg_txn_batch`:

| source_system | business_key | amount | status | source_lsn |
|---|---|---|---|---|
| POS | K1 | 12.00 | PENDING | 110 |
| POS | K1 | 15.00 | COMPLETED | 120 |
| POS | K1 | 15.00 | COMPLETED | 120 |
| POS | K2 | 7.00 | PENDING | 105 |

After: `(POS, K1, 15.00, COMPLETED, 120)` and `(POS, K2, 7.00, PENDING, 105)`.

## Edge cases you must handle

- Several versions of one key in the same batch (a single `INSERT ... ON CONFLICT` statement
  cannot touch the same target row twice).
- Exact duplicate rows in the batch.
- A stored row that is newer than everything in the batch.
- The same `business_key` in two different source systems.

## Constraints

PostgreSQL 17. Prefer one statement. Be ready to explain why a re-run of the same batch is harmless.
