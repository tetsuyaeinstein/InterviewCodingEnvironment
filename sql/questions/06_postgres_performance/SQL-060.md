# SQL-060 · Deduplicate, enforce a unique key, then load idempotently with ON CONFLICT DO NOTHING

**Topic:** PostgreSQL performance & load design · **Level:** hard · **Interview time:** ~30 min · **Mode:** mutation (sandboxed)

## In plain words

> "Our events table has duplicate deliveries and no key. Clean it up, make the database reject duplicates from now on, then load the new batch so that re-running it is harmless."

**You return:** no result set. What is graded is the final contents of `txn_events`, and that a unique key on `message_id` exists.

**The fine print, in short:**
- Do three steps in this order: remove duplicates keeping, per `message_id`, the row with the earliest `delivered_at`. Add a unique key on `message_id`. Load `new_batch` using PostgreSQL's native upsert.
- A message already stored is skipped and its stored row is kept. A message repeated inside the batch is inserted once, with its earliest `delivered_at`.
- Do not change `new_batch`. Do not write `BEGIN` or `COMMIT`.

## Business context

A message broker delivers transaction events **at least once**: the same message (same
`message_id`) can arrive several times. The landing table `txn_events` was created years ago
without a key and already contains redeliveries. Before the next micro-batch is loaded the
platform team wants three things done, in order:

1. Clean up the existing duplicates.
2. Make the **database** reject duplicates from now on (not just the loader code).
3. Load the new batch so that re-running the load, or a batch that repeats a message, is harmless.

In production the table has about **500 million rows**, so be ready to discuss how the approach scales.

## Tables (created for you inside a disposable sandbox schema)

| table | grain | columns |
|---|---|---|
| `txn_events` | one row per received delivery (currently **not unique** per message) | `message_id text`, `transaction_id bigint`, `event_type text`, `delivered_at timestamptz`, `payload jsonb` |
| `new_batch` | the next micro-batch, **not unique** either | same columns, all `NOT NULL` |

`txn_events` has no constraint or index at the start.

## Requirements

Write the statements, in this order:

1. **De-duplicate `txn_events`**: for every `message_id` keep exactly **one** row, the one with the
   **earliest `delivered_at`**. Rows of messages that were delivered once must stay.
2. **Enforce the key** on `txn_events`: add a unique constraint (or unique index) on `message_id`.
3. **Load `new_batch`** into `txn_events` with `INSERT ... ON CONFLICT DO NOTHING`:
   - a message that is already stored is skipped (the stored row is kept as it is);
   - a message that appears several times **inside the batch** is inserted once, using its
     **earliest** `delivered_at`;
   - new messages are inserted.
4. Do not change `new_batch`. Do not write `BEGIN`/`COMMIT`.

Your statements run as the grader role in a sandbox schema whose `search_path` puts the sandbox
first; everything is rolled back afterwards.

## What is graded

- The final contents of `txn_events`
  (`message_id, transaction_id, event_type, delivered_at, payload->>'amount' AS amount`), compared as a set.
- Edge-case assertions on the sandbox state, including a check that a **valid unique index or
  constraint on `txn_events(message_id)`** exists in the sandbox schema.
- Source text: it must contain `ON CONFLICT` and a `UNIQUE` / `PRIMARY KEY` definition.

## Illustrative example (not the real data)

`txn_events` before: `(A, t1 10:00)`, `(A, t1 10:02)`, `(B, t2 10:01)`. `new_batch`: `(B, 10:05)`,
`(C, 10:06)`, `(D, 10:09)`, `(D, 10:08)`.

After: `(A, 10:00)`, `(B, 10:01)`, `(C, 10:06)`, `(D, 10:08)`.

## Edge cases you must handle

- Several identical-looking copies of one message: they have the same values in every column
  except possibly `delivered_at`, so you need something to tell physical rows apart, or a rewrite.
- The unique constraint cannot be created while duplicates exist.
- The batch contains one message twice, with the **later** delivery listed first.
- The batch repeats a message that is already stored (with a different `delivered_at`).
- `ON CONFLICT DO NOTHING` must name the right conflict target and must not be the
  mechanism that silently hides a missing constraint: without the constraint there is no conflict.

## Constraints

PostgreSQL 17. Everything runs in one sandbox transaction. Prefer set-based statements.

## Clarify before you code (what a strong candidate asks)

- Is `message_id` really the dedup key, or is it `(transaction_id, event_type)`? (Two different
  `message_id`s can still describe the same business event: double posting.)
- Which copy wins: earliest, latest, or the one with the most complete payload?
- Can the table be locked or rewritten, or must the cleanup run online in batches?
- Does a concurrent loader keep inserting while you add the constraint?
