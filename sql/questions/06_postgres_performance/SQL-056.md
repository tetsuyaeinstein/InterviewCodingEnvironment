# SQL-056 · Typed attributes from messy JSON without errors (amount, member flag, device)

**Topic:** PostgreSQL performance & semi-structured data · **Level:** medium · **Interview time:** ~25 min · **Mode:** query

## Business context

Product analytics wants a typed, queryable view of clickstream payloads for a pilot customer
(customer 67), whose events exercise every way the mobile app and the web shop have ever
serialised JSON. `customer_events.payload` has **inconsistent typing**: `amount` can be a JSON
number, a numeric string, a padded string, scientific notation, `"N/A"`, `null` or missing. A
single bad value must **never abort the whole query**, because this logic ends up in a nightly
job over 500 million events.

## Source table

| table | grain | columns you need |
|---|---|---|
| `customer_events` | one row per client event | `event_id` (bigint), `customer_id`, `event_type`, `payload` (jsonb) |

Payload keys used here: `amount`, `is_member`, `device`.

## Requirements

Return **one row per event of customer 67** (all event types) with these rules.

1. **`amount` (numeric):**
   - JSON number: its value.
   - JSON string: surrounding whitespace is **trimmed**, then the text is parsed as a decimal
     number. Scientific notation is valid (`"1e3"` is 1000). Anything that does not parse
     (`"N/A"`, `""`, `"abc"`) gives NULL. `NaN` and `Infinity` are **not** valid amounts.
   - Missing key, JSON `null`, or any other JSON type: NULL.
   - Negative numbers are kept as they are.
2. **`is_member` (boolean):** a JSON boolean is used as is. A JSON string is accepted only when
   it is (case-insensitively, trimmed) exactly `true` or `false`. **Everything else is NULL**,
   including strings such as `"yes"`, `"1"`, `"on"`, and a missing key.
3. **`device` (text):** the text of the `device` key, NULL when missing.
4. **`has_amount_issue` (boolean, never NULL)** is true when
   - the event is a `checkout` and the parsed `amount` is NULL, or
   - the parsed `amount` is negative (any event type).
5. **`amount_issue` (text):** the reason, otherwise NULL.
   - `NEGATIVE`: parsed amount below zero.
   - `MISSING`: checkout whose `amount` key is absent or JSON `null`.
   - `INVALID`: checkout whose `amount` is present but not parsable (including wrong JSON types).
   - Events other than checkouts have no amount issue unless the amount is negative.

## Output contract

| column | type | notes |
|---|---|---|
| `event_id` | bigint | |
| `event_type` | text | |
| `amount` | numeric | compared rounded to 2 decimals |
| `is_member` | boolean | |
| `device` | text | |
| `has_amount_issue` | boolean | |
| `amount_issue` | text | `NEGATIVE`, `MISSING`, `INVALID` or NULL |

Ordering: none required.

## Illustrative example (not the real data)

| payload | amount | is_member | device | has_amount_issue | amount_issue |
|---|---|---|---|---|---|
| checkout `{"amount": "9.50", "is_member": true, "device": "web"}` | 9.50 | true | web | false | NULL |
| checkout `{"amount": "free", "is_member": "on"}` | NULL | NULL | NULL | true | INVALID |
| page_view `{"page": "/x"}` | NULL | NULL | NULL | false | NULL |

## Edge cases you must handle

- A string that cannot be cast: the query must still return every row, not raise
  `invalid input syntax for type numeric`.
- Numeric strings with padding or exponent notation.
- A value that PostgreSQL's own boolean input would accept but the contract above does not.
- Events that are not checkouts: no `MISSING` flag just because they have no amount.
- Three-valued logic: `has_amount_issue` must be true/false, never NULL.

## Constraints

One read-only `SELECT`/`WITH`, PostgreSQL 17 (which has built-in functions to test whether a
text value is valid for a type). Be ready to explain why the cast `(payload->>'amount')::numeric`
is not acceptable at scale.

## Clarify before you code (what a strong candidate asks)

- Should invalid values be NULL, an error, a quarantine row, or a default?
- How is padding handled: trim, reject, or keep as text?
- Are numeric strings with thousands separators or locale commas possible?
- Is a negative amount an error (refund) or valid data?
