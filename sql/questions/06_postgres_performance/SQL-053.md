# SQL-053 · Composite index column order for equality + range + ORDER BY ... LIMIT

**Topic:** PostgreSQL performance · **Level:** hard · **Interview time:** ~30 min · **Mode:** plan, sandboxed (result + plan facts graded, interpretation via rubric)

## Business context

The customer portal shows "the 20 oldest transactions of an account in a quarter", paged by
the front end. In production `transactions` has about **500 million rows** and the portal's
heaviest accounts have millions of them. The baseline indexes are single-column
(`customer_id`) or time-led (`transaction_ts`, `(store_id, transaction_ts)`); there is
deliberately **no** `(customer_id, transaction_ts)` index.

You get a disposable sandbox schema that holds `txn_copy`, a copy of `transactions` with fresh
statistics and **no indexes at all**. Create the index you think is best, then write the query.
Everything is rolled back afterwards, so nothing in the shared database changes.

## Sandbox table (created for you)

| table | grain | columns |
|---|---|---|
| `txn_copy` | one row per transaction (copy of `public.transactions`) | `transaction_id`, `customer_id`, `store_id`, `transaction_ts` (timestamptz, UTC), `gross_amount`, `currency`, `transaction_status`, `payment_method`, `source_system`, `ingested_at` |

## Requirements

Your answer is a script with the **last statement** being the query. Before it you may run
`CREATE INDEX`, `ANALYZE` and `SET LOCAL enable_*` statements.

The query returns, for customer **1001**, the **20 oldest** transactions with `transaction_ts`
in `[2025-04-01 00:00 UTC, 2025-07-01 00:00 UTC)`, oldest first. All statuses count. Read
`txn_copy`, not `public.transactions`.

## Output contract

| column | type | notes |
|---|---|---|
| `transaction_id` | bigint | |
| `transaction_ts` | timestamptz | |
| `store_id` | integer | |

Ordering: **graded**, `transaction_ts` ascending (customer 1001 has no two rows with the same

## What is graded

Automatically:

- The result (ordered) and edge-case assertions.
- Required plan facts: `txn_copy` is read through an **index scan** that uses your index; the
  index condition **starts with `customer_id`**; there is **no Sort node** (the index supplies
  the order); no sequential scan of `txn_copy`.
- Advisory: no `Rows Removed by Filter` (every index entry visited was useful).

By you, against the rubric: why that column order, what the other orders do, and what changes at
500M rows. Try the alternatives (for example `(transaction_ts, customer_id)` or
`(customer_id)` alone) and compare the plans and `Buffers:` before you settle.

## Constraints

PostgreSQL 17. Only `CREATE INDEX`, `ANALYZE` and `SET LOCAL enable_* / work_mem / random_page_cost / jit`
may precede the final `SELECT`. Do not write `EXPLAIN`. The final statement must be the `SELECT`.

## Clarify before you code (what a strong candidate asks)

- Is the page always the oldest 20, or does the front end page forward (keyset)? Newest first?
- How skewed are accounts: the median customer has dozens of rows, the largest millions.
- Which other queries use `customer_id` alone, or `transaction_ts` alone? Can the new index replace an existing one?
- How write-heavy is the table, and can the index be built `CONCURRENTLY`?
