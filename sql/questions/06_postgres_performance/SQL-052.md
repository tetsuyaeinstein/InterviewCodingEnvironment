# SQL-052 · Make a one-day filter sargable (half-open timestamp range)

**Topic:** PostgreSQL performance · **Level:** medium · **Interview time:** ~15 min · **Mode:** plan (result + plan facts graded)

## Business context

Finance runs a "daily store close" report every morning. On the 500-million-row production
table it takes minutes, even though one day is a tiny slice of the data and there is an index
on `transaction_ts`. The report's filter is:

`WHERE transaction_status = 'COMPLETED' AND transaction_ts::date = DATE '2025-02-28'`

`EXPLAIN` shows a sequential scan of the whole table. Rewrite the query so it returns **exactly
the same rows** but lets the planner use `ix_transactions_ts`.

## Source table

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `store_id`, `transaction_ts` (timestamptz, UTC), `gross_amount`, `transaction_status` |

Index you are expected to use: `ix_transactions_ts (transaction_ts)`.

## Requirements

1. The business day is **2025-02-28 in UTC**. Lab sessions run with `TimeZone = UTC`, which is
   what the original `::date` cast relied on.
2. Only `transaction_status = 'COMPLETED'`.
3. One row per store that has at least one completed transaction that day.
4. The filter on `transaction_ts` must compare the **bare column** with constant bounds: no cast,
   no `AT TIME ZONE`, no date function on the column, and no `BETWEEN` (write a half-open range).

## Output contract

| column | type | notes |
|---|---|---|
| `store_id` | integer | |
| `completed_txns` | bigint | number of completed transactions that UTC day |
| `gross_sales` | numeric | sum of `gross_amount`, compared rounded to 2 decimals |

Ordering: none required.

## Illustrative example (not the real data)

| store_id | completed_txns | gross_sales |
|---|---|---|
| 11 | 3 | 140.25 |
| 24 | 1 | 9.99 |

## Edge cases you must handle

- A transaction one second before midnight at the end of the day belongs to the day.
- A transaction at exactly midnight at the start of the **next** day does not.
- Stores whose only transactions that day were not completed are not listed.

## What is graded

- The result (unordered) and edge-case assertions.
- Objective plan facts from `EXPLAIN (ANALYZE, BUFFERS)`: the day must be read through
  `ix_transactions_ts`, with no sequential scan of `transactions`.
- The source text must not cast or wrap `transaction_ts`.

## Constraints

One read-only `SELECT`, PostgreSQL 17, written without the `EXPLAIN` keyword.

## Clarify before you code (what a strong candidate asks)

- Is "the day" a UTC day or a store-local day? (Here: UTC.)
- What session time zone does the report run with, and does the rewrite depend on it?
- Is the bound inclusive at midnight on both sides?
- Would an expression index on `transaction_ts::date` be an acceptable alternative? Why might it be rejected?
