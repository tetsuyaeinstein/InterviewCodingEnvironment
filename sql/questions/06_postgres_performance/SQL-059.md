# SQL-059 · Partition pruning on a monthly range-partitioned fact table

**Topic:** PostgreSQL performance · **Level:** hard · **Interview time:** ~25 min · **Mode:** plan (result + plan facts graded, interpretation via rubric)

## Business context

`fact_sales_partitioned` is the line-grain sales fact, range-partitioned by month on `sale_date`
(`fact_sales_p2024_01` ... `fact_sales_p2025_12`, plus a default partition). In production it holds
about **500 million lines** over five years. The month-end close needs December 2025 net sales
per store. A first version, `WHERE to_char(sale_date, 'YYYY-MM') = '2025-12'`, scans **every**
partition and takes minutes. Write the version that reads only the December partition.

## Source table

| table | grain | columns you need |
|---|---|---|
| `fact_sales_partitioned` | one row per COMPLETED sales line | `sale_date` (date, the partition key), `store_id`, `net_amount` (numeric) |

Partitions: monthly, named `fact_sales_pYYYY_MM`, 2024-01 through 2025-12, plus `fact_sales_p_default`.

## Requirements

1. All sales lines with `sale_date` in **December 2025** (`2025-12-01` through `2025-12-31`, i.e. the half-open range
   `[2025-12-01, 2026-01-01)`).
2. One row per store that has at least one line in the period.
3. Query the **parent table** `fact_sales_partitioned`. Do not name a partition.
4. Filter on the **bare partition key**: no function, cast or text conversion of `sale_date`.

## Output contract

| column | type | notes |
|---|---|---|
| `store_id` | integer | |
| `line_count` | bigint | number of lines |
| `net_sales` | numeric | sum of `net_amount`, compared rounded to 2 decimals |

Ordering: none required.

## Illustrative example (not the real data)

| store_id | line_count | net_sales |
|---|---|---|
| 12 | 140 | 3,215.40 |
| 31 | 75 | 1,820.00 |

## What is graded

Automatically:

- The result and edge-case assertions.
- Source text: no date function / cast on `sale_date`, no partition named in the query.
- Required plan facts (`EXPLAIN (ANALYZE, BUFFERS)`): `fact_sales_p2025_12` is scanned; **no** 2024
  partition, **no** Jan-Nov 2025 partition and **not** the default partition appears in the plan.
- Advisory: the plan has no `Append` over several children.

By you, against the rubric: when pruning happens (plan time vs run time), why the `to_char`
version cannot prune, what changes with prepared statements and parameters, and what partitioning
costs. Run the slow `to_char` version once with `lab run` (in a scratch file) and compare plans.

## Constraints

One read-only `SELECT`, PostgreSQL 17, without the `EXPLAIN` keyword.

## Clarify before you code (what a strong candidate asks)

- Is the month boundary UTC? (`sale_date` is a plain date; the conversion from timestamp was done at load.)
- Will the month come from a parameter (prepared statement, BI tool) rather than a literal?
- What is in the default partition, and should reports include it?
- Does the report join other tables, and can that join also be pruned?
