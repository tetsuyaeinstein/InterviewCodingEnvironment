# SQL-051 · Read an EXPLAIN (ANALYZE, BUFFERS) plan for a customer statement query

**Topic:** PostgreSQL performance · **Level:** medium · **Interview time:** ~20 min · **Mode:** plan (result graded + plan shown + self-assessed rubric)

## Business context

The account-management portal shows enterprise customers a monthly statement. Support says the
statement for the biggest account is "sometimes slow" and asks you to look at it. In production
`transactions` holds about **500 million rows**. The lab holds the small seed (about 21,000 rows),
so the timings mean nothing, but the **shape** of the plan does.

Your job has two parts:

1. Write the statement query (its result is graded).
2. Read the `EXPLAIN (ANALYZE, BUFFERS)` output that `lab check` prints for it, and explain it the
   way you would in an interview: access path, estimated vs actual rows, sorting, buffers, and the
   index you would propose. Then compare your notes with the rubric that `lab check` prints.

## Source table

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `transaction_id`, `customer_id`, `store_id`, `transaction_ts` (timestamptz, UTC), `gross_amount`, `transaction_status` |

Existing indexes on `transactions` (do not assume any others): primary key `(transaction_id)`,
`ix_transactions_customer (customer_id)`, `ix_transactions_ts (transaction_ts)` and
`ix_transactions_store_ts (store_id, transaction_ts)`.

## Requirements

1. Customer **1001** only.
2. Only `transaction_status = 'COMPLETED'` transactions.
3. December 2024 in UTC: `transaction_ts` from 2024-12-01 00:00:00 UTC (inclusive) to
   2025-01-01 00:00:00 UTC (exclusive).
4. Order the rows by `transaction_ts`, then `transaction_id` (oldest first; the id breaks ties).

## Output contract

| column | type | notes |
|---|---|---|
| `transaction_id` | bigint | |
| `transaction_ts` | timestamptz | unchanged from the table |
| `store_id` | integer | |
| `gross_amount` | numeric | compared rounded to 2 decimals |

Ordering: **graded** (`transaction_ts`, then `transaction_id`, ascending).

## Illustrative example (not the real data)

| transaction_id | transaction_ts | store_id | gross_amount |
|---|---|---|---|
| 500017 | 2024-12-02 08:14:00+00 | 12 | 31.40 |
| 500233 | 2024-12-02 08:14:00+00 | 9 | 7.95 |
| 501870 | 2024-12-05 19:02:11+00 | 12 | 112.00 |

## What to write down after `lab check` (before you read the rubric)

- Which node reads `transactions`, which index it uses, and what is in `Index Cond` vs `Filter`.
- Estimated rows vs actual rows on that node, and where the estimate comes from.
- How many rows were read and thrown away, and what that would mean at 500 million rows.
- Whether and how the planner sorts, and what "Presorted Key" tells you.
- What the `Buffers:` lines mean (`shared hit` vs `read`), and why the timing is not evidence.
- The index you would create for this query, its column order, and its cost on writes.

## Constraints

- One read-only `SELECT`, PostgreSQL 17. Write the query **without** the `EXPLAIN` keyword;
  `lab check` adds `EXPLAIN (ANALYZE, BUFFERS)` itself.
- Keep the predicates on the raw columns so the planner can use the existing indexes.

## Clarify before you code (what a strong candidate asks)

- Is "December" defined in UTC or in the customer's or store's local time?
- Do cancelled or pending transactions belong on a statement?
- Is the page size bounded, or does the portal fetch the whole month?
- How often does the query run, and how write-heavy is the table (cost of a new index)?
