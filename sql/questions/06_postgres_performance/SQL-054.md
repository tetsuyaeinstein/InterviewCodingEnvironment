# SQL-054 · Quantify key skew before choosing a distribution key (stores, customers, guest NULL)

**Topic:** PostgreSQL performance & distributed-engine design · **Level:** hard · **Interview time:** ~30 min · **Mode:** modeling (query graded + written rationale graded with a rubric)

## Business context

The platform team is moving the 500-million-row `transactions` fact to a hash-distributed
warehouse (Azure Synapse dedicated pool, 60 distributions) and a Spark lake. Someone proposes
`HASH(store_id)` for the fact and `customer_id` for the customer-centric marts. Before the
design review, you must show with data how uneven those keys are, and say what that means for
the distribution choice. You work on the seeded subset, but the skew pattern is what matters.

## Source table

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `store_id`, `customer_id` (NULL = guest checkout) |

## Requirements

1. Count **all** transactions, whatever their status (distribution cares about stored rows).
2. Report two kinds of key: `store` (by `store_id`) and `customer` (by `customer_id`).
3. Treat the **guest bucket (`customer_id IS NULL`) as one key** of the customer kind, with
   `key_value` = `(null)`. It competes for a place in the top 5 like any other key.
4. For each key kind, rank keys by `txn_count` descending (rank 1 = most rows). Ties are broken
   by the key's numeric value ascending (the guest bucket sorts as key 0). Ranks are unique
   (1, 2, 3, ...): no shared ranks.
5. Keep the **top 5** keys of each kind.
6. `pct_of_total` = `txn_count` as a percentage of **all** transactions (the same denominator for
   both kinds), rounded to 2 decimals.

## Output contract

| column | type | notes |
|---|---|---|
| `key_type` | text | `store` or `customer` |
| `key_value` | text | the id as text; `(null)` for the guest bucket |
| `rank_in_type` | integer | 1..5 within each `key_type` |
| `txn_count` | bigint | transactions with that key |
| `pct_of_total` | numeric | percent of all transactions, 2 decimals |

Ordering: **graded**: `key_type` ascending, then `rank_in_type` ascending (10 rows).

## Illustrative example (not the real data)

| key_type | key_value | rank_in_type | txn_count | pct_of_total |
|---|---|---|---|---|
| customer | 77 | 1 | 600 | 30.00 |
| customer | (null) | 2 | 250 | 12.50 |
| store | 3 | 1 | 900 | 45.00 |

## The written part: RATIONALE

Below your query, fill in the `-- RATIONALE:` comment block (at least 80 words) in the practice
file. Cover, in your own words:

- What the numbers say about `store_id` and `customer_id` as hash-distribution keys on 60
  distributions, and what happens to a query's elapsed time.
- What happens to the guest (NULL) rows when you hash on `customer_id`.
- At least two mitigations (for example for hot keys, for joins to small dimensions, for NULL keys)
  and the trade-off of each.

`lab check` prints a rubric to compare against. The rationale is only checked for length
automatically.

## Constraints

One read-only `SELECT`/`WITH` statement, PostgreSQL 17. Rows are compared exactly, in the order
given above.

## Clarify before you code (what a strong candidate asks)

- Do cancelled/declined rows count towards skew? (Yes for storage and shuffle; maybe not for a
  mart that filters them first.)
- Is the skew stable over time, or are there hot days (campaigns) as well as hot keys?
- Which joins and aggregations will run on this table? The distribution key should match the
  most frequent join or group key, not just be even.
- What is the NULL policy for `customer_id` in downstream marts?
