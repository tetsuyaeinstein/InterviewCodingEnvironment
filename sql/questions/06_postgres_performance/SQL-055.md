# SQL-055 · p50 / p95 ingestion delay per source with ordered-set aggregates

**Topic:** PostgreSQL performance & SLAs · **Level:** medium · **Interview time:** ~20 min · **Mode:** query

## In plain words

> "For each source system, what are the median and 95th percentile ingestion delays in December 2025?"

**You return:** one row per source system with at least one event in the window: `source_system`, `loaded_events`, `skewed_events_excluded`, `p50_delay_s`, `p95_delay_s`.

**The fine print, in short:**
- Per event, only its first successful (`LOADED`) attempt counts: earliest `ingest_ts`, ties by `log_id`. Retried, duplicate and rejected rows are never used. Events by `event_ts` in December 2025 (UTC).
- Delay is in seconds. Negative delays are counted in `skewed_events_excluded` and left out of the percentiles. A delay of exactly 0 is valid.
- Percentiles interpolate between the two nearest values and are rounded to 2 decimals.

## Business context

The data platform promises downstream teams "95% of events are loaded within 15 minutes".
Averages hide the tail, so the SRE team wants the **median and 95th percentile ingestion delay
per source system** for December 2025. The log has one row per **ingestion attempt**, and
retries, duplicates and rejections all leave rows, so the first job is to decide which attempt
defines "the delay of an event". The log also contains a few rows with a negative delay (the
producer's clock ran ahead of the ingester).

## Source table

| table | grain | columns you need |
|---|---|---|
| `event_ingestion_log` | one row per ingestion attempt (`raw_event_id` repeats on retry) | `log_id`, `raw_event_id`, `source_system`, `event_ts` (timestamptz), `ingest_ts` (timestamptz), `ingestion_status` (`LOADED`, `REJECTED`, `DUPLICATE`, `RETRIED`) |

## Requirements

1. **Which attempt counts:** for each `raw_event_id`, only its **first `LOADED` attempt** (earliest
   `ingest_ts`, ties by `log_id`). `RETRIED`, `DUPLICATE` and `REJECTED` rows are never used.
   An event that never reached `LOADED` is not part of the statistics.
2. **Delay** = `ingest_ts - event_ts` of that attempt, in **seconds**.
3. **Window:** events whose `event_ts` is in `[2025-12-01 00:00 UTC, 2026-01-01 00:00 UTC)`.
4. **Negative delays (clock skew)** are excluded from the percentiles but counted. A delay of
   exactly 0 is valid and is included.
5. Percentiles use **linear interpolation** between the two nearest values (the continuous
   definition), not nearest-rank. Round each percentile to **2 decimals**.
6. One row per `source_system` that has at least one event in the window.

## Output contract

| column | type | notes |
|---|---|---|
| `source_system` | text | |
| `loaded_events` | bigint | events included in the percentiles (non-negative delay) |
| `skewed_events_excluded` | bigint | events dropped because the delay was negative |
| `p50_delay_s` | numeric | median delay in seconds, 2 decimals |
| `p95_delay_s` | numeric | 95th percentile delay in seconds, 2 decimals |

Ordering: none required.

## Illustrative example (not the real data)

Source `X`, first-LOADED delays in seconds: `-10, 0, 10, 20, 100`.

`-10` is skew: excluded. The remaining four sorted values are 0, 10, 20, 100.
`loaded_events = 4`, `skewed_events_excluded = 1`, p50 = 15.00 (halfway between 10 and 20),
p95 = 88.00 (position 1 + 0.95 * 3 = 3.85, so 20 + 0.85 * (100 - 20)).

## Edge cases you must handle

- An event that was `RETRIED` first and `LOADED` later: its delay is the delay of the `LOADED`
  attempt (later), not of the failed attempt.
- An event with a `LOADED` row and a later `DUPLICATE` row: the duplicate does not create a
  second observation.
- An event that was only `REJECTED`: absent from the statistics.
- Heavy tail: one event arrived two days late. A mean would be dominated by it; a percentile is not.
- Negative delay: counted in `skewed_events_excluded`, not in `loaded_events`.

## Constraints

One read-only `SELECT`/`WITH`, PostgreSQL 17. Use PostgreSQL ordered-set aggregates or an
equivalent technique. Be ready to explain why the **definition** (which attempt, which window,
how skew is treated, which percentile formula) matters as much as the code.

## Clarify before you code (what a strong candidate asks)

- Delay until the first attempt, the first success, or the last attempt?
- Are negative delays errors to drop, or values to clamp to 0? How many are there?
- Continuous or discrete percentile? Does the SLA contract say?
- Is the window defined by `event_ts` or by `ingest_ts`? (Late events change past windows.)
