# SQL-004 · Classify duplicate deliveries in an at-least-once event feed

**Topic:** foundations · **Level:** hard · **Interview time:** ~30 min · **Mode:** query

## Business context

Transaction events reach the lake from a message broker with **at-least-once** delivery. Every
delivery is landed as-is in `raw_transaction_events`. Before the platform team builds the
deduplicating loader, they want a data-quality report explaining **why** a business key
(`transaction_id`) shows up in more than one delivery. Some repeats are harmless transport
noise, some are expected business events, and some are real upstream defects that must be raised
with the producing team.

## Source table

| table | grain | columns |
|---|---|---|
| `raw_transaction_events` | one row per **delivery** (`delivery_id` is unique) | `delivery_id`, `message_id`, `transaction_id`, `event_type` (`CREATED` / `STATUS_CHANGED`), `delivered_at`, `payload` (jsonb) |

Semantics of the identifiers:

- `message_id` identifies one logical message from the producer. When the broker redelivers a
  message, the new delivery has a new `delivery_id` but the **same** `message_id` and payload.
- `transaction_id` is the business key. Each transaction should have exactly **one** `CREATED`
  message. A `STATUS_CHANGED` message (with its own new `message_id`) is a legitimate later
  lifecycle event, for example `PENDING` → `COMPLETED`.

## Requirements

Report every `transaction_id` that appears in **more than one delivery**, with these metrics:

1. `deliveries`: number of delivery rows for the transaction.
2. `distinct_messages`: number of distinct `message_id`s.
3. `created_messages`: number of distinct `message_id`s with `event_type = 'CREATED'`.
4. `status_change_messages`: number of distinct `message_id`s with `event_type = 'STATUS_CHANGED'`.
5. `has_redelivery`: true when at least one message was delivered more than once.
6. `classification`: exactly one label, using the **first** rule that applies (top to bottom):

| precedence | classification | rule |
|---|---|---|
| 1 | `CONFLICTING_DUPLICATE` | two or more distinct `CREATED` messages, and their payloads are **not** all identical |
| 2 | `BUSINESS_KEY_DUPLICATE` | two or more distinct `CREATED` messages, all with identical payloads |
| 3 | `LIFECYCLE_EVENTS` | otherwise, more than one distinct message (one creation plus status changes) |
| 4 | `REDELIVERY_ONLY` | otherwise: a single message delivered several times |

Payloads are compared as JSON **values** (key order and formatting do not matter); `delivered_at`
and `delivery_id` are never part of the comparison. Payloads of `STATUS_CHANGED` messages are
not compared: they are expected to differ.

## Output contract

| column | type | notes |
|---|---|---|
| `transaction_id` | bigint | one row per repeated business key |
| `deliveries` | integer | ≥ 2 |
| `distinct_messages` | integer | |
| `created_messages` | integer | |
| `status_change_messages` | integer | |
| `has_redelivery` | boolean | |
| `classification` | text | one of the four labels above |

Ordering: none required (unordered set). Transactions with exactly one delivery are not returned.

## Illustrative example (not the real data)

| delivery_id | message_id | transaction_id | event_type | payload |
|---|---|---|---|---|
| 1 | m-A | 900 | CREATED | `{"amount": "5.00", "status": "PENDING"}` |
| 2 | m-B | 900 | STATUS_CHANGED | `{"amount": "5.00", "status": "COMPLETED"}` |
| 3 | m-B | 900 | STATUS_CHANGED | `{"amount": "5.00", "status": "COMPLETED"}` |
| 4 | m-C | 901 | CREATED | `{"amount": "8.00", "status": "COMPLETED"}` |
| 5 | m-D | 901 | CREATED | `{"amount": "8.50", "status": "COMPLETED"}` |

Expected:

| transaction_id | deliveries | distinct_messages | created_messages | status_change_messages | has_redelivery | classification |
|---|---|---|---|---|---|---|
| 900 | 3 | 2 | 1 | 1 | true | LIFECYCLE_EVENTS |
| 901 | 2 | 2 | 2 | 0 | false | CONFLICTING_DUPLICATE |

## Edge cases you must handle

- One message delivered three times (only transport noise).
- A creation followed by a status change: two messages, nothing is wrong.
- The same creation posted twice under two different `message_id`s with identical content.
- Two creations for one key that disagree on the content.
- Combinations: a status change that is also redelivered; a double-posted creation plus a status change.

## Constraints

- One read-only `SELECT` / `WITH` statement, valid PostgreSQL 17.
- The production feed carries about 50 million deliveries per day. Be ready to explain which key
  the downstream loader should deduplicate on, and why a consumer must be idempotent.

## Clarify before you code (what a strong candidate asks)

- What exactly identifies a duplicate: the delivery, the message or the business key?
- Can a redelivered message ever carry a different payload than the original?
- If a key is both double-posted and redelivered, which finding matters most to report?
- For a conflicting duplicate, which version should the loader keep (first, last, or quarantine)?
