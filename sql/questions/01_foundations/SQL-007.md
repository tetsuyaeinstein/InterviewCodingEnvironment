# SQL-007 · Orphan and broken lines in the staging table

**Topic:** foundations · **Level:** medium · **Interview time:** ~15 min · **Mode:** query

## Business context

Order lines are landed by a bulk loader into `stg_transaction_items` **without any constraints**.
Before a batch is merged into the warehouse, a data-quality gate must list every staging line that
would break referential integrity, together with a machine-readable reason, so the loader can
quarantine those rows and alert the source team.

## Source tables

| table | grain | columns you need |
|---|---|---|
| `stg_transaction_items` | **none** (no key, no constraints; rows can repeat) | `load_batch_id`, `transaction_id`, `line_number`, `product_id` |
| `transactions` | one row per transaction (`transaction_id` is the primary key) | `transaction_id` |
| `products` | one row per product (`product_id` is the primary key) | `product_id` |

## Requirements

1. Check every staging row of **every** load batch.
2. A row is broken when its `transaction_id` or its `product_id` is NULL, or does not exist in the
   parent table.
3. Give each broken row exactly one `issue`, using the **first** rule that applies:

| precedence | issue | rule |
|---|---|---|
| 1 | `NULL_TRANSACTION_ID` | `transaction_id` is NULL |
| 2 | `NULL_PRODUCT_ID` | `product_id` is NULL |
| 3 | `MISSING_TRANSACTION_AND_PRODUCT` | neither the transaction nor the product exists |
| 4 | `MISSING_TRANSACTION` | the transaction does not exist (the product does) |
| 5 | `MISSING_PRODUCT` | the product does not exist (the transaction does) |

4. Return **one output row per broken staging row** (if a broken row was loaded twice, it appears twice).
5. Rows whose references are both valid are **not** returned, even if they are exact duplicates
   of each other. Duplicate valid lines are a different data-quality rule (a uniqueness check on
   `(transaction_id, line_number)`), not a referential one.
6. `line_number`, `quantity` and prices are not validated here.

## Output contract

| column | type | notes |
|---|---|---|
| `load_batch_id` | integer | |
| `transaction_id` | bigint | as staged (may be NULL) |
| `line_number` | integer | as staged (may be NULL) |
| `product_id` | integer | as staged (may be NULL) |
| `issue` | text | one of the five labels above |

Ordering: none required (unordered set).

## Illustrative example (not the real data)

Parents: transactions {10, 11}, products {1, 2}.

| load_batch_id | transaction_id | line_number | product_id | issue |
|---|---|---|---|---|
| 7 | 10 | 1 | 1 | (valid, not returned) |
| 7 | 10 | 1 | 1 | (valid duplicate, not returned) |
| 7 | 12 | 1 | 2 | `MISSING_TRANSACTION` |
| 7 | 11 | 2 | 9 | `MISSING_PRODUCT` |
| 7 | NULL | NULL | 2 | `NULL_TRANSACTION_ID` |

## Edge cases you must handle

- NULL foreign keys, which must not be reported as "missing" and must not silently disappear.
- A row where both references are dangling.
- A dangling product on an otherwise valid transaction.
- Valid rows that occur twice.

## Constraints

- One read-only `SELECT` / `WITH` statement, valid PostgreSQL 17.
- Production batches hold ~20M lines; the parents hold 500M transactions and 50k products. Your
  approach must not multiply staging rows.

## Clarify before you code (what a strong candidate asks)

- Should the gate check only the newest batch or all batches?
- Is a NULL key a "missing reference" or a separate defect?
- Should duplicate broken rows be reported once or per occurrence?
- What happens downstream: quarantine the row, the whole transaction, or the whole batch?
