# SQL-006 · Store status mix for 2025 in one row per store

**Topic:** foundations · **Level:** easy · **Interview time:** ~12 min · **Mode:** query

## Business context

Store operations wants a single wide row per store showing how 2025 checkouts ended: completed,
still pending, cancelled or declined. The dashboard tool cannot pivot, so the pivot has to happen
in SQL.

## Source table

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `store_id`, `transaction_ts` (UTC), `gross_amount`, `transaction_status` |

## Requirements

1. Scope: all transactions (all four statuses, guests included) with a **UTC business date in
   2025**, i.e. `transaction_ts` in `[2025-01-01 00:00:00 UTC, 2026-01-01 00:00:00 UTC)`.
2. One row per store that has **at least one** in-scope transaction.
3. For `COMPLETED`, `PENDING` and `CANCELLED`, report both the number of transactions and the
   sum of `gross_amount`.
4. `DECLINED` transactions never had their payment authorised, so their amount is meaningless:
   report only their **count**. Declined rows are included in `total_txn_count` but never in
   any amount column.
5. Counts are 0 and amounts are 0.00 when a store has no transaction of that status (**never NULL**).

## Output contract

| column | type | notes |
|---|---|---|
| `store_id` | integer | |
| `total_txn_count` | integer | all in-scope transactions of the store, every status |
| `completed_count` | integer | |
| `completed_amount` | numeric | |
| `pending_count` | integer | |
| `pending_amount` | numeric | |
| `cancelled_count` | integer | |
| `cancelled_amount` | numeric | |
| `declined_count` | integer | |

Ordering: none required (unordered set). Amounts are compared at 2 decimals.

## Illustrative example (not the real data)

Store 77 in 2025: completed 10.00 and 15.00, cancelled 40.00, declined 99.00.

| store_id | total_txn_count | completed_count | completed_amount | pending_count | pending_amount | cancelled_count | cancelled_amount | declined_count |
|---|---|---|---|---|---|---|---|---|
| 77 | 4 | 2 | 25.00 | 0 | 0.00 | 1 | 40.00 | 1 |

## Edge cases you must handle

- A store with no transaction of some status (zero, not NULL).
- Declined transactions: counted, never summed.
- Transactions in 2024 must not leak in.

## Constraints

- One read-only `SELECT` / `WITH` statement, valid PostgreSQL 17.
- Read the table **once** (no self-joins or one subquery per status).

## Clarify before you code (what a strong candidate asks)

- Should declined amounts be reported anywhere?
- Is the status the final status, or can it still change after the report is produced?
- Do stores without any 2025 activity need a row?
