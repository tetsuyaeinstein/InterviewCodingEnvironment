# SQL-015 · Month-over-month store revenue growth

**Topic:** aggregates & windows · **Level:** medium · **Interview time:** ~20 min · **Mode:** query

## In plain words

> "For stores 4 and 5, how did revenue change month over month from February to December 2025?"

**You return:** one row per store per month (22 rows): `store_id`, `month_start`, `revenue`, `prev_month_revenue`, `mom_change_pct`.

**The fine print, in short:**
- Revenue is from **completed** transactions by UTC month. Months with no sales show 0.00.
- For February, the previous month is January. A previous month of 0 is 0.00, never NULL.
- The change is a percentage rounded to 2 decimals, NULL when the previous month is 0.

## Business context

Finance publishes a monthly growth table per store: revenue, the previous month's revenue and
the percentage change. The two stores under review trade irregularly. Some months have no sales
at all, and last year's version of this report crashed with a division by zero and silently
skipped empty months. Finance wants every month shown and a percentage that is safe and well
defined.

## Source table

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `store_id`, `transaction_ts` (timestamptz, UTC), `gross_amount`, `transaction_status` |

## Parameters (fixed)

- Stores: **4 and 5**.
- Report months: **February 2025 through December 2025** (11 months), UTC calendar months.

## Requirements

1. Revenue = `SUM(gross_amount)` of `COMPLETED` transactions in the UTC calendar month
   `[first day 00:00 UTC, first day of next month 00:00 UTC)`.
2. One row per store per report month (22 rows), **including months without sales**
   (`revenue = 0.00`).
3. `prev_month_revenue`: the store's revenue in the immediately preceding calendar month. For
   February 2025 this is **January 2025**, even though January is not a report month. It is
   `0.00` (never NULL) if that month had no sales.
4. `mom_change_pct = 100 × (revenue − prev_month_revenue) / prev_month_revenue`, rounded to
   **2 decimals** (half away from zero, i.e. PostgreSQL `round(numeric, 2)`).
5. When `prev_month_revenue = 0`, `mom_change_pct` is **NULL**, whatever the current month's
   revenue. Growth from nothing is undefined. A drop to zero is −100.00.

## Output contract

| column | type | notes |
|---|---|---|
| `store_id` | integer | |
| `month_start` | date | first day of the month, e.g. `2025-02-01` |
| `revenue` | numeric | 2 decimals, never NULL |
| `prev_month_revenue` | numeric | 2 decimals, never NULL |
| `mom_change_pct` | numeric | 2 decimals, NULL when the previous month is 0 |

Ordering: none required.

## Illustrative example (not the real data)

| month | revenue | prev_month_revenue | mom_change_pct |
|---|---|---|---|
| 2024-07 | 90.00 | 120.00 (June, outside the report) | −25.00 |
| 2024-08 | 0.00 | 90.00 | −100.00 |
| 2024-09 | 0.00 | 0.00 | NULL |
| 2024-10 | 40.00 | 0.00 | NULL |
| 2024-11 | 50.00 | 40.00 | 25.00 |

## Edge cases you must handle

- Months with no completed sales (in the middle and at the end of the period).
- A first report month whose previous month lies outside the report period.
- Previous month with zero revenue (current month zero or non-zero).
- Non-completed transactions (including a large cancelled one).
- Percentages that need rounding (e.g. a one-third drop).

## Constraints

- One read-only `SELECT` / `WITH` statement, valid PostgreSQL 17.
- Do not rely on integer division.

## Clarify before you code (what a strong candidate asks)

- UTC month or store-local month?
- What should the percentage be when the previous month is 0? When both are 0?
- Does the first month of the report compare with the month before the report?
- Percent as 25.00 or ratio 0.25? How many decimals?
