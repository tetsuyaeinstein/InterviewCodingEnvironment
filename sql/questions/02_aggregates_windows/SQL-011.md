# SQL-011 · Latest completed transaction per customer

**Topic:** aggregates & windows · **Level:** easy · **Interview time:** ~12 min · **Mode:** query

## In plain words

> "For each customer, show me their most recent completed transaction."

**You return:** one row per customer with a completed purchase: `customer_id`, `transaction_id`, `transaction_ts`, `store_id`, `gross_amount`.

**The fine print, in short:**
- Only **completed** transactions count, over the whole history. Guests are excluded.
- If two share the latest timestamp, take the one with the highest `transaction_id`.
- Customers with no completed transaction are not returned.

## Business context

The CRM team sends a "thanks for your last visit" message and needs, for every customer, the
**one** most recent completed purchase: which transaction it was, when, where and how much. The
message system rejects a customer that appears twice, so the answer must contain exactly one
row per customer, and it must be the **same** row every time the job runs.

## Source table

| table | grain | columns you need |
|---|---|---|
| `transactions` | one row per checkout transaction | `transaction_id`, `customer_id`, `store_id`, `transaction_ts` (timestamptz, UTC), `gross_amount`, `transaction_status` |

## Requirements

1. Only `transaction_status = 'COMPLETED'` transactions count. A later `PENDING`, `CANCELLED`
   or `DECLINED` transaction never replaces an earlier completed one.
2. Guest checkouts (`customer_id IS NULL`) are excluded.
3. "Latest" means the greatest `transaction_ts`. If several completed transactions of the same
   customer share that greatest timestamp, pick the one with the **highest `transaction_id`**.
4. Exactly one row per customer who has at least one completed transaction (whole history, no
   date filter). Customers without any completed transaction are **not** returned.

## Output contract

| column | type | notes |
|---|---|---|
| `customer_id` | integer | one row per customer |
| `transaction_id` | bigint | the chosen transaction |
| `transaction_ts` | timestamptz | its timestamp |
| `store_id` | integer | its store |
| `gross_amount` | numeric | its amount, compared at 2 decimals |

Ordering: none required.

## Illustrative example (not the real data)

| customer | transactions (id, ts, status) | returned |
|---|---|---|
| 801 | (10, Jan 3 09:00, COMPLETED), (11, Jan 9 12:00, COMPLETED) | 11 |
| 802 | (20, Feb 1 10:00, COMPLETED), (21, Feb 1 10:00, COMPLETED) | 21 |
| 803 | (30, Mar 1 08:00, COMPLETED), (31, Mar 2 08:00, PENDING) | 30 |
| 804 | (40, Apr 1 08:00, CANCELLED) | (not returned) |

## Edge cases you must handle

- Two completed transactions of one customer at exactly the same timestamp.
- A newer transaction that is not completed.
- Customers with no completed transaction at all.
- Guest checkouts.

## Constraints

- One read-only `SELECT` / `WITH` statement, valid PostgreSQL 17.
- About 2,000 customers in the small seed; the interviewer will ask how this behaves on a
  500-million-row fact.

## Clarify before you code (what a strong candidate asks)

- What decides between two transactions at the same timestamp?
- Should non-completed transactions ever count as "the last visit"?
- Do you want customers who never purchased (with NULLs), or only buyers?
- Is "latest" by event time (`transaction_ts`) or by load time (`ingested_at`)?
