# SQL-020 · Ledger running balances and negative-balance flags

**Topic:** aggregates & windows · **Level:** hard · **Interview time:** ~25 min · **Mode:** query

## Business context

Risk operations investigates stored-value accounts that went into the red. The ledger stores
only signed postings (positive = credit, negative = debit); the balance is never stored. For
accounts **1 to 5** they want to replay the ledger entry by entry: the balance **after** each
posting, whether it is negative, and exactly which entry pushed the account below zero.

## Source table

| table | grain | columns you need |
|---|---|---|
| `account_ledger` | one row per ledger entry | `entry_id`, `account_id`, `posting_ts` (timestamptz, UTC), `signed_amount` |

## Requirements

1. Scope: all ledger entries of accounts `1 … 5`.
2. Entries of an account are applied in the order **`posting_ts` ascending, then `entry_id`
   ascending**. Entry ids are *not* guaranteed to follow time, and several entries can share one
   timestamp. Each entry is applied individually, never as a group.
3. `running_balance` = sum of `signed_amount` of all entries up to and **including** this one in
   that order, starting from 0.00 for every account.
4. `is_negative` = `running_balance < 0` (exactly 0.00 is **not** negative).
5. `enters_negative` = true when this entry makes the balance negative while the balance before
   it was not (the previous balance is 0.00 for the account's first entry). Otherwise false.
6. One row per entry. Accounts without entries produce no rows.

## Output contract

| column | type | notes |
|---|---|---|
| `account_id` | integer | |
| `entry_id` | bigint | |
| `posting_ts` | timestamptz | |
| `signed_amount` | numeric | 2 decimals |
| `running_balance` | numeric | 2 decimals |
| `is_negative` | boolean | never NULL |
| `enters_negative` | boolean | never NULL |

Ordering: none required.

## Illustrative example (not the real data)

Account 900 (entries listed in application order):

| entry_id | posting_ts | signed_amount | running_balance | is_negative | enters_negative |
|---|---|---|---|---|---|
| 31 | Jan 1 08:00 | +50.00 | 50.00 | false | false |
| 30 | Jan 2 09:00 | −60.00 | −10.00 | true | true |
| 32 | Jan 2 09:00 | −5.00 | −15.00 | true | false |
| 33 | Jan 3 10:00 | +15.00 | 0.00 | false | false |

(Entry 31 is applied before 30 because it is earlier in time; 30 and 32 share a timestamp and
are applied in id order.)

## Edge cases you must handle

- Several entries with the same `posting_ts` in one account: each one must show its own balance.
- Entry ids that do not follow time order.
- An account whose first entry is already negative.
- A balance of exactly 0.00 after being negative (not negative).
- An entry posted exactly at midnight.

## Constraints

- One read-only `SELECT` / `WITH` statement, valid PostgreSQL 17.
- Expect a question on running this for 40M accounts and 5 billion entries.

## Clarify before you code (what a strong candidate asks)

- Is the opening balance 0, or is there a snapshot to start from?
- How are same-timestamp entries ordered, and is the intermediate balance meaningful?
- Is a balance of exactly 0 "negative"? Is the credit limit relevant (it is not here)?
- Do reversals or corrections change history, or are they new entries?
