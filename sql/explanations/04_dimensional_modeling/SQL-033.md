# SQL-033 · Sales with no matching customer version, and why: explanation

## Core idea

This is the **exception report** of the point-in-time join in SQL-031. Two steps:

1. **Anti-join:** keep sales for which no version contains `transaction_ts` (half-open).
2. **Classify:** once nothing contains the sale, every version of that customer lies entirely
   before it (`effective_to <= ts`) or entirely after it (`effective_from > ts`). The closest
   version on each side gives both the evidence columns and the reason.

| previous_version_end | next_version_start | reason |
|---|---|---|
| NULL | value | `NO_VERSION_YET`: the dimension row arrived later than the first fact (late-arriving dimension) |
| value | value | `GAP_BETWEEN_VERSIONS`: the loader closed one version and opened the next too late |
| value | NULL | `AFTER_LAST_VERSION`: the last version was closed but nothing replaced it |
| (no versions at all) | | `CUSTOMER_NOT_IN_DIMENSION`: the dimension load missed the customer entirely |

## (a) NOT EXISTS + filtered aggregates (`SQL-033.sql`)

`NOT EXISTS` is the clearest anti-join. It cannot fan out and it handles a customer with many
versions naturally. The classification `LEFT JOIN`s the unmatched sales back to all versions
of their customers and uses `MAX(...) FILTER (WHERE effective_to <= ts)` and
`MIN(...) FILTER (WHERE effective_from > ts)`. `COUNT(d.customer_sk)` (not `COUNT(*)`) is 0 only
when the outer join found no versions at all.

## (b) Outer join + two LATERAL probes (`SQL-033_alt.sql`)

`LEFT JOIN ... WHERE hit.customer_sk IS NULL` is the other classic anti-join. For each exception,
two `LATERAL ... ORDER BY ... LIMIT 1` probes find the neighbours. On a big fact with few
exceptions this is attractive: the anti-join is a hash join, and the probes run only for the
handful of unmatched rows, each as a short index scan.

Trade-off: in (b) the `hit` join would duplicate matched sales if the dimension had overlaps.
That is harmless here, because matched rows are filtered out, but it is a trap if someone later
reuses the join for matched rows. `NOT EXISTS` has no such risk.

## Edge cases and how the fixtures prove them

| txn | sale | versions of the customer | correct |
|---|---|---|---|
| 5301 | 02-28 23:59:59 | 53: `[2023-12-01, 2025-03-01)` | matches (last second) |
| **5302** | **03-01 00:00:00** | first version ends exactly here | **GAP**: `<=` on the end would hide it |
| 5303 | 03-10 | inside the March gap | GAP |
| 5304 | 04-01 00:00:00 | second version starts exactly here | matches |
| **5401** | 2024-12-31 23:59:59 | 54: first version starts 2025-01-01 | **NO_VERSION_YET** |
| 5402 | 2025-01-01 00:00:00 | | matches |

Two typical wrong answers:

- `BETWEEN effective_from AND effective_to` (inclusive end): 5302 "matches" the closed version and
  disappears from the exception list. That is exactly the sale the loader would mis-attribute.
- `effective_to < ts` for the previous version: 5302's previous version (ending at exactly
  03-01 00:00) is not found, so 5302 is misclassified as `NO_VERSION_YET`.

`AFTER_LAST_VERSION` and `CUSTOMER_NOT_IN_DIMENSION` have no example in this seed (every
customer's last version is open-ended). They are in the contract because they are what a broken
SCD2 loader actually produces.

## Complexity and indexes

- The anti-join reads every completed customer sale once. In PostgreSQL it becomes a **Hash Anti
  Join** (dimension hashed on `customer_id`, interval re-checked per candidate) or a nested-loop
  anti join with an index probe on `dim_customer_scd2(customer_id, effective_from)`.
- The classification touches only the exceptions, so its cost is negligible.
- At 500M facts: do not run this over all history every night. Run it for the sales loaded in
  the current batch (by `ingested_at`), plus a full sweep after any dimension backfill. Persist the
  exceptions with a run id.

## Production considerations

- **Late-arriving dimensions** (customer 54) are normal in event-driven systems: the sale event
  arrives before the CRM change. Common patterns:
  - insert an **inferred member** (a placeholder version with default attributes, flagged
    `is_inferred`) and update it in place when the real row arrives; or
  - load the fact against the `-1` unknown member and **re-key** it later.
  Either way, this report is the work queue.
- **Gaps** (customer 53) are usually loader bugs: closing the old version at time X and opening
  the new one at X + something. Fix the loader so the new `effective_from` is exactly the old
  `effective_to`.
- **Monitoring:** alert on the exception count per load. A spike usually means the dimension
  load failed or ran late.

## SQL Server / Azure Synapse notes

- `NOT EXISTS` and the `LEFT JOIN ... IS NULL` anti-join both work. `OUTER APPLY (SELECT TOP (1)
  ...)` replaces `LEFT JOIN LATERAL ... LIMIT 1`.
- `MAX(...) FILTER (WHERE ...)` becomes `MAX(CASE WHEN effective_to <= ts THEN effective_to END)`.
- Synapse: replicate the dimension; the anti-join is then local to each distribution. Many Synapse
  loaders use `ISNULL(d.customer_sk, -1)` to map misses to the unknown member. This report is
  then "facts with `customer_sk = -1`", which is far cheaper. Keep the natural key on the fact so
  you can re-key later.
