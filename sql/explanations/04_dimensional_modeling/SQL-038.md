# SQL-038 · Monthly first-purchase cohorts with month-1 and month-2 repeat rates: explanation

## Core idea

A cohort table is a **two-grain** problem:

1. Reduce transactions to **customer × active month** (distinct). Several purchases in a month
   are one fact, and the retention question is "was the customer active in month X?".
2. Define the cohort from **all history** (`MIN(active_month)` per customer), and filter the
   *cohorts* to 2025 **afterwards**. Filtering transactions to 2025 first assigns customers who
   first bought in 2024 to a 2025 cohort (customer 9: first purchase 2024-12-29). That is the
   classic cohort bug.

Then count cohort members and, for each, whether an activity row exists exactly one and two months
later. Retention is "exact month N", not "within N months", which is why month 2 is not a subset
of month 1 (an active-in-month-2-only customer counts only in `month2_customers`).

## (a) MIN per customer + two LEFT JOINs (`SQL-038.sql`)

`LEFT JOIN activity a1 ON customer AND active_month = cohort_month + 1 month`. `COUNT(a1.customer_id)`
counts only matched rows, so unmatched members stay in `COUNT(*)` (the cohort size). Joining the same
activity set twice is safe: each join is on the unique (customer, month) key, so no fan-out.

## (b) Window stamp + conditional aggregation (`SQL-038_alt.sql`)

`MIN(active_month) OVER (PARTITION BY customer_id)` stamps the cohort month on each activity row. Then
one `GROUP BY cohort_month` with `COUNT(*) FILTER (WHERE active_month = cohort_month + n months)` produces
size, month 1 and month 2 in a single pass. Cohort size is the count of rows in the cohort month (one per
customer). This generalises easily to months 3, 4, ... as extra FILTER columns (or to a long format with
`months_since_cohort = age`), whereas (a) needs one join per column.

## Immature cohorts (right-censoring)

The data ends 2025-12-31. The November cohort cannot show month 2 (January 2026) and December cannot show
month 1 or 2. Reporting 0.00 would tell the business that nobody returned. The contract returns NULL for the rate
and still the observed count (0). Fixtures: Dec cohort has `month1_rate` NULL; Nov has a real
`month1_rate` (0.84) and NULL `month2_rate`. In dashboards show immature cells greyed out.

## Edge cases

| case | effect |
|---|---|
| first purchase 2024, repeat in 2025 (customer 9) | no 2025 cohort |
| PENDING before the first completed purchase (customer 22) | cohort = first completed month |
| 2025-02-28 23:59:59 then 2025-03-01 00:00:00 (customer 53) | Feb cohort, counted in month 1 |
| month arithmetic on timestamps instead of month-start dates | off-by-one at month ends; always compare `date_trunc('month', ...)` values |
| `INTERVAL '1 month'` on a date returns timestamp | cast back to date before comparing with date |

## Complexity and indexes

The distinct customer-month set is far smaller than the fact (at most 12 rows per customer-year), so
every later step is cheap; the one expensive step is the scan and de-duplication of the fact.
Maintain a `customer_month_activity` table (or the existing `customer_daily_activity` rolled up) and run
cohorts from it. At 500M rows, store each customer's `first_purchase_month` as a dimension attribute
(set once, immutable except for back-dated data), making the cohort join trivial.

## Production considerations

- First purchase is **immutable** unless late data arrives with an earlier timestamp: a late 2024
  purchase can move a customer from a 2025 cohort to a 2024 cohort and change reported history. Decide
  whether history is restated or frozen, and monitor.
- Time zone: UTC months here; marketing often wants store/head-office months.
- Guests and merged identities: guest purchases never form cohorts; identity resolution changes cohort
  membership.
- Reconcile: sum of cohort sizes (all years) equals distinct purchasing customers.

## SQL Server / Azure Synapse notes

`DATETRUNC(month, ...)` exists from SQL Server 2022; before that `DATEFROMPARTS(YEAR(d), MONTH(d), 1)` or
`DATEADD(month, DATEDIFF(month, 0, d), 0)`. `DATEADD(month, 1, cohort_month)` replaces
`+ INTERVAL '1 month'`. `COUNT(*) FILTER` becomes `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`. Synapse:
distribute the activity table on `customer_id` so the window and the self-joins are local.
