# SQL-037 · Products frequently bought together: explanation

## Core idea

This is the **bridge / market-basket** pattern. A basket (transaction) is related to many products,
so "pairs in a basket" is a self-join of the basket-product relation. Three decisions make it
correct:

1. **Grain first.** Collapse order lines to one row per `(transaction_id, product_id)` with
   `DISTINCT`. Otherwise a product on two lines multiplies its pairs (the 331 line-duplicates in the
   seed, and fixture basket 6102 with product 8 on two lines).
2. **Canonical pair order.** `a.product_id < b.product_id` removes self-pairs and the mirror image
   in one predicate. `<>` doubles every row, `<=` adds (p, p).
3. **Count baskets.** After step 1, `COUNT(*)` equals the number of distinct baskets.

Fixtures: pair (5, 6) is in 6101 (p5 + p6) and 6004 (p1 + p5 + p6), so `co_occurrences = 2`. Cancelled
basket 6103 and (8, 8) never contribute.

## (a) Self-join (`SQL-037.sql`)

Hash join on `transaction_id`, then aggregate on the pair. Simple, readable, and the plan is obvious.

## (b) Sorted distinct array + `generate_subscripts` (`SQL-037_alt.sql`)

Aggregate each basket to a sorted distinct array and generate the index pairs `i < j` inside it. It
avoids joining the big line table to itself and de-duplicates implicitly. The cost is the same
quadratic term, `sum(k^2)` over basket sizes `k`, but without the join machinery; the array needs to
fit in memory per basket. PostgreSQL specific.

## Complexity and production

- Pairs per basket are `k(k-1)/2`. Average baskets are small here, but a handful of huge baskets
  (wholesale, a 300-line order) dominate: cap basket size (e.g. 30 distinct products) or sample.
- At 500M lines: do not run this ad hoc. Build a `basket_product` table once (distinct), prune to
  products with minimum support first (a pair cannot be frequent if a member is not: the **Apriori**
  idea), then self-join only the frequent items. Compute incrementally per day and merge counts.
  Partition by date and keep daily pair counts that can be summed (counts of baskets add up across
  disjoint baskets).
- Indexes: `transaction_items(transaction_id)` for the join; `transaction_items(product_id)` for
  per-product pruning.
- Better metrics than raw counts: support, confidence and lift. Raw counts favour popular items.

## SQL Server / Azure Synapse notes

`generate_subscripts` and arrays do not exist. Use the self-join (a), or `STRING_AGG`-free pair
generation through `CROSS APPLY`. `SELECT DISTINCT` plus the self-join works identically. In Synapse,
distribute the basket-product table on `transaction_id` so the self-join is local.
