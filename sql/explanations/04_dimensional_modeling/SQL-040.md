# SQL-040 · Monthly net sales with partial refunds and units, without fan-out: explanation

## Core idea

Sales header, order lines and refunds are three facts at three grains, all one-to-many from the
transaction:

| fact | grain | measure | recognised at |
|---|---|---|---|
| `transactions` | transaction | `gross_amount`, order count | `transaction_ts` |
| `transaction_items` | line | `quantity` | `transaction_ts` (of its header) |
| `refunds` | refund payment | `refund_amount` | `refund_ts` |

Joining them in one query multiplies rows (**fan-out**, "chasm trap"): transaction 2301 has 2 lines
and 2 refunds, so the join yields 4 rows; `SUM(gross_amount)` counts 100.00 four times and
`SUM(quantity)` counts each line twice. The rule: **aggregate each fact at its own grain and
recognition month first, then combine on the conformed dimension (month)**. Months are the conformed
dimension shared by all three; the join between facts is on `month_start`, never on `transaction_id`.

## (a) Separate aggregates on a month grid (`SQL-040.sql`)

`months` (generated) LEFT JOIN `sales`, `units`, `refunded`, each already one row per month, so each join is
1:1 and cannot multiply. The grid keeps 2026-01 (refunds, no sales) and `COALESCE` turns the
missing sales measures into 0. Inner-joining `sales` drops January: its `refunded_amount` of 1,415.10 would vanish and net
sales for the quarter would be overstated.

Fixtures: 2301 (two lines, two Oct refunds), 2401 (full refund in Oct, net 0), 2501 (sale Oct 30, refunds Nov 5/6: **November** gets
-60.00 although the sale is in October).

## (b) Stack the streams with `UNION ALL` (`SQL-040_alt.sql`)

Each fact becomes event rows `(month, orders, units, sales, refunds)` with zeros for the measures it does not carry; one
`GROUP BY` sums everything. No join between facts exists, so fan-out is impossible. This is the form to use when adding a fourth
stream (chargebacks, adjustments) and the one that maps naturally to a unified "revenue events" table.

## Why recognition rules matter

- Refund in month of **payment** (cash/accounting view): closed months never change. Restating into the month of
  **sale** (cohort/product view) changes closed months: the number answers a different question ("what did October
  sales really yield?"). Both are valid; state which one. Wrong choice shows up in the fixtures: customer 25.
- `net_sales` can be negative for a month with refunds and little sales (2026-01 here).

## Complexity and indexes

Each CTE is a single pass; the line table is the only big one. `units` needs the header only for status and time: at 1.5B lines,
denormalise `transaction_ts`/status (or a `sale_month` key) onto the line fact so units never need the join, and keep monthly
aggregates in a summary table. Indexes: `refunds(transaction_id)` is not even needed here, because the refund CTE has no join.

## Production considerations

- Reconcile: `sum(gross_sales)` across all months equals the header total; units equal the line total.
  Check that `transactions.gross_amount` equals the sum of its lines.
- Late data: a refund arriving late changes an already-published month if recognised by `refund_ts` of the original; recognising by
  ingestion month avoids restatement. Decide and document.
- Currency: single currency here; multi-currency needs conversion at the recognition date.
- Metric naming: "net sales (cash basis)" vs "net sales (as sold)".

## SQL Server / Azure Synapse notes

`GENERATE_SERIES` is only available in SQL Server 2022+; otherwise use a calendar table. `FORMAT(d, 'yyyy-MM')` is slow:
use `DATEFROMPARTS(YEAR(d), MONTH(d), 1)`. UNION ALL stacking is the preferred pattern in Synapse: it parallelises across
distributions; distribute facts by `transaction_id` so line and header aggregation is local.
