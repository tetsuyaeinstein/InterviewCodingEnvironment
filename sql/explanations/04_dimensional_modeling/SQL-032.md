# SQL-032 · Data-quality audit of the customer SCD2 dimension: explanation

## Core idea

Every point-in-time join (SQL-031, SQL-039) silently assumes two invariants of a type-2
dimension:

1. **No overlap:** for one natural key, at most one version is valid at any instant. Otherwise the
   as-of join fans out and facts are double-counted.
2. **Consistent current flag:** exactly the open-ended version is `is_current`. Otherwise
   "current" reports (`WHERE is_current`) return two rows or none.

The audit turns each invariant into a query that returns violations at a clear grain (pair or
version), and combines them with `UNION ALL` into one alert list.

## (a) Explicit comparisons (`SQL-032.sql`)

**Overlap test for half-open intervals.** `[s1, e1)` and `[s2, e2)` intersect iff
`s1 < e2 AND s2 < e1`. The intersection is `[GREATEST(s1, s2), LEAST(e1, e2))`.

| customer | a | b | `a.s < b.e` | `b.s < a.e` | overlap? |
|---|---|---|---|---|---|
| 51 | `[2024-01-01, 2025-02-01)` | `[2025-01-15, 9999)` | yes | yes | **yes**: `[2025-01-15, 2025-02-01)` |
| 52 | `[2024-01-01, 9999)` | `[2024-06-01, 9999)` | yes | yes | **yes**: `[2024-06-01, 9999)` |
| 56 | `[2024-01-01, 2024-07-01)` | `[2024-07-01, 9999)` | yes | 07-01 < 07-01? **no** | no (touching) |

With `<=` instead of `<`, every customer with more than one version is flagged (about a thousand
false positives in this seed, including customer 56). An alert that always fires is soon ignored.

**Pairs once.** `a.customer_sk < b.customer_sk` excludes self-pairs (a row always overlaps
itself) and the mirror pair. With `<>` every pair appears twice.

**Multiple current.** A window `COUNT(*) FILTER (WHERE is_current) OVER (PARTITION BY
customer_id)` keeps the version grain while counting per customer. A `GROUP BY ... HAVING` plus a
join back gives the same result.

**Flag consistency.** `is_current <> (effective_to = sentinel)` catches both directions in one
predicate. Note the sentinel: this table uses `9999-12-31`, not NULL. A check written as
`effective_to IS NULL` flags every current row and misses customer 55.

## (b) Alternative: range types (`SQL-032_alt.sql`)

`tstzrange(effective_from, effective_to)` is half-open (`'[)'`) by default. Then `&&` is the
overlap test and `*` the intersection. The single-row checks are generated with a
`CROSS JOIN LATERAL (VALUES ...)` that emits one candidate issue per rule.

- Pros: the half-open semantics are built in, so there is no `<`/`<=` to get wrong. A GiST index
  on the range supports `&&`. The same expression can become a constraint:
  `EXCLUDE USING gist (customer_id WITH =, tstzrange(effective_from, effective_to) WITH &&)`
  (needs `btree_gist`). That **prevents** overlaps instead of detecting them.
- Cons: PostgreSQL-specific. SQL Server and Synapse have no range types.

**Cheaper detection (mention it):** order each customer's versions by `effective_from` and
compare each row with the previous one, `LAG(effective_to) OVER (...) > effective_from`. It is a
single sort with no self-join, so it is O(n log n) even for customers with many versions. But it
only compares **neighbours**. If one version spans several later ones, it reports the first
collision and misses the other pairs. Using a running `MAX(effective_to)` over the preceding rows
instead of `LAG` fixes that for detection, but still does not list every pair. That is fine for
an alert ("customer X is broken") but not for this contract.

## Edge cases and how the fixtures prove them

| fixture | situation | correct outcome |
|---|---|---|
| 51 | versions overlap for two weeks | 1 pair row with the shared interval |
| 52 | two open-ended current versions | 1 pair row (overlap until the sentinel) **and** 2 `MULTIPLE_CURRENT` rows |
| 55 | only version is open-ended, `is_current = false` | `OPEN_BUT_NOT_CURRENT` |
| 56 | adjacent versions touching at 2024-07-01 | **no** row |
| 50, generated customers | clean history | no rows |

`CLOSED_BUT_CURRENT` has no example in this seed. It is still part of the contract because a
failed "close the old version" step in the SCD2 loader produces exactly that.

## Complexity and indexes

- The self-join is per customer. With `k` versions per customer it costs O(k²) per customer. That
  is cheap when `k` is small (here ≤ 3), but a customer with thousands of versions (a
  status-flapping account) makes it quadratic. The window/`LAG` detection is O(n log n) overall.
- `dim_customer_scd2(customer_id, effective_from)` supports both the self-join (merge join on
  `customer_id`) and the windowed check (presorted input).

## Production considerations

- Run the audit **after every dimension load and before the fact load** that stamps surrogate
  keys. Fail the pipeline (or quarantine the customer) when overlaps appear.
- Store the findings with a run id and first-seen date, so you alert on **new** defects only.
- Add a reconciliation check downstream: row count of the fact after the as-of join equals the
  count before it.
- Fix at the source with constraints: a partial unique index
  `CREATE UNIQUE INDEX ON dim_customer_scd2 (customer_id) WHERE is_current` blocks duplicate
  current rows; the `EXCLUDE` constraint blocks overlaps. Also consider
  `CHECK (effective_from < effective_to)`.

## SQL Server / Azure Synapse notes

- The explicit comparison version ports directly. `GREATEST`/`LEAST` exist in SQL Server 2022 and
  Azure SQL; on older versions use `CASE WHEN a > b THEN a ELSE b END`.
- `COUNT(*) FILTER (WHERE ...)` becomes `SUM(CASE WHEN is_current = 1 THEN 1 ELSE 0 END)`.
  `is_current` is usually a `bit`.
- SQL Server's filtered unique index (`WHERE is_current = 1`) enforces one current row. There is
  no exclusion constraint: overlap prevention needs a trigger or the loader's own logic.
- Synapse dedicated pools enforce no constraints at all (`NOT ENFORCED`), so these audit queries
  are the only protection. Distribute the dimension on `customer_id` so the self-join is local.

## Follow-up questions

1. Add `NO_CURRENT_VERSION` (customer with no current row at all) and `INVALID_RANGE`
   (`effective_from >= effective_to`). Which fixture would the first one catch?
2. Also detect **gaps** between consecutive versions. Why is a gap sometimes legitimate (customer
   closed and re-opened) and sometimes a defect (SQL-033)?
3. At 500M rows of dimension history (a high-churn attribute such as a loyalty balance stored as
   type 2), the self-join explodes. How do you redesign: windowed neighbour check, incremental
   audit of only the customers touched by today's load, or mini-dimensions?
4. Write the `EXCLUDE` constraint that makes overlaps impossible. What does the loader then have
   to do differently when it closes the previous version?
