# SQL-031 · Customer region and segment as of each June sale: explanation

## Core idea

A type-2 dimension stores **one row per version** of a customer. Joining the fact on
`customer_id` alone multiplies every transaction by the number of versions. Joining on
`is_current` gives *today's* attributes, which silently restates history. The correct join is a
**point-in-time (as-of) join**: customer key **plus** "the transaction timestamp lies inside the
version's validity interval".

## (a) Range join on the half-open interval (`SQL-031.sql`)

```
ON d.customer_id = t.customer_id
AND t.transaction_ts >= d.effective_from
AND t.transaction_ts <  d.effective_to
```

- It is a `LEFT JOIN`, and the interval predicate is in `ON`, not `WHERE`. Moving it to `WHERE`
  turns the outer join back into an inner join and drops guests.
- `effective_to` is **exclusive**. At the change instant only the new version matches.

| txn | transaction_ts | EAST `[2023-12-01, 06-15 10:00)` | WEST `[06-15 10:00, 9999)` | result |
|---|---|---|---|---|
| 5001 | 06-01 15:00 | yes | no | EAST |
| 5002 | 06-15 09:59:59 | yes | no | EAST |
| 5003 | 06-15 10:00:00 | **no** (`<` end) | yes | WEST |
| 5004 | 06-20 15:00 | no | yes | WEST |

With `BETWEEN` or `<=` on the end, txn 5003 matches both versions and is **duplicated**. The
revenue for that day is then counted twice. This is the most common SCD2 bug in production.

## (b) Alternative: `LEFT JOIN LATERAL ... ORDER BY effective_from DESC LIMIT 1` (`SQL-031_alt.sql`)

For each fact, take the latest version that started at or before the sale. Then check that the
sale is still before that version's end (otherwise the fact is in a gap).

| | range join (a) | LATERAL as-of (b) |
|---|---|---|
| Correct on a clean dimension | yes | yes |
| Overlapping versions (bad data) | fans out: duplicates facts | silently picks one version, hides the defect |
| Gaps in the dimension | NULL (correct) | NULL, but only because of the extra `< effective_to` check; without it the fact gets a stale version |
| Plan | hash/merge join + filter, or nested loop | nested loop with one index probe per fact |
| Best when | many facts, set-based (warehouse) | few facts, or an index on `(customer_id, effective_from)` |

Neither is "safe" against bad dimension data: (a) shows the problem loudly, (b) hides it. Test the
dimension instead (SQL-032) and add a row-count check after the join.

## Edge cases and how the fixtures prove them

| fixture | situation | correct outcome |
|---|---|---|
| customer 50, txn 5002 | one second before the change | EAST |
| customer 50, txn 5003 | exactly at the change | WEST, **one** row |
| customer 50 | current region WEST, history EAST | `current_region` WEST on all rows |
| guests (10 in June) | no customer at all | returned with NULLs |
| ~190 generated customers | moved region/segment after the sale | historical ≠ current |

## Complexity and indexes

- Fact side: range scan on `transactions(transaction_ts)` (about 1k of 21k rows here).
- Dimension side: PostgreSQL cannot use a plain equi-join on intervals. It hash-joins on
  `customer_id` and filters the interval per candidate pair. That is fine when customers have few
  versions (here at most 3).
- The baseline index `dim_customer_scd2(customer_id, effective_from)` supports the LATERAL plan:
  one backward index scan per fact.
- Optional: a GiST index on `(customer_id, tstzrange(effective_from, effective_to))` with the
  `btree_gist` extension, queried with `@>`. The same structure can enforce non-overlap with an
  `EXCLUDE` constraint, which prevents the fan-out bug at write time.

## Production considerations

- **Surrogate keys at load time.** Most warehouses resolve the version once, when the fact is
  loaded, and store `customer_sk` on the fact. Reports then use a cheap equi-join. The as-of join
  you wrote is what the loader runs, so it must be correct at the boundary.
- **Late-arriving dimension changes** (a version back-dated into the past) mean facts that were
  already loaded with the old `customer_sk` must be re-keyed. Keep the natural key and
  `transaction_ts` on the fact so you can re-run the as-of join.
- **Unknown member.** Many teams map unmatched facts to a `-1` "unknown" dimension row instead of
  NULL, so inner joins in BI tools don't drop revenue. Log unmatched counts (SQL-033).
- **Reconciliation:** `count(*)` and `sum(gross_amount)` after the join must equal the fact before
  the join.

## SQL Server / Azure Synapse notes

- The range join is identical in T-SQL. `LATERAL` is `OUTER APPLY (SELECT TOP (1) ... ORDER BY
  effective_from DESC)`.
- SQL Server uses `datetime2`/`datetimeoffset`. The sentinel end date is often `'9999-12-31'`.
  `DATETIME2` handles it, but `smalldatetime` and `datetime` limits differ.
- Synapse dedicated pools: replicate the customer dimension (if under a few GB) so the join is
  local, and hash-distribute the fact on `customer_id` if you must join a large dimension.
  `OUTER APPLY` with `TOP 1` is a row-by-row pattern and scales poorly there; prefer the range join.
