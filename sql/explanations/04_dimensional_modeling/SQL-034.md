# SQL-034 · Daily account balance snapshot from the posting ledger: explanation

## Core idea

The ledger is a **transaction fact** (one row per event). The snapshot is a **periodic snapshot
fact** (one row per account per day, whether or not anything happened). Turning one into the
other takes three moves:

1. **Densify:** build the grid `accounts in scope × days` (`generate_series`). Without it,
   quiet days and accounts with no postings (account 4) disappear.
2. **Accumulate:** balance = opening balance before the window + running sum of daily net
   changes. Quiet days add 0, which *is* the carry-forward.
3. **Semi-additive measures:** `net_change` and `posting_count` add up over time. `closing_balance`
   and `lowest_balance` do **not**: you can sum them across accounts for one day, but never across
   days.

## (a) Set-based: running balances and a cumulative window (`SQL-034.sql`)

- `opening`: postings before 2025-01-01 (none for these accounts, but production always has
  history before the window).
- `postings`: running balance per posting, `ORDER BY posting_ts, entry_id`. The `entry_id`
  tie-break makes same-timestamp postings deterministic (account 1's two 09:00 debits).
- `daily`: count, net and lowest running balance per account-day.
- `dense`: grid `LEFT JOIN daily`, `COALESCE` to 0, cumulative `SUM` over the days.
- `lowest_balance = LEAST(start_of_day, lowest_after_posting)` with
  `start_of_day = closing - net_change`. PostgreSQL's `LEAST` ignores NULLs, so quiet days fall
  back to the start-of-day value. (SQL Server's `LEAST` does too, but if you write a `CASE`
  instead, handle NULL explicitly.)

Worked example, account 1:

| day | postings (order) | start | after each | close | low |
|---|---|---|---|---|---|
| 01-01 | +100 | 0 | 100 | 100 | **0** (00:00–10:00 the balance was 0) |
| 01-02 | −30, −80 @09:00 | 100 | 70, −10 | −10 | −10 |
| 01-03 | +50 | −10 | 40 | 40 | **−10** |
| 01-04 | – | 40 | – | 40 | 40 |
| 01-05 | −5 @**00:00:00** | 40 | 35 | 35 | 35 |

## (b) Alternative: calendar grid + correlated LATERAL (`SQL-034_alt.sql`)

For every cell, one LATERAL sums everything before midnight (start-of-day balance), and another
replays the day's postings with a small window. It reads like the business definition and makes a
midnight bug hard to write. But it re-reads each account's history once per day, so the cost is
O(accounts × days × postings per account). That is fine for one week and five accounts. For a
year of snapshots across millions of accounts it is a disaster unless you only produce **one new
day** per run (which is exactly what an incremental snapshot job does: yesterday's closing +
today's postings).

## Edge cases and how the fixtures prove them

| fixture | situation | proves |
|---|---|---|
| account 1, entries 2+3 | two debits at the same instant | deterministic ordering, balance −10 |
| account 1, entry 5 at 01-05 00:00:00 | midnight posting | `<` next midnight: it belongs to 01-05 |
| account 2 | postings on 01-01 and 01-04 only | carry-forward across quiet days |
| account 3 | −20 then +20 at 23:59:59 | closes at 0.00, intraday low −20 (risk sees the dip) |
| account 4 | no postings at all | dense grid, 0.00 every day |
| account 5 | entry_id order ≠ time order; reaches exactly 0 | order by time first, `entry_id` only for ties |

Typical wrong answers: grouping the ledger by day without a grid (account 4 and quiet days
vanish); taking the intraday low only over posting rows (account 1 on 01-03 shows 40 instead of
−10); bucketing with `<= midnight` (the 00:00:00 fee lands on 01-04).

## Complexity and indexes

- The baseline index `account_ledger(account_id, posting_ts, entry_id)` matches the window
  ordering exactly. PostgreSQL can read postings in window order without a sort, and the LATERAL
  variant becomes short index range scans.
- The grid is accounts × days. For 10M accounts × 365 days that is 3.65 billion rows a year, which
  is why many teams keep a **sparse** snapshot (only days with postings) plus a "valid until"
  column, or a **monthly** dense snapshot.

## Production considerations

- **Incremental build:** `snapshot(D) = snapshot(D−1).closing + postings on D`. Each run produces
  one day from yesterday's row and today's postings. It is O(active accounts), not O(history).
- **Late postings:** a posting back-dated to D−3 invalidates D−3 … today for that account.
  Recompute from the earliest affected date (watermark on `ingested_at`, lookback window) and
  upsert idempotently.
- **Reconciliation:** the sum of `closing_balance` over all accounts for day D must equal the sum
  of the ledger up to D's midnight. Run it daily.
- **Time zone:** for customer-facing statements the "day" is usually the account's local day.
  The midnight boundary then moves per account; keep the UTC instants and convert at the edge.

## SQL Server / Azure Synapse notes

- `generate_series` exists only from SQL Server 2022 (`GENERATE_SERIES(start, stop)` over
  integers). Elsewhere, use a calendar/date dimension table, which every warehouse should have
  anyway.
- `SUM(...) OVER (PARTITION BY ... ORDER BY ... ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`
  is identical. Always write `ROWS`: the default frame `RANGE` treats equal timestamps as one peer
  group and gives every same-instant posting the same running balance.
- `CROSS APPLY` replaces `CROSS JOIN LATERAL`.
- Synapse: distribute the ledger and the snapshot on `account_id` so the window is local. Use a
  CTAS per day (or per month) and partition switching to load the snapshot.

1. Snapshot by the **account's local day** (accounts in different time zones). What changes in
   the grid and in the bucketing?
2. A posting for 2025-01-02 arrives on 01-06. Which snapshot rows change, and how do you make
   the reprocessing idempotent?
3. At 500M postings and 10M accounts, would you keep a dense daily snapshot? Compare dense daily,
   sparse with valid-from/valid-to, and month-end snapshots plus on-demand replay.
4. Risk asks for "accounts below zero at any moment in the last 30 days". Which column answers
   it, and why is `closing_balance` not enough (account 3)?
