# SQL-039 · Monthly active customers by historical region: explanation

## Core idea

Two traps meet here:

1. **Point-in-time attribute** (SQL-031): region comes from the version containing `transaction_ts`,
   joined with the interval predicate inside a `LEFT JOIN`.
2. **Grain of a distinct metric:** "customers per month per region" is not additive and not a count of
   transactions. The unit being counted is a customer within a `(month, region)` cell. A customer
   with several purchases in the cell counts once, and a customer who moved counts once in
   **each** cell. So the sum over regions can exceed the number of distinct customers (June: customer 50
   is EAST and WEST).

## (a) Reduce to the metric's grain, then count (`SQL-039.sql`)

`customer_month_region` = `SELECT DISTINCT purchase_month, region_at_purchase, customer_id`. Then `COUNT(*)` per
`(month, region)`. This makes the grain explicit and easy to test: no duplicates can slip in.

## (b) LATERAL as-of + `COUNT(DISTINCT)` (`SQL-039_alt.sql`)

Look up the latest version starting at or before the sale (one index probe per fact), verify the sale is before that
version's end, and aggregate with `COUNT(DISTINCT customer_id)`. No intermediate set, shorter, and the optimizer can
use one sort/hash per group. Trade-off: if the dimension had overlapping versions, (b) silently picks one while (a)'s
range join would count the customer in both regions, i.e. (a) lets data-quality problems show up (SQL-032).

## NULL region

`GROUP BY` puts all NULLs in one group. The NULL bucket holds purchases whose version has a NULL region
(unknown) **and** purchases with no matching version at all (customer 53's March 2025 gap, SQL-033). Relabelling
via `COALESCE(region, 'UNKNOWN')` is fine for presentation, but only after the grouping so a real region
named 'UNKNOWN' can never collide. Dropping NULLs makes the regional totals silently lower than the company total, which
finance will notice.

## Edge cases

| case | outcome |
|---|---|
| customer 50, 06-15 09:59:59 vs 10:00:00 | EAST vs WEST |
| customer 50 four purchases in June | counted once in EAST, once in WEST |
| customer 53 in March (gap) | NULL-region group of 2025-03 |
| `<=` on `effective_to` | boundary sale matched twice: still one customer per region, but a mover shows in both regions wrongly |
| `COUNT(*)` over joined rows | counts purchases, not customers |
| `is_current` join | restates all history into today's region |

## Complexity and production

- Cost is dominated by the as-of join on a year of facts. At 500M facts, stamp `customer_sk` or `region_at_purchase` on the
  fact at load time so the report is a plain `GROUP BY`.
- `COUNT(DISTINCT)` does not roll up: monthly actives cannot be summed across months or regions. Pre-aggregate the grain
  (`month, region, customer_id`) into a small table and count from it, or use HyperLogLog sketches if approximate is fine.
- Name the metric precisely in the semantic layer: "active customers (region at purchase)"; the number differs from
  "active customers by current region" by design.

## SQL Server / Azure Synapse notes

`COUNT(DISTINCT)` works on a single expression; to count distinct pairs use a subquery. `OUTER APPLY (SELECT TOP (1) ...)`
replaces the LATERAL lookup. `DATETRUNC(month, ...)` from SQL Server 2022, else `DATEFROMPARTS(YEAR(), MONTH(), 1)`. Synapse supports
`APPROX_COUNT_DISTINCT` for very large cuts.
