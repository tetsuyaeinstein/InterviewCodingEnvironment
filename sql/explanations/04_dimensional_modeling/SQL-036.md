# SQL-036 · Daily product availability snapshot from interval history: explanation

## Core idea

Interval history (`valid_from`, `valid_to`, `available`) is compact but awkward for BI. A **daily
snapshot** turns it into a dense grid `day × product`. The modeling question is *what one row per
day should mean*, because an interval can cover part of a day:

| measure | question it answers | blind spot |
|---|---|---|
| `available_any_time` | "Could a customer have bought it today?" (validating sales lines, conversion denominators) | a 23-hour outage still shows true |
| `available_end_of_day` | "What is the stock position tonight?" (replenishment, like other EOD snapshots) | intraday outages are invisible; product 6 on 05-10 sold all day yet shows false |
| `available_minutes` | "How much of the day was it on the shelf?" (availability KPI, lost-sales estimate) | needs interval math; ignores *when* |

A strong rationale picks per consumer, says what each hides, and proposes persisting
flags **and** minutes in the snapshot, keeping the interval table as the source of truth.

## (a) Clip and aggregate (`SQL-036.sql`)

1. Grid: generated days × products (4, 5, 6).
2. Join history rows that **intersect** the day: `valid_from < day_end AND coalesce(valid_to,
   infinity) > day_start` (half-open intersection).
3. `seg_from/seg_to` = clipped bounds (`GREATEST` / `LEAST`); minutes = sum over available rows.
4. End of day = an available row that is still in force at `day_end`: its `valid_to` is NULL or
   `>= day_end`. A row ending exactly at midnight is not in force at 23:59:59.999999 and a row
   starting at the next midnight is not even joined (`valid_from < day_end`).
5. `LEFT JOIN` + `COALESCE(..., false)` so cells with no rows still appear and mean "unavailable".

Fixtures (store 2, 05-10): p4 out `[13:00, 15:00)` gives 1320 minutes, any/EOD true. p6 out
`[09:00,12:00)`, available `[12:00,20:00)`, uncovered after 20:00 gives 1020 minutes, any true,
**EOD false**. 05-11: p6 uncovered until 08:00, then available: EOD true, 960 minutes.

## (b) Range types (`SQL-036_alt.sql`)

`tstzrange(valid_from, valid_to)` with `&&` for any-time, `@>` at `day_end - 1 microsecond` for
end-of-day, and `*` for intersection lengths. Shorter, boundary-safe (half-open by default) and
GiST-indexable; PostgreSQL only, and one correlated subquery per cell, so it scales worse than (a).

## Complexity and indexes

(a) is one join of the grid to history, proportional to rows overlapping the window. An index on
`(store_id, product_id, valid_from)` supports it. For the whole chain (40 stores × 60 products ×
365 days) the dense grid is ~900k rows a year, fine; across 10k stores and 100k SKUs it is not.

## Production considerations

- Store the snapshot incrementally: today's rows only, plus a re-run for days touched by late
  history corrections (watermark on load time).
- At large scale use a **sparse** change table (rows only when a status changes) and densify at
  query time against a date dimension, or snapshot only tracked/assortment products.
- Reconcile: for any product-day with sales, `available_any_time` should be true (SQL-029 style);
  report violations.
- Define "not stocked" explicitly in the model. Many warehouses add an explicit `NOT_STOCKED`
  status row so that gaps are data, not absence.

## SQL Server / Azure Synapse notes

No range types: use the explicit intersection predicate and `DATEADD(microsecond, -1, day_end)`
(`datetime2(6)`; `datetime` only has 3 ms precision, so `23:59:59.997` is the last instant there).
Generate days from a date dimension or `GENERATE_SERIES` (SQL Server 2022). `bool_or` becomes
`MAX(CASE ... THEN 1 ELSE 0 END)`.
