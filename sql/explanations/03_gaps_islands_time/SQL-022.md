# SQL-022 · Every purchase streak with start, end and length: explanation

## Core idea

Same gaps-and-islands pattern as SQL-021, but now the **island itself** is the output, not just
a yes/no per customer. Fix the grain first, which is one row per `(customer_id, UTC purchase_date)`.
Then label each run and aggregate each label to `MIN`, `MAX` and `COUNT`.

## (a) `date - ROW_NUMBER()` island key (`SQL-022.sql`)

| purchase_date | rn | date − rn | island |
|---|---|---|---|
| 2025-07-01 | 1 | 06-30 | A |
| 2025-07-02 | 2 | 06-30 | A |
| 2025-07-03 | 3 | 06-30 | A |
| 2025-07-04 | 4 | 06-30 | A |
| 2025-07-06 | 5 | 07-01 | B |
| 2025-07-07 | 6 | 07-01 | B |
| 2025-07-08 | 7 | 07-01 | B |

(That is fixture customer 11: two rows, 4 days and 3 days.)

`GROUP BY customer_id, island_key HAVING COUNT(*) >= 3` gives one row per maximal streak.
Islands are maximal by construction: the key changes exactly when a day is skipped. So streaks
never overlap, and a 7-day run (customer 4) is one row, not five 3-day windows.

Because the days are distinct, `COUNT(*) = streak_end - streak_start + 1`. If you forget the
`DISTINCT`, the two numbers disagree, which is a useful self-check.

## (b) `LAG` + running sum of streak starts (`SQL-022_alt.sql`)

`is_streak_start = 0` when the previous purchase day is exactly yesterday, otherwise 1. A running
`SUM` of that flag is a streak number. Group by it.

**Trade-offs.** (a) needs one window function and no explicit frame. (b) needs two window passes
(`LAG`, then `SUM`), although PostgreSQL evaluates both over the same sort. (b) generalises to any
break rule ("gap > 2 days", "gap > 30 minutes": SQL-026), while (a) only works when consecutive
members differ by exactly one unit of a discrete domain (dates, integers). Both sort each
customer's days once: O(n log n) overall, O(n) after the sort.

A "fixed window" answer such as `LEAD(d, 2) = d + 2` finds 3-day windows, not streaks. It returns
overlapping rows and the wrong lengths, and the grader rejects it.

## Edge cases (fixtures)

| fixture | situation | correct rows |
|---|---|---|
| 5 | two disjoint 5-day runs | two rows: 05-01..05-05, 05-10..05-14 |
| 6 | 7 purchases, distinct days 06-02..06-05 then 06-07 | one row, 4 days (the 06-07 singleton is too short) |
| 7 | 5 days with 3 purchases on one day | one row, 5 days |
| 9 | 2024-12-29 .. 2025-01-02 | one row crossing the year |
| 10 | 2024-02-26 .. 03-01 | one row crossing the leap day (5 days, not 4) |
| 11 | 4 + 3 around a skipped day | two rows |
| 12 | 07-12 has only a CANCELLED txn (plus a PENDING on 07-11) | no row (two 2-day runs) |

Without `DISTINCT`, customer 6's duplicate days produce row numbers that run ahead of the dates.
The island key then shifts and the run splits into fragments (the grader shows 2 rows instead of 1).

## Plan and indexes

- The cost is one scan of `transactions`, a hash/sort `DISTINCT`, a sort on
  `(customer_id, purchase_date)`, a `WindowAgg` and a `HashAggregate`.
- In production, run it on a pre-aggregated `customer_daily_activity` table (customer × day),
  ideally clustered or indexed on `(customer_id, activity_date)`. The window can then consume an
  index scan without a sort.
- In `EXPLAIN (ANALYZE, BUFFERS)`, check the `Sort Method` (external merge = spilling) and the
  row count entering the `WindowAgg`.

## Production considerations

- **Incremental maintenance.** Keep a streak table `(customer_id, streak_start, streak_end)`. A
  new purchase day D can extend a streak ending on D−1, prepend to a streak starting on D+1, or
  **bridge** two streaks (D−1 and D+1 both exist). Late-arriving data makes all three happen.
  Recompute the affected customer, or apply a MERGE that deletes the 1–2 touched streaks and
  inserts the merged one.
- **Open streaks.** A streak ending on the last loaded date may continue tomorrow. Expose an
  `is_open` flag rather than letting consumers assume it ended.
- **Reconciliation.** `SUM(streak_days)` over all streaks (no length filter) must equal the number
  of distinct customer-days.

## SQL Server / Azure Synapse notes

- The island key is `DATEADD(day, -ROW_NUMBER() OVER (...), purchase_date)`. The alt uses
  `DATEDIFF(day, LAG(...), purchase_date) = 1`.
- In SQL Server 2022+, `DATETRUNC` and `DATE_BUCKET` help with other grains.
- In Synapse, hash-distribute the daily activity table on `customer_id` so the window is
  node-local. A `PARTITION BY customer_id` on a ROUND_ROBIN table forces a shuffle.
