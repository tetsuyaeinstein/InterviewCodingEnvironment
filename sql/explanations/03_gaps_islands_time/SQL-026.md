# SQL-026 · Sessionization with a 30-minute inactivity rule: explanation

## (a) Gap flag + running sum (`SQL-026.sql`)

1. Scope: identified customers, `event_ts` in `[2025-07-01, 2025-08-01)`.
2. `is_session_start = 1` if there is no previous event, or if
   `event_ts - LAG(event_ts) > INTERVAL '30 minutes'`; otherwise 0.
3. `session_number = SUM(is_session_start) OVER (PARTITION BY customer_id ORDER BY event_ts, event_id ROWS UNBOUNDED PRECEDING)`.
4. `GROUP BY customer_id, session_number` → start = `MIN(event_ts)`, end = `MAX(event_ts)`,
   `event_count = COUNT(*)`.

Worked example on fixture customer 40:

| event_ts | gap | start? | session |
|---|---|---|---|
| 07-01 10:00:00 | – | 1 | 1 |
| 10:10:00 | 10:00 | 0 | 1 |
| 10:40:00 | **30:00** | 0 | 1 |
| 11:10:01 | **30:01** | 1 | 2 |
| 11:10:01 | 0 | 0 | 2 |
| 11:20:00 | 9:59 | 0 | 2 |
| 23:50:00 | 12:30 | 1 | 3 |
| 07-02 00:05 | 15:00 | 0 | 3 |
| 07-03 09:00 | 32:55 h | 1 | 4 |

## (b) Carry the session start forward (`SQL-026_alt.sql`)

Instead of *counting* starts, put `start_ts = event_ts` on session-opening rows (NULL elsewhere)
and carry it forward with a running `MAX(start_ts)`. Timestamps never decrease within the
ordered partition, so the latest start seen so far is the current session's start. That value is
the session key, and `DENSE_RANK()` over it yields the session number. This is handy when the
consumer wants a stable, meaningful key (`customer_id, session_start`) rather than an ordinal that
shifts if an earlier event arrives late. In engines with `IGNORE NULLS`
(`LAST_VALUE(start_ts) IGNORE NULLS`), it is the idiomatic "fill forward".

## Edge cases and pitfalls

- **`>` vs `>=`.** A gap of exactly 30:00 continues the session. With `>=`, customer 40 gets 5
  sessions and session 1 ends at 10:10.
- **Equal timestamps.** Order by `(event_ts, event_id)`. With a `ROWS` frame and only
  `ORDER BY event_ts`, peers are processed in arbitrary order. The *grouping* happens to survive
  here (the second identical timestamp is never a session start), but anything order-dependent
  (event sequence numbers, first event type of the session) becomes nondeterministic.
  The default `RANGE` frame treats peers as one step, which is a different, sometimes surprising,
  semantic.
- **Midnight.** Session 3 crosses 07-01/07-02. Never partition by date.
- **Client `session_id`.** Partitioning by it splits customer 40's activity into 6 "sessions"
  (S-A, NULL, S-B, …). This shows why the server-side rule exists.
- **Window boundaries.** Events before 07-01 do not exist for this report. A session that began
  at 06-30 23:55 is cut at the window edge. In production, read a 30-minute look-back and assign
  sessions to the window in which they *start*.

## Plan and indexes

`customer_events(customer_id, event_ts)` exists. For a selective scope, the planner can feed the
window in index order. For the month, it is a scan plus one sort on
`(customer_id, event_ts, event_id)`. Both window functions share that sort. O(n log n), single
pass afterwards.

## Production considerations

- **Streaming.** Spark, Flink and Beam implement exactly this as *session windows* with a gap
  duration. Late events can **merge** two sessions, so downstream tables need upsert semantics
  keyed by a deterministic session key (for example customer + first event_id).
- **Incremental batch.** Reprocess from the last *open* session start of each customer
  (watermark − 30 minutes), not from the watermark itself.
- **Monitoring.** Watch the session count per day, the median length, and the share of
  single-event sessions. A sudden jump often means clock skew on a client release.

## SQL Server / Azure Synapse notes

- `DATEDIFF_BIG(second, LAG(event_ts) OVER (...), event_ts) > 1800` gives the gap.
  `DATEDIFF(minute, ...)` counts minute **boundaries crossed**, so 10:40:59 → 11:10:01 would be
  30, which is wrong. Use seconds.
- SQL Server 2022 supports `LAST_VALUE(...) IGNORE NULLS` for variant (b).
- In Synapse, distribute events on `customer_id`. The session table is then a local window
  computation per distribution.
