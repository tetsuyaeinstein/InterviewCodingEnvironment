# SQL-030 · Gaps in daily device reports: explanation

## The key insight

Missing days have **no rows**. You cannot find them by reading `device_status_events` alone. You
need either an **expected calendar** (what should exist) or the **jumps between existing rows**.

## (a) Calendar, anti-join, islands (`SQL-030.sql`)

1. `generate_series('2025-01-01', '2025-02-28', '1 day')` builds the calendar.
2. `expected`: join devices to the calendar with the in-service rule
   `installed_on <= d AND (decommissioned_on IS NULL OR d < decommissioned_on)`.
3. `missing`: `NOT EXISTS` a `SCHEDULED` event whose `event_ts` lies in `[d, d + 1)` UTC. The
   bound is written as a timestamp range so the `(device_id, event_ts)` index can be used.
   `received_at` is irrelevant: a late report counts for the day it was produced.
4. Islands: `report_date - ROW_NUMBER()` per device → `MIN`, `MAX`, `COUNT` per gap.

## (b) LEAD between report days plus sentinels (`SQL-030_alt.sql`)

There is no calendar. Take the distinct report dates inside each device's window
`[max(installed_on, Jan 1), min(decommissioned_on, Mar 1) − 1]`. Add two **sentinel** days (the
day before the window and the day after it) so leading and trailing gaps become ordinary jumps.
Then `LEAD(report_date)`: any `next − current > 1` is a gap from `current + 1` to `next − 1`.

| | calendar + anti-join | LEAD + sentinels |
|---|---|---|
| rows processed | devices × days (dense) | report days (sparse) |
| boundary handling | automatic | sentinels, easy to get wrong |
| reusable for "36-hour gaps" | no | yes: compare `event_ts` of consecutive reports instead of dates |

The **36-hour** variant asks for something different: `LEAD(event_ts) - event_ts > INTERVAL '36 hours'`
over SCHEDULED reports. A device that reports at 00:05 on day 1 and 23:55 on day 2 has a 47h50m
gap but **no missing day**. Conversely, two reports 25 hours apart across a day boundary are
fine on both rules. Calendar completeness (this exercise) is what SLAs usually mean; elapsed-time
gaps are what alerting usually means.

## Edge cases (fixtures)

| device | situation | expected |
|---|---|---|
| KIOSK-F01 | missing 01-10, 01-11, 01-20; decommissioned 02-01 | gaps [01-10..01-11] (2) and [01-20] (1); nothing in February |
| KIOSK-F02 | 01-15 report received on 01-16; two reports on 01-22; decommissioned 02-01 | no gaps (by `received_at`, 01-15 would wrongly be missing) |
| KIOSK-F03 | reports in January, silent all of February, decommissioned 03-01 | one gap 02-01..02-28, 28 days |
| KIOSK-0030 | 01-30 has only a CHANGE event | 01-30 is missing |
| devices installed in the period (e.g. 2025-01-04, 01-18, 02-13) | – | no gap before `installed_on` |

Ignoring `decommissioned_on`, or treating it as inclusive, invents February gaps for F01/F02.

## Plan and indexes

The calendar side is small (63 devices × 59 days ≈ 3.7k rows here). Each `NOT EXISTS` is an index
probe on `device_status_events(device_id, event_ts)`. Writing the condition as
`(event_ts AT TIME ZONE 'UTC')::date = d` would defeat that index unless you add an expression
index. At scale, aggregate first: one row per (device, UTC day) with a report count, kept as a
daily summary. The anti-join becomes a cheap join of two dense tables.

## Production considerations

- **Late data.** A report for day D can arrive days later. Treat days as provisional until a
  lateness bound has passed, and recompute the last N days on every run.
- **Ticketing idempotency.** Key tickets on `(device_id, gap_start)`. A gap that grows keeps its
  key, and only `gap_end` changes. When a late report splits a gap in two, close the old ticket
  and open two.
- **Calendar dimension.** Use a real `dim_date` in the warehouse instead of `generate_series`.
  It also carries holidays and maintenance windows that may be excluded from SLAs.

## SQL Server / Azure Synapse notes

- There is no `generate_series` before SQL Server 2022 (`GENERATE_SERIES(start, stop)` returns
  integers there). Use a `dim_date` table or a numbers CTE with `DATEADD(day, n, @start)`.
- The island key is `DATEADD(day, -ROW_NUMBER() OVER (...), report_date)`.
- In Synapse, REPLICATE `devices` and `dim_date`, and distribute the event fact on `device_id`.
