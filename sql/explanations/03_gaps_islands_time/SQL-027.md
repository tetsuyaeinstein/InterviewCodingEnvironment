# SQL-027 · Merge overlapping downtime incidents: explanation

## Why the naive answers are wrong

- **Summing raw intervals** counts every overlapping minute once per report. KIOSK-F01 gives
  90 + 15 + 60 + 15 + 30 = 210 minutes instead of 165; KIOSK-F02 gives 120 instead of 60.
- **Pairwise self-join** (subtract the overlap of each pair) is inclusion–exclusion truncated at
  pairs. With three mutually overlapping intervals you subtract too much, nested intervals get
  subtracted twice, and touching intervals are not "overlapping" at all, so the outage count is
  wrong (KIOSK-F01 comes out as 4 outages). It is also O(n²) per device.
- **Comparing with the previous row only** (`down_from <= LAG(down_to)`) fails when an earlier,
  longer interval is still open. Sorted F01 rows are [08:00, 09:30), [08:30, 08:45),
  [09:00, 10:00): the third starts after the *previous row's* end (08:45) but before the
  *outage's* end (09:30).

## (a) Running MAX of the end (`SQL-027.sql`)

1. Keep incidents that intersect January (`down_from < '2025-02-01' AND down_to > '2025-01-01'`)
   and clip them: `GREATEST(down_from, Jan 1)`, `LEAST(down_to, Feb 1)`.
2. Sort per device by `(s, e, incident_id)`. A row starts a new outage when
   `s > MAX(e) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)`. `s = max_e` means
   touching, which merges. The first row has NULL, which also counts as new.
3. Running `SUM` of the flags gives the outage id (same full ordering, including `incident_id`, so
   exact duplicates are not split).
4. Per outage, `MIN(s)` and `MAX(e)`. Per device, `COUNT(*)` and
   `SUM(EXTRACT(EPOCH FROM (end - start))) / 60`, rounded to 2 decimals.

| s | e | max e before | new? | outage |
|---|---|---|---|---|
| 08:00 | 09:30 | – | 1 | 1 |
| 08:30 | 08:45 | 09:30 | 0 | 1 |
| 09:00 | 10:00 | 09:30 | 0 | 1 |
| 10:00 | 10:15 | 10:00 | 0 (touch) | 1 |
| 01-16 12:00 | 12:30 | 10:15 | 1 | 2 |

Outage 1 = [08:00, 10:15) = 135 min, outage 2 = 30 min → **165**.

## (b) `range_agg` (`SQL-027_alt.sql`, PostgreSQL 14+)

`range_agg(tstzrange(down_from, down_to, '[)'))` returns a `tstzmultirange` in which overlapping
**and adjacent** ranges are already coalesced (`[a, b)` and `[b, c)` are adjacent). Intersecting
it with the January multirange (`*`) clips it, and `unnest()` returns the outages. It is
declarative and hard to get wrong. The trade-offs are that it is PostgreSQL-specific, the
aggregate materialises one multirange per device in memory, and interviewers usually want the
window version as well.

## Plan and indexes

One scan filtered by the January range, one sort per device by start, then two window passes over
the same sort. O(n log n) overall. An index on `(device_id, down_from)` helps only for selective
per-device queries. For the monthly job, a range filter on `down_from` with a bounded maximum
incident length (`down_from >= '2024-12-01'`) lets a `down_from` index or partition pruning work.
`down_to > X` alone is not prunable. A GiST index on `tstzrange(down_from, down_to)` supports
`&&` overlap filtering directly.

## Production considerations

- **Source precedence.** Real SLAs often trust MONITORING over VENDOR reports. Merging all
  sources is the conservative choice. Make it a parameter.
- **Open incidents** (`down_to` unknown): cap them at the report cut-off and flag them.
- **Month attribution.** Clipping (used here) vs "month of start" changes the numbers of outages
  crossing month boundaries. Write the rule into the SLA report.
- **Reconciliation.** Merged minutes ≤ raw minutes, and merged outages never overlap per device.
  Both are cheap assertions to run after every load.

## SQL Server / Azure Synapse notes

- There are no range types or `range_agg`. Use the window approach:
  `MAX(down_to) OVER (PARTITION BY device_id ORDER BY down_from, down_to, incident_id ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)`
  works in SQL Server 2012+ and Synapse.
- `DATEDIFF_BIG(second, a, b) / 60.0` for minutes. `GREATEST`/`LEAST` exist only from SQL Server
  2022 (and in Synapse serverless/dedicated recent versions); otherwise use `CASE`.
- An alternative classic is the "start/end event stream": +1 at each start, −1 at each end,
  running sum. Outages are the stretches where the running count is > 0. Process ends before
  starts at equal timestamps if touching should **not** merge, and starts before ends if it
  should.
