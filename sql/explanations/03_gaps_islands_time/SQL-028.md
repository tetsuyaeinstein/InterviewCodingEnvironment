# SQL-028 · Point-in-time list price: explanation

## (a) Range join on `[valid_from, valid_to)` (`SQL-028.sql`)

```
LEFT JOIN product_price_history ph
  ON  ph.product_id  = ti.product_id
  AND ph.valid_from <= t.transaction_ts
  AND (ph.valid_to IS NULL OR t.transaction_ts < ph.valid_to)
```

- **Half-open.** At the change instant (`ts = valid_to` of the old row = `valid_from` of the new
  row) only the new row matches. `BETWEEN`, or `<= valid_to`, matches **both** rows, so the line
  is duplicated (fixture txn 6602 at 2025-03-01 12:00:00 and txn 6604 at 2025-06-15 08:30:00).
- **Open-ended.** `valid_to IS NULL` must be handled explicitly. `COALESCE(valid_to, 'infinity')`
  is an equivalent idiom.
- **LEFT JOIN, with the conditions in `ON`.** Product 7 has no history. An inner join silently
  drops its 81 lines; the spec asks for NULL. Putting the interval condition in `WHERE` instead of
  `ON` would turn the outer join back into an inner one for any product whose versions do not
  cover the sale. It happens to be harmless on this data, but it is a classic bug.
- `price_diff = unit_price - list_price` is NULL automatically when the list price is NULL.

## (b) Latest version at or before the timestamp, via LATERAL (`SQL-028_alt.sql`)

For each line, `SELECT ... WHERE product_id = ? AND valid_from <= ts ORDER BY valid_from DESC LIMIT 1`.
This is an "as-of" join. It is served by the primary key `(product_id, valid_from)` scanned
backwards: one index probe per line, O(m log n). The `CASE` on `valid_to` ensures that a gap in
the history (version ended, no successor yet) returns NULL instead of a stale price.

| | range join | LATERAL as-of |
|---|---|---|
| correctness | needs a correct `valid_to` | needs only `valid_from` (if gaps are impossible) |
| duplicate risk | yes, if history overlaps | no (`LIMIT 1`) — but it then *hides* bad data |
| plan | hash/merge join with filter, or nested loop on the PK | nested loop + index scan per line |
| best when | many lines per product, set-based | few lines, or very long histories |

Overlapping versions cannot occur here (an `EXCLUDE` constraint enforces it). In a warehouse
without such constraints, the range join *reveals* overlaps as duplicates, while LIMIT 1 hides
them. Decide which behaviour you want, and add a data-quality check for overlaps.

## Edge cases (fixtures, customer 66)

| txn | ts | charged | list | diff |
|---|---|---|---|---|
| 6601 | 03-01 11:59:59 | 10.00 | 10.00 | 0.00 |
| 6602 | 03-01 12:00:00 | 12.00 | **12.00** | 0.00 |
| 6603 | 03-02 15:00 | 11.00 | 12.00 | **−1.00** (override) |
| 6605 | 06-15 08:29:59 | 4.25 | 4.25 | 0.00 |
| 6604 | 06-15 08:30:00 | 4.50 | **4.50** | 0.00 |

Product 1 changes at midnight 2025-04-01 (18.00 → 19.50). Product 7 → NULL / NULL.
`products.standard_price` is today's price and would mark every pre-change line as an override.

## Plan and indexes

The PK `(product_id, valid_from)` supports both approaches. A GiST index on
`tstzrange(valid_from, valid_to)` (which the `EXCLUDE` constraint already creates, together with
`product_id`) supports `@>` containment queries:
`ON ph.product_id = ti.product_id AND tstzrange(ph.valid_from, ph.valid_to, '[)') @> t.transaction_ts`.
At warehouse scale, the dimension is tiny compared with the fact: broadcast it and do the range
join in memory.

## Production considerations

- **Late price corrections** rewrite history. Decide whether the audit uses the price as known at
  sale time (bitemporal: add `recorded_at`) or the corrected price.
- **Time zone.** Price changes "at midnight" are usually store-local midnight. Here they are UTC.
  Confirm this with the business.
- **Data-quality checks:** no overlaps per product, no gaps unless intended, exactly one open
  version per product.

## SQL Server / Azure Synapse notes

- There is no LATERAL. Use `OUTER APPLY (SELECT TOP (1) ... ORDER BY valid_from DESC)`.
- `ISNULL(valid_to, '9999-12-31')` is the common sentinel. Keep it half-open (`<`).
- In Synapse, REPLICATE the small price-history table so the join is local to each distribution.
