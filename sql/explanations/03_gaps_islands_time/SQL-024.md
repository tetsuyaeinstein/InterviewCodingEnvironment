# SQL-024 · Five consecutive days with daily spend above 100: explanation

## Approach: aggregate, filter, then find islands

1. **Aggregate to the grain of the rule.** The threshold is about a *day's total*, so build
   `daily_spend = SUM(gross_amount)` per `(customer_id, UTC date)` from `COMPLETED` rows.
2. **Filter days.** Keep `day_total > 100.00` (strict, exact `numeric`).
3. **Islands.** Apply `spend_date - ROW_NUMBER()` per customer to the *qualifying* days, then group
   and keep runs with `COUNT(*) >= 5`.
4. **First run.** `DISTINCT ON (customer_id) ... ORDER BY customer_id, run_start` keeps the earliest
   run. The full run length is reported (customer 18 → 6 days).

The order of steps is the whole exercise:

| mistake | effect | fixture |
|---|---|---|
| filter transactions `gross_amount > 100` before aggregating | loses days that are big only in total | 15 (09-02 = 60 + 50), 18 (55 + 50 every day) |
| `>= 100` | a day of exactly 100.00 qualifies | 16 |
| no status filter | the cancelled 150 makes 09-03 = 200 | 17 |
| islands on *all* purchase days, then check `min(day_total) > 100` per island | a sub-threshold day sits inside a longer purchase streak, so the island is rejected although 5 big days may exist on either side | general |
| `LEAD(spend_date, 4) = spend_date + 4` on all days | works only if non-qualifying days were removed first | general |

The fourth row is subtle. Islands must be built on the filtered set, because a non-qualifying day
is a **break**, exactly like a day without purchases.

## Edge cases (fixtures)

- **15** qualifies, 09-01..09-05 (120, 110, 101, 150, 100.01): it shows that aggregation must come
  first and that 100.01 counts.
- **18** qualifies, 09-10..09-15, run of **6** days: no single purchase exceeds 100.
- **16** is excluded (100.00 on 09-03); **17** is excluded (09-03 has only 50 completed).
- Ordinary streak customers (3, 4, 7, …) buy 20.00 a day and are never big.

## Complexity, plan and indexes

One aggregation pass (`HashAggregate` over customer × day), then a sort and window over the much
smaller set of big days. Big days are rare, so the window input is tiny. On 500M rows the
aggregation dominates. Feed it from the daily summary instead (`customer_daily_activity` already
holds daily completed spend in this lab) and the query becomes cheap. A partial index such as
`... WHERE transaction_status = 'COMPLETED'` helps only if the query runs against the raw fact
repeatedly.

## Production considerations

- **Refunds.** The business must decide gross vs net. If net, the daily value changes when a
  refund lands weeks later, so a badge could be revoked. Decide whether badges are immutable once
  granted.
- **Late data** can create a qualifying run retroactively. Recompute customers whose days within
  ±4 of the late transaction date changed.
- **Precision.** Keep `numeric`. Floats make 100.00 vs 100.01 comparisons fragile.

## SQL Server / Azure Synapse notes

- `CAST(transaction_ts AT TIME ZONE 'UTC' AS date)` for the day; `DATEADD(day, -ROW_NUMBER() ..., d)`
  for the island key.
- There is no `DISTINCT ON`; use `ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY run_start) = 1`.
- `decimal(12,2)` sums are exact in both engines.

## Follow-up questions

1. Make the threshold store-local per day. What must you join, and which DST issues appear?
2. Change the rule to "5 consecutive days with a **combined** spend over 500". Is this still
   gaps-and-islands, or a sliding window (`SUM(...) OVER (ORDER BY date RANGE BETWEEN INTERVAL '4 days' PRECEDING AND CURRENT ROW)`)?
3. At 500M transactions per year with late refunds, design the daily job and the badge table so
   reruns are idempotent.
