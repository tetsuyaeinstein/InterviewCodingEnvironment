# SQL-021 · Five consecutive purchase days: explanation

## Core idea

This is a **gaps-and-islands** problem. The trap is grain. The question is about *purchase days*,
but the table is at *transaction* grain. Collapse to one row per `(customer_id, purchase_date)`
**before** you look for consecutive runs.

## (a) Window-function islands: `date - ROW_NUMBER()` (`SQL-021.sql`)

1. `purchase_days`: `SELECT DISTINCT customer_id, (transaction_ts AT TIME ZONE 'UTC')::date`
   over completed, non-guest transactions.
2. Number each customer's days in date order with `ROW_NUMBER()`.
3. For consecutive dates, the date and the row number both go up by 1, so
   `purchase_date - row_number` stays constant within a run. That constant is the island key.

   | purchase_date | rn | date - rn |
   |---|---|---|
   | 2025-03-03 | 1 | 2025-03-02 |
   | 2025-03-04 | 2 | 2025-03-02 |
   | 2025-03-05 | 3 | 2025-03-02 |
   | 2025-03-07 | 4 | 2025-03-03 ← new island |

4. `GROUP BY customer_id, island_key HAVING count(*) >= 5`, then `DISTINCT customer_id`, because
   a customer can have more than one qualifying island.

**Why the DISTINCT in step 1 is essential:** with duplicate purchase days, `ROW_NUMBER` keeps
increasing while the date doesn't, so the island key shifts and runs get split. A naive
`COUNT(*) >= 5` over transactions also over-counts the other way. Fixture customer 6 has 6
purchases on 4 consecutive days followed by a gap, and naive versions report them as a streak.
Fixture customer 7 has 8 purchases over 5 days and must be reported **once**.

**Why it is calendar-safe:** `date - integer` in PostgreSQL is real calendar arithmetic, so month
ends, year ends and 2024-02-29 need no special handling (fixture customers 8, 9 and 10). Approaches
like `EXTRACT(DAY ...)` or `month * 31 + day` break here.

## (b) Alternative: `LAG` + running sum of streak breaks (`SQL-021_alt.sql`)

1. Same distinct purchase days.
2. `starts_new_streak = 0` when `purchase_date - LAG(purchase_date) = 1`, else `1` (this includes the
   first row, where `LAG` returns NULL).
3. A running `SUM(starts_new_streak)` gives a streak number. Group by it and count.

**Trade-offs vs (a):**

- (b) generalises: change the break condition to "gap > 1 day" or "gap > 30 minutes" and it
  becomes sessionization (SQL-026).
- (a) is shorter and needs only one window pass.
- Both need a sort per customer by date: O(n log n) per partition, and one windowed pass over the
  de-duplicated rows.
- Third variant worth mentioning aloud: on distinct days,
  `LEAD(purchase_date, 4) OVER (PARTITION BY customer_id ORDER BY purchase_date) = purchase_date + 4`
  is true exactly when the 5 days starting there are consecutive. It works for a fixed length, but
  doesn't give you run boundaries or lengths (SQL-022 needs those).

## Edge cases and how the fixtures prove them

| fixture | situation | correct outcome |
|---|---|---|
| 2 | exactly 4 days | excluded |
| 3 | exactly 5 days | included once |
| 5 | two separate 5-day runs | included **once** |
| 6 | 6 purchases, 4 distinct consecutive days | excluded |
| 7 | 5 distinct days, several purchases per day | included once |
| 8 / 9 / 10 | month end / year end / leap day | included |
| 11 | skipped day splits the run 4 + 3 | excluded |
| 12 | middle day only has a CANCELLED transaction | excluded |
| 13 | 5 UTC days; not consecutive in Los Angeles local time | included (the spec says UTC) |

## (c) Scaling to 500 million transactions

**1. Reduce before you window.** The expensive step is the window sort. Run it on
customer-day grain, not transaction grain. If customers average 1.3 transactions per purchase day,
that cuts the sorted rows by about 25%. In a warehouse you would keep a **daily customer activity
summary** (`customer_daily_activity` in this lab), maintained incrementally, and run
gaps-and-islands on that. It is usually 10–50x smaller than the fact.

**2. Partition-local work.** The window is `PARTITION BY customer_id`, so the computation is
embarrassingly parallel by customer:

- Synapse / Spark: hash-distribute or partition on `customer_id` so each node sorts its own
  customers without a shuffle.
- PostgreSQL: parallel aggregates help with the `DISTINCT`/`GROUP BY`. The window step itself runs
  single-threaded on the sorted stream, so pre-aggregation matters more.

**3. Indexes (PostgreSQL).**

- A B-tree on `(customer_id, transaction_ts)` lets the planner stream rows in window order, with
  no big sort, for selective per-customer queries.
- For the full-table version, an expression index such as
  `CREATE INDEX ON transactions (customer_id, ((transaction_ts AT TIME ZONE 'UTC')::date)) WHERE transaction_status = 'COMPLETED'`
  can feed `DISTINCT` in order. It only pays off if you run this often; the summary table is
  usually better.
- Verify with `EXPLAIN (ANALYZE, BUFFERS)`. Look for `Sort Method: external merge` (spilling to
  disk; raise `work_mem` or reduce rows), how big the `WindowAgg` input is, and whether you get an
  `Index Only Scan` (needs a recently vacuumed visibility map).

**4. Partitioning and pruning.** Range-partition the fact by `transaction_date` (monthly).
"Ever had a 5-day streak" scans everything, but incremental maintenance only needs the latest
partitions plus a small overlap window.

**5. Incremental and late-arriving data.**

- Store per-customer streak state (current run start and end) and update it per day.
- A late transaction for day D can **join two runs** (e.g. 2 days + gap D + 2 days → 5 days) or
  extend one. So reprocess the affected customer with a lookback window around D (D-4 … D+4 is
  enough for a fixed 5-day rule), not just day D.
- Watermark on `ingested_at`, recompute affected customers, and make the write idempotent (MERGE /
  `INSERT ... ON CONFLICT`). PY-040 covers the same logic in Python.

**6. Correctness at scale.** Reconcile counts against the summary (distinct customer-days must
equal `customer_daily_activity` rows). Spot-check fixture-like customers after each deploy.

## SQL Server / Azure Synapse dialect notes

- T-SQL: `DATEADD(day, -ROW_NUMBER() OVER (...), purchase_date)` is the classic island key.
  PostgreSQL uses `purchase_date - (row_number() ...)::int`.
- `CAST(transaction_ts AT TIME ZONE 'UTC' AS date)` works in both. In SQL Server, `AT TIME ZONE`
  on a `datetimeoffset` converts, while on a `datetime` it *assigns* an offset. Know which one you
  have.
- Synapse dedicated pools: distribute the activity table on `customer_id` (HASH) so the window
  stays node-local. Avoid ROUND_ROBIN for this workload.

## Follow-up questions an interviewer may ask

1. Return every streak with start, end and length (SQL-022), then only the longest per customer
   with a deterministic tie-break (SQL-023).
2. Make the definition store-local time instead of UTC. Which fixture changes answer, and why
   (customer 13)?
3. Change "each day had a purchase" to "each day's spend > $100" (SQL-024). Where does the
   aggregation move?
4. The fact is 500M rows and arrives with up to 10 days of lateness. Design the incremental job:
   watermark, lookback window, idempotent upsert, and reconciliation check.
