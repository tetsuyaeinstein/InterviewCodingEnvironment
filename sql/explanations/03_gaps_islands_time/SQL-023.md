# SQL-023 · Longest purchase streak per customer: explanation

## Approach

1. **Scope first.** Keep completed purchases with
   `transaction_ts >= '2025-01-01' AND transaction_ts < '2026-01-01'` (UTC, half-open, sargable).
   Filtering *before* building streaks is what clips a run that started in 2024. Filtering
   afterwards (`WHERE streak_end >= '2025-01-01'`) would report customer 9 as 5 days starting
   2024-12-29.
2. **Streaks.** Use distinct purchase days and the `date - ROW_NUMBER()` island key, grouped to
   `(start, end, length)`, exactly as in SQL-022.
3. **Pick one per customer, deterministically.** Use
   `ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY streak_days DESC, streak_start ASC)` and
   keep `rn = 1`. Two streaks of one customer can never share a start date, so this order is
   **total** and the choice is reproducible.
4. **Tie count.** `COUNT(*) OVER (PARTITION BY customer_id, streak_days)` counts the streaks of the
   same length. Computed before the `rn = 1` filter, it gives `tied_streaks` for the winning row.
5. Apply `longest_streak_days >= 2` **last**. Applying it to individual streaks before ranking
   gives the same rows here, but it is a different statement in general (for example if the rule
   were "longest streak ≥ N, report all customers").

## Why determinism matters

`ORDER BY streak_days DESC` alone leaves equal-length streaks in an **arbitrary** order. The result
can change between runs, parallel plans or engine versions, and the e-mail would then show
different dates on a re-send. Fixture customer 5 has two 5-day streaks (05-01..05-05 and
05-10..05-14). Customer 12 has two 2-day streaks around a CANCELLED-only day. Both must give the
earliest one with `tied_streaks = 2`.

Alternatives for the "pick one" step:

| technique | notes |
|---|---|
| `ROW_NUMBER()` + filter | portable; tie-break explicit |
| `DISTINCT ON (customer_id) ... ORDER BY customer_id, streak_days DESC, streak_start` | PostgreSQL-only, concise, same semantics |
| `RANK()` / `DENSE_RANK()` = 1 | returns **all** tied streaks (a different contract, useful when the spec says "return all ties") |
| `max(streak_days)` then join back | returns all ties and needs a second pass; easy to get duplicates |

## Edge cases (fixtures)

| fixture | expected |
|---|---|
| 5 | 5 days, 05-01..05-05, `tied_streaks` 2 |
| 12 | 2 days, 07-10..07-11, `tied_streaks` 2 |
| 9 | clipped: 2025-01-01..01-02, 2 days |
| 10 | absent (2024 only) |
| 6 | 4 days despite 7 transactions |
| 11 | 4 days (beats the 3-day streak), tie 1 |
| 19 | absent (purchases 7 days apart, longest = 1) |
| 14 | 2 days in UTC (11-02 and 11-03), although in New York both are 11-02. A good discussion point |

## Plan and indexes

There are two window passes over small inputs: one over customer-days and one over streaks, which
is a much smaller set. The year filter can use the `transactions(transaction_ts)` index. With
monthly partitions, only the 12 2025 partitions are scanned.

## Production considerations

- Store all streaks (SQL-022) as a maintained table. "Longest per customer" then becomes a cheap
  top-1-per-group query and the e-mail job does not rescan the fact.
- Document the clipping rule. Finance and marketing often disagree on whether a cross-year streak
  belongs to the year in which it started.
- Write a test that runs the query twice and compares, or better, check that the tie-break
  columns form a key of the ranked set.

## SQL Server / Azure Synapse notes

- There is no `DISTINCT ON`. Use `ROW_NUMBER()` or `TOP (1) WITH TIES` inside `CROSS APPLY`.
- `COUNT(*) OVER (PARTITION BY ...)` works the same. In Synapse, keep the partition key aligned
  with the distribution key (`customer_id`).
