# SQL-029 · Were all selected products available at checkout time? Explanation

## (a) Grid + boolean aggregates (`SQL-029.sql`)

1. `selected_products` as an inline `VALUES` list, so the set is defined once.
2. `txns`: COMPLETED store-2 transactions in `[2025-05-10, 2025-05-12)`.
3. `CROSS JOIN` transactions × products gives exactly one cell per (transaction, product).
4. `LEFT JOIN` the availability version that covers `transaction_ts`, half-open:
   `valid_from <= ts AND (valid_to IS NULL OR ts < valid_to)`.
5. `is_available = COALESCE(a.available, false)`. **No covering row means not stocked, which
   means false.**
6. Per transaction: `BOOL_AND` (ALL), `BOOL_OR` (ANY), `COUNT(*) FILTER (WHERE is_available)`.

Why the `COALESCE` matters: `BOOL_AND` and `BOOL_OR` **ignore NULLs**. Without it, the 21:00
basket (p6 uncovered) yields `BOOL_AND(true, true, NULL) = true`. Every aggregate-based "for all"
needs an explicit decision about missing data.

## (b) Relational division with `NOT EXISTS` (`SQL-029_alt.sql`)

"All selected products are available" ⇔ "there is **no** selected product for which **no**
available version covers the instant":

```
NOT EXISTS (SELECT 1 FROM selected_products sp
            WHERE NOT EXISTS (<available row covering ts for sp>))
```

ANY is a plain `EXISTS`. The "uncovered = unavailable" rule falls out naturally, because a
missing row simply does not satisfy the inner `EXISTS`. Division by double negation is the
textbook way to express "for all" in SQL. It also stays correct if the set of products is empty
(ALL is vacuously true and ANY false, which matches set semantics; decide whether the business
agrees). A third classic: `COUNT(DISTINCT available product) = (SELECT COUNT(*) FROM selected_products)`.

| | grid + BOOL_AND | NOT EXISTS division | count = count |
|---|---|---|---|
| ANY / count for free | yes | extra subqueries | count yes, ANY = count > 0 |
| missing-row trap | needs `COALESCE` | none | needs DISTINCT if versions could duplicate |
| plan | hash join + aggregate | semi/anti joins, can short-circuit | aggregate |

## Edge cases (fixtures, customer 65 at store 2)

| txn | ts | p4 | p5 | p6 | all | any | n |
|---|---|---|---|---|---|---|---|
| 6501 | 05-10 10:00 | ✓ | ✓ | ✗ `[09:00, 12:00)` | f | t | 2 |
| 6502 | 13:00:00 | ✗ starts at 13:00 | ✓ | ✓ | f | t | 2 |
| 109203 | 14:30:15 | ✗ | ✓ | ✓ | f | t | 2 |
| 6503 | 14:59:59 | ✗ | ✓ | ✓ | f | t | 2 |
| 6504 | 15:00:00 | ✓ back at 15:00 | ✓ | ✓ | **t** | t | 3 |
| 6505 | 21:00 | ✓ | ✓ | ✗ **no row** `[20:00, 08:00)` | f | t | 2 |
| 6506 | 05-11 09:00 | ✓ | ✓ | ✓ | t | t | 3 |

With an inclusive `valid_to`, the instant 13:00:00 matches both p4 rows and the count becomes 3.
At 15:00:00, both the `false` and `true` versions match. Treating "no row" as available marks
6505 as fully available.

## Plan and indexes

The primary key `(store_id, product_id, valid_from)` supports the lookup. The `EXCLUDE` GiST index
on `(store_id, product_id, tstzrange(valid_from, valid_to))` supports `@>` containment probes. The
grid is |transactions| × |products|, which is fine for small sets. For large product sets, the
`NOT EXISTS` form can stop at the first unavailable product.

## Production considerations

- An availability feed usually has **gaps by design** (product delisted, store not ranging it).
  Make "unknown" vs "unavailable" an explicit business rule, and monitor coverage.
- Late availability corrections change history. Snapshot the result if it drives compensation.
- Store-local time: shelf events are recorded locally. Confirm the feed's time zone.

## SQL Server / Azure Synapse notes

- There is no `BOOL_AND`/`BOOL_OR`: use `MIN(CASE WHEN ... THEN 1 ELSE 0 END)` for ALL and `MAX`
  for ANY, and cast to `bit`.
- `COUNT(*) FILTER (...)` becomes `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`.
- `VALUES` row constructors work in SQL Server (`(VALUES (4),(5),(6)) AS sp(product_id)`).
  `NOT EXISTS` division is fully portable.
