# SQL-060 · Dedup, unique key and idempotent load: explanation

## Approach

Three steps in this order, because each one depends on the previous:

1. **Remove existing duplicates** (`SQL-060.sql`):
   ```
   DELETE FROM txn_events WHERE ctid IN (
       SELECT ctid FROM (SELECT ctid, row_number() OVER (PARTITION BY message_id ORDER BY delivered_at, ctid) rn
                         FROM txn_events) d WHERE rn > 1);
   ```
   `ctid` is the physical row address `(page, tuple)`. It is the only thing that distinguishes two rows
   that are equal in every column. The window orders by `delivered_at` so the earliest delivery gets
   `rn = 1` and survives; `ctid` is the final tie-break.
2. **Add the constraint**: `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE (message_id)`. If duplicates were
   still present it fails with `could not create unique index ... Key (message_id)=(...) is duplicated`.
3. **Load** with `INSERT ... SELECT ... ORDER BY delivered_at ON CONFLICT (message_id) DO NOTHING`.

## Hand-checked result

Start: 10 rows, 8 distinct messages. Message `msg-fx-2301-c` was delivered at 10:00:05, 10:00:35 and 10:05:00.

| message_id | action | final `delivered_at` |
|---|---|---|
| msg-fx-2301-c | 3 rows → earliest kept; the batch redelivery at 10:30 is skipped | 10:00:05 |
| msg-fx-2302-c, 2302-s1, 2401-c, 2401-c2, 2501-c, 2601-c, 2601-c2 | single deliveries, untouched | unchanged |
| msg-fx-2701-c | new in the batch | 10:45 |
| msg-fx-2702-c | in the batch twice (11:05 listed first, 11:00 second); earliest wins | 11:00 |

Final: 10 rows, 10 distinct messages, a unique index on `message_id`.

## Why `ORDER BY delivered_at` in the INSERT

`ON CONFLICT DO NOTHING` handles rows one at a time in the order the SELECT produces them: the first
`msg-fx-2702-c` inserts, the second hits the unique index and is skipped. Without `ORDER BY` the
order is the physical order of `new_batch`, which lists the 11:05 row first, so the **later** delivery would win.
(`DISTINCT ON (message_id) ... ORDER BY message_id, delivered_at` in the alternative states the intent directly.)
`DO NOTHING` also covers a duplicate inside one statement. `DO UPDATE` would not: it raises
`ON CONFLICT DO UPDATE command cannot affect row a second time` (SQL-046).

## The constraint is the point

Deduplicating inside the loader (`WHERE NOT EXISTS`, a read-then-write check) is a race: two loaders can
both see "not there" and both insert. A **unique index** is the only mechanism that is correct under
concurrency; `ON CONFLICT` uses it to make the insert atomic. Without the constraint, `ON CONFLICT` has no
conflict target and `ON CONFLICT DO NOTHING` without target is accepted but never triggers, so it
silently inserts duplicates. That is why the assertions check the catalog (`pg_index`) for a
unique index on `message_id` in the sandbox schema.

Also note: the constraint guarantees one row per `message_id`, not per business event. In the fixtures,
transaction 2401 has two different `message_id`s (`msg-fx-2401-c`, `msg-fx-2401-c2`): a double-posting that a
key on `message_id` does not catch. That needs a business key rule (SQL-041 / SQL-046 territory) and
a conscious decision.

## Alternative (`SQL-060_alt.sql`): rebuild instead of delete

`CREATE TABLE ... AS SELECT DISTINCT ON (message_id) ... ORDER BY message_id, delivered_at`, drop the old
table, rename, `CREATE UNIQUE INDEX`, then load a batch that was `DISTINCT ON`-reduced as well.

| | delete in place | rebuild + swap |
|---|---|---|
| dead tuples / bloat | yes (needs VACUUM) | none |
| WAL | high (every deleted row) | one write of the surviving rows |
| locking | row locks, concurrent reads fine | exclusive lock at swap |
| extras | keeps grants, triggers, dependent objects | must recreate them |
| best when | few duplicates | many duplicates, or a rewrite is fine |

A third option is `DELETE FROM t a USING t b WHERE a.message_id = b.message_id AND a.ctid > b.ctid`,
which keeps the lowest `ctid` instead of the earliest `delivered_at` and is only right when physical order
equals delivery order. It is O(n²) without an index on `message_id`. `MERGE` can also drive the load, but it
does not give `ON CONFLICT`'s concurrency guarantee, and the source must already be de-duplicated.

## Complexity and production

- Step 1: one scan and one sort/hash by `message_id`, O(n log n); at 500M rows run it in
  `message_id` hash ranges, in batches of 10-100k, committing between them, to avoid a huge transaction
  and replication lag.
- Step 2: `ADD CONSTRAINT UNIQUE` builds a B-tree and takes a lock that blocks writes while it builds.
  Online alternative: `CREATE UNIQUE INDEX CONCURRENTLY ux ON t(message_id)`, then
  `ALTER TABLE t ADD CONSTRAINT c UNIQUE USING INDEX ux`. Needs no duplicates at the time the build
  finishes, so keep the loader on `ON CONFLICT` during the migration or deduplicate in a staging table first.
- Step 3: one index probe per row; batch size trades latency against speculative-insertion overhead.
  Count the skipped rows (`INSERT ... RETURNING` vs batch size) and export it as a metric: a rising
  duplicate rate says the broker or producer misbehaves.
- Idempotency: running the whole load twice changes nothing the second time (every message conflicts).
  The DDL in steps 1-2 is **not** re-runnable as written; production migrations guard with
  `IF NOT EXISTS` / catalog checks (`CREATE UNIQUE INDEX IF NOT EXISTS`).
- Keep the earliest, or the latest? Earliest preserves "first seen" for latency metrics; latest
  is right when later deliveries carry corrections. Decide per feed and document it.
- Quarantine instead of delete: move removed duplicates into an `txn_events_dupes` table
  (`DELETE ... RETURNING` into an `INSERT`) so the cleanup is auditable.

## SQL Server / Azure Synapse notes

- T-SQL: delete duplicates with `WITH d AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY message_id ORDER BY delivered_at) rn
  FROM txn_events) DELETE FROM d WHERE rn > 1;` (deleting through the CTE works in SQL Server; there is no `ctid`).
  `CREATE UNIQUE INDEX ... WITH (IGNORE_DUP_KEY = ON)` silently drops duplicate inserts, the closest relative of
  `ON CONFLICT DO NOTHING`. Otherwise use `MERGE ... WHEN NOT MATCHED` (with `HOLDLOCK`) or `INSERT ... WHERE NOT EXISTS`
  inside a serializable transaction.
- Synapse dedicated pools **do not enforce** `UNIQUE`/`PRIMARY KEY` (only `NOT ENFORCED` metadata). Deduplication is the loader's job:
  `ROW_NUMBER()` in the staging table, then `CTAS` with `rn = 1` and a partition switch. Delta Lake: `MERGE INTO ... WHEN NOT MATCHED INSERT`
  on a de-duplicated source (`dropDuplicates`).

## Follow-up questions

1. Two loaders run the same batch at the same time. What guarantees there is no duplicate, and what
   would go wrong with `INSERT ... WHERE NOT EXISTS`?
2. The business key is `(transaction_id, event_type)` and a double-posting arrives with a **different**
   `message_id`. Which constraint, and which copy should win?
3. At 500M rows, how do you add the constraint without blocking the loader for an hour, and
   what do you do if the concurrent index build fails and leaves an INVALID index?
4. Should duplicates be deleted or kept with a flag? Discuss audit, replays and storage.
