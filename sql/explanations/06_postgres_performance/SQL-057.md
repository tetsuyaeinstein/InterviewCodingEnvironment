# SQL-057 · Expanding JSON item arrays safely: explanation

## Approach

`jsonb_array_elements(x)` turns a JSON array into one row per element, but it raises
`cannot extract elements from an object` (or `from a scalar`) for anything else. So:

1. **Normalise the argument per row**, with a `CASE` on `jsonb_typeof(payload->'items')`:
   `array` → itself, `object` → `jsonb_build_array(items)` (a one-line basket), anything else
   (JSON null, missing, string, number) → `'[]'`.
2. **Expand in a `CROSS JOIN LATERAL`**, so the function is evaluated once per event.
   A missing/empty basket yields zero rows, so the event disappears (the inner-join semantics we
   want; use `LEFT JOIN LATERAL ... ON true` if events without lines must remain visible).
3. **Filter lines before aggregating**: element is an object, `sku` is not NULL (`->>` turns a JSON
   `null` into SQL NULL), and `pg_input_is_valid(qty_text, 'integer')`.
4. **Aggregate** `GROUP BY event_id, sku` with `sum(qty::int)`.

## Hand-checked result for 2025-08-15 checkouts

|---|---|---|

| 102 | `[]` | none |

| 110 | `{"qty":1,"sku":"SKU-00006"}` (an object) | (SKU-00006, 1) |

| 119085, 119096, 119121 | generated baskets (3, 4 and 2 distinct skus) | 3 + 4 + 2 rows |

15 rows in total. Events 106, 108 and 109 belong to customer 67 but are not checkouts.

## Why each trap matters

- **Unguarded expansion**: `jsonb_array_elements(payload->'items')` crashes the entire scan the
  moment it meets event 110 (an object). A JSON `null` is a different case: it is a scalar and
  errors too, while a *missing* key gives SQL NULL, which yields zero rows. Three behaviours for
  three flavours of "no array".
- **Fan-out**: if you join the expanded lines back to a one-row-per-event table and then sum,
  duplicated lines inflate numbers. Here the duplicate lines of event 105 are summed into one row.
- **The cast must come after the filter.** `(item->>'qty')::int` on `"two"` errors. In the
  reference the filter is in `WHERE` (with `pg_input_is_valid`), and the cast sits in an aggregate
  over only the surviving rows. When in doubt, wrap casts in `CASE WHEN valid THEN ... END`.
- **Silent drops are a decision.** The contract drops bad lines; production code should also count
  them (a `rejected_lines` metric per run) so a schema change is noticed.

## Alternative (`SQL-057_alt.sql`): SQL/JSON path

`jsonb_path_query(payload, 'lax $.items[*] ? (@.sku != null)')` returns each matching element.
In **lax** mode the path engine wraps a non-array in an array automatically, so the single-object
case works without any `CASE`, and a missing key yields no rows. The filter expression drops
null/missing skus inside the path. In **strict** mode the same path raises errors, so the mode is
part of the contract. Other ways to expand: `jsonb_to_recordset(items) AS x(sku text, qty text)`
(concise and typed, but it requires an array and fails on objects: guard it with the same `CASE`),
or `jsonb_array_elements` with `WITH ORDINALITY` when you also need the line number.

## Performance and production

- Unnesting multiplies rows: 500M events × ~3 lines = 1.5B rows. Do it in the ingestion layer
  once, store the result as a typed `event_items` table (`event_id, line_no, sku, qty`) and index
  it on `(sku)` or `(event_id)`.
- `payload` is jsonb (parsed, binary). Large payloads are TOASTed; expanding touches the TOAST
  table, so project only what you need and avoid `SELECT *`.
- A GIN index on `payload` (`jsonb_path_ops`) answers containment questions such as "events that
  contain sku X" (`payload @> '{"items":[{"sku":"SKU-00001"}]}'`) without unnesting.
- Keep `WHERE` predicates on the raw columns (`event_ts` range) so partition pruning and the
  `customer_events(customer_id, event_ts)` index can be used before any JSON work.

## SQL Server / Azure Synapse notes

- T-SQL: `OPENJSON(payload, '$.items') WITH (sku varchar(50) '$.sku', qty varchar(20) '$.qty')`
  with `CROSS APPLY`. When the path points to an object, `OPENJSON` iterates its **properties**
  (key/value rows), not a one-item array, so event 110 would not behave like an array: normalise
  with `ISJSON` and a check on the first character first. `TRY_CAST(qty AS int)` replaces
  `pg_input_is_valid`.
- Synapse/Spark: shred JSON at load (`explode(from_json(...))`). `from_json` with a schema returns
  NULL for malformed fields. `explode` drops null/empty arrays; `explode_outer` keeps them.
