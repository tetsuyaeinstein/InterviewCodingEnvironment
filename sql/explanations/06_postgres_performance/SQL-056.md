# SQL-056 · Typed attributes from messy JSON: explanation

## Approach

1. **Look at the JSON type first.** `jsonb_typeof(payload->'amount')` returns `number`, `string`,
   `boolean`, `null`, `object`, `array`, or SQL NULL when the key is missing. The two kinds of
   "nothing" (JSON `null` vs missing) are different values but, per the contract, both mean
   `MISSING`.
2. **Parse only what is safe.** A `CASE` expression evaluates a branch only when its condition is
   true, so `ELSE`/`THEN` casts are protected by the guard in `WHEN`.
   - JSON numbers: `(payload->>'amount')::numeric` is always safe.
   - Strings: `btrim()` then `pg_input_is_valid(txt, 'numeric')` (PostgreSQL 16+). True means the
     cast will succeed; false means NULL.
3. **Booleans by exact comparison**, never by cast.
4. **Flags with explicit NULL handling.** `amount < 0` is NULL when `amount` is NULL, so
   `(checkout AND amount IS NULL) OR COALESCE(amount < 0, false)` keeps the column two-valued.

## Traps this exercise sets

- **The naive cast.** `(payload->>'amount')::numeric` raises `invalid input syntax for type numeric: "N/A"`
  and the whole statement fails: one bad row kills a 500M-row job. `WHERE` clauses do not protect
  you either, because PostgreSQL may evaluate the cast before the filter. Only `CASE` (or a
  validity function) guarantees ordering.
- **`::boolean` is too generous.** PostgreSQL's boolean input accepts `yes`, `no`, `on`, `off`, `1`,
  `0`, `t`, `f` and unique prefixes, so `'yes'::boolean` is `true`. A contract that says "only true/false"
  has to be written out. `pg_input_is_valid('yes', 'boolean')` is also true: validity is not the same
  as business validity.
- **`pg_input_is_valid(..., 'numeric')` accepts `NaN` and `Infinity`**, and tolerates surrounding
  spaces (so the `btrim` is for clarity and for the regex alternative). The guard
  `!~* '^[+-]?(nan|inf)'` rejects the special values.
- **Scientific notation** (`1e3`) is valid numeric input; a naive `^[0-9.]+$` regex rejects it.
- **Three-valued logic**: `amount IS NULL OR amount < 0` can be NULL; the flag must be
  a clean boolean for downstream `WHERE has_amount_issue`.

## Alternative (`SQL-056_alt.sql`): regex guard

Where `pg_input_is_valid` is not available (PostgreSQL < 16, other engines) validate the text
with a regular expression, then cast inside a `CASE`:
`btrim(txt) ~ '^[+-]?([0-9]+(\.[0-9]*)?|\.[0-9]+)([eE][+-]?[0-9]+)?$'`. It works everywhere and
excludes NaN/Infinity by construction, but the regex has to track the real grammar (locale
separators, `_` digit separators in PG 16 input, huge exponents that overflow) and it costs CPU.
Also: `jsonb_path_query_first(payload, '$.amount.double()')` raises an error on bad input unless you
use the `silent` argument (`jsonb_path_query_first(payload, '$.amount.double()', '{}', true)`), which
turns errors into NULL. That is a third way, useful for number-or-numeric-string inputs.

## Performance and production

- Cost is one JSON parse per row: `payload->'amount'` on jsonb is a lookup in a binary structure,
  not a text parse. Repeating the extraction three times is cheap but not free; use a `LATERAL`
  or CTE to extract once.
- Don't repeat this logic in every query: put it in a view or, better, **materialise typed columns
  at ingestion** (generated columns, or a silver-layer table) and store the failure reason.
- Quarantine instead of silently NULLing: write `INVALID` rows with the raw value to a reject table
  and alert on the rate (a jump from 0.01% to 3% means a producer changed its contract).
- If the type of a key flips between releases, track a `schema_version` in the payload.
- For queries by `payload->>'device'`, index the expression (`(payload->>'device')`) or use a GIN
  index with `jsonb_path_ops` for containment (`payload @> '{"device":"ios"}'`).

## SQL Server / Azure Synapse notes

- T-SQL: `TRY_CAST(JSON_VALUE(payload, '$.amount') AS decimal(12,2))` returns NULL on failure,
  and `TRY_CONVERT` works too. `ISJSON`, `JSON_VALUE` (scalar), `JSON_QUERY` (object/array) and
  `OPENJSON ... WITH (...)` are the counterparts. `TRY_CAST('1e3' AS decimal)` fails (NULL) because
  decimal does not accept exponents; cast through `float` first, as a dialect difference.
- `JSON_VALUE` returns NULL for a missing key in lax mode, so "missing vs null vs invalid" cannot be
  told apart without `OPENJSON` or `JSON_PATH_EXISTS`.
- Synapse dedicated pool has limited JSON functions: shred JSON at load time (Spark
  `from_json` with a schema and `try_cast`, or `_corrupt_record` handling) rather than at query time.
- Spark SQL: `try_cast`, `get_json_object`, `from_json` with `mode => 'PERMISSIVE'`.
