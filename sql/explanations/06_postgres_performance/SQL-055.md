# SQL-055 · p50 / p95 ingestion delay: explanation

## Approach

1. **Fix the grain first.** `event_ingestion_log` is one row per *attempt*. Reduce it to one row per
   event: `DISTINCT ON (raw_event_id) ... WHERE ingestion_status = 'LOADED' ORDER BY raw_event_id, ingest_ts, log_id`
   keeps the first successful attempt. Failed (`RETRIED`, `REJECTED`) and `DUPLICATE` attempts never
   define the delay of the event.
2. **Delay in seconds**: `extract(epoch FROM ingest_ts - event_ts)` (double precision).
3. **Skew**: keep negative delays out of the percentile with `FILTER (WHERE delay_s >= 0)`, but count
   them in a separate column, so the exclusion is visible rather than silent.
4. **Percentile**: `percentile_cont(0.5) WITHIN GROUP (ORDER BY delay_s)`: sorts the group and
   interpolates linearly at position `p * (n - 1)` (0-based). Cast to `numeric` and `round(..., 2)`.

## Hand-checked fixture (source FIXTURE, all events at 12:00:00)

| event | rows in the log | counts as |
|---|---|---|
| evt-fx-001 … 020 | LOADED at +0, +30, … +570 s | 20 values 0 … 570 |
| evt-fx-021 | LOADED at **-45 s** | skew: excluded, counted |
| evt-fx-022 | RETRIED at +20, LOADED at **+620** | one value: 620 (not 20) |
| evt-fx-023 | REJECTED only | not in the statistics |
| evt-fx-024 | LOADED +15, DUPLICATE +75 | one value: 15 |
| evt-fx-025 | LOADED +2 days (172,800 s) | one value: 172800 |

Sorted (n = 23): 0, 15, 30, 60, 90, …, 570, 620, 172800.

- p50: position 0.5 × 22 = 11 (0-based) → 12th value = **300.00**.
- p95: position 0.95 × 22 = 20.9 → between the 21st value (570) and the 22nd (620): 570 + 0.9 × 50 = **615.00**.
- The 2-day outlier does not move either number. The mean would be about 7,788 s.

Common wrong answers and what they give: counting all attempts (retries and the duplicate create
extra observations); including the `-45 s` row (shifts p50 down to 285.00 and p95 to 612.50); using the
first attempt of the retried event (20 s instead of 620 s); `percentile_disc(0.95)` (570, a real
data point, not interpolated).

## `percentile_cont` vs `percentile_disc`

| | returns | for `0.95` here |
|---|---|---|
| `percentile_cont(p)` | interpolated value, may not exist in the data; input must be numeric/interval | 615.00 |
| `percentile_disc(p)` | the first actual value whose cumulative share >= p (nearest-rank); works on any sortable type | 570 |

Which one is right is a **contract** question: SLAs are usually written on observed values
(discrete: "95% of events arrive within X") while dashboards and SQL Server's `PERCENTILE_CONT`
are continuous. Say which one you used.

## Alternative (`SQL-055_alt.sql`)

The same continuous percentile by hand: number the sorted delays per source with `ROW_NUMBER()`,
count with `COUNT(*) OVER`, compute the fractional position `1 + p * (n - 1)`, and weight the two
neighbouring rows. It is longer, and it is what `percentile_cont` does internally. It is worth
knowing for engines without ordered-set aggregates (Spark SQL `percentile`/`approx_percentile`
exist, but T-SQL has `PERCENTILE_CONT` only as a window function) or when you need several
percentiles in one pass.

## Complexity and performance

- Ordered-set aggregates **sort each group fully** and cannot be computed incrementally or in
  parallel partials: O(n log n) with memory for the group (spills if it exceeds `work_mem`).
  PostgreSQL has no `approx_percentile` built in.
- Run the pre-reduction (`DISTINCT ON`) over an index on `(raw_event_id, ingest_ts)` or sort once;
  `ix_event_ingestion_raw_id` exists on `raw_event_id`.
- Cheaper than sorting everything at scale: pre-bucket delays into a histogram per source and hour
  and derive percentiles from the histogram (error bounded by bucket width).

## Production considerations

- Late data: a December window defined by `event_ts` changes as late events arrive; freeze the SLA
  report at a cut-off and state it (see SQL-043).
- Report the **exclusion counts** (skew, never-loaded, rejected) next to the percentiles. A clean
  p95 over a shrinking population is a classic way to fake an SLA.
- Clock skew is a data-quality signal in itself: alert when negative delays exceed a threshold per
  source; consider clamping to 0 only if the contract says so, and say that the result is then
  slightly optimistic.
- Don't average percentiles across sources or hours; recompute from raw values or histograms.

## SQL Server / Azure Synapse notes

- T-SQL has `PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY delay) OVER (PARTITION BY source)`,
  **only as a window function**, so use `SELECT DISTINCT` or `TOP 1 WITH TIES` to collapse rows.
  There is no `FILTER` clause: use `CASE WHEN delay >= 0 THEN delay END` (NULLs are ignored).
- `DATEDIFF(second, event_ts, ingest_ts)` counts boundaries crossed, with whole-second
  granularity; use `DATEDIFF_BIG` or fractional arithmetic when sub-second accuracy matters.
- Synapse dedicated pool: `PERCENTILE_CONT` / `PERCENTILE_DISC` exist as window functions, but there
  is no approximate percentile. For exact percentiles at scale pre-aggregate per source in a CTAS first.

## Follow-up questions

1. The SLA is "95% within 15 minutes". Compute the **percentage** of events within 900 s per source
   with one conditional aggregate, and compare with the p95 approach.
2. How do p95 values per source combine into an overall p95? (They don't: why, and what do you
   store instead?)
3. At 500M events per month, the exact percentile sort is too slow. Design a histogram / t-digest
   based daily rollup and say what error it introduces.
4. Retries create several `LOADED` rows for one event in a different feed. Which attempt defines
   delay now, and how do you make the definition explicit in the data model?
