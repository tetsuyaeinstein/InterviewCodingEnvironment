# SQL-051 · Reading EXPLAIN (ANALYZE, BUFFERS): explanation

## The query

The SQL is deliberately simple: three predicates on raw columns, a half-open UTC month, and an
`ORDER BY transaction_ts, transaction_id`. The id is a **unique tie-breaker**: without it two
transactions at the same instant could come back in either order, and any "next page" logic built
on the statement would skip or repeat rows.

Write the month as `transaction_ts >= '2024-12-01 00:00+00' AND transaction_ts < '2025-01-01 00:00+00'`.
Customer 1001 has three completed purchases on 2024-12-31, so `<= '2024-12-31'` (which means
`<= 2024-12-31 00:00:00`) silently drops them; the half-open bound on the next month's first
instant is always right, including across the year boundary.
`date_trunc('month', transaction_ts) = ...` or `transaction_ts::date BETWEEN ...` give the same
rows but hide the column from the index (SQL-052).

## Reading the plan (small seed)

```
Incremental Sort  (cost=4.80..72.97 rows=16) (actual rows=24 loops=1)
  Sort Key: transaction_ts, transaction_id
  Presorted Key: transaction_ts
  Full-sort Groups: 1  Sort Method: quicksort  Memory: 26kB
  ->  Index Scan using ix_transactions_ts on transactions  (cost=0.29..72.25 rows=16) (actual rows=24 loops=1)
        Index Cond: ((transaction_ts >= ...) AND (transaction_ts < ...))
        Filter: ((customer_id = 1001) AND (transaction_status = 'COMPLETED'))
        Rows Removed by Filter: 676
        Buffers: shared hit=21
```

| what you see | what it means |
|---|---|
| `Index Scan using ix_transactions_ts` | the planner walks the time index over December and fetches every heap row in that range |
| `Index Cond` = time range only | the index narrows by time; the customer and status are checked afterwards |
| `Rows Removed by Filter: 676` | 700 rows fetched, 24 kept: about 3.4% useful work |
| `rows=16` vs `actual rows=24` | a reasonable estimate: MCV frequency of 1001 × December fraction × COMPLETED fraction |
| `Incremental Sort`, `Presorted Key: transaction_ts` | the index already delivers time order; only ties need a sort by id |
| `Buffers: shared hit=21` | 21 pages, all from PostgreSQL's cache; `read=` would count pages requested from the OS |

Why not `ix_transactions_customer`? It narrows to about 530 rows (customer 1001's entire
history, all statuses) scattered over the heap, and then needs a sort. The time index reads more
rows, but they are physically adjacent, because the table was loaded in time order (correlation
≈ 1 in `pg_stats`), and it provides the order. On another month, or after the table has been
rewritten, the planner may switch to a `Bitmap Heap Scan` on the customer index. Both plans do
wasted work for the same reason: **no single index matches both the equality and the range.**

## Estimates in more detail

- `customer_id = 1001` uses the most-common-values list (1001 is the top MCV at about 2.5%).
- The time range uses the histogram of `transaction_ts`.
- `transaction_status = 'COMPLETED'` uses its MCV.
- PostgreSQL multiplies these selectivities as if independent. When predicates are correlated
  (e.g. a customer that only buys in December), the product is wrong. Extended statistics
  (`CREATE STATISTICS s (dependencies, mcv) ON customer_id, transaction_status FROM transactions`)
  fix equality combinations; nothing fixes range × equality correlation except a better index.
- A 10× misestimate on a leaf node is where bad join orders come from. Check leaves first.

## The index to propose

`CREATE INDEX CONCURRENTLY ix_txn_customer_ts ON transactions (customer_id, transaction_ts, transaction_id);`

- Equality column first, so all of customer 1001's rows are adjacent in the index.
- Then the range column: December is one contiguous slice of that block, returned in time order.
- Then the tie-breaker: no sort node at all, and `LIMIT n` stops after n index entries.
- Status stays a cheap filter (about 1 in 7 rows of a customer). Alternatives:
  `WHERE transaction_status = 'COMPLETED'` as a partial index, or `INCLUDE (store_id, gross_amount)`
  for an index-only scan. Both trade size and write cost for read speed.
- `ix_transactions_customer` becomes redundant: the new index serves every query on
  `customer_id =` alone. Drop it after checking `pg_stat_user_indexes` for other users.

SQL-053 lets you build these candidates in a sandbox and compare plans.

## Production considerations

- `EXPLAIN ANALYZE` **executes** the statement. For `UPDATE`/`DELETE`, wrap it in
  `BEGIN; ... ROLLBACK;`. For long queries, start with plain `EXPLAIN`.
- Capture plans from production with `auto_explain` (`log_min_duration`, `log_analyze`,
  `log_buffers`). Find the expensive statements with `pg_stat_statements`, sorted by total time,
  not mean time.
- "Sometimes slow" usually means cold cache (`read=` instead of `hit=`), a plan flip after
  `ANALYZE`, or a generic plan for a prepared statement (`plan_cache_mode`). Compare the slow plan
  with the fast one; don't tune the fast one.
- Index builds on a hot 500M-row table: `CREATE INDEX CONCURRENTLY` (no write lock, but two table
  scans; check for an `INVALID` index if it fails), and enough `maintenance_work_mem`.

## SQL Server / Azure Synapse notes

- SQL Server: `SET STATISTICS IO, TIME ON` plus the actual execution plan is the counterpart of
  `ANALYZE, BUFFERS` (logical reads ≈ shared hits + reads). A "Key Lookup" is the heap fetch you
  see here. The fix is the same composite index, usually with `INCLUDE` columns to make it
  covering.
- Synapse dedicated pools have no B-tree secondary index on a clustered columnstore by default.
  Performance comes from distribution, partition elimination, rowgroup elimination (segment
  min/max on `transaction_ts`) and result-set caching. `EXPLAIN` shows the distributed (DSQL)
  plan: look for `ShuffleMove`/`BroadcastMove` rather than index choices.

## Follow-up questions

1. The statement page shows 20 rows at a time. Rewrite it with keyset pagination
   (`(transaction_ts, transaction_id) > (:last_ts, :last_id)`) and explain why `OFFSET 2000` gets
   slower page by page.
2. The estimate is `rows=16`, but for another customer it is `rows=1` while the actual is 4,000.
   What happens to a nested-loop join above it, and how do you fix the estimate?
3. At 500M rows the table is range-partitioned by month. Which index do you build: one per
   partition, or a global one? How does partition pruning change the plan?
4. The table receives 3,000 inserts per second. How do you justify one more index, and which
   existing index would you drop?
