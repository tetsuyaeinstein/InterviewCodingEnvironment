# SQL-058 · Sale-less days with a generated calendar: explanation

## Approach

Gaps in dates cannot be found from the fact table, because absent days have no rows. Generate the
universe, then subtract what exists (an **anti-join**).

1. **Calendar**: `generate_series(0, DATE '2025-03-31' - DATE '2025-01-01')` yields 0 ... 89, and
   `DATE '2025-01-01' + g` turns each into a date. `date - date` is an integer in PostgreSQL, so the
   end date is derived, not typed twice. Both ends are inclusive: 90 days.
2. **Days with a sale**: `SELECT DISTINCT (transaction_ts AT TIME ZONE 'UTC')::date` for store 4,
   COMPLETED only, restricted with a half-open range on the raw timestamp so the time index can be
   used (SQL-052).
3. **Anti-join**: `calendar LEFT JOIN sale_days ... WHERE sale_days.sale_date IS NULL` (or
   `NOT EXISTS`).
4. `EXTRACT(isodow FROM date)` gives 1 = Monday ... 7 = Sunday, independent of the language
   setting (unlike `to_char(d, 'Day')`, which depends on `lc_time`).

## Expected result (hand-checkable)

Store 4 completed days in Q1: Jan 5, 12, 20; Feb 3, 14; Mar 1, 2, 3, 15 = 9 days. 90 - 9 = **81**
sale-less days. Notable cases:

| date | transactions | sale-less? |
|---|---|---|
| 2025-01-01 | none | yes (first day of the calendar) |
| 2025-02-14 | COMPLETED + PENDING | no |
| 2025-03-15 | COMPLETED + CANCELLED | no |
| 2025-03-16 | DECLINED only | **yes** |
| 2025-03-31 | none | yes (last day: an off-by-one `< '2025-03-31'` loses it) |

## Pitfalls

- `generate_series(date, date, interval)` returns **timestamptz**; `::date` of it depends on the session
  time zone (in a zone with DST at midnight you can get duplicates or gaps). An integer series plus
  `date + integer` has no time zone involved.
- Filtering the status in the `WHERE` of an outer query after a `LEFT JOIN` turns it into an inner
  join and loses exactly the days you are looking for. The status filter belongs in the right-hand
  side (`sale_days`) or in the `NOT EXISTS`.
- Duplicate rows: without `DISTINCT` (or `NOT EXISTS`), a LEFT JOIN from calendar to transactions
  repeats a date once per transaction; the `IS NULL` filter happens to hide that, but a
  `count(*)` over the join does not.
- Local vs UTC dates: store 4 is Phoenix (UTC-7, no DST); a sale at 02:00 UTC belongs to the previous local
  day. The question fixes UTC. In production, say which.

## Alternative (`SQL-058_alt.sql`)

A **recursive CTE** generates the calendar (`UNION ALL` with `sale_date + 1` until the end date)
and `NOT EXISTS` replaces the join. It is longer and slower for big ranges (row-by-row recursion,
default limit none in PostgreSQL but 100 levels in SQL Server: `OPTION (MAXRECURSION 0)`), but works
in engines without `generate_series`. The `NOT EXISTS` predicate uses the timestamp bounds of the day
(`>= day start AND < next day start`), so `ix_transactions_store_ts (store_id, transaction_ts)` can serve
each probe. A permanent `dim_date` table is the best option when many reports need a calendar.

## Performance and production

- 90 calendar rows against a few thousand store-4 rows: trivial. For a multi-store, multi-year report
  cross join the calendar with the store list (`stores x calendar`) and anti-join per store; the
  result can reach millions of rows, so filter by store opening/closing dates (`opened_on`, `closed_on`).
- Persist a `dim_date` with fiscal periods, holidays and weekday names; join to it instead of
  regenerating.
- Alerting on missing days is a data-quality check, but note that "no sale" can
  also mean "no data": compare with the pipeline run history before raising an incident.

## SQL Server / Azure Synapse notes

- SQL Server 2022 has `GENERATE_SERIES(0, 89)`; earlier versions use a numbers/tally table or a
  recursive CTE with `OPTION (MAXRECURSION 0)` (default limit 100). `DATEADD(day, n, '2025-01-01')`
  replaces `date + n`, and `DATEPART(iso_week...)`/`DATEPART(weekday, d)` depend on
  `SET DATEFIRST`: use `((DATEPART(weekday, d) + @@DATEFIRST - 2) % 7) + 1` for ISO weekdays.
- Synapse dedicated pool has neither `GENERATE_SERIES` nor reliable recursive CTEs: keep a
  `dim_date` table (replicated distribution) and join to it.
- Spark SQL: `sequence(date '2025-01-01', date '2025-03-31', interval 1 day)` + `explode`.
