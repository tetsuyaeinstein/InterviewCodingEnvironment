# SQL-054 · Key skew before choosing a distribution key: explanation

## Approach

1. Aggregate per `store_id` and per `customer_id`. `GROUP BY customer_id` keeps NULL as one group
   (the guest bucket); label it so a NULL key never disappears from reports.
2. Stack both aggregates with `UNION ALL` and a `key_type` label.
3. `row_number() OVER (PARTITION BY key_type ORDER BY txn_count DESC, sort_key)` gives unique ranks
   with a deterministic tie-break. Ties are real here: stores 7 and 38 both have 767 rows, and
   many ordinary customers have exactly 70, 71 or 72.
4. Filter to rank <= 5 and divide by the total count (the same denominator for both kinds).

Result on the small seed:

| key_type | key_value | rank | txn_count | pct |
|---|---|---:|---:|---:|
| customer | 1001 | 1 | 529 | 2.49 |
| customer | (null) | 2 | 302 | 1.42 |
| customer | 1266 | 3 | 72 | 0.34 |
| customer | 1390 | 4 | 72 | 0.34 |
| customer | 2339 | 5 | 72 | 0.34 |
| store | 6 | 1 | 3487 | 16.40 |
| store | 1 | 2 | 1276 | 6.00 |
| store | 7 | 3 | 767 | 3.61 |
| store | 38 | 4 | 767 | 3.61 |
| store | 33 | 5 | 756 | 3.56 |

Why `row_number` rather than `rank`/`dense_rank`: the question wants a top 5 with exactly five rows.
`rank()` would give rows 3, 3 for a tie and could return more than five. Always state the tie policy.

## Reading skew

Even distribution over 60 distributions is 1.67% each. Store 6 is 16.4%: roughly ten fair shares
on one node. The slowest of 60 workers decides the elapsed time of the query, so a 10x hot
distribution makes the whole query up to 10x slower than ideal, whatever the DWU level. The
same story applies to a Spark shuffle: one task reads 16% of the data while the others finish
early, then it spills or fails with OOM.

`customer_id` is far better (top key 2.5%, the rest below 0.4%), but still has two special
cases: the heavy enterprise account (1001) and the NULL bucket. Hashing NULL puts all guest
rows on one distribution; and since NULL never matches in an equi-join, those rows are shuffled
for no result.

## Design options (the content of a strong RATIONALE)

| option | helps | costs |
|---|---|---|
| distribute the fact on a high-cardinality surrogate (`transaction_id`) | even storage and scans | joins on customer/store need data movement; mitigated by replicating small dimensions |
| `customer_id` with NULLs handled separately | co-located customer joins and aggregates | hot customer 1001 remains (salt it); NULL path needs its own logic |
| salting hot keys | spreads one key over N workers | two-stage aggregation; dimension side must be expanded for hot keys |
| replicate/broadcast `stores` (40 rows), `products` (200) | no shuffle for dimension joins, so the fact key can be chosen for evenness | refresh cost, memory per node, Spark broadcast threshold |
| pre-aggregate before shuffle | cuts the volume that moves | only for decomposable aggregates (sum/count; not exact median) |
| isolate the flagship store | predictable capacity | two tables to maintain, union views |

The key must be evenly distributed **and** match the dominant join/group key. If 90% of queries
group by customer, a customer-based key avoids a shuffle each time and the skew mitigation is
worth it. If they are dashboards by date and store, an even key and cached aggregates win.

## Alternative implementation (`SQL-054_alt.sql`)

`GROUP BY GROUPING SETS ((store_id), (customer_id))` computes both aggregates in one scan.
Pitfall: in the output, `customer_id` is NULL both for the guest bucket and for the rows of the
store grouping. Use `GROUPING(customer_id)` (1 = column not grouped) to tell them apart. The
classic bug is a `WHERE customer_id IS NOT NULL` or `COALESCE` that mixes them up, so the guest
bucket vanishes or is double counted. Note the totals: each grouping set sums to all rows.

## Production considerations

- Measure skew where it hurts: rows per distribution (`DBCC PDW_SHOWSPACEUSED` /
  `sys.dm_pdw_nodes_db_partition_stats` in Synapse), Spark task-duration quantiles and shuffle read
  sizes, `approx_count_distinct`/Count-Min sketches on huge tables rather than exact counts.
- Skew changes over time (a campaign, a new flagship). Re-check after major launches.
- In PostgreSQL itself the same numbers feed `pg_stats` (`most_common_vals/freqs`), which is how
  the planner knows that `customer_id = 1001` is a lot of rows and `= 1500` is not (SQL-051).
- Adaptive Query Execution in Spark 3 splits skewed shuffle partitions; it handles the symptom for
  joins but not for skewed `GROUP BY` or a NULL partition.

## SQL Server / Azure Synapse notes

- Synapse dedicated pool: `CREATE TABLE ... WITH (DISTRIBUTION = HASH(col))`; 60 distributions
  regardless of DWU. Rows with the same hash value go to the same distribution, NULL included.
  `ROUND_ROBIN` for staging, `REPLICATE` for small dimensions (under about 2 GB).
- Choose a column that is not used in a `WHERE` filter (a filtered hash column would
  send the query to one distribution), has many distinct values, and has no dominant value.
  Updating a distribution column is not allowed.
- Row counts per distribution: `DBCC PDW_SHOWSPACEUSED('dbo.fact_sales')`.

1. The `store_id` distribution is already in production. How do you migrate to a new key with no
   downtime (CTAS into the new distribution, rename swap, backfill the delta)?
2. How would you salt `customer_id = 1001` only for a customer-level aggregation, and what is the

3. At 500M rows, you cannot count exactly each night. How do you estimate heavy hitters
   (Count-Min sketch, `approx_top_k`, sampling) and alert on skew drift?
4. A join between the fact and `dim_customer_scd2` is on `customer_id` and the NULL guests make up
   2% of rows. What is the cost of the NULL partition in each engine, and how do you avoid it?
