# SQL-059 · Partition pruning on a monthly range-partitioned fact: explanation

## Approach

`fact_sales_partitioned` is `PARTITION BY RANGE (sale_date)` with one partition per month. Filter
on the bare key with constant bounds:

```
WHERE sale_date >= DATE '2025-12-01' AND sale_date < DATE '2026-01-01'
```

At plan time PostgreSQL compares `[2025-12-01, 2026-01-01)` with each partition's bounds and keeps only
`fact_sales_p2025_12`. The 23 earlier monthly partitions **and** the default partition (which could hold
any out-of-range date, so it is kept unless the bounds exclude it; here they do) are left out of the plan.

Plans on the small seed:

```
-- pruned (reference)
HashAggregate
  ->  Seq Scan on fact_sales_p2025_12 fact_sales_partitioned  (rows=3969)    Buffers: shared hit=38
-- to_char(sale_date, 'YYYY-MM') = '2025-12'
GroupAggregate
  ->  Sort
        ->  Append
              ->  Seq Scan on fact_sales_p2024_01 ... Filter: (to_char(sale_date, 'YYYY-MM') = '2025-12')
              ... (24 more partitions, including the default)
```

The unpruned plan reads all 41,987 lines in 25 relations (about 400+ pages here, hundreds of
millions of lines in production) to return 3,969.

## Plan-time vs run-time pruning

| predicate | when pruned | `EXPLAIN` shows |
|---|---|---|
| constants / immutable expressions (`DATE '2025-12-01'`, `make_date(2025,12,1)`) | planning | only the surviving partitions |
| stable expressions (`CURRENT_DATE - 30`, `now()`) | executor start-up | all partitions listed, `Subplans Removed: N` |
| bind parameter in a generic plan (`$1`) | executor start-up | same |
| join key from an outer relation (nested loop) | executor, per outer row | subplans marked `(never executed)` |
| function of the key (`to_char`, `date_trunc`, cast to text) | **never** | everything scanned |

A prepared statement uses a **custom** plan (constants substituted, plan-time pruning) for its first
five executions and may then switch to a **generic** plan, which relies on executor pruning.
`SET plan_cache_mode = force_custom_plan | force_generic_plan` lets you see both. Pruning
is controlled by `enable_partition_pruning` (on by default). The grader's plan check relies on plan-time
pruning because the query has literal bounds.

## Why `to_char(...)` blocks pruning

The partition bounds are statements about `sale_date`. The planner can prove "no row of
`[2024-01-01, 2024-02-01)` satisfies `sale_date >= 2025-12-01`" by comparing constants. It cannot
prove anything about `to_char(sale_date, 'YYYY-MM') = '2025-12'` because it does not know how
`to_char` relates to the order of dates. (The same rule makes `transaction_ts::date = ...` non-sargable
for an index in SQL-052; partition bounds behave like an index over partitions.)

Equivalent rewrites that **do** prune: `BETWEEN DATE '2025-12-01' AND DATE '2025-12-31'` (only because
`sale_date` is a `date`; for timestamps use half-open ranges), and `sale_date >= make_date(2025,12,1)`.
Rewrites that don't: `date_trunc('month', sale_date) = DATE '2025-12-01'`,
`EXTRACT(YEAR FROM sale_date) = 2025 AND EXTRACT(MONTH FROM sale_date) = 12`,
`sale_date::text LIKE '2025-12%'`.

## Alternative (`SQL-059_alt.sql`)

Bounds built with `make_date(...)` and `BETWEEN`: still plan-time pruning because `make_date` is
IMMUTABLE with constant arguments, so the planner evaluates it during planning. Equally valid, but
`BETWEEN` on a `timestamp` column would be a bug (it includes the first instant of the next month).

## Production considerations

- Check pruning in CI: assert on `EXPLAIN (FORMAT JSON)` (count of scanned relations), or use the
  `pg_stat_user_tables` scan counts per partition after a test run. Do not rely on timing.
- ORMs and BI tools often send `WHERE sale_date >= $1 AND sale_date < $2`: that prunes at executor
  start-up. Watch for tools that wrap the column (`DATE(sale_date)`, `TO_CHAR(...)`) or cast the parameter
  the wrong way round (`sale_date::timestamp >= $1`).
- Make the partition key the column that the **time-range** filters actually use; if
  most reports filter on `transaction_ts` while the table is partitioned by `sale_date`, pruning will
  not help them.
- Partition-wise aggregation (`enable_partitionwise_aggregate`) and joins (`enable_partitionwise_join`)
  help for multi-month queries; they are off by default because of planning cost.
- Indexes: create them on the parent; they are created per partition. The primary key must contain
  the partition key.
- Retention: `ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY`, then drop or archive.

## SQL Server / Azure Synapse notes

- SQL Server: partitioned tables use a **partition function** and scheme; elimination happens when
  the predicate is on the partitioning column and sargable (`WHERE sale_date >= '20251201' AND sale_date < '20260101'`).
  Check the actual plan for `Actual Partition Count`. Wrapping the column in `YEAR()`/`FORMAT()` blocks
  elimination, exactly like here. Partition switching (`ALTER TABLE ... SWITCH PARTITION`) is the
  analogue of attach/detach.
- Synapse dedicated pool: partitioning is on top of 60 distributions, so each partition has about 1/60 of
  its rows per distribution. Rule of thumb: with columnstore, at least 1M rows per distribution per
  partition, otherwise rowgroups are too small and partitioning hurts. Partition elimination works on
  sargable predicates against the partition column.
- Spark/Delta: partition pruning on the directory layout works for equality/range on the partition
  column; use generated columns (`event_date GENERATED ALWAYS AS (CAST(ts AS DATE))`) so predicates on `ts`
  still prune.
