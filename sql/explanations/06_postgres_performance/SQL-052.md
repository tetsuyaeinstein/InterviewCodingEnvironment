# SQL-052 · Sargable one-day filter: explanation

## Approach

The original filter applies a function to the indexed column:

| original | rewrite |
|---|---|
| `transaction_ts::date = DATE '2025-02-28'` | `transaction_ts >= TIMESTAMPTZ '2025-02-28 00:00:00+00' AND transaction_ts < TIMESTAMPTZ '2025-03-01 00:00:00+00'` |

A B-tree on `transaction_ts` is sorted by the raw value. The planner can turn
`column >= a AND column < b` into "descend to `a`, walk the leaf pages until `b`". It cannot do
that for `column::date = d`: the index is not sorted by that expression, so every row is read and
converted. The rewritten predicate is **sargable** (Search ARGument ABLE).

Plans on the small seed:

```
-- original
GroupAggregate
  ->  Sort
        ->  Seq Scan on transactions   (rows=96 estimated)
              Filter: ((transaction_status = 'COMPLETED') AND ((transaction_ts)::date = '2025-02-28'))
-- rewrite
HashAggregate
  ->  Index Scan using ix_transactions_ts on transactions   (rows=25 estimated, 25 actual)
        Index Cond: ((transaction_ts >= '2025-02-28 00:00:00+00') AND (transaction_ts < '2025-03-01 00:00:00+00'))
        Filter: (transaction_status = 'COMPLETED')
```

Notice the estimate as well. For the cast expression PostgreSQL has no statistics, so it guesses
(rows=96). For the bare column it uses the histogram (25, exactly right). Sargable predicates
give the planner better estimates, and better estimates give better join plans further up.

## Why the boundaries matter (fixture customer 53, store 1)

| txn | transaction_ts | in the day? | breaks which wrong version |
|---|---|---|---|
| 5301 | 2025-02-28 23:59:59 | yes | `<= '2025-02-28 23:59:00'`, or `BETWEEN ... '23:59:58'` style bounds |
| 5302 | 2025-03-01 00:00:00 | **no** | `<= '2025-03-01'` and `BETWEEN '2025-02-28' AND '2025-03-01'` include it |

Half-open intervals `[start, next_start)` need no "last instant" (23:59:59.999999?), compose
without gaps or overlaps (day after day, month after month), and work identically for `date`,
`timestamp` and `timestamptz`.

## Time zones

- `transaction_ts::date` converts using the session `TimeZone`. The original report was correct
  only because the session ran in UTC. Run it from a client set to `America/New_York` and it
  silently reports a different day.
- An untyped literal compared with a timestamptz column (`transaction_ts >= '2025-02-28'`) is also
  read in the session time zone. The reference solution writes `+00` explicitly.
- For a store-local day, compute the bounds instead of converting the column:
  `transaction_ts >= (DATE '2025-02-28')::timestamp AT TIME ZONE s.timezone` and
  `< (DATE '2025-03-01')::timestamp AT TIME ZONE s.timezone`. Still sargable, and correct across
  DST changes.

## Alternatives

- **Range containment** (`SQL-052_alt.sql`):
  `transaction_ts <@ tstzrange(start, next_start, '[)')`. Since PostgreSQL 14 a planner support
  function rewrites `elem <@ range` into the two B-tree comparisons, so the plan is identical.
  It reads well and makes the half-open intent explicit, but on older versions it is **not**
  indexable. Check the plan, don't assume.
- **Expression index**: `CREATE INDEX ON transactions (((transaction_ts AT TIME ZONE 'UTC')::date))`.
  The expression must be IMMUTABLE. `transaction_ts::date` on timestamptz depends on `TimeZone`,
  so PostgreSQL refuses to index it; the explicit `AT TIME ZONE 'UTC'` form is accepted. It helps
  only queries that use exactly that expression, and every insert pays for one more index. Rewrite
  the query first; add expression indexes for predicates you cannot change (an ORM, a BI tool).
- **Generated column** `business_date date GENERATED ALWAYS AS ((transaction_ts AT TIME ZONE 'UTC')::date) STORED`
  plus a normal index. Explicit, gives statistics, and is a good fit for the partition key of a
  fact table.

## Production considerations

- Audit for non-sargable patterns with `pg_stat_statements` + `auto_explain`: Seq Scans on big
  tables with a highly selective `Filter`.
- Typical offenders besides date casts: `lower(col) = ...` (fix with an index on `lower(col)`, or
  citext), `col::text = '42'`, joins on mismatched types (`int` vs `bigint` is fine, `text` vs `int`
  is not), `COALESCE(col, '') = ''`, `col + 0 = ...`, and leading-wildcard `LIKE '%x'` (needs
  `pg_trgm`).
- ORMs often generate `DATE(created_at) = ?`. Catch it in code review, or with a lint rule on the
  query log.

## SQL Server / Synapse notes

- SQL Server: `CAST(ts AS date) = @d` is a special case that **is** sargable (the optimizer adds
  a dynamic range seek), but `CONVERT(varchar, ts, 112) = '20250228'`, `DATEADD(...)` on the
  column, and `YEAR(ts) = 2025` are not. Teach the half-open pattern anyway: it is portable.
- `datetime` rounds to 3.33 ms, so `<= '23:59:59.999'` rounds up to the next day. That is another
  reason to use half-open ranges.
- Synapse/Spark/Databricks: the same predicate shape enables partition elimination and file or
  rowgroup skipping from min/max statistics. Wrapping the column in a function disables both.
