# SQL-053 · Composite index column order: explanation

## Approach

1. In the sandbox, `txn_copy` has no index. Without one the plan is `Seq Scan` over all 256 pages,
   then `Sort Method: top-N heapsort`, then `Limit`.
2. Create `CREATE INDEX ON txn_copy (customer_id, transaction_ts)`.
3. Query with `customer_id = 1001`, the half-open quarter range and `ORDER BY transaction_ts LIMIT 20`.

A composite B-tree is sorted by its first column, then by the second within equal first values.
Think of it as a phone book sorted by (last name, first name):

| index | what the search sees for `customer_id = 1001 AND ts in [a, b) ORDER BY ts LIMIT 20` |
|---|---|
| `(customer_id, transaction_ts)` | one contiguous slice: "customer 1001, from a". Already in ts order. Stop after 20 entries. |
| `(transaction_ts, customer_id)` | one contiguous slice of **all customers** from a to b, in ts order. 1001's entries are scattered through it; the scan filters them inside the index and continues until 20 are found. |
| `(customer_id)` | all 529 entries of customer 1001; fetch the heap rows of all history, filter the range, **then** sort, **then** limit. |
| none | read the whole table, sort. |

Plans on the small seed (customer 1001 is dense, so the wrong order looks fine here):

```
-- (customer_id, transaction_ts)
Limit (actual rows=20)
  -> Index Scan using ix_..  Index Cond: ((customer_id = 1001) AND (transaction_ts >= ..) AND (transaction_ts < ..))   Buffers: shared hit=13
-- (transaction_ts, customer_id)
Limit (actual rows=20)
  -> Index Scan using i1     Index Cond: ((transaction_ts >= ..) AND (transaction_ts < ..) AND (customer_id = 1001))   Buffers: shared hit=17
-- (customer_id)
Limit -> Sort (top-N heapsort) -> Bitmap Heap Scan (Heap Blocks: exact=182, Rows Removed by Filter: 479) -> Bitmap Index Scan (rows=529)
-- no index
Limit -> Sort -> Seq Scan (Rows Removed by Filter: 21207)   Buffers: shared hit=256
```

The grader's required facts are chosen so the wrong index is rejected even where the small seed
makes it cheap: `Index Cond` must begin with the `customer_id` equality.

## Why the order is a rule, not a taste

- Columns tested with `=` can go in any order among themselves, and go **first**.
- The column used by the range predicate **and** the ORDER BY goes next. After the equality
  columns, the entries are in its order.
- Columns after the range column can only act as filters on index entries (or as `INCLUDE`
  payload). They do not narrow the search range.
- A leading range column (`transaction_ts`) means "skip to a, scan to b" across all other
  values: the index is useful only if the range itself is narrow.

## Why LIMIT makes it matter so much

With an ordered index, `Limit` pulls rows lazily and stops after 20: the cost is O(log n + 20).
Every alternative needs the whole candidate set before the first row can be returned, so the
cost is O(matching rows) (plus the sort). At 500M rows, with a customer that has 5M rows in the
quarter, that is 20 entries versus 5M.

The trap with `(transaction_ts, customer_id)` is the reverse: it looks right (no Sort, an Index
Scan) and it is right for heavy customers, because 20 matches are found quickly. For a customer
with 3 rows in the quarter it scans every entry of the quarter, tens of millions at scale, and
returns 3 rows. Always check `Index Cond` and `Buffers`, not just the node names.

## Variants worth knowing

- **Deterministic order**: `ORDER BY transaction_ts, transaction_id` with an index on
  `(customer_id, transaction_ts, transaction_id)` keeps "no Sort". With the two-column index
  PostgreSQL adds an `Incremental Sort` (cheap, but a Sort node), which the required check here
  would flag, so the question says ties do not occur in the range for customer 1001.
- **Covering** (`SQL-053_alt.sql`): `INCLUDE (transaction_id, store_id, gross_amount)` gives an
  `Index Only Scan`; `Heap Fetches` will be non-zero until VACUUM sets visibility-map bits.
- **Partial**: `WHERE transaction_status = 'COMPLETED'` if every consumer filters on it.
- **Descending / keyset**: for "newest 20" PostgreSQL scans the same index backwards, no need for
  `DESC` in the index. Keyset paging: `WHERE customer_id = $1 AND (transaction_ts, transaction_id) > ($2, $3)`.
- **`IN (list of customers)`**: the order guarantee across customers is lost; use a merge
  (`LATERAL` per customer with `LIMIT`, or `MergeAppend`).

## Production considerations

- Prove it on a copy with realistic skew; row counts like the small seed hide the difference.
- `CREATE INDEX CONCURRENTLY`. It builds without blocking writes, takes two scans, can leave an
  INVALID index to drop, and cannot run in a transaction block.
- Check what becomes redundant: `(customer_id, transaction_ts)` makes `ix_transactions_customer`
  unnecessary. Use `pg_stat_user_indexes` to confirm before dropping.
- On a partitioned table, indexes are per partition: build them concurrently on each and attach.
- Keep statistics fresh (`ANALYZE`), and for correlated columns consider extended statistics.

## SQL Server / Azure Synapse notes

- SQL Server follows the same rule for rowstore B-tree indexes: equality keys first, then the
  range/sort key; `INCLUDE` for covering. A `TOP (20) ... ORDER BY` with a matching index gives a
  "Top" over an ordered "Index Seek", with no Sort operator.
- Synapse dedicated pools use clustered columnstore by default: no B-tree seek, rowgroup elimination
  from min/max. Use `ORDER (customer_id, transaction_ts)` clustered columnstore (ordered CCI) so
  segment ranges are narrow, and hash-distribute on `customer_id` so one customer lives on one
  distribution.
- Serverless / Spark: Z-order or sort within partitions by `(customer_id, transaction_ts)` for the
  same data-skipping effect.
