# SQL-016 · First / latest purchase and time to first purchase: explanation

## Approach

1. Aggregate **completed** transactions per customer: `MIN(ts)`, `MAX(ts)`, `COUNT(*)`.
2. `LEFT JOIN` that aggregate **from** `customers` so non-buyers survive.
3. Convert to UTC dates, then subtract dates: `date - date` is an `integer` number of calendar days.
4. `COALESCE(count, 0)` for non-buyers; dates and days stay NULL (unknown/undefined, not zero).

## Three classic mistakes

**1. The status filter in `WHERE` after a `LEFT JOIN`.**
`customers LEFT JOIN transactions ... WHERE status = 'COMPLETED'` removes every customer whose
only joined rows are not completed (customer 33), because their rows fail the predicate.
`OR t.transaction_id IS NULL` rescues customers with *no* transactions (customer 1) but still
loses customer 33 and customer 31 (only a CANCELLED purchase). The filter belongs in the
aggregate subquery or in the `ON` clause.

**2. Elapsed time instead of calendar days.**
`EXTRACT(DAY FROM first_ts - registered_at)` counts full 24-hour periods. A customer who
registers at 16:23 and buys at 09:00 three days later gets 2 instead of 3. In the small seed
832 of 2,042 buyers differ between the two definitions. Fixture customers register at midnight,
so they hide the bug. The generated customers expose it.

**3. Status ignored.**
Customer 22's PENDING 2025-01-31 becomes the "first purchase" (427 days instead of 428).
Customer 26's and 36's later PENDING rows become the "latest purchase".

## (b) Window-function variant (`SQL-016_alt.sql`)

Join with the status in the `ON` clause, compute `FIRST_VALUE` / `LAST_VALUE` / `COUNT` over a
per-customer window, and keep one row per customer. It is longer and slower than the
pre-aggregation (it materialises every joined row), but it demonstrates two things interviewers
like to probe:

- `LAST_VALUE` with an `ORDER BY` and **default frame** returns the *current* row's value,
  because the frame ends at the current row (and its peers). You need
  `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`, or just use `MAX`.
- `COUNT(column)` ignores NULLs, so non-buyers get 0 without a `CASE`.

When you need *other attributes* of the first purchase (its store, its amount), the window or
`DISTINCT ON` version is the natural one. `MIN(ts)` alone doesn't tell you which row it was.

## Complexity and indexes

- (a) One scan + hash aggregate of transactions (O(n)), one hash join with customers (O(c)).
  No sort needed. This is the best plan for "all customers".
- (b) Sorts every joined row by customer and date: O(n log n).
- For a single customer, `transactions(customer_id)` (or `(customer_id, transaction_ts)`) is the
  access path. For all customers a sequential scan is correct.

## Production considerations

- First-purchase date is effectively immutable once known, **except** for late-arriving or
  re-stated data (a backdated transaction, a cancellation of the first purchase). Maintain a
  customer milestone table with `first_purchase_ts`, updated by `LEAST(existing, new)` on insert,
  and recomputed when a status changes away from COMPLETED.
- Data quality: assert `first_purchase_date >= registration_date`. Negative values mean clock
  or migration problems (0 cases in this seed).
- Agree the day boundary (UTC vs local) with the business. The same activation could be 0 days
  in UTC and 1 day in New York.

## SQL Server / Azure Synapse notes

- `DATEDIFF(day, start, end)` counts **date boundaries crossed**, i.e. calendar days, the same as
  PostgreSQL `date - date`. In PostgreSQL, `timestamp - timestamp` is an interval (elapsed time).
  Know which semantics each engine gives you.
- `CAST(registered_at AT TIME ZONE 'UTC' AS date)` for a `datetimeoffset` column.
- `FIRST_VALUE`/`LAST_VALUE` have the same default-frame pitfall in T-SQL.
