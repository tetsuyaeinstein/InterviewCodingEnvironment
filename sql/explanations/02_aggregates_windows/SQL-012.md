# SQL-012 · Second-largest distinct amount per store: explanation

## Approach

"Second largest" is ambiguous until you fix two things: **distinct values vs rows**, and **what
to return when there is no second value**. The contract says distinct values and NULL.

The three ranking functions on store 5 (2025, completed):

| amount | `ROW_NUMBER` | `RANK` | `DENSE_RANK` |
|---|---|---|---|
| 78.00 | 1 | 1 | 1 |
| 78.00 | 2 | 1 | 1 |
| 66.00 | 3 | 3 | **2** |
| 66.00 | 4 | 3 | 2 |
| 60.00 | 5 | 5 | 3 |
| 58.50 | 6 | 6 | 4 |

- `ROW_NUMBER() = 2` returns **78.00** (a copy of the max).
- `RANK() = 2` matches **nothing** (ranks jump 1 → 3), so the store would get NULL.
- `DENSE_RANK() = 2` returns 66.00. Correct.

## (a) `DENSE_RANK` + conditional aggregate (`SQL-012.sql`)

Rank per store, then `GROUP BY store_id` with `MAX(amount)` and
`MAX(amount) FILTER (WHERE amount_rank = 2)`. Grouping (instead of `WHERE amount_rank = 2`)
keeps stores with no rank-2 row, such as store 4, and yields NULL for them automatically. The
duplicates at rank 2 collapse because `MAX` of equal values is that value.

## (b) Max below the max (`SQL-012_alt.sql`)

`second = MAX(amount) WHERE amount < store max`. No window function. The strict `<` is what
makes it "distinct". `<=` would return the max again. The outer join keeps store 4. It works in
any SQL dialect and is a good whiteboard answer. For the N-th value it becomes clumsy (nested N
times), while `DENSE_RANK() = N` generalises directly.

A third option: `NTH_VALUE(DISTINCT ...)` does not exist in PostgreSQL. `NTH_VALUE(amount, 2)`
over rows is just `ROW_NUMBER() = 2` in disguise (wrong for store 5). It also needs a full frame
(`ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`).

## Edge cases and fixtures

| fixture | trap | correct |
|---|---|---|
| store 5: 6001 and 6101 both 78.00; 6002 and 6102 both 66.00 | duplicate max, duplicate second | 78.00 / 66.00 |
| store 5: 6103 CANCELLED 300.00 | status filter missing → 300 / 78 | excluded |
| store 4: 11 completed baskets, all 25.00 | no second value; `WHERE rank = 2` drops the store | 25.00 / NULL |
| store 4: customer 33's CANCELLED 45.00 | would invent a second value (45 / 25) | excluded |
| stores 13, 22, 29, 38, 40… | a non-completed basket larger than every completed one | status filter |

## Complexity and indexes

- One scan of the year plus a sort per store by amount: O(n log n). The `GROUP BY` after the
  window is cheap.
- (b) scans `scoped` twice (CTE may be inlined) and hash-joins on `store_id`. The join condition
  `amount < max` is a non-equi residual filter, so each store's rows are compared once.
- Index candidate: `(store_id, gross_amount DESC) WHERE transaction_status = 'COMPLETED'` plus the
  date predicate. For "top 2 distinct per store" over few stores, a `LATERAL (SELECT DISTINCT amount ... ORDER BY amount DESC LIMIT 2)`
  per store reads only a handful of index entries.

## Production considerations

- Decide and document the NULL policy. Downstream rules such as `highest / second_highest > 3`
  must handle NULL explicitly, or the store silently never alerts.
- Money is `numeric`. Equality of amounts is exact. With floats, "distinct" becomes fuzzy
  (`78.0000001`).
- If refunds should count, compute net basket value first (pre-aggregate refunds per
  transaction to avoid fan-out; see SQL-005).

## SQL Server / Azure Synapse notes

- `DENSE_RANK` is identical. T-SQL has no `FILTER` clause. Use `MAX(CASE WHEN amount_rank = 2 THEN amount END)`.
- `SELECT TOP (1) amount FROM ... WHERE amount < (SELECT MAX(amount) ...)` is the classic T-SQL
  "second highest salary" form. `OFFSET 1 ROWS FETCH NEXT 1 ROWS ONLY` over `SELECT DISTINCT` works
  for a single group but not per store without `CROSS APPLY`.
