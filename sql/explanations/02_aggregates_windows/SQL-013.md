# SQL-013 · Seven-calendar-day rolling revenue: explanation

## Approach

Three separate problems hide in one sentence:

1. **Missing days.** `transactions` has no rows for days without sales, so a calendar has to
   come from somewhere else: `generate_series` per store.
2. **Window semantics.** "Current day + 6 preceding calendar days" is a *time distance*, not a
   *row count*. `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` means "this row and the 6 rows before
   it". That is only the same thing when there is exactly one row per day with no gaps.
3. **Lookback.** The first report day (store 4, 2025-01-15) needs sales from 01-09 … 01-14. If
   you filter to the report period *before* the window runs, those sales are gone.

## (a) Dense calendar + `ROWS` frame (`SQL-013.sql`)

1. `calendar`: per store, every day from `first_day - 6` to `last_day`.
2. `daily`: completed revenue per store per UTC day (sparse), restricted with a sargable
   timestamp range rather than `::date` on the column.
3. `LEFT JOIN` + `COALESCE(revenue, 0)` gives a dense series.
4. `SUM(...) OVER (PARTITION BY store_id ORDER BY business_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)`
   is now correct because one row = one day.
5. Filter to `business_date >= first_day` in the **outer** query. Window functions run after
   `WHERE` of their own level, so the filter must be one level up.

| store 4 | daily | rows in frame | rolling |
|---|---|---|---|
| 01-15 | 0 | 01-09 … 01-15 (01-12 = 25) | 25.00 |
| 01-19 | 0 | 01-13 … 01-19 | 0.00 |
| 03-03 | 25 | 02-25 … 03-03 | 75.00 |
| 03-09 | 0 | 03-03 … 03-09 | 25.00 |
| 03-16 | 0 (DECLINED) | 03-10 … 03-16 | 25.00 |

## (b) Correlated range sums (`SQL-013_alt.sql`)

For each report day, sum transactions with `transaction_ts` in
`[d - 6 days, d + 1 day)` (UTC). No window, no lookback trick: the predicate itself reaches back.
It is easy to reason about and correct by construction. The cost is one index range scan per
(store, day), which is fine for a few hundred report rows with an index on
`(store_id, transaction_ts)`. It degrades to O(days × window) work and re-reads every sale 7 times.

## (c) `RANGE` frame with an interval offset (mention it)

PostgreSQL 11+ supports `RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW` on a
date/timestamp `ORDER BY`. On the **sparse** daily table this is calendar-correct without a
dense calendar. You still need the calendar to *output* zero days, and still need the lookback
rows in the input. SQL Server does **not** support value offsets in `RANGE`, so the dense
calendar + `ROWS` pattern is the portable answer.

## Classic wrong answers

| attempt | symptom on the fixtures |
|---|---|
| `ROWS 6 PRECEDING` over sales rows only | store 4 03-15 window reaches back to 01-12 (7 sales ago); 03-09 is missing entirely |
| filtering the report period before the window | store 4 01-15 … 01-18 show 0.00 instead of 25.00 |
| no calendar (inner join) | 02-25 and every other no-sale day is missing; row count ≠ 76 / 37 |
| no status filter | 03-15 = 50.00, 11-21 = 300.00 |
| `COALESCE` forgotten | NULL instead of 0.00 on empty days |

## Complexity and indexes

- (a) One range scan of `transactions` per store via `(store_id, transaction_ts)`, a hash
  aggregate to days, a tiny calendar, one sort of (days) rows for the window: O(n + D log D).
- (b) D correlated index scans, each covering 7 days: O(D × sales per week). Fine here,
  wasteful at scale.
- At warehouse scale, compute the rolling metric from a **daily store aggregate** (one row per
  store-day, maintained incrementally), not from the raw fact.

## Production considerations

- A calendar/date dimension table is better than `generate_series` in production: it carries
  fiscal periods and holidays, and is joinable in every engine.
- Late data: a sale arriving late for day D changes the rolling value of D … D+6. Incremental
  refresh must recompute that range, not just day D.
- Define and test the zero-day policy (0 vs NULL vs omitted). Charts and anomaly detectors
  behave very differently for each.

## SQL Server / Azure Synapse notes

- No `generate_series` before SQL Server 2022 (`GENERATE_SERIES` exists in 2022+ / Azure SQL;
  not in Synapse dedicated pools). Use a calendar table or a tally CTE.
- `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` works identically. `RANGE` only supports
  `UNBOUNDED`/`CURRENT ROW`, so interval offsets are not available.
- Default frame with `ORDER BY` is `RANGE UNBOUNDED PRECEDING` in both engines. Always state
  the frame explicitly.
