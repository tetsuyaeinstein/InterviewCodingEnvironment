# SQL-020 · Ledger running balances and negative-balance flags: explanation

## Approach

1. Order each account's entries by `posting_ts, entry_id`. This is a **total** order.
2. Running balance = `SUM(signed_amount) OVER (PARTITION BY account_id ORDER BY posting_ts, entry_id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`.
3. `is_negative = running_balance < 0`.
4. `enters_negative = running_balance < 0 AND previous balance >= 0`, where the previous balance
   is `LAG(running_balance, 1, 0)` over the same ordering (0 for the first entry). `LAG` must
   be applied to the **computed** balance, so it sits one query level above the `SUM`.

| account 1 in application order | amount | balance | negative | enters |
|---|---|---|---|---|
| e1 01-01 10:00 | +100 | 100.00 | no | no |
| e2 01-02 09:00 | -30 | 70.00 | no | no |
| e3 01-02 09:00 | -80 | -10.00 | **yes** | **yes** |
| e4 01-03 12:00 | +50 | 40.00 | no | no |
| e5 01-05 00:00 | -5 | 35.00 | no | no |

## The default-frame trap

With `ORDER BY` and no frame the default is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.
`RANGE` includes all **peers**, rows equal on the ordering columns. If the window were ordered by
`posting_ts` only, entries 2 and 3 are peers and both would show -10.00 (the balance after the
whole group): entry 2 would be wrongly reported negative. Even with `entry_id` in the `ORDER BY`
there are no peers, but writing `ROWS` states the intent and is cheaper (no peer detection).
Ordering by `posting_ts` alone with `ROWS` is just as wrong: the order of entries 2 and 3 is then
arbitrary.

| mistake | effect on fixtures |
|---|---|
| `ORDER BY posting_ts` only (default RANGE) | account 1 entry 2 shows -10.00 / negative; account 5 entries 10 and 12 both show 0.00 |
| `ORDER BY entry_id` | account 5 order becomes 10, 11, 12: balance -12.00, 28.00, 0.00, so a bogus negative |
| `ORDER BY posting_ts, entry_id` but `is_negative` on `<= 0` | account 3 entry 9 and account 5 entry 12 flagged |
| `LAG` on `signed_amount`, not the balance | flags wrong rows |
| `enters_negative` = `is_negative` | same on these fixtures, but over-reports every entry of a longer red run |

## (b) Recursive CTE (`SQL-020_alt.sql`)

Number the entries per account, start the recursion with `seq = 1`, then add each next entry to
the previous balance. It is O(n) iterations of a join on `(account_id, seq)`, much
slower than a window sum and more memory-hungry. It is the right tool when the state
transition is not a plain sum: overdraft fees that depend on the previous balance, interest
accrual, caps. A window `SUM` cannot express those. For plain sums, always prefer the window.

## Complexity and indexes

- Window: one sort by `(account_id, posting_ts, entry_id)`, which the index
  `account_ledger(account_id, posting_ts, entry_id)` already provides, so the planner can
  stream with no sort for the selected accounts. O(n) after that.
- The two window functions (`SUM` and `LAG`) have the same partition and order, so they share
  one sort.

## Production considerations

- **Never store only the running balance** without the entries; do store periodic balance
  snapshots (e.g. daily close) so a query only replays since the last snapshot:
  `snapshot_balance + SUM(entries after the snapshot)`.
- Late or back-dated entries change every later balance of that account: partition the
  recomputation by account and rerun from the earliest affected entry.
- Reconcile: the last running balance per account must equal `SUM(signed_amount)` and the
  external system's balance.
- Intermediate balances within one timestamp are **an artefact of the tie-break**. If the
  business only cares about end-of-timestamp (or end-of-day) balances, say so and compute
  balances per timestamp or day instead.

## SQL Server / Azure Synapse notes

- Identical window syntax. SQL Server's default frame is also `RANGE UNBOUNDED PRECEDING`, and
  it spools to disk; always write `ROWS`.
- `LAG(x, 1, 0)` exists. Recursive CTEs need no `RECURSIVE` keyword and default to a
  100-level recursion limit (`OPTION (MAXRECURSION 0)`), a practical reason to avoid them at scale.
- Boolean expressions are not first-class in T-SQL: use `CASE WHEN ... THEN 1 ELSE 0 END` or `bit`.
