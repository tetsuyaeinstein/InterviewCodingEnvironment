# SQL-014 · Running daily spend per customer: explanation

## Approach

1. **Fix the grain first.** Aggregate completed transactions to one row per
   `(customer_id, UTC date)` with `SUM(gross_amount)`.
2. **Then accumulate.** `SUM(daily_spend) OVER (PARTITION BY customer_id ORDER BY purchase_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`.

| customer 15 | daily_spend | running_total |
|---|---|---|
| 09-01 | 120.00 | 120.00 |
| 09-02 | 110.00 (60 + 50) | 230.00 |
| 09-03 | 101.00 | 331.00 |
| 09-04 | 150.00 | 481.00 |
| 09-05 | 100.01 | 581.01 |

## Why the order of operations matters

If you window over **transaction** rows instead of day rows:

- With `ROWS` framing, customer 15's 09-02 produces two rows (180.00 and 230.00, in an
  arbitrary order). Customer 26's 2602/2603 have the *same* timestamp, so even the partial totals
  are non-deterministic.
- With the default frame (`RANGE UNBOUNDED PRECEDING`), peers (same `ORDER BY` value) share the
  frame end, so both 09-02 rows show 230.00. The *values* are right, but you return duplicate rows.
  `SELECT DISTINCT` would hide it, which works but obscures intent.

The default frame when `ORDER BY` is present is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.
On day-grain rows there are no peers, so `ROWS` and `RANGE` give the same result here. Writing
`ROWS` explicitly is still the better habit: it is cheaper (no peer detection) and it is the
semantics you mean. SQL-020 shows a case where the default silently gives a wrong answer.

## Edge cases and fixtures

| fixture | situation | correct |
|---|---|---|
| 15, 09-02 | two transactions in one day | one row, 110.00 |
| 17, 09-03 | CANCELLED 150 + completed 50 | 50.00, running 350.00 |
| 18 | 55 + 50 every day for 6 days | 6 rows of 105.00, ending at 630.00 |
| 26, 10-05 | 2602 and 2603 at the same timestamp | one row, 30.00 |
| 26, 10-06 | only PENDING | no row |
| 19–22 | purchases only in Feb 2025 | not returned |
| 23, 24, 25 | refunds exist | ignored by contract (gross spend) |

Forgetting `PARTITION BY customer_id` yields one running total across all customers in
arbitrary customer order. Customer 23's first row would not be 100.00.

## Complexity and indexes

- Hash aggregate to customer-days, then one sort by `(customer_id, purchase_date)` and a single
  streaming `WindowAgg`: O(n + d log d) for n transactions and d customer-days.
- The scope (12 customers, 2 months) makes `transactions(customer_id)` the natural access path.
  A composite `(customer_id, transaction_ts)` would serve both the filter and the order.

## Production considerations

- Running totals are **path dependent**: a late transaction for 09-02 changes every later row
  for that customer. Incremental pipelines must recompute from the earliest affected day.
- Persisting cumulative columns invites drift. Store daily facts and compute cumulative views
  on read, or recompute per customer partition on change.
- Reconciliation: the last `running_total` per customer must equal `SUM(daily_spend)`.

## SQL Server / Azure Synapse notes

- Same syntax. SQL Server also defaults to `RANGE UNBOUNDED PRECEDING`, which is noticeably
  slower there (on-disk spool) than explicit `ROWS UNBOUNDED PRECEDING`. Always write `ROWS`.
- `CAST(transaction_ts AT TIME ZONE 'UTC' AS date)` for the UTC date of a `datetimeoffset`.
