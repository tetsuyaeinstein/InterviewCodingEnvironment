# SQL-011 · Latest completed transaction per customer: explanation

## Approach

This is the canonical **top-1-per-group** problem. Three things decide whether an answer is
right:

1. **Filter first.** The status filter belongs in the `WHERE` clause *before* ranking. Rank all
   statuses and filter afterwards, and a later `PENDING` row wins rank 1 and then gets filtered
   away, so the customer disappears or gets the wrong row.
2. **Total order inside the group.** `ORDER BY transaction_ts DESC` alone is not a total order
   when two rows share a timestamp. Add `transaction_id DESC` as the tie-breaker the spec asks for.
3. **One row per group.** `ROW_NUMBER() = 1` (not `RANK() = 1`, which keeps both tied rows).

| customer 26 rows (completed) | ts | `ROW_NUMBER` (ts desc, id desc) | `RANK` (ts desc) |
|---|---|---|---|
| 2603 | 2025-10-05 18:00 | 1 | 1 |
| 2602 | 2025-10-05 18:00 | 2 | 1 |
| 2601 | 2025-09-01 15:00 | 3 | 3 |

## (a) `ROW_NUMBER()` (`SQL-011.sql`)

Window per customer, ordered newest first with the id tie-breaker, keep `rn = 1` in an outer
query (window functions cannot appear in `WHERE` at the same level). Portable to every engine.

## (b) `DISTINCT ON` (`SQL-011_alt.sql`)

PostgreSQL keeps the first row of each `DISTINCT ON` group in `ORDER BY` order. It is shorter
and usually a little faster (one sort, no window materialisation), but it is PostgreSQL-only, and
the `ORDER BY` must begin with the `DISTINCT ON` expressions.

## Wrong answers interviewers see

| attempt | what goes wrong |
|---|---|
| `MAX(transaction_ts)` per customer, join back on (customer, ts) | customer 26 returns **two** rows (2602 and 2603) |
| `MAX(transaction_id)` per customer | assumes ids follow time; true here by accident for some, false in general (late-loaded rows, multiple sources) |
| `ROW_NUMBER() OVER (... ORDER BY transaction_ts DESC)` without the id | picks 2602 or 2603 arbitrarily; may change between runs |
| status filter after ranking | customer 26 gets 2604 (PENDING) ranked first, then is dropped; customer 36 vanishes |
| `RANK() = 1` | customer 26 twice |

## Edge cases and fixtures

| fixture | situation | correct row |
|---|---|---|
| 26 | 2602/2603 same ts, later PENDING 2604 | 2603 |
| 36 | completed 06-01, PENDING 12-20 | 3601 |
| 12 | CANCELLED 1203 and PENDING 1206 among completed rows | 1205 |
| 64 | 6412 was ingested last (2026-01-05) but happened before 6413 | 6413 (event time) |
| 33 | only CANCELLED | not returned |
| 1 / guests | no rows / NULL customer | not returned |

## Complexity and indexes

- Full-history version: one scan plus one sort by `(customer_id, ts desc, id desc)`, i.e.
  O(n log n). `WindowAgg` streams over the sorted input. PostgreSQL 15+ can stop evaluating the
  window early for `rn = 1` (a "run condition"), but it still has to sort.
- A partial index `(customer_id, transaction_ts DESC, transaction_id DESC) WHERE transaction_status = 'COMPLETED'`
  lets the planner read rows already in window order. For a **few** customers the best plan is a
  `LATERAL (... ORDER BY ... LIMIT 1)` index probe per customer: O(customers × log n).
- `DISTINCT ON` and `ROW_NUMBER` have the same asymptotic cost. The skip-scan style
  `LATERAL` approach wins when customers are few relative to transactions.

## Production considerations

- Event time vs load time: "latest" is by `transaction_ts`. Late-arriving data (customer 64)
  means yesterday's answer can change today. An incremental job must re-evaluate customers that
  received late rows, not just new rows.
- A deterministic tie-break makes the job idempotent and testable. Without it, two runs over
  the same data can emit different rows, and downstream diffs light up for no reason.
- Keep a **current-state table** `customer_last_purchase(customer_id PK, ...)` maintained with
  `INSERT ... ON CONFLICT (customer_id) DO UPDATE ... WHERE (excluded.ts, excluded.id) > (t.ts, t.id)`.
  That row-value comparison is the same tie rule.

## SQL Server / Azure Synapse notes

- No `DISTINCT ON`. Use `ROW_NUMBER()` in a CTE, or `CROSS APPLY (SELECT TOP (1) ... ORDER BY ts DESC, id DESC)`.
- `TOP (1) WITH TIES` keeps ties: the opposite of what you want here.
- Synapse dedicated pool: hash-distribute the fact on `customer_id` so the partitioned window
  runs without data movement.
