# SQL-015 · Month-over-month growth with empty months: explanation

## Approach

1. **Dense month series** per store: `generate_series` from **one month before** the first
   report month to the last report month.
2. **Monthly revenue** (sparse) from completed transactions, grouped by
   `date_trunc('month', transaction_ts AT TIME ZONE 'UTC')`.
3. `LEFT JOIN` + `COALESCE(..., 0)` → every month has a revenue, zero included.
4. `LAG(revenue)` per store → previous month. Because the series is dense, the previous **row**
   is the previous **calendar month**.
5. Safe percentage: `ROUND(100 * (cur - prev) / NULLIF(prev, 0), 2)`. Division by NULL is NULL.
6. Drop the lookback month in the **outer** query, after `LAG` has used it.

| store 4 | revenue | prev | pct |
|---|---|---|---|
| (Jan, lookback) | 75.00 | – | – |
| Feb | 50.00 | 75.00 | −33.33 |
| Mar | 100.00 | 50.00 | 100.00 |
| Apr | 0.00 | 100.00 | −100.00 |
| May | 50.00 | 0.00 | NULL |
| Jun | 0.00 | 50.00 | −100.00 |
| Jul … Dec | 0.00 | 0.00 | NULL |

## (b) Join to "month − 1" (`SQL-015_alt.sql`)

Instead of `LAG`, join the monthly aggregate a second time on
`prev.month_start = cur.month_start - interval '1 month'`. No dense lookback row is needed, and
a gap in the series can never shift the comparison. `LAG` on a **sparse** series silently
compares May with March when April is missing, which is the bug this alternative cannot have. It
costs a second probe of the (small) monthly aggregate. It is the more robust choice when the
series cannot be guaranteed dense, e.g. year-over-year (`- interval '12 months'`).

## Classic wrong answers

| attempt | symptom |
|---|---|
| `LAG` on monthly aggregates without a calendar | April missing; May compared with March (−50.00 instead of NULL) |
| report filter applied before `LAG` | Feb gets `prev = NULL` instead of 75.00 |
| `revenue / prev - 1` without `NULLIF` | `division by zero` error on May |
| `COALESCE(pct, 0)` | 0.00 → 0.00 and 0 → 50 both show 0 % growth, which is a lie |
| integer arithmetic on counts | 50 / 75 = 0 (not an issue with `numeric`, but a classic on integer measures) |
| rounding before multiplying by 100 | −0.33 × 100 = −33.00 |

## Edge cases and fixtures

| fixture | trap |
|---|---|
| store 4 Jan (75.00) outside the report | lookback month must feed February |
| store 4 03-15 CANCELLED, 03-16 DECLINED, 04-10 CANCELLED, PENDING 06-01 | status filter; April must still be 0.00 |
| store 4 Apr and Jun–Dec | empty months must appear |
| store 4 May (prev 0) and store 5 Nov (prev 0, revenue 348.00) | NULL percentage policy |
| store 5 Nov CANCELLED 300.00 | would make November 648.00 |
| Feb 50/75 | −33.333… must round to −33.33 |

## Complexity and indexes

- The work is one range scan per store over a year via `(store_id, transaction_ts)` and a hash
  aggregate into at most 13 × stores groups. The calendar and window are trivial.
- `date_trunc` on the converted timestamp is applied after the sargable range predicate, so it
  does not prevent index use.

## Production considerations

- Publish the NULL policy with the metric definition. Dashboards often show NULL as blank. Some
  teams prefer a separate flag (`is_new_revenue = prev = 0 AND cur > 0`).
- Keep a monthly store aggregate (`store_id, month_start, revenue`) and compute growth on read.
  Late transactions only touch the affected month and the next month's percentage.
- Make the month boundary definition explicit (UTC vs store-local vs fiscal calendar). A
  calendar dimension makes fiscal months a join instead of code.

## SQL Server / Azure Synapse notes

- `LAG(revenue, 1, 0) OVER (...)` supplies a default for the first row in both engines. Useful,
  but here the lookback month gives the true value instead.
- `NULLIF` exists in T-SQL. `ROUND(x, 2)` in SQL Server keeps the input scale (−33.330000…).
  Cast to `decimal(9,2)` for presentation.
- `DATETRUNC(month, ...)` exists only in SQL Server 2022+. Otherwise use
  `DATEFROMPARTS(YEAR(d), MONTH(d), 1)` or `EOMONTH`.
- Synapse dedicated pools have no `generate_series`. Use a calendar table.
