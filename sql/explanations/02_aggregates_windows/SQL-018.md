# SQL-018 · Top three products per region with share of region revenue: explanation

## Approach

1. **Grain.** Revenue lives at order-line grain: `quantity * unit_price - discount_amount`.
   `transactions.gross_amount` is a header amount; joined to lines it repeats once per line and
   over-counts every multi-line basket. Never sum it after a line join.
2. **Aggregate to (region, product).** Join transactions to lines and stores, filter to
   COMPLETED and the 2025 UTC range, group by `stores.region, product_id`. A product sold in
   several stores of a region collapses into one row.
3. **Window over that grain.** In the same level compute
   `RANK() OVER (PARTITION BY region ORDER BY net_revenue DESC)` and
   `SUM(net_revenue) OVER (PARTITION BY region)`.
4. **Filter in an outer query** (`rank <= 3`). If you filter before computing the total, the
   percentage is relative to the top three and every region shows ~100 %.
5. Join `products` for the name last (it cannot change the grain: one row per product).

## Tie handling

`RANK() <= 3` keeps all products tied at the boundary (1,2,2,4 keeps ranks 1, 2, 2). It
returns 3 or more rows per region. `ROW_NUMBER() <= 3` would cut ties non-deterministically.
`DENSE_RANK() <= 3` would return three revenue *levels*, a different question. The current
small seed has no tie at the boundary (amounts are sums of many lines), so the contract is
verified by reasoning, not data. Say so in an interview and offer a unit test with a synthetic tie.

## (b) LATERAL top-N with `FETCH FIRST 3 ROWS WITH TIES` (`SQL-018_alt.sql`)

For each region (a tiny table) a lateral subquery sorts that region's products and takes the
first three plus ties (PostgreSQL 13+). Rank is recomputed as 1 + count of strictly larger rows
and the region total comes from a separate aggregate. It is clumsier for this output but it is
the right shape when the group list is small and each group is huge: with an index that
delivers rows in order, each probe reads about three entries instead of sorting the group. Here the
input is already aggregated, so the benefit is small; at warehouse scale the same pattern applies
to a (region, product) rollup table.

## Wrong answers

| attempt | symptom |
|---|---|
| `SUM(t.gross_amount)` after joining lines | multi-line baskets counted per line; wrong revenue and ranking |
| no status filter | cancelled baskets (e.g. 50 x product 4 at store 5, 300.00) inflate revenue |
| `ROW_NUMBER() <= 3` | ties cut arbitrarily |
| `WHERE rank <= 3` before the total | percentages relative to the top three |
| revenue ignores `discount_amount` | e.g. store 5's 3 x p2 @ 24 - 6.00 discount overstated |
| region taken from customers (`home_region`) | NULL regions, wrong attribution |

## Complexity and indexes

- One pass over 2025 lines: hash join lines to transactions (range on `transaction_ts`), join
  stores (40 rows), hash aggregate to at most regions x products groups (~800 here).
  Window and sort run on those ~800 rows, so they are negligible.
- At 500M lines: the join and aggregate dominate. Pre-aggregate daily `(store, product)`
  revenue into a rollup (partitioned by date), then roll up to region. Partition pruning on the
  date range, and a columnar/hash-distributed layout on `product_id` for the aggregate.

## Production considerations

- Region is a current attribute of the store. Decide whether history should follow the region at
  sale time (an SCD2 store dimension) before reorganisations change last year's report.
- Reconcile: SUM of `net_revenue` over all products must equal finance's line-level revenue
  for the same scope, and region totals must add to the company total.
- Ties: publish the tie rule with the report so consumers are not surprised by 4 rows.

## SQL Server / Azure Synapse notes

- `RANK`, `SUM() OVER` are identical. T-SQL `TOP (3) WITH TIES` with `CROSS APPLY` is the
  analog of the lateral version, and needs `ORDER BY`.
- PostgreSQL's `FETCH FIRST n ROWS WITH TIES` requires 13+; no equivalent `FILTER` in T-SQL
  (use `CASE`).
- Synapse dedicated pools: distribute the line fact on `transaction_id`, replicate `stores`.
