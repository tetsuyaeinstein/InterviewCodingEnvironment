# SQL-017 · Spending quartiles with explicit tie rules: explanation

## Approach

1. **Population.** Cohort = `registered_at` in `[2023-12-01, 2023-12-02)` UTC. That is 56 fixture
   customers registered at midnight **plus** generated customer 1601 (09:39 UTC), so **N = 57**.
   `registered_at = '2023-12-01'` would miss 1601. Customer 1075 (2023-12-02 00:07 UTC) is out.
2. **Spend with zeros.** `cohort LEFT JOIN transactions` with the status and date conditions in
   the `ON` clause, `COALESCE(SUM, 0)`. Fifteen cohort members have 0.00 (no transactions,
   only CANCELLED/PENDING ones, or only 2024 purchases).
3. **Equal-size tiers.** `NTILE(4) OVER (ORDER BY spend DESC, customer_id)`. 57 = 4 × 14 + 1,
   so the sizes are 15, 14, 14, 14 (larger groups first). `customer_id` makes the ordering total.
   Without it, PostgreSQL may split a tie group differently on another run or plan.
4. **Tie-safe tiers.** `CUME_DIST()` = (rows with spend ≥ mine, peers included) / N, so peers
   share it. `CEIL(4 × CUME_DIST())` gives the tier of the **last** member of the tie group.

## The boundary that matters

| pos | customers | spend | NTILE (15/14/14/14) | s (≥ spend) | ceil(4s/57) |
|---|---|---|---|---|---|
| 1–13 | 17, 16, 18, 15, 64, 65, 60, 5, 7, 50, 53, 62, 61 | 650 … 144 | 1 | ≤ 13 | 1 |
| 14–15 | 4, 6 | 140 | **1** | 17 | **2** |
| 16–17 | 11, 23 | 140 | 2 | 17 | 2 |
| 28–29 | 26, 30 | 60 | **2** | 29 | **3** |
| 43 | 1 | 0 | **3** | 57 | 4 |
| 44–57 | 10, 31, 32, 33, … | 0 | 4 | 57 | 4 |

The 140.00 tie is split 2/2 by `NTILE`. The tie-safe rule keeps all four together in tier 2.

## Floating point

`CUME_DIST` returns `double precision`. `CEIL(4 × k/N)` is still exact at the boundaries: when
`k/N` is exactly 0.25, 0.5 or 0.75, IEEE division returns it exactly, and multiplying by 4 is
exact. If you prefer to avoid the argument entirely, use integer arithmetic:
`(4 * s + N - 1) / N` with `s = COUNT(*) OVER (ORDER BY spend DESC)`. The default `RANGE` frame
includes peers, so this count is "spend ≥ mine" (that is the alternative's approach).

## (b) First-principles integer version (`SQL-017_alt.sql`)

- Equal-size: `N = 4q + r`. Rows `1 … r(q+1)` fall into the first `r` tiers of size `q+1`; the
  rest into tiers of size `q`. That is exactly `NTILE`'s documented behaviour.
- Tie-safe: a correlated count of cohort members with spend ≥ mine, then integer ceil.
- O(N²) for the correlated count. Fine for 57 rows, useless at millions, but a strong answer when
  the interviewer asks "what does `NTILE` actually do?" or the engine lacks the functions.

## Other tie-safe definitions (say them out loud)

| definition | 140.00 group | zero spenders | note |
|---|---|---|---|
| `ceil(4 × CUME_DIST)` (this spec) | tier 2 | tier 4 | ties pushed **down** |
| `1 + floor(4 × (RANK − 1) / N)` | tier 1 | tier 3 | ties pushed **up**; tier 4 can end up empty |
| `PERCENTILE_CONT` thresholds (`spend >= p75`) | depends on interpolation | | thresholds are reusable for new customers |

None is "correct". The point is that the contract has to say which one it is.

## Wrong answers interviewers see

- Starting from `transactions` (inner join): zero spenders vanish, N becomes 42, every boundary
  moves.
- `WHERE t.transaction_status = 'COMPLETED'` after a `LEFT JOIN`: same effect.
- `NTILE(4) OVER (ORDER BY spend DESC)` without `customer_id`: non-deterministic tie split.
  It may pass on one run and fail on the next.
- `registered_at::date = '2023-12-01'` relies on the session time zone (UTC here). Use a
  half-open UTC range.

## Complexity and indexes

- The cohort is selective (57 of 2,056 customers). Index `customers(registered_at)` helps.
  Transactions are probed via `transactions(customer_id)`.
- Two window functions with different `ORDER BY` lists mean two sorts of N rows: trivial here,
  O(N log N) in general.

## Production considerations

- Persist the tier **and** the definition version used. Tier boundaries move every time the
  population changes (a late purchase can bump a whole tie group).
- For customer-facing tiers, fixed spend thresholds (computed once per period with
  `PERCENTILE_DISC`) are easier to explain than rank-based tiers, and they are stable for new
  customers.
- Monitor tier sizes. A tie-safe rule can produce very uneven tiers when many customers spend 0.

## SQL Server / Azure Synapse notes

- `NTILE`, `CUME_DIST`, `PERCENT_RANK` exist with the same semantics. `CEILING` instead of `CEIL`.
- `CUME_DIST` returns `float` in T-SQL as well. The integer formula is the safe portable form.
- Synapse: computing a global `NTILE` (no `PARTITION BY`) forces all rows onto one distribution.
  At scale compute thresholds with `PERCENTILE_DISC` or approximate percentiles first, then join.
