# SQL-046 · Incremental upsert with ON CONFLICT: explanation

## Approach

1. **Collapse the batch to one row per key.** `DISTINCT ON (source_system, business_key) ... ORDER BY
   source_system, business_key, source_lsn DESC` keeps the newest version of each key and
   discards exact duplicates.

   Without this step PostgreSQL raises:

   > `ON CONFLICT DO UPDATE command cannot affect row a second time`

   One statement can't update the same target row twice, because the outcome would depend on row
   order.
2. **Upsert** with `INSERT ... ON CONFLICT (source_system, business_key) DO UPDATE SET col = EXCLUDED.col`.
   `EXCLUDED` is the proposed row.
3. **Guard against stale versions** with `WHERE EXCLUDED.source_lsn > t.source_lsn`. When the
   guard is false, the conflicting row is left as-is. That covers both a batch older than the
   warehouse (fixture `FX-0010`) and an exact replay of an already applied batch.

Expected end state (hand-checkable from the sandbox setup):

| source_system | business_key | amount | status | source_lsn | why |
|---|---|---|---|---|---|
| POS | FX-0001 | 60.00 | COMPLETED | 9000030 | newest of 3 batch versions beats stored 9000020 |
| POS | FX-0003 | 35.00 | COMPLETED | 9000230 | new key; newest of two inserts |
| POS | FX-0004 | 40.00 | COMPLETED | 9000320 | duplicate delivery collapses to one |
| POS | FX-0005 | 15.00 | COMPLETED | 9000430 | two updates with equal commit_ts; LSN decides |
| POS | FX-0008 | 95.00 | COMPLETED | 9000720 | new key; update arrived before insert, LSN still decides |
| POS | FX-0010 | 99.00 | COMPLETED | 9999999 | stored row is newer → untouched |
| ECOM | FX-0001 | 510.00 | COMPLETED | 9000020 | same key text, different source system |

## Why it is idempotent

Running the same batch twice changes nothing the second time. Every proposed row now has
`EXCLUDED.source_lsn = t.source_lsn`, so the strict `>` guard skips it. Note that `>=` would still
give the same final state here, but it rewrites rows for nothing: extra WAL, dead tuples and
fired triggers. SQL-048 explores this further.

## Complexity and performance

- One pass over the batch: the sort for `DISTINCT ON` costs O(b log b) for batch size b.
- One unique-index probe per batch row. Cost is independent of target size apart from index
  depth, as long as the primary key exists.
- `ON CONFLICT` **requires** a unique index or constraint that matches the conflict target exactly.
- Large batches: sort in `work_mem`, or pre-aggregate into a temp table. Rows that fail the guard
  still lock the conflicting row, so run concurrent batches for the same keys serially, or
  partition the work by key.

## Alternatives worth naming

- **`MERGE`** (PostgreSQL 15+, also SQL Server and Synapse):
  `WHEN MATCHED AND s.source_lsn > t.source_lsn THEN UPDATE ... WHEN NOT MATCHED THEN INSERT ...`.
  It is more readable and supports a `DELETE` branch (useful for CDC tombstones, SQL-047).
  In PostgreSQL, though, MERGE does **not** have ON CONFLICT's built-in race safety: under
  concurrent inserts it can fail with unique violations. ON CONFLICT is the idiomatic concurrent
  upsert.
- **UPDATE ... FROM, then INSERT ... WHERE NOT EXISTS**: portable, but two statements, and racy
  without locking.

## SQL Server / Synapse notes

- T-SQL has no `ON CONFLICT`. Use `MERGE` (watch its known concurrency caveats and use `HOLDLOCK`),
  or UPDATE + INSERT inside a serializable transaction.
- Synapse dedicated pools support `MERGE` on hash-distributed tables. Many teams still use CTAS
  "swap" patterns for very large batches.
