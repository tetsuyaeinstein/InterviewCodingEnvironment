# SQL-048 · Idempotent restatement: explanation

## What idempotent means here

`f(f(state, batch), batch) = f(state, batch)`. The load must be a function of the **batch**, not
of what the target already holds. `INSERT` (fails or duplicates) and
`ON CONFLICT DO UPDATE SET amount = amount + excluded.amount` (doubles on retry) both depend on
the previous state.

## (a) Partition overwrite: delete + insert (`SQL-048.sql`)

1. `DELETE FROM daily_store_sales WHERE sales_date IN (dates in the batch)`.
2. `INSERT` the recomputed rows from the latest delivery per transaction
   (`DISTINCT ON (transaction_id) ... ORDER BY transaction_id, delivery_id DESC`), counting only
   `COMPLETED` current versions, grouped by UTC date and store.

Running it twice deletes and re-inserts the same rows. The end state is identical. It is also the
only simple approach that removes rows which no longer have sales: the stale **2025-12-09 store 4**
row, and **2025-12-08 store 15**, whose only sale (119493) went PENDING, then COMPLETED, then
CANCELLED across three deliveries.

Fixture-level checks after two runs:

| case | value |
|---|---|
| 12-08 store 29: 119529 delivered at 255.99, corrected to 250.99 | 1 txn, 250.99 |
| 12-09 store 30: 119561 cancelled by a later delivery; 119575 arrived after the first load | 1 txn, 58.72 |
| 12-08..12-10 total | 156 sales, 7,979.49 |
| 12-01..12-07 | untouched: 183 rows, 384 sales, 20,135.02 (12-07 is even slightly stale, by design) |

## (b) MERGE with `WHEN NOT MATCHED BY SOURCE` (`SQL-048_alt.sql`, PostgreSQL 17)

One statement: `WHEN MATCHED THEN UPDATE SET` (assign, don't add), `WHEN NOT MATCHED BY TARGET
THEN INSERT`, and `WHEN NOT MATCHED BY SOURCE AND t.sales_date IN (restated dates) THEN DELETE`.
The date condition is essential: without it, MERGE deletes every row not in the batch,
including all older days. The `IS DISTINCT FROM` guard on the update avoids rewriting unchanged
rows (less WAL, fewer dead tuples).

Trade-offs: (b) touches only changed rows, which helps when most rows are unchanged and the table
has many indexes. (a) is simpler, works in every engine, and maps onto **partition exchange** at
scale.

## Wrong approaches and why they fail

| approach | symptom |
|---|---|
| increment on conflict | 12-08/12-09 contain old + new; the 2nd run doubles everything |
| upsert recomputed values, no delete | stale rows survive (12-09 store 4, 12-08 store 15) |
| delete + insert without "latest delivery" | 119529 counted at 255.99 + 250.99; cancelled 119561 still counted |
| `DELETE FROM daily_store_sales` (whole table) | wipes 12-01..12-07, which the batch doesn't cover |
| recompute from `public.transactions` | ignores the batch's corrections and restates days outside the batch |
| `CREATE TABLE helper AS ...` without `IF EXISTS` handling | the second run fails |

## Complexity and plan

Sort or hash of the batch (b log b) for the latest version, a hash aggregate, and deletes/inserts
proportional to the number of (date, store) rows of the restated dates. Independent of the
target's total size if `sales_date` is the leading PK column (index range delete).

## Production considerations

- **Partitioned targets:** with `daily_store_sales` range-partitioned by date, the delete becomes
  `TRUNCATE` of the affected partitions, or build a new table and `ATTACH`/`DETACH` (or swap)
  partitions. That's minimal WAL and the restatement is atomic per partition.
- Run the delete and insert in **one transaction** so readers never see an empty day. PostgreSQL
  MVCC gives readers the old version until commit.
- Concurrency: two loaders restating the same date must be serialised (advisory lock per date,
  or a single writer per partition).
- Record a load audit row (batch id, dates restated, row counts, checksum) so a retry can be
  verified to be identical.
- The "complete per date" contract must hold upstream. If the extract sends only deltas, partition
  overwrite silently **loses** data. In that case you need a transaction-grain table (upsert by
  `transaction_id` with version guard), and the summary is recomputed from it.

## SQL Server / Azure Synapse notes

- T-SQL `MERGE` has supported `WHEN NOT MATCHED BY SOURCE THEN DELETE` for years. Scope it with
  an extra predicate, or merge into a filtered CTE/view of the restated dates.
- Synapse dedicated pools: prefer **CTAS + partition SWITCH** for restatements:
  `CREATE TABLE ... AS SELECT` the new day, then `ALTER TABLE ... SWITCH PARTITION`. Row-level
  DELETE/UPDATE on columnstore is expensive (delete bitmaps, fragmentation).
- Spark/Delta: `INSERT OVERWRITE ... PARTITION (sales_date)` with dynamic partition overwrite, or
  `MERGE INTO` with `WHEN NOT MATCHED BY SOURCE` (Delta Lake 2.3+ / Databricks).

   pipeline so it stays idempotent.
2. The summary is 500M rows, partitioned by month, with 3 days restated each hour. Compare
   row-level MERGE vs partition rebuild (I/O, locking, vacuum, index maintenance).
3. Two orchestrator retries run concurrently. What can go wrong with delete + insert, and how do
   you prevent it?
