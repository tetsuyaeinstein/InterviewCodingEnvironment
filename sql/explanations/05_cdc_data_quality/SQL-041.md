# SQL-041 · Current state of every CDC key: explanation

## Approach

1. **Rank inside each key by commit order.**
   `ROW_NUMBER() OVER (PARTITION BY source_system, business_key ORDER BY source_lsn DESC, cdc_event_id DESC)`.
   Rank 1 is the current version. The secondary `cdc_event_id DESC` makes the pick deterministic
   when several events share the top LSN, and implements the stated tie policy (latest arrival wins).
2. **Detect conflicts separately.** Among the events where `source_lsn = max_lsn` of the key,
   `COUNT(DISTINCT (operation, payload)) > 1` means two *different* versions claim the same commit
   position. Identical redeliveries collapse to one distinct value, so they are not conflicts.
3. **Project the after-image.** `(payload->>'amount')::numeric(12,2)` and `payload->>'status'`,
   but only when the chosen operation is not `D`. A delete's payload has no amount, and carrying
   an older amount forward would make a deleted transaction look alive.

| key | events (arrival order) | chosen | why |
|---|---|---|---|
| POS FX-0001 | I 9000010, U 9000030, U 9000020 | U 9000030 (60.00) | highest LSN; the 55.00 update arrived last but is older |
| POS FX-0002 | I 9000110, D 9000120, U 9000115 | D 9000120 | the stale update cannot outrank the delete |
| POS FX-0003 | I, D, I 9000230 | I 9000230 (35.00) | legitimate re-insert after a delete |

| POS FX-0005 | U 9000430, U 9000420 (same commit_ts) | 9000430 (15.00) | commit_ts ties; LSN decides |
| POS FX-0006 | U 9000520 (75.00), U 9000520 (80.00) | 3790 (80.00), conflict | tie policy plus flag |
| POS FX-0007 | D only | D, deleted | delete for a never-seen key |

| ECOM FX-0001 | I, U 9000020 | 510.00 | separate key: LSNs are per source |

## Why the edge cases matter

- **Latest by `ingested_at` / `cdc_event_id`** is the classic bug. It gets FX-0001 (55.00), FX-0002
  (resurrected at 25.00), FX-0005 (12.00) and FX-0008 (90.00) wrong.
- **Partitioning by `business_key` alone** merges POS and ECOM FX-0001 into one key. Comparing
  their LSNs is meaningless, because the sequences are independent.
- **`COUNT(*) > 1` at the top LSN as the conflict test** flags FX-0004's harmless redelivery.
  Compare the *versions*, not the number of rows.
- **Silently picking one of FX-0006's versions** is the worst outcome. Whatever tie rule you use,
  someone has to be told that the source emitted two different rows for one commit position.

## Alternatives

- **`DISTINCT ON (source_system, business_key) ... ORDER BY ..., source_lsn DESC, cdc_event_id DESC`**
  is the shortest PostgreSQL form. It needs the same separate conflict check.
- **Anti-join "no newer event exists"** (`SQL-041_alt.sql`):
  `NOT EXISTS (newer LSN, or same LSN and higher cdc_event_id)`. With the
  `(source_system, business_key, source_lsn)` index each probe is an index range scan. That suits
  "current version of these 50 keys" lookups, while the window version wins for full rebuilds
  (one sort, one pass).
- **`MAX(source_lsn)` per key joined back** also works, but it returns both tied rows for FX-0004
  and FX-0006 unless you add a second tie-break step. That is a common source of duplicate keys.

## Complexity, plan and indexes

- Window version: one sort by (key, lsn desc, id desc) over all events, O(n log n). An index on
  `(source_system, business_key, source_lsn DESC, cdc_event_id DESC)` lets PostgreSQL stream rows
  in window order without a Sort node.
- The jsonb extraction runs only for the ~1,500 winners when it is placed after the filter. On large
  logs, avoid extracting payload fields for every event.

## Production considerations

- Never rebuild from the full log every time. Maintain a current-state table incrementally
  (SQL-046 / SQL-047) and use this query as a **reconciliation check**: rebuilt-from-log vs
  maintained table should match.
- Route `has_lsn_conflict` keys to a quarantine table and alert the source team. Picking "latest
  arrival" is a policy decision that the business should sign off on.
- Deleted keys need **tombstones** downstream. Otherwise a late stale update recreates them
  (FX-0002, SQL-047).
- Parse `amount` defensively (`payload->>'amount' ~ '^-?\d+(\.\d+)?$'`) in a real pipeline. Bad
  payloads should fail into a dead-letter table, not crash the batch.

## SQL Server / Azure Synapse notes

- No `DISTINCT ON`. Use `ROW_NUMBER()` in a CTE and filter `rn = 1`. T-SQL can't filter on a
  window function in `WHERE`, so it needs the CTE or subquery. Newer engines support `QUALIFY`
  (Databricks, Snowflake) but SQL Server does not.
- JSON: `JSON_VALUE(payload, '$.amount')` and `TRY_CAST(... AS decimal(12,2))`. There is no jsonb
  type, so payload equality for the conflict check compares normalized strings (or a `HASHBYTES`
  of them).
- Synapse dedicated pool: hash-distribute the event table on `business_key` so the ranking runs
  without data movement.

## Follow-up questions

1. The log holds 500M events and grows by 5M per hour. How do you keep a current-state table
   correct without rescanning everything? (Incremental merge of only the touched keys, with LSN
   guards and tombstones: SQL-046/047.)
2. The source system re-sequences LSNs after a failover. How do you detect and handle a
   sequence reset?
3. How would you expose the history (SCD2-style validity intervals per key) from the same log?
4. Product asks for "current state as of 2025-12-31 12:00". Which timestamp do you filter on:
   `commit_ts` or `ingested_at`, and why?
