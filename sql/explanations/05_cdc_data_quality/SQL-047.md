# SQL-047 · Applying I/U/D with tombstones: explanation

## The core idea

A current-state table alone forgets that a key *was* deleted. An update with an older LSN that
arrives later looks like a brand-new key and gets inserted (resurrection). The fix is to keep a
**tombstone**, `(key, deleted_lsn)`, and treat "the newest LSN we have ever applied for this key"
as `max(live.source_lsn, tombstone.deleted_lsn)`. An event is applied only if it beats that.

## Approach (reference `SQL-047.sql`, one statement)

1. `winner`: `DISTINCT ON (source_system, business_key) ... ORDER BY source_lsn DESC, cdc_event_id DESC`.
2. `apply`: left-join the live row and the tombstone. Keep winners with
   `source_lsn > GREATEST(live_lsn, deleted_lsn)` or with neither known.
3. Four data-modifying CTEs, all working on the **same snapshot**, on disjoint rows:
   - `D`: `DELETE` the live row, and `INSERT ... ON CONFLICT DO UPDATE` the tombstone
     (raise only if newer);
   - `I`/`U`: upsert the live row with an LSN guard, and `DELETE` the tombstone.

## Why each piece is needed

- **Ignoring D events** (SQL-046 logic only): FX-0007 and FX-0002 come out wrong and FX-0010 keeps
  a stale tombstone, which breaks the "never both live and deleted" invariant.
- **Only looking inside the batch:** the batch's newest FX-0002 event is the stale update. Without
  the tombstone lookup, FX-0002 is resurrected. This is the production incident from the question.
- **Keying tombstones on `business_key` only:** the ECOM FX-0003 tombstone (9500000) blocks the POS
  FX-0003 re-insert.
- **Order of operations:** if you delete tombstones before deciding what to apply (or decide per
  statement after earlier statements already ran), later statements see a changed state.
  Compute `apply` once, either in one statement with CTEs (one snapshot) or materialised.

Data-modifying CTEs in PostgreSQL all see the snapshot from the start of the statement, and their
effects are invisible to each other. That is why the four writes must not touch the same rows
twice, and why the filter is computed from the original state.

## Alternative: two MERGE statements (`SQL-047_alt.sql`)

Materialise the applicable set (`CREATE TABLE cdc_apply AS ...`), then:

- `MERGE INTO txn_current ... WHEN MATCHED AND op='D' THEN DELETE WHEN MATCHED THEN UPDATE WHEN NOT MATCHED AND op<>'D' THEN INSERT`
- `MERGE INTO txn_tombstone ... WHEN MATCHED AND op='D' THEN UPDATE WHEN MATCHED THEN DELETE WHEN NOT MATCHED AND op='D' THEN INSERT`

MERGE reads naturally for CDC (I/U/D map to WHEN branches) and is the dialect you will use in SQL
Server and Synapse. In PostgreSQL, MERGE has no ON CONFLICT-style race handling: concurrent
writers on the same keys can hit unique violations, so serialise batches per key range.

An alternative design keeps deletes **in** the live table as soft-deletes (`is_deleted`,
`source_lsn`) instead of a separate tombstone table. It needs one table, and every consumer
filters `NOT is_deleted`.

## Idempotency and retention

- Re-applying the same batch is a no-op: every winner now has `lsn = max known`, and the strict `>`
  rejects it.
- Tombstones can't live forever. Keep them at least as long as the maximum event delay (e.g. 7
  days beyond the CDC retention), then purge them, ideally together with a watermark that
  guarantees no older event can still arrive.

## Complexity

One sort of the batch (b log b), and index probes into both tables per winner (PK lookups).
Independent of the table size apart from index depth.

## SQL Server / Azure Synapse notes

- T-SQL `MERGE` supports `WHEN MATCHED AND ... THEN DELETE` and `WHEN NOT MATCHED BY SOURCE`. Use
  `WITH (HOLDLOCK)` on the target to avoid race conditions, and remember MERGE must end with `;`.
- T-SQL has no data-modifying CTEs or `ON CONFLICT`. Use a temp table of winners and separate
  `DELETE` / `UPDATE` / `INSERT` statements in one transaction.
- Synapse dedicated pools: MERGE is supported on hash-distributed targets. For large batches,
  CTAS a new version of the affected distribution or partition and switch it in.
