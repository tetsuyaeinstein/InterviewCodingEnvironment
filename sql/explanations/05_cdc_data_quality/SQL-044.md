# SQL-044 · Source vs target reconciliation: explanation

## (a) FULL OUTER JOIN + IS DISTINCT FROM (`SQL-044.sql`)

1. `source_transactions s FULL OUTER JOIN target_transactions t ON t.transaction_id = s.transaction_id`
   keeps unmatched rows of both sides. `COALESCE(s.id, t.id)` is the reported key.
2. Presence flags: `s.transaction_id IS NULL` means extra in the target, and
   `t.transaction_id IS NULL` means missing in the target.
3. Per column, `CASE WHEN s.col IS DISTINCT FROM t.col THEN 'col' END`. `concat_ws(',', ...)`
   drops the NULLs, which yields the fixed-order list (`''` when nothing differs).
4. Keep rows that are one-sided or have a non-empty list.

| id | source | target | `<>` | `IS DISTINCT FROM` |
|---|---|---|---|---|
| 90010 | customer NULL | 1001 | NULL (row lost!) | true |
| 90011 | NULL | NULL | NULL | false (correct: equal) |
| 90013 | note `''` | NULL | NULL (row lost!) | true |
| 90014 | 12:14:00 | 12:14:01 | true | true |

`IS DISTINCT FROM` is the SQL-standard NULL-safe inequality. Plain `<>` hides 90010 and 90013,
and so do generated rows where `payment_method` was nulled. That is 19 rows in this data set.
`COALESCE(col, '')` "fixes" NULLs but makes `''` equal to NULL, so 90013 disappears.

## (b) Set difference first (`SQL-044_alt.sql`)

`(S EXCEPT T) UNION (T EXCEPT S)` over the business columns gives the keys whose row differs in
any way. Set operators compare rows with *not distinct* semantics (NULL equals NULL), so no
per-column predicate is needed to find the differences. Only those keys are joined back to
name the columns.

Trade-offs:

- EXCEPT is very concise for "is anything different?". It's the go-to for a quick check and works
  the same in SQL Server and Synapse.
- It sorts or hashes the full width of both tables, while the join version compares column by
  column after a key join. For wide tables both are dominated by I/O.
- Naming the columns still needs the join, so for a column-level report (a) is simpler.

## Complexity and plan

A hash full join on `transaction_id` (or a merge join if both sides are indexed and sorted). O(n)
with hashing. Memory is the hash table of the smaller side. With unique indexes on both keys,
a merge full join streams with almost no memory.

## Production considerations

- **Scale strategy:** reconcile in tiers. First counts and sums per partition (day/store), then
  row fingerprints per partition (SQL-045), and only then column-level diffs for the partitions
  whose fingerprint aggregate differs. Never full-join 500M × 500M rows across systems if you can
  compare 10,000 partition checksums.
- Decide tolerances explicitly (timestamp precision after a type migration, decimal scale) and
  encode them in the comparison, e.g. `date_trunc('second', ...)`.
- Persist the exception report with a run id. Reconciliation results are audit evidence.
- Separate **metadata** columns (`loaded_at`) from business columns in a config list so new
  columns are added consciously.

## SQL Server / Azure Synapse notes

- `IS [NOT] DISTINCT FROM` exists in SQL Server 2022+ and Azure SQL. Check support before you
  rely on it in a Synapse pool. On older versions:
  `NOT (a = b OR (a IS NULL AND b IS NULL))`, or the `EXISTS (SELECT a EXCEPT SELECT b)` idiom,
  which is NULL-safe.
- `CONCAT_WS` (SQL Server 2017+) also skips NULLs. `STRING_AGG(... ) WITHIN GROUP (ORDER BY ...)`
  is the T-SQL way to build ordered lists.
- `FULL OUTER JOIN` on distributed tables in Synapse dedicated pools: distribute both tables on
  `transaction_id` so the join is distribution-local (no shuffle).

## Follow-up questions

1. Both tables have 500M rows in different systems (Oracle source, Synapse target). Design a
   reconciliation that moves as little data as possible (partition-level checksums, then
   drill-down).
2. Allow a 1-second timestamp tolerance and a 0.01 amount tolerance. Where do they go, and what
   new false negatives can they cause?
3. How would you report duplicate keys if `transaction_id` were not unique in the target?
4. Turn this into a nightly data-quality check with thresholds (e.g. fail if > 0.1 % rows differ).
