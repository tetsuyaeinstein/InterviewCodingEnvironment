# SQL-050 · Safe committed watermark: explanation

## Approach (a): interval islands (`SQL-050.sql`)

1. Distinct `SUCCEEDED` windows per source. Duplicates from re-runs collapse.
2. `covered_until = MAX(window_end) OVER (PARTITION BY source ORDER BY window_start ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)`.
3. A window starting after `covered_until` (or the first window) opens a new island. A running
   `SUM` of those flags numbers the islands.
4. Safe watermark = `MAX(window_end)` of island 1, if island 1 starts at or before the history
   start. Otherwise NULL.
5. Join `pipeline_watermarks`, compare, and look up the latest attempt of the window starting at
   `COALESCE(safe, history_start)`.

| source | successful windows | first hole | safe | recorded | unsafe? | blocking window |
|---|---|---|---|---|---|---|
| POS | 00–01, 01–02 (×2), 02–03, 03–04 (retry), 04–05, 05–06 | 06:00 | 06:00 | 06:00 | no | 06–07 NOT_RUN |
| ECOM | 00–01, 02–03, 03–04 | 01:00 | 01:00 | 04:00 | **yes** | 01–02 FAILED |
| KIOSK | 00–01, 01–02, 03–04 | 02:00 | 02:00 | 02:00 | no | 02–03 RUNNING |
| MOBILE | none | 00:00 | NULL | 00:00 | no | 00–01 FAILED (2 attempts) |

The running maximum (rather than the previous row's end) makes the method robust to overlapping
and multi-hour windows: a long window that already covers later starts doesn't create false holes.

## Approach (b): recursive walk (`SQL-050_alt.sql`)

Start each source at 00:00 and repeatedly step to the `window_end` of a successful run with
`window_start = position`. `UNION` (not `UNION ALL`) removes duplicate steps from re-runs, which
keeps the recursion linear. `MAX(position)` is how far it got. `NULLIF(..., history_start)` turns
"no progress" into NULL.

Trade-offs: (b) reads like the business rule ("advance while the next hour succeeded") and stops
early, which is nice when history is long and the hole is near the start. But it assumes aligned
windows (exact `window_start = position` matches) and does one index probe per step. (a) is a
single sort plus window pass and handles arbitrary windows.

## Typical mistakes

- `MAX(window_end) WHERE status = 'SUCCEEDED'`: ECOM 04:00 and KIOSK 04:00, which is exactly the
  production bug.
- "First failure" logic that ignores retries: POS stops at 03:00 although 03–04 was retried
  successfully.
- Treating RUNNING as done (KIOSK would jump to 04:00).
- Returning 00:00 for MOBILE: it hides the difference between "nothing loaded" and "loaded up to
  the start". The contract asks for NULL, and `recorded_is_unsafe` compares against the start.

## Complexity and indexes

Tiny here. In general O(r log r) per pipeline for r runs. An index on
`pipeline_runs (pipeline_name, source_system, window_start, started_at DESC)` serves both the
island sort and the latest-attempt lookup.

## Production considerations

- The **watermark must be derived, not asserted**. Advance it in the same transaction as the
  load, and only to the end of the contiguous successful prefix. Better still, make the
  scheduler refuse to start window N+1's commit before window N committed (or allow out-of-order
  loads but publish only the contiguous prefix to consumers).
- Alert when `recorded_is_unsafe` is true, when the blocking window has been FAILED for longer
  than an SLA, or when a RUNNING attempt exceeds its timeout (zombie runs block forever).
- Downstream consumers should read the safe watermark, not the job's own one.
- Late data inside already-successful windows is a separate concern (overlap re-reads, SQL-042).

## SQL Server / Azure Synapse notes

- The same window functions exist (`MAX() OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)`).
- Recursive CTEs: T-SQL uses `WITH` (no `RECURSIVE` keyword) and allows only `UNION ALL` in the
  recursive part, so de-duplicate re-runs before recursing. `OPTION (MAXRECURSION n)` caps depth
  (default 100). Synapse dedicated pools do **not** support recursive CTEs, so use approach (a).
- In ADF, control tables like `pipeline_watermarks` live in Azure SQL. Update them from a stored
  procedure that applies this logic, not from the copy activity.

## Follow-up questions

1. Windows become variable-length and may overlap (backfills of 6 hours). Which approach still
   works, and why?
2. You run 10,000 pipelines × 24 windows/day for 2 years (~175M run rows). How do you compute
   safe watermarks cheaply every minute? (Incremental state: store the safe mark and only examine
   runs after it.)
3. Should a SUCCEEDED window that wrote 0 rows (while the source shows activity) count as covered?
   How would you detect it?
4. Design the alerting: which conditions page someone, and which only create a ticket?
