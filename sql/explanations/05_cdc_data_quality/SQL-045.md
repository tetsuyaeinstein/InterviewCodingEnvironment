# SQL-045 · Row fingerprints: explanation

## What makes a fingerprint correct

`fingerprint = H(encode(row))`. Hash collisions are a probability question. **Encoding
collisions** are a correctness bug that happens every time. The encoding must be:

1. **Injective**: different value tuples give different strings.
2. **Deterministic**: the same values give the same string in every session and system.
3. **Scoped**: business columns only, no keys and no load metadata.

| encoding | breaks on |
|---|---|
| `concat(a, b)` | `('AB','C')` = `('A','BC')`: 90015/90016-style |
| `a \|\| '\|' \|\| b` | NULL makes the whole string NULL, so the fingerprint is NULL |
| `coalesce(a,'') \|\| '\|' \|\| ...` | NULL = `''` (90013); `('X\|Y','')` = `('X','Y')` (90017/90018) |
| `coalesce(a,'NULL')` | NULL = the string `'NULL'` (90019/90020) |
| `concat_ws('\|', ...)` | skips NULLs: `(NULL,'X')` = `('X',NULL)`; `('X\|Y',NULL)` = `('X','Y')` |
| `row_to_json(t)` of the whole row | includes `extracted_at`/`loaded_at`, so identical rows never match across systems |

The grader proves these failures with synthetic rows. Its assertions shadow `source_transactions` /
`target_transactions` with CTEs holding pairs such as `('AB','C')` vs `('A','BC')`, then run your
query on them. That's why schema-qualified names are not allowed.

## (a) JSON array + sha256 (`SQL-045.sql`)

`jsonb_build_array(customer_id, store_id, <ts text>, <amount text>, status, payment_method, merchant_ref, note)::text`

- JSON string escaping makes delimiters inside values harmless: `["AB","C"]` vs `["A","BC"]`.
- SQL NULL becomes the JSON literal `null`, distinct from `""` and `"NULL"`. Integers stay
  unquoted, so NULL vs `0` is `null` vs `0`.
- Array position encodes the column, so moving a value to the neighbouring column changes the text.
- `encode(sha256(convert_to(txt, 'UTF8')), 'hex')`: `sha256()` is built into PostgreSQL 11+ and
  works on `bytea`, so pgcrypto is not needed.

`jsonb` canonicalises (key order, whitespace) and is stable across sessions for arrays of scalars.
Plain `json` would also work here, because the array is built in a fixed order.

## (b) Length-prefixed encoding + md5 (`SQL-045_alt.sql`)

Each value becomes `N` (NULL) or `V<len>:<value>`. Self-delimiting, so no escaping is needed:
`V2:ABV1:C` vs `V1:AV2:BC`. This is portable to any engine (`LEN`, `CONCAT`), which matters when
two different systems must produce byte-identical inputs.

## Type-formatting stability

- `timestamptz::text` is rendered in the **session `TimeZone`**. A source session in UTC and a
  target session in `America/New_York` would hash the same instant differently. Render
  explicitly: `to_char(ts AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US')`.
- `numeric` text keeps the value's scale: `10.0` and `10.00` are equal numbers but different
  strings. Cast to the declared type (`amount::numeric(12,2)`) or format with `to_char`.
- Floats: never hash a float's text form across systems. Round or cast to numeric first.
- Text: collation doesn't change bytes, but **Unicode normalisation** and trailing spaces
  (`char(n)` padding) do. Decide whether `'é'` composed vs decomposed is "the same".
- Encoding: hash bytes, so fix the character set (`convert_to(..., 'UTF8')`).

## md5 vs sha256, and collision risk

- md5 is 128 bits. The birthday bound for an *accidental* collision among n distinct rows is about
  n²/2¹²⁹: around 10⁻²¹ for 10⁹ rows. For comparing the same key across two systems it is plenty,
  and it's fast and compact (16 bytes as `bytea`, 32 as hex text).
- md5 is cryptographically broken: collisions can be *crafted*. If inputs are user-controlled and
  a collision could hide fraud, use sha256 (32 bytes).
- Store as `bytea` (`decode(..., 'hex')`) rather than hex text to halve the space. Or keep a 64-bit
  prefix if you only need a fast first-pass filter and verify matches column by column.

## Schema evolution

Adding a column changes every fingerprint, which looks like a full-table change. Options:

- Version the fingerprint definition (`fp_v2`) and recompute both sides in the same release.
- Append new columns at the end and **skip NULL trailing values**. The old fingerprint stays
  valid while the new column is NULL. That only works with a carefully designed encoding.
- Keep the column list in metadata so both systems generate the same expression.

## Complexity and plan

A single pass with per-row hashing. CPU-bound: sha256 costs a few hundred ns per row, md5 less.
At 500M rows, compute fingerprints at load time, store them in the table, and compare
`(key, fingerprint)` pairs, or aggregate them per partition (`sum` of a 64-bit prefix, or
`md5(string_agg(fp, '' ORDER BY key))`) for a partition-level first pass.

## SQL Server / Azure Synapse notes

- `HASHBYTES('SHA2_256', @input)` returns `varbinary(32)`. The input limit was 8,000 bytes before
  SQL Server 2016.
- `CONCAT` treats NULL as `''`, the same trap as `coalesce(...,'')`. `CONCAT_WS` skips NULLs. Use
  explicit markers or `FOR JSON PATH, INCLUDE_NULL_VALUES`, or `ISNULL(QUOTENAME(col,''''), 'N')`
  style escaping.
- `CHECKSUM` / `BINARY_CHECKSUM` are 32-bit and collide easily, so never use them for change
  detection at scale.
- Datetime to string in T-SQL: `CONVERT(varchar(33), ts, 126)` (ISO 8601) gives stable output.
