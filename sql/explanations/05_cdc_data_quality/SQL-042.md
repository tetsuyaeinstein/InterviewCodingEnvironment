# SQL-042 · Watermark with overlap: explanation

## Approach

1. A one-row CTE turns configuration into bounds:
   `read_from = watermark_ts - interval '10 minutes'`, `read_to = '2025-12-15 07:00 UTC'`.
2. Select `source_system = 'POS'` rows with `ingested_at >= read_from AND ingested_at < read_to`.
3. `is_overlap_reread = ingested_at < watermark_ts`.

With W = 06:00 (customer 64 fixtures, all ingested on 2025-12-15):

| txn | ingested_at | result |
|---|---|---|
| 6401 | 05:49:59 | excluded (before the overlap) |
| 6402 | 05:50:00 | included, overlap (lower bound is inclusive) |
| 6403 | 05:59:59 | included, overlap |
| 6404 | 06:00:00 | included, **new** (the previous run's upper bound was exclusive) |
| 6405 | 06:30:00 | included |
| 6406 | 07:00:00 | excluded (belongs to the next run) |

One generated row (119938, 06:00:49) is also selected.

## Why an overlap at all?

A watermark on arrival time assumes that once the job has seen time T, no row with
`ingested_at < T` can appear later. That is false in practice:

- **In-flight transactions:** `ingested_at` is set when the writer *starts* its insert, but the
  row becomes visible only at commit. A long transaction that commits after the extract ran is
  missed forever.
- **Clock skew** between ingestion hosts and the database (see the negative delays in
  `event_ingestion_log`).
- **Replica lag** when extracting from a read replica.

Re-reading a window larger than the worst expected delay closes that gap. The cost is duplicates,
which the load must absorb: an **idempotent upsert keyed on the business key** with a version
guard (`ON CONFLICT ... DO UPDATE ... WHERE excluded.version > target.version`, SQL-046) or a
`MERGE`. Re-applying the same row is then a no-op.

## Typical mistakes

- `ingested_at > watermark` (no overlap): loses 6402/6403, which may have been invisible last time.
- `BETWEEN` on both ends: 6406 is processed by this run *and* the next one. Inclusive upper
  bounds also make the overlap flag ambiguous (6404 counted as re-read).
- Filtering by `transaction_ts`: a sale from 05:00 that lands at 06:30 is never extracted, because
  late data is exactly what a business-time watermark misses (SQL-043).
- Hard-coding the watermark makes the job non-restartable. Read it from the control table, and
  update it in the **same transaction** that commits the load.

## Plan and indexes

A B-tree on `transactions (source_system, ingested_at)`, or `(ingested_at)` plus a filter, turns
this into a narrow index range scan. Without it every hourly run scans the whole fact. At scale,
partition the landing table by ingestion date so old partitions are pruned.

## Production considerations

- Size the overlap from data: monitor `max(visible_at - ingested_at)` and alert when it nears the
  overlap length.
- Commit protocol: load rows, then advance the watermark to `read_to` (not `max(ingested_at)`
  seen) in the same transaction. If the run fails, the watermark doesn't move and the window is
  retried (SQL-050).
- Even better: a CDC log position (LSN/offset) instead of a timestamp. Offsets are gap-free by
  construction.

## SQL Server / Azure Synapse notes

- `DATEADD(minute, -10, watermark_ts)` instead of `- interval '10 minutes'`. Use `datetime2` or
  `datetimeoffset`, never `datetime` (3.33 ms rounding breaks exact boundaries).
- SQL Server rowversion / Change Tracking / CDC give a monotonic, commit-ordered position. Prefer
  them to wall-clock watermarks.
- Synapse/ADF: the "high watermark" copy pattern is identical. Keep the control table in a
  transactional store (SQL DB), not in the lake.
