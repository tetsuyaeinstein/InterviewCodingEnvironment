# SQL-049 · CDC sequence anomalies: explanation

## Approach

Each rule is a self-join (or anti-join) of the event log on the key, producing candidate rows
`(event, priority, issue, related)`. A final `DISTINCT ON (cdc_event_id) ORDER BY cdc_event_id,
priority` keeps the highest-precedence issue.

| rule | predicate on the other event `o` | related |
|---|---|---|
| LSN_CONFLICT | same LSN, `o.id <> e.id`, `(op, payload) IS DISTINCT FROM` | `min(o.id)` |
| DUPLICATE_DELIVERY | same LSN, `o.id < e.id`, same op and payload | `min(o.id)` (first copy) |
| STALE_ARRIVAL | `o.id < e.id AND o.lsn > e.lsn` | `min(o.id)` (first newer arrival) |
| ORPHAN_CHANGE | `NOT EXISTS` an `I` with lower LSN, for U/D | NULL |
| COMMIT_TS_TIE | same commit_ts, different LSN | `min(o.id)` |

Result on this log (10 rows):

| event | key | issue | related | note |
|---|---|---|---|---|
| 3774 | FX-0001 | STALE_ARRIVAL | 3773 | lsn 9000020 arrived after 9000030 |
| 3778 | FX-0002 | STALE_ARRIVAL | 3777 | update arrived after the delete |
| 3784 | FX-0004 | DUPLICATE_DELIVERY | 3783 | the first copy 3783 is clean |
| 3786 | FX-0005 | COMMIT_TS_TIE | 3787 | |
| 3787 | FX-0005 | STALE_ARRIVAL | 3786 | precedence over its tie |
| 3789 / 3790 | FX-0006 | LSN_CONFLICT | each other | both versions flagged |
| 3791 | FX-0007 | ORPHAN_CHANGE | NULL | delete without insert |
| 3793 | FX-0008 | STALE_ARRIVAL | 3792 | insert after its own update |
| 1667 | POS-000601 | STALE_ARRIVAL | 1660 | generated: a 1h34m ingestion delay |

Clean: FX-0003 (I, D, I is legitimate: the re-insert has an `I` with a lower LSN *and* arrives in
order), FX-0010, and ECOM FX-0001 (its LSNs collide numerically with POS FX-0001, but they are a
different key).

## Why the subtle parts matter

- **Strictly higher LSN** for staleness: with `>=`, the duplicate 3784 and the conflict 3790 would
  also be "stale". Precedence would hide it here, but the definition would be wrong.
- **LAG-based staleness** (compare with the previous arrival only) misses events that are stale
  relative to an *earlier* arrival that isn't the immediate predecessor. Use the running max:
  `MAX(source_lsn) OVER (PARTITION BY key ORDER BY cdc_event_id ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) > source_lsn`.
  That is the efficient single-pass alternative to the self-join. The related id then needs a
  second step.
- **`COUNT(*) > 1` per LSN** can't separate duplicates from conflicts. Compare versions.
- **Arrival order by `ingested_at`** is ambiguous on ties (two in this log). The contract says
  `cdc_event_id`.

## Complexity and plan

The self-joins are per key and the groups are tiny (≤ ~10 events per key), so with the
`(source_system, business_key, source_lsn)` index or a hash join on the key the cost is near
linear. A pathological key with millions of events would make the inequality joins quadratic. In
that case use window functions (running max for staleness, `COUNT(DISTINCT ...)` per LSN for
conflicts), which are O(n log n).

## Production considerations

- Run it as a **continuous monitor**: per micro-batch, compare new events with per-key state
  (max LSN seen, set of (LSN, payload hash) for a retention window). Emit metrics such as the
  stale-arrival rate, duplicate rate and conflict count, and alert on conflicts and orphans
  (they mean data loss or a source bug). Stale arrivals and duplicates are expected and should be
  handled by the apply logic (SQL-046/047).
- Store a payload hash (SQL-045) rather than comparing full jsonb documents.
- ORPHAN_CHANGE for a key that started before the CDC snapshot is normal. Exclude keys present in
  the initial snapshot.

## SQL Server / Azure Synapse notes

- No `DISTINCT ON`: use `ROW_NUMBER() OVER (PARTITION BY cdc_event_id ORDER BY prio)`.
- No jsonb equality: compare a normalised JSON string or `HASHBYTES('SHA2_256', payload)`.
  Logically equal JSON with different key order then compares as different, so normalise at
  ingestion.
- Row-value `IS DISTINCT FROM` does not exist. Write
  `NOT (o.op = e.op AND o.payload_hash = e.payload_hash)` with NULL handling.
