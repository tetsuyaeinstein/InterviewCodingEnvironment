# SQL-003 · Customers inactive in the last 90 days: explanation

## Defining the window first

"The 90 days ending on 2025-12-31" contains exactly 90 dates: 2025-10-03 … 2025-12-31.

| expression | value | window length |
|---|---|---|
| `DATE '2025-12-31' - 89` | 2025-10-03 | 90 dates ✓ |
| `DATE '2025-12-31' - 90` | 2025-10-02 | 91 dates ✗ |

As timestamps: `[2025-10-03 00:00:00 UTC, 2026-01-01 00:00:00 UTC)`. Nearly every off-by-one
in retention reporting comes from mixing up "N days ago" and "a window of N days".

## (a) One aggregation pass (`SQL-003.sql`)

Start from `customers`, `LEFT JOIN` completed transactions up to the end of the window (the
conditions are in `ON`), and compute per customer:

- `MAX(transaction_ts)`: the last completed purchase (NULL when there is none);
- `COUNT(*) FILTER (WHERE transaction_ts >= window_start)`: purchases inside the window.

Keep customers whose in-window count is 0. One scan, one hash aggregate.

## (b) `NOT EXISTS` + correlated `MAX` (`SQL-003_alt.sql`)

`WHERE NOT EXISTS (completed purchase in window)` states the rule literally, and PostgreSQL plans
it as a **hash anti-join**. The last purchase date is a correlated scalar subquery evaluated
only for the customers that survive. It is clear and efficient when the audience is small relative
to the customer base; the subquery becomes an index probe per inactive customer.

Avoid `customer_id NOT IN (SELECT customer_id FROM transactions ...)`. If the subquery can produce
a NULL (guest checkouts!), `NOT IN` yields NULL for every row and the audience is empty.

## Edge cases and fixtures

| fixture | data | outcome |
|---|---|---|
| 1, 32 | no transactions | in audience, last date NULL |
| 33 | only CANCELLED | in audience, last date NULL (not 2025-05-05) |
| 34 | completed at exactly **2025-10-03 00:00:00** | active → excluded (`>` instead of `>=` includes them) |
| 35 | completed at **2025-10-02 23:59:59** | inactive → included, last date 2025-10-02 (`anchor - 90` excludes them) |
| 36 | completed 06-01, PENDING 12-20 | inactive → included, last date 2025-06-01 |
| 26 | completed on 10-05 | active → excluded |

## Complexity and indexes

- (a): one sequential scan of completed transactions + a hash aggregate per customer, O(T + C).
- (b): hash anti-join over in-window transactions (a 90-day slice, so the range index on
  `transaction_ts` helps), plus one probe on `transactions(customer_id)` per inactive customer for
  the last date.
- A composite `(customer_id, transaction_ts) WHERE transaction_status = 'COMPLETED'` index turns
  the last-date lookup into a single backward index step (`LIMIT 1`-like), and the existence
  test into one index range probe. The lab deliberately does not ship that index.

## Production considerations

- Never use `now()` in a scheduled job. Pass the anchor date as a parameter so reruns and
  backfills are reproducible.
- Maintain `last_purchase_ts` per customer incrementally (it only moves forward, except when a
  purchase is cancelled or reversed: decide how you handle that). Inactivity then becomes a
  cheap filter on a 20M-row table instead of a scan of 500M facts.
- Late-arriving purchases can move a customer out of the audience after the campaign list has been
  built. Snapshot the audience with the data watermark used.

## SQL Server / Azure Synapse notes

- `DATEADD(day, -89, @anchor)` builds the inclusive start. `DATEDIFF(day, x, @anchor) < 90` is
  correct but not sargable.
- `NOT EXISTS` produces an anti semi join in SQL Server too. `NOT IN` has the same NULL trap.
- In Synapse, a per-customer "last activity" table distributed on `customer_id` replicates well
  into marketing marts.
