# SQL-009 · Average transaction value by segment: explanation

## Approach

Two-step aggregation through the customer grain:

1. `customers LEFT JOIN transactions` with every transaction condition (status and 2025 range)
   in the `ON` clause, grouped per customer:
   `COUNT(t.transaction_id)` (0 for non-buyers) and `COALESCE(SUM(t.gross_amount), 0)`.
2. Group those rows by segment:
   - `customers = COUNT(*)`, `customers_without_purchases = COUNT(*) FILTER (WHERE completed_txns = 0)`
   - `avg_txn_value = ROUND(SUM(amount) / NULLIF(SUM(txns), 0), 2)` → NULL when undefined
   - `avg_spend_per_customer = ROUND(SUM(amount) / COUNT(*), 2)` → 0.00 when nobody bought

## Which average?

Illustration from the question (customers 1, 2, 3; purchases 10 + 20, 90, none):

| metric | formula | value |
|---|---|---|
| average transaction value (asked) | 120 / 3 transactions | 40.00 |
| average of per-customer averages | (15 + 90) / 2 | 52.50 |
| average spend per customer (asked) | 120 / 3 customers | 40.00 |
| average spend per **buying** customer | 120 / 2 | 60.00 |

All four are legitimate metrics with different meanings. In the real data the difference is
driven by heavy accounts such as ENTERPRISE customer 1001, which has many transactions: averaging
per-customer averages under-weights them.

## Division by zero and NULL policy

| PILOT (customers 32 and 33) | value | reason |
|---|---|---|
| customers | 2 | both exist |
| customers_without_purchases | 2 | 33 only has a CANCELLED 45.00 |
| completed_txn_count | 0 | `COUNT(t.transaction_id)`, not `COUNT(*)` (which gives 1 per customer) |
| total_completed_amount | 0.00 | `COALESCE` |
| avg_txn_value | **NULL** | 0 / 0 is undefined. `NULLIF(denominator, 0)` avoids the error, and showing 0.00 would claim "baskets are worth nothing" |
| avg_spend_per_customer | **0.00** | 0 / 2 is a real zero |

`AVG(t.gross_amount)` on the outer join would also give the right `avg_txn_value` (AVG ignores
NULLs and returns NULL for no input), but computing averages from totals makes the denominator
explicit and lets you roll up further correctly (averages are not additive; sums and counts are).

## Complexity and indexes

- One scan of 2025 completed transactions, a hash aggregate per customer (C entries), then a
  4-group aggregate: O(T + C).
- You can skip the customer-grain step by aggregating transactions per segment and joining
  customer counts per segment separately. That is two smaller aggregates and a 4-row join, which is
  attractive at scale.

## Production considerations

- **Current vs historical segment:** `customers.segment` is today's value. A customer who moved
  from CONSUMER to SMALL_BUSINESS in October has all 2025 spend under the new segment. For target
  setting that is often acceptable; for historical reporting join `dim_customer_scd2` on the
  transaction timestamp (point-in-time).
- Store **sums and counts** in aggregates, never averages: they roll up correctly across time and
  dimensions.
- A segment with zero buyers is usually a pipeline smell (new segment, broken mapping). Alert on it.

## SQL Server / Azure Synapse notes

- Integer division: in T-SQL, `SUM(int_col) / COUNT(*)` truncates. Here the amount is decimal, but
  cast explicitly (`CAST(... AS decimal(18,4))`) when both operands are integers.
- `NULLIF` works the same. `ROUND(x, 2)` in T-SQL keeps the scale (it returns `x.xx00`). Use
  `CAST(... AS decimal(12,2))` to change the type.
- No `FILTER`: `SUM(CASE WHEN completed_txns = 0 THEN 1 ELSE 0 END)`.
