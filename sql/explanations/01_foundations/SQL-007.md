# SQL-007 · Orphan and broken staging lines: explanation

## Approach

For each staging row you need two facts: does the transaction exist, and does the product exist?
Both lookups use the parent's **primary key**, so each returns at most one match: an outer join
cannot multiply staging rows, and every row of the staging table is evaluated exactly once
(including exact duplicates).

### (a) Two LEFT JOINs + CASE (`SQL-007.sql`)

`stg LEFT JOIN transactions LEFT JOIN products`, keep rows where either parent did not match, and
classify. The `CASE` **must test the NULL keys first**: a NULL key also produces "no match", and
without the explicit test it gets labelled `MISSING_TRANSACTION` / `MISSING_PRODUCT`.

### (b) EXISTS flags (`SQL-007_alt.sql`)

Compute `txn_exists` and `product_exists` with `EXISTS (...)` subqueries (PostgreSQL turns these
into hashed or index-probe semi-joins), then classify. `EXISTS` is always TRUE or FALSE, never
NULL, so the logic is easy to reason about. It's also the natural shape when the check list grows
(one flag per rule) and when you want to persist the flags to a DQ results table.

## The `NOT IN` trap

`WHERE s.transaction_id NOT IN (SELECT transaction_id FROM transactions)`:

| staged value | `NOT IN` result | row kept? |
|---|---|---|
| 99999999 | TRUE | yes |
| 2301 | FALSE | no |
| NULL | **NULL** (unknown) | **no**: the NULL-key row disappears silently |

And if the *subquery* side could contain a NULL, `NOT IN` returns no rows at all. For data quality
checks, silently passing bad rows is the worst failure mode.

| NULL | NULL | 4 | NULL_TRANSACTION_ID |

Not reported: 2401 line 1 (valid, loaded **twice**: a uniqueness violation on
`(transaction_id, line_number)`, which is a separate rule), 2302 line 1 (valid), all of batch 2.

## Complexity and indexes

- Both parents are probed by PK. For a 20M-line batch the planner picks hash joins: it builds a
  hash on the *smaller* side (or on the distinct staged keys) and streams the rest. For small
  batches it does index nested loops.
- Hashing 500M transaction ids to check 20M staged lines is wasteful. Better: semi-join against
  only the relevant key range (staged lines usually reference recent transactions), or check the
  **distinct** staged keys first, then join the result back.

## Production considerations

- Run the gate **before** the merge, and write results to a DQ table
  `(batch_id, rule, row_ref, issue, detected_at)` so trends are visible.
- Decide the policy per rule: quarantine the row, the whole transaction (a header without all its
  lines is worse than a missing header), or fail the batch above a threshold.
- **Late-arriving parents:** a line can legitimately land before its header (different feeds).
  Treat `MISSING_TRANSACTION` as "retry for N hours" before it becomes a hard error.
  `NULL_TRANSACTION_ID` never resolves itself.
- Staging has no constraints on purpose (bulk loads must not fail on one bad row). The
  warehouse fact *should* enforce PK/FK, or at least validate them, as in this query.

## SQL Server / Azure Synapse notes

- Identical SQL works in T-SQL (`LEFT JOIN`, `EXISTS`, `CASE`). `NOT IN` has the same NULL semantics.
- Synapse dedicated pools do **not enforce** foreign keys (and PK/UNIQUE only with `NOT ENFORCED`),
  so this kind of query is the only referential integrity you get. Run it as part of every load.
- Distribute staging on `transaction_id` matching the fact so the transaction check is local.
  Replicate `products` (small dimension).
