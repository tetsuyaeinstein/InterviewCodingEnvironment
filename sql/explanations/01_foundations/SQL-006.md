# SQL-006 · Store status mix (conditional aggregation): explanation

## Approach

Pivoting a small, fixed set of values into columns is **conditional aggregation**: one
`GROUP BY store_id`, and each output column is an aggregate that only "sees" its status.

```text
COUNT(*)          FILTER (WHERE transaction_status = 'PENDING')   -> 0 when none
SUM(gross_amount) FILTER (WHERE transaction_status = 'PENDING')   -> NULL when none -> COALESCE(..., 0.00)
```

The table is read once. Writing one subquery or self-join per status reads it four times and
is a red flag in an interview.

## NULL vs 0

| expression over zero matching rows | result |
|---|---|
| `COUNT(*) FILTER (...)` | 0 |
| `SUM(x) FILTER (...)` | NULL |
| `SUM(CASE WHEN ... THEN x ELSE 0 END)` | 0 (because every row contributes 0) |
| `SUM(CASE WHEN ... THEN x END)` | NULL |

Store 5 has no pending transactions: `pending_amount` must be 0.00, not NULL. A dashboard showing
an empty cell or treating NULL as "unknown" is a different message from "zero".

## DECLINED policy

A declined payment never moved money, so its `gross_amount` is the attempted amount, not
revenue or exposure. The contract counts declines (useful as a payment-health signal), includes
them in `total_txn_count`, and keeps them out of every amount. Folding them into "cancelled" is a
common mistake: store 4 would show 4 cancelled / 120.00 instead of 3 / 95.00.

## Edge cases and fixtures

| store | expected |
|---|---|
| 4 | total 17 = 11 completed (275.00) + 2 pending (50.00) + 3 cancelled (95.00, incl. customer 33's 45.00) + 1 declined |
| 5 | total 7 = 6 completed (406.50) + 0 pending (0.00) + 1 cancelled (300.00) + 0 declined |
| all | `total = completed + pending + cancelled + declined` (an invariant worth asserting) |

The 2025 filter matters: without it, the generated stores pick up all of 2024.

## Complexity and indexes

- One scan of the 2025 slice plus a hash aggregate with one entry per store: O(n) time, O(stores)
  memory. All `FILTER` aggregates are evaluated in the same pass.
- A range-partitioned fact prunes to 2025. A covering index rarely beats a sequential scan when you
  read a full year of a two-year table.

## Production considerations

- Status is **mutable** (PENDING becomes COMPLETED or CANCELLED). A report run on Jan 2 will
  differ from one run on Jan 20. State "as of" with the data watermark, or snapshot statuses daily.
- New statuses appear over time (e.g. `REFUNDED`, `CHARGEBACK`). A hard-coded pivot silently
  ignores them, so add an `other_count` column or a data-quality check:
  `total = sum of known buckets`.
- For many or dynamic categories, do not pivot in SQL. Return long format (store, status, count,
  amount) and pivot in the BI tool.

## SQL Server / Azure Synapse notes

- No `FILTER` clause in T-SQL: use `SUM(CASE WHEN transaction_status = 'PENDING' THEN gross_amount ELSE 0 END)`
  and `COUNT(CASE WHEN ... THEN 1 END)`. T-SQL also has `PIVOT`, but it supports only one aggregate
  per pivot, so you would need two pivots (count and sum) plus a join. Conditional aggregation is
  clearer.
- Synapse: on a clustered columnstore this is a single scan with batch-mode hash aggregation.
  Distribution on `store_id` makes it local, but watch skew from the online flagship.
