# SQL-010 · Bought A but never B: explanation

## Approach

Define **one** set of in-scope purchase lines: completed, known customer, UTC date in
`[2025-01-01, 2025-07-01)`, product 1 or 2. Then: customers with an A line in that set, minus
customers with a B line in that set. Most mistakes apply different rules to A and B.

### (a) Semi-join + `NOT EXISTS` anti-join (`SQL-010.sql`)

`SELECT DISTINCT customer_id FROM purchases a WHERE product_id = 1 AND NOT EXISTS (B line for the same customer)`.
PostgreSQL plans `NOT EXISTS` as a **hash anti-join**. `DISTINCT` is needed because a customer
can have several A lines.

### (b) One pass with boolean aggregates (`SQL-010_alt.sql`)

`GROUP BY customer_id HAVING BOOL_OR(product_id = 1) AND NOT BOOL_OR(product_id = 2)`. One scan
of the in-scope lines, one hash aggregate, no second probe. It generalises nicely: "bought A and
C but not B or D" is just more boolean aggregates. (Portable spelling:
`SUM(CASE WHEN product_id = 2 THEN 1 ELSE 0 END) = 0`.)

### Other correct shapes worth naming

- `SELECT customer_id ... A EXCEPT SELECT customer_id ... B`: set semantics (`EXCEPT` also removes
  duplicates), NULL-safe (`EXCEPT` treats NULLs as equal), very readable.
- `LEFT JOIN b_buyers USING (customer_id) WHERE b_buyers.customer_id IS NULL`: the classic anti-join.

## The `NOT IN` trap (fixture-proven)

```text
WHERE customer_id NOT IN (SELECT customer_id FROM <B purchases>)
```

One guest checkout (customer NULL) bought B in the period. The subquery therefore contains a NULL,
so `x NOT IN (..., NULL)` is never TRUE, and the query returns **zero rows**. Adding
`WHERE customer_id IS NOT NULL` in the subquery fixes it, but `NOT EXISTS` doesn't need the
reminder.

## Edge cases and fixtures

| customer | data | outcome |
|---|---|---|
| 28 | A completed; B only in a CANCELLED transaction | qualifies |
| 29 | A and B in the **same** transaction | excluded (checking B only in *other* transactions, or only in the same one, is wrong) |
| 30 | A in March; B on 2025-08-01 | qualifies (B is outside the period) |
| 31 | A only in a CANCELLED transaction | excluded (A must be a purchase too) |
| generated 2146, 2339 | B bought in 2024, A in the period | qualify under this contract ("never in the period") |
| generated 2600 | B before **and** in the period | excluded |

## Complexity and indexes

- Both shapes scan the in-period completed transactions and probe or join lines for products 1
  and 2. The `transaction_items(product_id)` index makes "lines of product 1 or 2" cheap; then join
  to transactions by PK and filter status and date.
- (a) does an anti-join over a small B set (hash). (b) does a single aggregate. At scale the
  difference is small. Choose for readability, and prefer (b) when there are several conditions.

## Production considerations

- Marketing audiences must be reproducible: fix the period and the data watermark, store the
  audience with the parameters used.
- "Never" usually means "not in the lookback period". Write the period into the column or table
  name so that nobody reads it as "never ever".
- Consider refunds: a customer who bought B and returned it may still be a good target. That is a
  product decision, so make it explicit.

## SQL Server / Azure Synapse notes

- `NOT EXISTS` → anti semi join in SQL Server. `EXCEPT` exists in T-SQL. `BOOL_OR` doesn't: use
  `MAX(CASE WHEN product_id = 1 THEN 1 ELSE 0 END) = 1`.
- Synapse: if lines are distributed on `transaction_id` and the audience is per customer, the
  aggregate needs a shuffle on `customer_id`. Pre-filtering to products 1 and 2 before the
  shuffle keeps data movement tiny.
