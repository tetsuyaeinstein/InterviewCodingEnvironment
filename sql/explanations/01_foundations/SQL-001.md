# SQL-001 · Lifetime completed spend per customer: explanation

## Approach

The output grain is **one row per customer**, so `customers` drives the query and transactions
are attached with an outer join. Two things go wrong in almost every first attempt:

1. **The filter moves into `WHERE`.** `LEFT JOIN transactions t ... WHERE t.transaction_status = 'COMPLETED'`
   discards the NULL-extended rows of customers without a match, so the outer join silently
   becomes an inner join. Customers 1, 32 and 33 vanish.
2. **The aggregates on the outer join are wrong for non-matches.** For a customer with no match,
   the join produces one row whose transaction columns are all NULL:

   | expression | value for customer 1 | why |
   |---|---|---|
   | `COUNT(*)` | 1 | counts the customer row itself |
   | `COUNT(t.transaction_id)` | 0 | NULLs are not counted |
   | `SUM(t.gross_amount)` | NULL | sum of no values is NULL |
   | `COALESCE(SUM(...), 0.00)` | 0.00 | what the contract wants |

### (a) Pre-aggregate, then LEFT JOIN (`SQL-001.sql`)

Aggregate completed transactions to customer grain in a CTE, then `customers LEFT JOIN` that CTE
and `COALESCE` both columns. The join is 1:1, so no fan-out is possible, and the status filter
lives inside the CTE where it cannot damage the outer join.

### (b) `CROSS JOIN LATERAL` per customer (`SQL-001_alt.sql`)

An aggregate **without** `GROUP BY` always returns exactly one row: `COUNT(*) = 0` and
`SUM = NULL` over an empty set. Running that aggregate per customer through `LATERAL` therefore
keeps every customer, even with a `CROSS JOIN`. It reads as "for each customer, compute ...",
and with an index on `transactions(customer_id)` it becomes a nested loop of index probes.

## Edge cases and fixtures

| fixture | situation | correct output |
|---|---|---|
| customer 1 | no transactions | 0, 0.00 |
| customer 32 | PILOT, no transactions | 0, 0.00 |
| customer 33 | only a CANCELLED 45.00 | 0, 0.00 (a `CASE`-inside-`SUM` without a status filter gives count 1) |
| customer 23 | 100.00 + 40.00, with refunds | 2, 140.00 (refunds are not part of this metric) |
| customer 26 | 30 + 10 + 20 completed, 99.00 PENDING | 3, 60.00 |
| customer 22 | PENDING then two completed | 2, 50.00 |
| guests 9801/9802 | `customer_id IS NULL` | no row (they cannot match a customer) |

## Complexity, plans and indexes

- (a) is one scan of `transactions` + a hash aggregate (one entry per buying customer) + a hash
  right join against `customers`. O(T + C) time, O(C) memory. This is the right plan for a
  full snapshot.
- (b) is C index probes. Excellent for a handful of customers (an API call), poor for all
  customers on a 500M-row table: random I/O per customer instead of one sequential scan.
  PostgreSQL does not decorrelate `LATERAL` aggregates into a hash join for you.
- A partial covering index `ON transactions (customer_id) INCLUDE (gross_amount) WHERE transaction_status = 'COMPLETED'`
  enables an index-only scan for both shapes.

## Production considerations

- This is a classic **snapshot attribute**. Rather than re-aggregating 500M rows nightly, keep a
  customer-level aggregate table and maintain it incrementally from new or changed transactions
  (`INSERT ... ON CONFLICT DO UPDATE SET total = total + EXCLUDED.delta`). Status changes
  (PENDING → COMPLETED, COMPLETED → refunded) mean you need the change *delta*, not just new rows.
- Reconcile: `SUM(total_completed_spend)` must equal the completed total of non-guest
  transactions; the row count must equal `count(*) FROM customers`.
- The 0 vs NULL policy is a contract with the consumer. Document it in the schema.

## SQL Server / Azure Synapse notes

- `COALESCE` and `ISNULL` both work. `ISNULL` takes the type of the first argument, which can
  truncate. Prefer `COALESCE`.
- `LATERAL` is `OUTER APPLY` / `CROSS APPLY` in T-SQL. Synapse dedicated pools support `APPLY`
  only in limited forms, so use the pre-aggregation pattern there.
- In Synapse, distribute `transactions` and the customer aggregate on `customer_id` (HASH). The
  join is then distribution-local, with no data movement (`ShuffleMove`) in the plan.
