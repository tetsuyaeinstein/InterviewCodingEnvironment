# SQL-004 · Classifying duplicates in an at-least-once feed: explanation

## The concepts the interviewer is really testing

**At-least-once delivery.** A broker (Kafka, Service Bus, SQS, Event Hubs) guarantees each message
arrives *at least* once. If the consumer crashes after processing but before acknowledging, the
message is delivered again. So **duplicates are normal**, not an incident.

**Three identities, three grains.**

| identifier | identifies | repeats when |
|---|---|---|
| `delivery_id` | one physical arrival | never (landing-table surrogate) |
| `message_id` | one logical message from the producer | the broker redelivers |
| `transaction_id` | the business entity | the entity has several events, or the producer double-posts |

**Idempotent consumer.** Processing the same message twice must have the same effect as
processing it once. The standard technique is a **dedup key**: record processed `message_id`s
(or upsert on them) and skip repeats. That removes transport duplicates, *and only those*:

- A double-posted CREATED has a **new** `message_id`, so the message-level dedup lets it through.
  Catching it requires a **business-key** rule (one CREATED per `transaction_id`), e.g. a unique
  constraint on the target, or `ON CONFLICT (transaction_id) DO NOTHING`.
- A STATUS_CHANGED is not a duplicate at all. It must be applied in order (by source sequence or
  event time) as an update.
- A conflicting double-post cannot be resolved by the consumer. Quarantine it and raise it with
  the producer.

## (a) One aggregation pass (`SQL-004.sql`)

Group by `transaction_id`, keep `HAVING COUNT(*) > 1`, and compute:

| metric | expression | trap |
|---|---|---|
| deliveries | `COUNT(*)` | |
| distinct_messages | `COUNT(DISTINCT message_id)` | |
| created_messages | `COUNT(DISTINCT message_id) FILTER (WHERE event_type = 'CREATED')` | `COUNT(*) FILTER ...` counts **deliveries**: 2301 would show 3 creations and become a business-key duplicate |
| status_change_messages | same, for STATUS_CHANGED | |
| created payload versions | `COUNT(DISTINCT payload) FILTER (WHERE event_type = 'CREATED')` | comparing *all* payloads flags every lifecycle key (2302) as a conflict |
| has_redelivery | `deliveries > distinct_messages` | |

The `CASE` lists the rules from most to least severe, so the first match wins. `jsonb` equality is
semantic: `{"a":1,"b":2}` equals `{"b":2,"a":1}`, so `COUNT(DISTINCT jsonb)` compares values, not
text. (With `json` or text you would compare formatting, which is a classic false positive.)

## (b) Dedup to messages first, pairwise conflict test (`SQL-004_alt.sql`)

1. `DISTINCT ON (message_id) ... ORDER BY message_id, delivery_id`: exactly what an idempotent
   consumer keeps (the first delivery of each message).
2. Aggregate the messages per key.
3. Find conflicts with a self-join of CREATED messages of the same key whose payloads are
   `IS DISTINCT FROM` each other.

It is longer, but it mirrors the production pipeline step by step, and the self-join variant can
easily report **which fields** differ (compare `payload->>'amount'` etc.), which the producing
team will ask for. Its cost is a sort for `DISTINCT ON` and a self-join that is quadratic per key
(harmless here: 2–3 messages per key).

## Complexity and indexes

- One hash aggregate over the feed. `COUNT(DISTINCT ...)` forces a sort per group in PostgreSQL
  (it can't hash distinct aggregates), so for big inputs it is cheaper to pre-aggregate at
  `(transaction_id, message_id, event_type)` grain first and then count rows.
- The `raw_transaction_events(transaction_id)` index doesn't help a full-table report. It helps
  the per-key lookup of a streaming consumer.

## Production considerations

- **Where to dedup:** at the landing → staging boundary, on `message_id`, with a bounded
  lookback window (redeliveries arrive within minutes or hours, not months). Keep the raw landing
  table immutable for replay and audit.
- **Business-key enforcement** belongs in the target model (unique `transaction_id` in the fact,
  `MERGE`/upsert). It must decide deterministically which version wins. "Latest delivered_at"
  is *not* deterministic across replays; a producer sequence number or event timestamp is.
- **Conflicts** go to a quarantine table with an alert. Silently picking one is how finance
  numbers drift.
- Metrics to monitor: redelivery rate (`deliveries / messages`), double-post rate, conflict
  count. A spike in redeliveries usually means consumer timeouts or rebalancing.

## SQL Server / Azure Synapse notes

- No `FILTER` clause: use `COUNT(DISTINCT CASE WHEN event_type = 'CREATED' THEN message_id END)`.
- No native JSON type: payloads are `nvarchar(max)`, so text comparison is sensitive to key order
  and whitespace. Compare extracted fields (`JSON_VALUE(payload, '$.amount')`) or a canonicalised
  hash (`HASHBYTES('SHA2_256', ...)` over the normalised fields).
- No `DISTINCT ON`: use `ROW_NUMBER() OVER (PARTITION BY message_id ORDER BY delivery_id) = 1`.
- Synapse dedicated pools: `COUNT(DISTINCT)` over a HASH(transaction_id)-distributed table is
  distribution-local. Fabric/Spark: `dropDuplicates(["message_id"])` with a watermark for streaming.
