# SQL-002 · Daily completed sales per store: explanation

## Approach

1. Filter: `transaction_status = 'COMPLETED'` and the **half-open** timestamp range
   `transaction_ts >= '2025-03-01 00:00 UTC' AND transaction_ts < '2025-03-17 00:00 UTC'`.
2. Group by `store_id` and `(transaction_ts AT TIME ZONE 'UTC')::date`.
3. `COUNT(*)` and `SUM(gross_amount)`. Because only completed rows reach the aggregation, a
   store-day exists in the output only if it had a completed sale. No `HAVING` is needed.

## Why half-open and not `BETWEEN`

`transaction_ts BETWEEN '2025-03-01' AND '2025-03-16'` compares a timestamp with
`2025-03-16 00:00:00`, so everything on March 16 after midnight is lost. That is 16 store-days
in this data. Patching it with `'2025-03-16 23:59:59'` loses sub-second timestamps and breaks
for `timestamp(6)` data. `>= start AND < next_day` is exact for every precision and composes
cleanly (adjacent ranges never overlap and never leave gaps).

## Why filter the raw column

`WHERE (transaction_ts AT TIME ZONE 'UTC')::date BETWEEN DATE '2025-03-01' AND DATE '2025-03-16'`
is logically correct but **not sargable**: a B-tree index on `transaction_ts` or
`(store_id, transaction_ts)` cannot be used for a function of the column. Keep the predicate on
the bare column, and apply the date expression only in `SELECT`/`GROUP BY`.

## Edge cases and fixtures

| fixture | situation | outcome |
|---|---|---|
| store 4, 03-01 / 03-02 / 03-03 | 25.00 vouchers | one row each: 1 / 25.00 |
| store 4, 03-15 | one completed + one CANCELLED (25.00 each) | 1 / 25.00 |
| store 4, 03-16 | only a DECLINED | no row |
| customer 53 (store 1) | 2025-02-28 23:59:59 and **2025-03-01 00:00:00** | first is out, second is in |
| guest checkouts | `customer_id` NULL | included (an inner join to `customers` drops 4 of them) |
| generated stores in LA, Chicago, Phoenix | evening sales | UTC date ≠ local date; the spec says UTC |

## Complexity and indexes

- With `(store_id, transaction_ts)` and a 16-day range the planner can use a bitmap or range
  scan on `transaction_ts` (index `transactions(transaction_ts)`); a 2-week slice of a 500M-row
  table is about 0.6% of it.
- Grouping is a hash aggregate over (store, date): tiny state, O(n) time.
- If the fact is range-partitioned by month, the predicate prunes to the March partition.

## Production considerations

- Settlement reconciliation needs **stable** numbers. Late-arriving transactions (`ingested_at`
  days after `transaction_ts`) change past days. Either publish with a watermark ("complete as of
  ingested_at < X") or re-run a trailing window daily and version the extract.
- Status changes after extraction (PENDING → COMPLETED) also restate history. That is another
  argument for recomputing a trailing window idempotently (`DELETE` + `INSERT` per day, or
  `MERGE` per (store, date)).
- Monitor: total completed amount per day vs. the source system, and the count of distinct
  stores per day (a store disappearing usually means a feed failure, not zero sales).

## SQL Server / Azure Synapse notes

- `CAST(transaction_ts AT TIME ZONE 'UTC' AS date)` on a `datetimeoffset` converts correctly. On a
  plain `datetime2` column, `AT TIME ZONE` *assigns* an offset instead of converting.
- T-SQL `BETWEEN` has the same end-boundary trap. `DATEADD(day, 1, @end)` builds the exclusive bound.
- Synapse: a clustered columnstore with an ordered segment layout (or partitioning) on the date
  gives segment elimination for the range predicate. Distribute on `store_id` if most queries
  group by store; beware skew from the high-volume online store (store 6).
