# SQL-005 · Net spend after refunds without fan-out: explanation

## The fan-out problem

`transactions` is the parent of **two independent** one-to-many children. Joining both at once
yields, per transaction, (#lines × #refunds) rows. Every aggregate over that join is wrong:

| transaction 2301 | lines | refunds | rows after `JOIN items LEFT JOIN refunds` |
|---|---|---|---|
| gross 100.00 | 60.00, 40.00 | 20.00, 30.00 | 4 |

- `SUM(t.gross_amount)` = 400.00 (×4)
- `SUM(i.quantity)` = 4 (×2)
- `SUM(r.refund_amount)` = 100.00 (×2)

Customer 23 comes out as gross 440.00 / refunds 100.00 / items 5 instead of 140.00 / 50.00 / 3.
`SUM(DISTINCT ...)` is not a fix: it collapses genuinely equal values (two lines of quantity 1
count once), so customer 23 gets `items_sold = 1`.

## (a) Pre-aggregate each child to the parent's grain (`SQL-005.sql`)

1. `q4_txn`: completed, known-customer transactions with a Q4 UTC business date.
2. `items`: `SUM(quantity)` per transaction (only for in-scope transactions).
3. `refunded`: `SUM(refund_amount)` per transaction, **without** a filter on `refund_ts`.
4. Join both to `q4_txn`. Every join is now 1:1. Refunds need a `LEFT JOIN`; most transactions
   have none. Aggregate to customer and `COALESCE` the missing refunds to 0.00.

Rule of thumb: **aggregate to the grain of the join key before joining siblings.**

## (b) Correlated scalar subqueries (`SQL-005_alt.sql`)

Compute `items_sold` and `refunded_amount` with a scalar subquery per header row. A scalar
subquery can only return one value, so fan-out is impossible by construction. PostgreSQL executes
them as SubPlans: two index probes per transaction (`transaction_items` PK,
`refunds(transaction_id)`). For 5k transactions that is fine. For 50M transactions the hash-join
plan of (a) wins clearly, because it reads each table once sequentially instead of doing 100M
random probes.

## Edge cases and fixtures

| customer | data | expected |
|---|---|---|
| 23 | 2301 (2 lines, refunds 20 + 30), 2302 (40.00) | 2 txns, 3 items, 140.00 − 50.00 = **90.00** |
| 24 | 2401 80.00 fully refunded | net **0.00** (still reported) |
| 25 | 2501 on 10-30, refunds 45.00 + 15.00 in **November** | 120.00 − 60.00 = **60.00** |
| 26 | 2601 in September (out), 2602 + 2603 on 10-05, 2604 PENDING | 2 txns, 30.00, no refunds → 0.00 |
| generated | 61 refunds of Q4 sales were issued in **2026** | must be included; filtering `refund_ts` to Q4 loses them |

## Complexity and indexes

- (a): one scan of each table (or a range scan of Q4 transactions), hash aggregates per child,
  hash joins. O(T + L + R).
- Pushing the Q4 filter into the child CTEs (join to `q4_txn` before aggregating) keeps the hash
  tables small. Without it, `items` would aggregate all 46k lines (1.2B in production).
- Useful indexes: `transactions(transaction_ts)` for the quarter slice; the `transaction_items`
  PK and `refunds(transaction_id)` for plan (b).

## Production considerations

- **Attribution policy:** refunds are attributed to the *sale* period here, so Q4 numbers keep
  changing until refunds stop arriving. Finance often wants both views: "net by sale period"
  (restated) and "refunds by refund period" (booked). Agree on one before building.
- **Restatement:** schedule a rerun of the previous quarter for N days after quarter close, or
  maintain per-transaction refunded totals incrementally from new refund events.
- **Guardrail:** `refunded_amount <= gross_spend` per transaction is a source invariant here.
  Assert it; a violation means duplicated refund events (see SQL-004).
- Reconciliation: `SUM(net_spend)` = `SUM(gross)` of scope − `SUM(refunds)` of scope, computed
  independently.

## SQL Server / Azure Synapse notes

- The same pre-aggregation pattern, CTEs included, works verbatim in T-SQL.
- `CROSS APPLY (SELECT SUM(...) ...)` is the T-SQL spelling of the correlated variant. SQL Server's
  optimiser often decorrelates it into a join.
- Synapse: when `transactions`, `transaction_items` and `refunds` are all HASH-distributed on
  `transaction_id`, the per-transaction aggregates and joins are local. A final shuffle on
  `customer_id` is required for the customer roll-up.
